### Papers

- [[summaries/2022-llm-int8]] — **LLM.int8()**（Dettmers, Lewis, Belkada, Zettlemoyer, NeurIPS 2022, arXiv:2208.07339）。**175B を性能劣化ゼロで INT8 にした初の手法**だが、価値の半分は量子化技法でなく**創発現象の記述**にある。手法は (a) **vector-wise 量子化**（行列積を独立な内積の列と見なし、隠れ状態の各行と重みの各列に別々の absmax スケールを持たせる）と (b) **混合精度分解**（大きさ 6.0 超の外れ値を含む特徴次元だけ 16 ビットへ分離し、残り 99.9% を 8 ビットに）。**なぜ vector-wise だけでは足りないか**が明快で、vector-wise は「行＝系列次元」をスケールするのに**外れ値は「列＝特徴次元」に生じる**——軸が直交している。§4 の創発の分析が白眉で、**6B→6.7B で相転移**（影響される層 65%→100%）、**1 系列 15 万個の外れ値がわずか 6 次元に集中**、それを消すと **top-1 attention 質量 40%→20%・パープレキシティ 600〜1000% 悪化**（ランダム 7 次元なら 0.1%）。そして**創発を予測するのはパラメータ数でなくパープレキシティ**（サイズには非単調、パープレキシティには単調）。速度は正直に報告されており、**モデル次元 4096 以下では FP16 より遅い**。
- [[summaries/2022-smoothquant]] — **SmoothQuant**（Xiao, Lin, Seznec, Wu, Demouth, Han / MIT・NVIDIA, ICML 2023, arXiv:2211.10438）。外れ値を**分離するのでなく「移す」**。活性を per-channel の平滑化係数で割り重みを逆方向に掛ける**数学的に等価な変換**で難しさを活性から重みへ移し、**W8A8**（重みも活性も INT8）を成立させて INT8 GEMM カーネルを使えるようにする。移す量は **migration strength α**（OPT/BLOOM 0.5、GLM-130B 0.75、LLaMA 0.8）。最も鋭いのは **「per-channel の活性量子化は精度的には正解なのに使えない」という証明**——INT8 GEMM はスケーリングを外側次元（トークン・出力チャネル）にしか置けず、内側の入力チャネルには原理的に届かない。**LLM.int8() を名指しで批判**し数字で示す: OPT-13B・seq256 で **FP16 152.6ms / LLM.int8() 237.1ms / SmoothQuant-O3 112.1ms**——精度は両者とも FP16 に一致するのに速度は正反対。MT-NLG 530B を 16 台→**8 台の単一ノード**へ。
- [[summaries/2023-qlora]] — **QLoRA**（Dettmers, Pagnoni, Holtzman, Zettlemoyer / UW, NeurIPS 2023, arXiv:2305.14314）。**65B のファインチューニングを 780GB 超から 48GB 未満へ**。3 つの技法——**NF4**（分位量子化に基づき、ゼロ中心正規分布に情報理論的に最適な 4 ビット表現）、**二重量子化**（スケール係数を量子化。0.5→0.127 ビット/param）、**paged optimizers**（統合メモリで OOM を防ぐ。33B の訓練には必須）。**QLoRA は QAT ではなく PTQ ＋ PEFT** である（§3「勾配は LoRA のパラメータについてのみ計算する」）。PEFT 側の知見も重い——**メモリの大半はアダプタでなく活性の勾配**（7B で LoRA 26MB に対し入力勾配 567MB）、ゆえに**全線形層にアダプタを置くべきで r は性能に無関係**。後半は評価方法論の論文になっており、**LLM-as-a-judge のバイアスを実測**: GPT-4 の**順序効果**、**自己贔屓**（自分の出力に Elo 1348、人間評価では 1176）、**サンプル水準の一致は Fleiss κ=0.25**（人間同士でも 0.42）。データは**量より適合性**（9k の OASST1 が 450k の FLAN v2 に勝つ）で、**強い MMLU は強いチャットボット性能を意味しない**。
- [[summaries/2021-roformer]] — **RoFormer / RoPE**（Su, Lu, Pan, Murtadha, Wen, Liu / Zhuiyi Technology, arXiv:2104.09864 → Neurocomputing 2024）。**query と key を位置に比例した角度だけ回転させる**位置符号化。手法を設計したのでなく、「内積が相対位置 $m-n$ にしか依存しない」を**関数方程式として立てて解いた**論文で、$m=n$ と $n=m+1$ を代入すると位相が等差数列になり、答えが「回せ」に一意に定まる。$d$ 次元は $d/2$ 平面に分けてブロック対角の回転行列に。**先行研究がすべて加法的なのに対し乗法的**で、直交行列ゆえノルムを保つので **linear attention と組める**（加法的な相対位置項は $q$/$k$ に分離できず組めない）。回転行列は疎なので実体化せず要素積 2 回で計算し、実質メモリ帯域律速——だから attention カーネルに融合できる。**ただし論文自身の実証は弱い**: GLUE は 6 タスク中 3 勝 3 敗（負け幅の方が大きく、唯一大きな勝ちの QQP は BERT 側の 71.2 が異常に低い）なのに本文は「3 つで有意に上回る」としか書かない、BLEU は +0.2、そして現在 RoPE と最も結びつけられる**外挿は一度も検証していない**。著者自身が §4.5.5 で「なぜ速く収束するのか」「なぜ長文で強いのか」の**どちらも説明できない**と明記。RoPE が標準になった理由は精度でなく**システムとしての扱いやすさ**であり、base 周波数という単一のつまみが後の YaRN 等の土台になった。
- [[summaries/2022-gptq]] — **GPTQ**（Frantar, Ashkboos, Hoefler, Alistarh / IST Austria・ETH Zurich・NeuralMagic, ICLR 2023, arXiv:2210.17323）。二次情報ベースの正確な量子化（OBQ）を **3 桁高速化**して 175B に届かせた論文。工夫は 3 つで、**(1) 任意順序**（貪欲な順序の利点は大きな層では消えるので全行を同じ順序にし、$\mathbf{H}_F^{-1}$ を全行共通化して更新回数を重みごと→列ごとへ）、**(2) 遅延バッチ更新**（計算対メモリアクセス比が低くメモリ帯域で詰まるので 128 列単位に。実測 1 桁）、**(3) コレスキー再定式化**（数十億超では $\mathbf{H}_F^{-1}$ が不定値になり更新が暴走するため、必要な行を前計算）。**OPT-175B を A100 1 枚・4.2 時間**で 3〜4 ビット化し、専用カーネルで **3.25 倍（A100）／4.5 倍（A6000）** のレイテンシ削減。ただし**高速化の出所はメモリ移動の削減であって乗算ではない**と論文自身が 2 度明記しており、活性の量子化も扱わない。**「大きなモデルほど量子化しやすい」**（例外の OPT-66B は初期層の死んだユニットが原因と示唆）。g8 なら**三値量子化**まで届く（OPT-175B で PPL 9.20）。
- [[summaries/2023-awq]] — **AWQ**（Lin, Tang, Tang, Yang, Dang, Gan, Han / MIT・SJTU・清華, MLSys 2024, arXiv:2306.00978）。**「どの重みが大事かは、重みでなく活性が決める」**。INT3-g128 の OPT-6.7B で 1% を FP16 に残すと、**活性基準 PPL 11.39 / 重みノルム基準 22.37 / ランダム 24.23**——機械学習で最も広く使われる「大きい重みが重要」という代理指標が**ランダム選択と大差ない**。混合精度を避けるため $w$ を $s$ 倍し $x$ を $1/s$ する等価変換に置き換えるが、**$s$ を上げすぎると守らない側のチャネルが壊れる**（最良は $s=2$、$s=4$ で悪化）。探索空間を $\mathbf{s}=\mathbf{s_X}^\alpha$ に縛り**グリッド 20 点**で終わる——**逆伝播も回帰もない**。これが汎化を生み、**較正と評価の分布がずれたときの劣化は AWQ 0.5〜0.6 に対し GPTQ 2.3〜4.9**、視覚言語モデルでは **GPTQ が素の丸めより悪くなる**（32-shot CIDEr: RTN −4.57 / GPTQ −6.72 / AWQ −1.17）。実測 3.2〜3.3 倍の高速化、**Llama-2-70B を Jetson Orin 1 枚**、8GB のラップトップ GPU で 13B が 33 tok/s。ただしグループなし量子化では原理的に劣る（**グループごとに 1 チャネルしか守れない**）。
- [[summaries/2024-efficientqat]] — **EfficientQAT**（Chen, Shao, Xu, Wang, Gao, Zhang, Qiao, Luo / OpenGVLab Shanghai AI Lab・香港大学, 2024, arXiv:2407.11062）。**「QAT はコストが法外」という前提を崩した論文**。訓練を 2 段に割る——**Block-AP**（トランスフォーマブロック単位で $s$・$z$・$\mathbf{W}$ の**全部**を訓練）と **E2E-QP**（量子化重みを固定しステップサイズ $s$ のみ＝全体の約 1.5% を端から端まで）。**Llama-2-70B の 2 ビット化が A100 1 枚・41 時間・訓練メモリ 34.2GB**、ゼロショット劣化 3% 未満。反直感的なのは**「全部訓練する」が最良**だったことで、従来の部分訓練（丸めパラメータ等）は正則化として解空間を狭めており、**サンプルを 128→4096 に増やすだけ**で過適合に対処できる。**4 ビットでは PTQ に勝てない**と著者自身が認めており、**「4 ビットなら PTQ、2〜3 ビットなら QAT」**という線が引ける。Q-PEFT への批判も重要——**LoRA をマージすると FP16 へ戻るので低ビットで出荷できない**（→ [[parameter-efficient-fine-tuning]]）。
- [[summaries/2019-bfloat16]] — **A Study of BFLOAT16 for Deep Learning Training**（Kalamkar ら / Intel Labs・Facebook, 2019, arXiv:1905.12322）。**「BF16 は範囲に振った 16 ビット形式であり、だから loss scaling が要らない」という今日ほぼ自明の主張の原典**。BF16 は指数部 8・仮数部 7 で、**指数部が FP32 と同じ**なので動的範囲が一致し、FP32 との変換が「下位 16 ビットを捨てる／埋める」だけで済む。FP16 は指数部 5 で最小正規化数が約 6.1×10⁻⁵ しかなく、逆伝播の勾配がアンダーフローするため **loss scaling**（損失に定数を掛けて勾配を表現可能な範囲へ押し上げる）が要り、**再帰型ネットワークではその調整が反復的で高くつく**。本論文はこの調整項目を消したことが実質的な貢献で、**5 領域 8 モデル**（AlexNet・ResNet-50・DeepSpeech2・GNMT・DC-GAN・SR-GAN・Deep&Cross・DNN Recommender）を**ハイパーパラメータ変更なし**で FP32 と同等に訓練した。実務的な細部として、**推薦システムでは丸め方式が効く**（最近接丸めなら完全一致だが直接切り捨てで約 0.02% 劣化。論文は「log loss で 0.001 の劣化は実務上受け入れがたい」と明記）。BF16 ハードウェア以前の研究なので **Quantlib による FP32 上のエミュレーション**が主だが、4.5 節では AVX512BF16 で ResNet-50 を実訓練し top-1 75.62% を得ている。**Transformer は対象外**（2019 年）。
- [[summaries/2023-fp8-lm]] — **FP8-LM**（Peng, Wu, Wei ら / Microsoft Azure・Microsoft Research, 2023, arXiv:2310.18313）。**FP8 を「行列積だけ」でなく訓練の全過程——計算・格納・通信——へ浸透させた初のフレームワーク**。当時唯一の実用フレームワークだった **NVIDIA Transformer Engine を名指しで批判**する（「TE は FP8 を GEMM にのみ適用し master weight と勾配は高精度のまま。end-to-end の恩恵が限定的」）。3 つの障壁を個別に潰す——**(1) auto-scaling**（all-reduce で pre-scaling はアンダーフロー、post-scaling はオーバーフローするので、FP8 最大値到達率 0.001% を閾値に係数を動かす。かつ**全 GPU でスケール係数の最小値を 1 つ共有**して標準 NCCL をそのまま使う）、**(2) precision decoupling**（**勾配の統計量は低精度でよいが master weight は高精度を要する**。一次モーメントは FP8 可＝Adam では大きさより方向が重要、二次モーメントは二乗でアンダーフローするので 16 ビット必要。パラメータあたり 16→**6 バイト**）、**(3) FP8 ZeRO**（テンソルを分割せず丸ごと配る貪欲アルゴリズム）。GPT-175B で **BF16 比 75% 高速・メモリ 39% 削減**、TE 比でも 37% 高速・42% 省メモリ。SFT で +27% 速度、RLHF で重み −32%・オプティマイザ状態 −62%。**BF16 と FP16 の優劣が反転する**（master weight は BF16 より FP16＋スケーリングが良い）のも重要な観察。ただし **175B は 40B トークンしか訓練しておらず**、**MFU は BF16 より低い**（39.0% → 34.2%）。
- [[summaries/2025-nvfp4-pretraining]] — **Pretraining Large Language Models with NVFP4**（NVIDIA, 2025, arXiv:2509.25149）。**12B を 10 兆トークン、4 ビットで訓練しきった初の公開記録**。MMLU-Pro **62.58 対 FP8 62.62**。FP4（E2M1）は表現できる値が **16 通りしかない**ので、形式単体では成立せず **4 つの技法を全部載せて初めて収束する**——**(1) 敏感な線形層を高精度に**（15%、主に終端。全部 FP4 にすると発散）、**(2) Wgrad の入力へ 16×16 の Random Hadamard 変換**（Fprop/Dgrad に適用すると**むしろ劣化**）、**(3) 重みは 16×16 の 2D スケーリング**（逆伝播で転置され内積の次元が変わるため、同じ重みが順伝播と逆伝播で違う量子化表現になり**連鎖律が破れる**）、**(4) 勾配にだけ確率的丸め**（活性・重みに適用すると発散）。**MXFP4 との差**も明快で、MXFP4 のスケールは 2 の冪しか取れないため **±4 と ±6 の 4 サンプルが死に**ほぼ 1 binade を失う。実測では **MXFP4 が追いつくには 36% 多いトークンが要る**。**終盤 18% だけ BF16 へ戻せば FP8 に一致**し、しかも損失の隔たりのほとんどは順伝播由来なので**全計算の 6% で済む**。ただし**速度は測っていない**（論文が明記）、**まだ 16% が高精度**、**コードタスクだけ 2.5〜3.2 ポイント劣化**して説明がついていない。
- [[summaries/2025-nvfp4-inference]] — **NVFP4: Same Accuracy with 2.3x Higher Throughput for 4-Bit LLMs**（Benjamin Marie / The Kaitchup, Medium, 2025-08）。**NVIDIA が FP8 としか比べていない NVFP4 を、AWQ・AutoRound・bitsandbytes という実際の競合と並べて実測**した記事。結論はベンダの宣伝とずれる——**精度では AWQ/AutoRound がわずかに上**（5901/5900 対 5858）、**サイズは NVFP4 が約 7GB 大きい**（グループサイズ 16 対 128 でスケールが 8 倍要る。値あたり平均 **4.5 ビット**）。**勝ち筋は速度だけ**で INT4 比 **2.35 倍**（1693 対 723 tok/s）。そして最重要の発見——**活性も量子化しないとその速度は出ない**。重みだけの **NVFP4A16 は 774 tok/s で INT4 の 723 とほぼ同じ**（Tensor Core が直接扱えず実行時の逆量子化が要るため）。[[model-quantization]] の「重みのみか、重みと活性か」の最も鮮明な実例になっている。運用の摩擦も記録されており、**FlashInfer が NVFP4 でクラッシュ**し、**`pip install vllm` が Blackwell 向けに正しく入らない**（ソースからのコンパイルが必要）。ただし査読なしの個人ブログで 1 モデル・1 GPU・1 ベンチマーク群のみ、**MXFP4 とは比較できていない**（LLM Compressor 未対応）、著者自身が「70B では 4 ビットが既に完全精度に近いので差が出にくい」と認めている。
- [[summaries/2025-llm-serving-techniques]] — **LLM Serving を支える技術**（釜堀 / ワシントン大学・Kotoba Technologies, Zenn, 2025-07）。**vLLM や SGLang の中で何が起きているのかを、機械学習システム研究者が体系的に棚卸しした記事**。本 wiki のサービング側の記述が箇条書き数行しかなかったところに、一次の設計論理を入れる。出発点は **Roofline モデルによるバッチングの根拠**——decode の線形層は演算密度が $n/(1+n)\approx 1$ で極端に memory-bound なので、**リクエストを 1 件から 2 件に増やすのは時間的にタダ**であり、**数百でようやく compute-bound** になる。だから「バッチサイズを上げる」が第一戦略になる。その障壁が **KV cache のメモリ**で、Llama 2 7B は 1 トークン 512KB・最大長ぶん確保すると 1 リクエスト 2GB なので **H100 でも 32 リクエスト程度**しか載らない——これを **PagedAttention**（OS のページングを持ち込む）と **prefix キャッシュ / RadixAttention**（causal attention なので共通接頭辞の KV は再利用できる）で解く。以降「実装」（カーネル融合・FlashInfer・**NanoFlow** が memory-bound と compute-bound の仕事を重ねる・**Multi-LoRA**・**CUDA Graph** のバッファ固定という制約・**非同期スケジューリング**が 1 トークン余分に出す代わりにクリティカルパスを外す）、「スケジューリング」（**TTFT と TPOT** の両立が壊れる状況と、**chunked prefill** / **P/D 分離**）、「アルゴリズム」（**量子化の 2 系統を Roofline 図で説明**・KV スパース化・投機的デコーディングは **TPOT を下げるがスループットは上げない**・**構造的デコーディングは高速化でもある**）、「アーキテクチャ」（GQA の有無で動作領域が切り替わる・SWA・Jenga）、「分散」（推論の DP/PP/TP/EP・**DeepSeek の推論インフラ**）と続く。**日本語記事のため翻訳ファイルは作成していない。**
- [[summaries/2025-understanding-llm-serving]] — **Understanding LLM Serving**（Thanh Tung Vu / Medium, 2025-04）。LLM serving を「適応 → 推論最適化 → ルーティング → 量子化 → 監視 → ツールスタック」の 6 段ライフサイクルとして俯瞰したビジネス寄りの入門。技術的な深さは上の Zenn 記事に大きく劣るが、**あちらが扱わない 2 つの層**を埋める——**(1) モデル間のルーティング**（**カスケード**＝小さいモデルで受け信頼度が足りなければ引き上げる／**ルータ**＝クエリの特徴から最初に振り分ける、の使い分け）と **(2) ツールスタック**（vLLM・Triton／Ray Serve・BentoML／HF Endpoints・OpenRouter・Replicate／MLflow・LangSmith・W&B）。**PEFT を「展開前の作業」でなく「serving の設計変数」として置く**（統合適応 vs モジュラー適応）のも有用。監視では **shadow deployment**（候補モデルを本番と並行して走らせ、ユーザーに影響を与えず出力を比較）を型として与える。ただし**技術的な誤りが 1 つある**——「GPTQ (**Gradient** Post-Training Quantization)」は誤りで、原典（[[summaries/2022-gptq]]）の脚注 1 が「**OPT ＋ PTQ** の合成」と明記している。early exit の説明も層単位の early exit と生成の打ち切りを区別していない。数値が一切なく、図 5 枚はすべて本文を復唱する装飾なので ingest 時に全部除外した。
- [[summaries/2023-pagedattention]] — **PagedAttention / vLLM**（Kwon, Li, Zhuang ら / UC Berkeley・Stanford・UCSD, SOSP 2023, arXiv:2309.06180）。**「LLM サービングのスループットはメモリ律速である」と診断し、原因が KV キャッシュを連続メモリに置いていることだと突き止め、OS の仮想メモリとページングをそのまま持ち込んで解いた論文**。手法の前に**無駄を 3 つに分解**したのが説得力の源で、**予約**（将来のトークンぶん。最終的には使うがその間ほかが使えない）・**内部断片化**（最大長への過剰供給。リクエストが終わって初めて分かる）・**外部断片化**（アロケータ由来。生成に決して使われない）。**既存システムが KV キャッシュのメモリのうち実際に使えているのは 20.4〜38.2% にすぎない。** OS の比喩を最後まで使い切る——ブロック=ページ、トークン=バイト、リクエスト=プロセス、block table=ページテーブル、**参照カウント＋copy-on-write**=fork、共有 prefix=共有ライブラリ、CPU メモリ=スワップ空間。そして**どこで比喩を捨てるか**も明示する（**all-or-nothing の退避**と、**OS では不可能な再計算による復旧**）。結果は**スループット 2〜4 倍**、同時処理数 Orca (Oracle) 比 2.2 倍。ビーム探索では共有パターンが動的に変わり **KV メモリを 37.6〜55.2% 節約**（ShareGPT では 44.3〜66.3%）。**正直なアブレーションが重要で、attention カーネル単体は FasterTransformer より 20〜26% 遅い**——カーネルを速くするのでなく**バッチサイズを上げて**勝っている。既定ブロックサイズ 16、再計算のオーバーヘッドは退避の 20% を超えない。**ただし共有 prefix は手動**（提供者が事前定義した prefix のために物理ブロックを予約する）で、**公開コードでは動かなかった**（→ [[summaries/2023-sglang]] の指摘）。
- [[summaries/2023-sglang]] — **SGLang / RadixAttention**（Zheng, Yin, Xie ら / Stanford・UC Berkeley, 2023, arXiv:2312.07104）。**「フロントエンドの言語とバックエンドの推論エンジンが別々に進化しているせいで最適化の機会が落ちている」と診断し、両方を一緒に設計した論文**。**論文の半分は言語処理系**である——Python 埋め込み DSL（`gen`・`select`・`extend`・**`fork`**・**`join`**）、**プロンプトを非同期ストリームとして扱うインタプリタ**（「CUDA のカーネルを CUDA のストリームへ非同期に起動するのに似ている」）、計算グラフへのトレースとコンパイラ。**中でも GPT-4 にコンパイラ最適化をさせるのが異色**で、IR ノードを並べ替えて定数 prefix を長くする——**「自然言語の指示が含まれるため伝統的なプログラム解析では達成できない」**から GPT-4 に頼む。**15 テンプレート中 12 件成功、共有可能 prefix が平均 +60 トークン**（失敗は「積極的すぎて意味論を変える場合でも定数を前へ持ってくる」）。ランタイム側の **RadixAttention** は、**リクエスト完了後に KV キャッシュを捨てず** radix tree で保持し、LRU で葉を退避、実行中バッチが使うノードは参照カウンタで守る。**オーバーヘッドは順伝播 17.6 秒に対し木の演算 0.07 秒、キャッシュヒットゼロでも 0.5%**。**キャッシュだけでは足りず**、先着順のままだと**キャッシュのスラッシング**が起きるので、**一致 prefix 長で並べ替えるスケジューリング**が組で要る。**本 wiki にとっての目玉は ReAct エージェントで vLLM 比スループット 5.6 倍・レイテンシ 13%**——理由は「**エージェントが思考・行動・観測を続く LLM 呼び出しのプロンプトへ追記していく過程**」で、**「安定した接頭辞、変動する末尾」に一次の数字が付いた**。1 シミュレーション 1 呼び出しの generative agents では 30% に留まる。ほかに MMLU 4.4 倍・GSM-8K 4.5 倍・生産性 206 行 → 91 行。**限界も候補**——コンパイラが**データ依存の制御フローに対応せず**（エージェントの制御フローは定義上そうなので緊張がある）、**文法制約付きデコーディングは未実装**。

- [[summaries/2023-llama-guard]] — **Llama Guard**（Meta / Hakan Inan ほか, arXiv:2312.06674, 2023-12）。**安全ポリシーをモデルの重みでなくプロンプトで渡す**——この 1 つの設計変更でコンテンツモデレーションを「固定された分類器」から「実行時に差し替えられる判定器」に変えた。既存 API（OpenAI Mod・Perspective・Azure）の不足は **(a) ユーザー側とエージェント側のリスクを区別しない、(b) 固定ポリシーしか強制できない、(c) API アクセスのみで仕立て直せない**の 3 点。**タスクは 4 部品**（ガイドライン／分類の種類／会話／出力形式）で、`safe`/`unsafe` を **SentencePiece の単一トークン**に選んだので**最初のトークンの確率がそのまま分類器スコアになる**。訓練は **Llama2-7b・13,997 件・500 ステップ（約 1 エポック）** と小規模。**適応性が主張の核**で、タクソノミーを渡すだけで OpenAI Mod の AUPRC 0.837→0.847、例を 2〜4 個足すと **0.872 で OpenAI 自身の API（0.856）をその API のデータセット上で上回る**。ToxicChat へのファインチューニングは **20% のデータで、Llama2-7b が 100% で到達する水準に並ぶ**。**批判点**: 自社テストセットの 0.945/0.953 は自社タクソノミー・自社ラベル上のもので、比較対象は完全にオフポリシー——カテゴリ別の 0.798 対 0.035 は品質差でなく**カテゴリの有無**である（外部データセット ToxicChat の **0.626** が素の実力）。ただし**評価プロトコルは自分に 1-vs-all（厳しい側）、ベースラインに 1-vs-benign（自ら「楽観的」と認める側）** を当てており公正。付録の表が白眉で、**モデレーション API はしきい値 0.5 で再現率 0.22〜0.25**（4 分の 3 を見逃す）、**ゼロショットの GPT-4 は逆に過剰遮断**（一部カテゴリで適合率 0.039〜0.052）。そして **§6 が「Llama Guard はプロンプトインジェクションで迂回されうる」と 2023 年に明記しながら緩和策を示していない**——実装で答えるのは 1 年半後の LlamaFirewall。
- [[summaries/2023-nemo-guardrails]] — **NeMo Guardrails**（NVIDIA / Traian Rebedea ほか, EMNLP 2023 Demo, arXiv:2310.10501, 2023-10）。**ガードレールをモデルでなくプログラムとして書く**ツールキット。最大の貢献は手法でなく**軸の提示**で、制約を **embedded rails（訓練時にモデルへ焼き込む。RLHF・p-tuning。変更できない）** と **programmable rails（実行時に書く。モデル非依存・解釈可能）** に二分した——本 wiki の 4 層（**どこで**介入するか）と**直交**する軸である。機構はタスク指向対話システムの再発明で、閉じた intent 集合を **canonical form**（LLM が生成するので閉じていない意図表現。ベクトル DB から類似例を引いて誘導）に置き換え、ランタイムが (1) 正準形生成 →(2) 次ステップ決定 →(3) 応答生成の 3 段で回る。**topical rails は内容を判定せず「可能な会話の形」を制約する**ので実質的に行動空間設計に近い。execution rails は fact-checking（含意判定）・hallucination（SelfCheckGPT 方式の自己一貫性）・moderation（入力＝jailbreak rail と出力）。**批判点**: 3 段が逐次連鎖するので**バッチ不可、通常の約 3 倍のレイテンシとコスト**。**論文自身が §7.1 で「とりわけ安全性のレールについては単独で使うべきでない」と明記**。評価はデモ規模（231 サンプル / 200 サンプル / **20 問**）。検査器と被検査者が同じモデルでありうる。そして**最も示唆的なのは gpt-3.5-turbo が中核機構で 4 モデル中最下位（38%、text-davinci-003 は 77%）** ——能力不足でなく「**より多様な canonical form を生成する**」ため（類似度マッチに変えると 0.38→0.73）。**出力を機械が消費する系では、創造的に応じる能力が不利になる**。細部の不整合も多い（本文 95% / 図 90% / 付録 +25pt、「上位 3 モデル」の図に 4 モデル、そして**付録 E.2 の jailbreak rail のコードが変数名の写し間違いで動かない**）。

- [[summaries/2022-flashattention]] — **FlashAttention**（Dao, Fu, Ermon, Rudra, Ré / Stanford・SUNY Buffalo, NeurIPS 2022, arXiv:2205.14135）。attention が遅いのは演算量ではなく **GPU のメモリ階層（HBM ⇄ SRAM）の往復**が律速だからだと指摘し、N×N の attention 行列を一度も HBM に書かずに済ませる CUDA カーネルを作った。**tiling**（softmax を行最大値と指数和の 2 統計量で漸進的に確定）と **recomputation**（backward 用に行列を保存せず SRAM で作り直す）を単一カーネルへ融合し、**出力は素の softmax attention と厳密に同一**。中心的証拠は「**GFLOPs 66.6 → 75.2（+13%）、HBM 読み書き 40.3 → 4.4 GB、実行時間 41.7 → 7.3 ms（5.7 倍速）**」——演算を増やして速くなった。IO 計算量 Θ(N²d²M⁻¹) と、**どの厳密 attention もこれを漸近的に上回れない下界**（命題 3）まで示す。BERT-large で MLPerf 1.1 記録を 15% 更新、GPT-2 は 3 倍、**Path-X（16K）でランダム超えを達成した初のトランスフォーマー**。近似 attention 群が普及しなかった理由（FLOPs は減らしたが IO を減らさなかった）を説明してしまった論文でもある。
- [[summaries/2023-flashattention-2]] — **FlashAttention-2**（Tri Dao / Princeton・Stanford, 2023, arXiv:2307.08691）。前作の続編で、問題設定が一段ずれている——**IO を直してもなお A100 理論ピークの 25〜40% しか出ていない**（最適化された GEMM は 80〜90%）。原因は GPU 上の**仕事の割り振り**で、対処は 3 つ: (1) **non-matmul FLOPs を減らす**（A100 は matmul 312 TFLOPs/s に対し non-matmul FP32 が 19.5 TFLOPs/s ＝ **1 FLOP あたり 16 倍の価格差**。毎ブロックのスケーリングを最後の 1 回にまとめ、統計量を m と ℓ の 2 本から logsumexp 1 本へ）、(2) **系列長方向にも並列化**して小バッチ時の occupancy を上げる、(3) warp 間の **"split-K" をやめ Q を分割**して warp 間通信を消す。結果は attention 単体で 1.7〜3.0 倍・**230 TFLOPs/s（ピークの 73%）**、エンドツーエンドで **225 TFLOPs/s・MFU 72%**。最も示唆的なのは 2k → 8k でスループットが**落ちない**（むしろ 205 → 225）こと——前作が長い窓を現実的にしたなら、本作は**長い窓のペナルティを消した**。ループ順序の入れ替えと系列長並列は **Phil Tillet の Triton 実装が先**と論文が明記しており、前作が限界に挙げた「高レベル言語からのコンパイル」が実際に作られ、そこでの発見が本家へ還流した形になっている。
- [[summaries/2024-flashattention-3]] — **FlashAttention-3**（Shah, Bikshandi, Zhang, Thakkar, Ramani, Dao, 2024, arXiv:2407.08608）。三部作の完結編で、要点は「**世代が変わって振り出しに戻った**」——A100 で理論ピークの 73% まで詰めた FlashAttention-2 は、**H100 では 35%** しか出ていなかった（同じ GPU の GEMM は 80〜90%）。原因は Hopper が持ち込んだ 2 つの前提を設計に組み込んでいないこと: **非同期性**（行列積は Tensor Core、データ転送は TMA という別ユニットで独立に走る）と **FP8**。対処は (1) warp を **producer（TMA でデータを運ぶ）と consumer（WGMMA で計算する）に役割分担**させる warp-specialization、(2) **softmax を GEMM の陰に隠す**（H100 は FP16 行列積 989 TFLOPS に対し**指数関数は 3.9 TFLOPS ＝ 256 分の 1**。ヘッド次元 128 では指数関数だけで約 50% のサイクルを食いうる）、(3) FP8 のレイアウト適合と精度対策。結果は **FP16 で 740 TFLOPs/s（75%）・FP8 で 1.2 PFLOPs/s 近く**、cuDNN を中〜長系列で上回る。精度側の **incoherent processing**（Q と K に同じランダム直交行列を掛ける。$MM^\top=I$ なので**出力は恒等**のまま外れ値がならされる）は、DeepSeek-V3 の細粒度量子化と対照的な「外れ値へのもう 1 つの答え」。ただし FP8 が cuDNN と competitive という主張には脚注で条件がつき（ヘッド次元 128・256 の因果マスクありでは負ける）、精度検証は合成データのみ、推論最適化は今後の課題。
- [[summaries/2023-lost-in-the-middle]] — **Lost in the Middle**（Liu, Lin, Hewitt ほか / Stanford・UC Berkeley・Samaya AI, TACL 2024, arXiv:2307.03172）。**入力の内容を変えず位置だけを動かして**測り、先頭と末尾が強く中間が弱い **U 字カーブ**を示した。よく引かれる主張より強いことが 2 つ書いてある——**GPT-3.5-Turbo は答えを中間に置くと closed-book（56.1%）を下回る**（渡さないほうがマシ）、そして**拡張コンテキスト版は元版とほぼ同じ曲線**。原因は 4 つの実験で切り分けられ、encoder-decoder も**訓練長を超えると** U 字、素のベースモデルも U 字、**7B は recency のみで 13B・70B から U 字**。§5 では **reader が retriever の recall より遥か手前で飽和**することを測り、**再ランキングと ranked list truncation** を処方箋に挙げる。本 wiki が 6 ページで参照してきた「lost in the middle / context rot」の一次資料。
- [[summaries/2023-swe-bench]] — **SWE-bench**（Jimenez, Yang ほか / Princeton・UChicago, ICLR 2024, arXiv:2310.06770）。**ベンチマークを作るのでなく収穫する**——実際の GitHub イシューと、それを解決したマージ済み PR の対から **93,139 PR → 3 段フィルタ → 2,294 件**を自動収集し、**リポジトリ自身のテストで実行ベースに採点**する。当時の水準は**オラクル検索でさえ Claude 2 が 4.8%**。最も重要な知見は **BM25 の文脈を広げると recall は 29.58 → 51.06 と上がるのに解決率は 1.96 → 1.22 と下がる**こと、そして**編集行の ±15 行以外を畳むだけで性能が上がる**こと。`FAIL_TO_PASS` と `PASS_TO_PASS` の分離、作成年による層別での汚染検査、「人間にも解けない問題」の能動的な除外など、評価設計として転用できる判断が多い。

- [[summaries/2024-graphrag]] — GraphRAG（Edge et al., Microsoft Research, arXiv:2404.16130, 2024-04）。**「検索では原理的に答えられない質問がある」**という診断——コーパス全体に向けたグローバルな質問は検索タスクでなく **QFS**（Query-Focused Summarization, クエリ焦点型要約）——から、検索でなく**索引の作り方**を変える。LLM にエンティティ知識グラフを作らせ、Leiden でコミュニティ検出して階層分割（MECE なので全体をカバーする）、各コミュニティ要約を事前生成し、質問時は全件に並列に答えさせて畳む（map-reduce）。素朴な RAG に網羅性 72〜83% で勝つが、**グラフなしの原文 map-reduce も競争力があり**、グラフの真価は品質でなくトークン単価（ルート水準は 9〜43 倍安い）。評価設計も見どころで、**対立する対照指標（直接性）を混ぜて判定系の妥当性を検査**する。

## Concepts

- [[parameter-efficient-fine-tuning]] — PEFT。事前学習済みの重みを凍結し少数のパラメータだけ訓練する手法群。**LoRA の定式化**、**PEFT のメモリの内訳という反直観的な事実**（アダプタ 26MB に対し活性の勾配 567MB——だからアダプタを削っても総メモリは減らず、逆に増やしても安い）、**チューニングすべきは r でなく配置**（全線形層に置く）、**QLoRA が QAT でなく PTQ ＋ PEFT である理由**、そして**データは量より適合性**。根拠は現時点で [[summaries/2023-qlora]] に依拠しており、LoRA 本体の原典は未取得である旨をページ冒頭に明記している。
- [[llm-programming-systems]] — **LLM の生成過程を制御するプログラムを書くための言語・実行系**。SGLang・LMQL・Guidance・DSPy・LangChain の層。独立して立つのは **LLM の使われ方が「単純なターン制のチャット」から「プログラム的利用」へ転換した**からで、**複数の依存し合う生成呼び出しがあり、制御フローが LLM の出力に依存しうる**。中心的な問いは「**プログラムの構造をランタイムへ伝えられているか**」——フロントエンドが構造を知りバックエンドが知らないと、キャッシュ・共有・並列化の機会が落ちる。プリミティブ設計（`gen`/`select`/`extend`/`fork`/`join` の 5 つだけ、制御フローは宿主言語に任せる）、**プロンプトを非同期ストリームとして扱うインタプリタ**、計算グラフと IR、**GPT-4 によるコンパイラ最適化**（自然言語を含むプログラムには従来のプログラム解析が効かない）、構造化出力が**正しさと速度の両方**であること。**一次資料は SGLang 1 本だけ**で、LMQL・Guidance・DSPy の記述はすべて SGLang 論文の §2.4 に依拠する（＝利害関係がある）旨をページに明記している。
- [[llm-serving-systems]] — **1 台の GPU で入出力長がばらばらな多数のクライアントをどう多重化するか**。[[llm-inference-optimization]] から切り出した（あちらは「1 回の前向き計算を速くする」側で、こちらは **OS・分散システムに近い主題**——資源の多重化・スケジューリング・断片化・SLO）。**Roofline によるバッチングの根拠**（decode は演算密度 ≈1 で極端に memory-bound。リクエストを増やすのは時間的にタダ）、**KV cache の配り方**（PagedAttention・prefix キャッシュ / RadixAttention）、**TTFT と TPOT の両立**（chunked prefill・P/D 分離）、**実装層**（カーネル融合・FlashInfer・NanoFlow・Multi-LoRA・CUDA Graph・非同期スケジューリング）、**アルゴリズム層**（量子化がどこで効くかの Roofline 図・KV スパース化・投機的デコーディングは誰にとって速いのか・構造的デコーディングは高速化でもある）、**分散サービング**（推論の DP/PP/TP/EP と DeepSeek の実例）、**モデル間ルーティング**（カスケードとルータ）、**スタックと運用**（shadow deployment・ワークロードのクラス分け）。エージェント固有の含意として、**多ターン trajectory は prefix キャッシュが最も効く形をしているので、プロンプトの可変部分を先頭に置かない**という規律が出る。
- [[low-precision-training]] — **訓練そのもの**を低精度で回してコストを下げる技法群。[[model-quantization]] から切り出した。冒頭で **QAT との区別**を立てる（低精度訓練は**訓練コストを下げる**もので成果物は高精度モデルでよく、QAT は**低ビットで配れるモデルを作る**もの。両者は直交する）。**BF16（2019）→ FP8（2023）→ FP4（2025）の系譜**、技法のカタログ（**loss scaling**・**tensor scaling**（just-in-time / delayed）・**precision decoupling**・**auto-scaling**・**確率的丸め**・**Random Hadamard 変換**・**2D スケーリング**）、**「どこを低精度にしないか」の規律**（6 年 3 世代を通じて埋め込み・出力ヘッド・正規化・attention 内部・オプティマイザ状態は変わらず高精度）、**否定的結果の一覧**（活性の勾配のブロック単位量子化で発散、master weight を FP8 にすると劣化、全線形層 FP4 で発散、確率的丸めを順伝播に適用すると発散）、そして**終盤だけ精度を上げる**運用。
- [[model-quantization]] — モデルの量子化。**推論サービングだけの道具ではない**（訓練・ファインチューニング・エッジ配布・カーネル実装にまたがる）ため [[llm-inference-optimization]] から切り出した。基礎（BF16 は範囲・FP16 は精度、affine 量子化の s と z）、量子化する 3 対象（重み・活性・KV cache）、**重みのみか重みと活性か**（前者はメモリ帯域の勝ち・後者は演算の勝ち。効く場面が違う）、**外れ値への 4 系統の対処**（分けて保持／粒度を細かく／重要な重みを守る／分布そのものをならす）、PTQ と QAT（偽量子化と STE）、**較正データへの過適合**（AWQ 対 GPTQ の実測）、**QAT は実用になったのか**（EfficientQAT を根拠に「4 ビットなら PTQ、2〜3 ビットなら QAT」）、代表手法（GPTQ・AWQ・EfficientQAT・GGUF・bitsandbytes・NF4・二重量子化）、**QLoRA は QAT ではなく PTQ ＋ PEFT** という分類の訂正、そして「量子化＝高速化ではない」。
- [[llm-agents]] — 総論ハブ。エージェントの定義と系譜・brain/perception/action・応用 3 形態・エージェント社会。各論ページへの入口。
- [[reasoning-and-planning]] — LLM に思考過程・計画を明示的に生成させる手法群。CoT・CoT-SC・ReAct・ToT を扱う。
- [[agent-loop]] — 観測→思考→行動の実行ループ。定式化、thought の密度、停止条件、典型的失敗モード。
- [[tool-use-and-function-calling]] — モデルが外部ツールを呼ぶ仕組み。ReAct の Wikipedia API から function calling までの系譜。
- [[multi-agent-systems]] — 複数 LLM エージェントの協調。debate / MoA / ルーティング / 学習されたオーケストレータ（Fugu）の類型と、MASFT による失敗分類。
- [[agent-evaluation]] — エージェント評価の方法論。ベンチマーク型／トレース分析型／LLM-as-a-judge の 3 類型と指標の整理。
- [[agent-frameworks]] — 設計パターン（workflow 5 種＋agent）とフレームワーク観。「まず単純に、複雑さは実証されたときだけ」。
- [[self-reflection]] — 失敗を言語で振り返り試行間で学ぶ仕組み。Reflexion / Self-Refine と、盲目的リトライ無効・FP 即死などの設計論点。
- [[reinforcement-learning-from-human-feedback]] — 事後訓練の RL。**時系列構成**（2022 古典的 RLHF → 2023 DPO → 2024 GRPO → 2025 RLVR/蒸留 → 2025 K2 joint RL → 2026 K2.5 → 2026 OPD）で「何が何を置き換えたか」を追う。
- [[research-agents]] — 調査・研究そのものを担うエージェント。**知識の集約（Deep Research 型）⇄ 知識の生成（AI Scientist 型）**の対比を骨格に、段階つき実験管理・統計を取るための探索ノード型・「良い研究か」を査読という制度を借りて測る評価の難所まで。
- [[retrieval-augmented-generation]] — 検索で外部知識を注入して生成。訓練時組み込み型と推論時注入型の 2 層、hot-swap、collapse。ローカル／グローバルな質問の分類と GraphRAG。
- [[agent-memory]] — コンテキストを超えて保持・想起する記憶の設計。MemGPT の階層記憶・Reflexion のエピソード記憶・共有境界。
- [[context-engineering]] — 限られたウィンドウに何をどう積むか。注意予算と context rot・各構成要素の絞り方・just-in-time 取得・区画化・圧縮と引き継ぎ・参照渡し・長時間タスクの 3 手法。
- [[agent-safety-and-guardrails]] — 安全対策の 4 層（行動空間・ガードレール・監視・HITL）と、**それと直交する第二の軸 embedded / programmable**（制約が訓練時に焼き込まれたものか、実行時に書かれたものか）。CoT モニタリングの可能性と限界。モデル内在の安全性がどこから来るか（整合の宛先の 4 層分解）。**層 (2) に実装された系の一次資料**（LlamaFirewall の 3 層カスケード・ガードレール自身が攻撃面・検知と阻止の区別）と、**層 (3) の CoT 監視をめぐる対立の整理**（cot-faithfulness の忠実性 25%/39% と AlignmentCheck の再現率 80% 超は衝突ではなく脅威モデルの違い＝**隠す動機の有無**）を追加。
- [[test-time-compute]] — 推論時に計算を積んで精度を買う第二のスケーリング軸。垂直/並列の 2 型・推論境界・overthinking。
- [[positional-encoding]] — **トランスフォーマに語順を教える仕組み**。[[transformer-architecture]] から切り出した（位置符号化は「モデルの表現力」に見えて、実際には **KV cache・カーネル融合・量子化・長コンテキスト拡張のすべてと絡む**ため）。**なぜ必要か**（attention は並べ替えに同変＝語順を見ていない）と**注入先の 3 択**（入力に足す／attention スコアに足す／query・key を回す）を軸に、系譜を **(a) 絶対**（正弦・学習可能）→ **(b) 相対**（Shaw・Transformer-XL・T5 バイアス・DeBERTa・ALiBi。$N\times N$ のバイアスが要る／$q$・$k$ に分離できず linear attention と組めない）→ **(c) RoPE** → **(d) 拡張**（Position Interpolation・NTK-aware・**YaRN**・p-RoPE・部分 RoPE・NoPE）と辿る。後半は**システムとの相互作用**——回転済み key をキャッシュできる、rotary は帯域律速ゆえ FP8 前処理の融合先になる（FlashAttention-3）、**RoPE 次元だけ BF16 で残す**混合精度 KV、そして **MLA との衝突**（位置依存の行列が挟まるので $q$/$k$ の行列を畳めず、DeepSeek は RoPE 専用 key を分離せざるを得なかった）。**「128K 対応」は「128K を等しく使える」ではない**（lost-in-the-middle・context rot）。一次資料・二次資料・原典なしの区別をページ末尾に明示している。
- [[transformer-architecture]] — decoder-only の基本構造と attention の系譜（softmax→linear→delta→gated→ハイブリッド）・AttnRes。MoE は概要のみで詳細は下記へ。
- [[mixture-of-experts]] — 条件付き計算としての MoE。ゲーティング関数の設計空間・ルーティング水準・負荷分散とシステム設計・スパース性の経済・アーキテクチャ外での利用（継続学習/メタ学習/マルチタスク/RL）・理論の現在地。
- [[llm-inference-optimization]] — 推論を速く安く捌く側。prefill/decode・TTFT/TPS・KV cache の帯域律速・カーネル融合。
- [[computer-use-agents]] — スクリーンショットを観測し GUI を直接操作するエージェント（CUA）。行動空間・OSWorld/WebArena・グラウンディング律速・安全性。
- [[coding-agents]] — コードを書き・実行し・検証するエージェント。ACI・最小ツール構成・長時間ハーネス（initializer/coding）・検証の設計・SWE-bench 系。
- [[model-context-protocol]] — エージェントを外部ツール・データ・他エージェントに繋ぐ標準プロトコル群。MCP（縦＝ツール接続）／A2A（横＝エージェント間相互運用）／ACP（ローカル協調）の三つ巴とプロトコル層のセキュリティ。
- [[agent-observability]] — 本番で動くエージェントを外から見えるようにする層。評価との境界・行動ログ/指標/監査証跡の 3 層・非決定性とトレースの限界（CoT の不忠実性）。
