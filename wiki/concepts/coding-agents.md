# Coding Agents（コーディングエージェント）

**コードを書き・実行し・その結果を観測して修正する**ループを回すエージェントの総称。[[agent-loop]] の応用形のうち最も成熟した領域で、環境は「リポジトリ＋実行環境（シェル・テスト・開発サーバー）」、行動は「ファイル編集・コマンド実行」、観測は「コンパイル結果・テスト出力・実行ログ」である。コーディングが応用の先頭を走る理由は、**環境からのフィードバックが速く・機械可読で・ほぼ無料**なことである。書いたものが動くかを即座に検証できるため、[[reinforcement-learning-from-human-feedback]] の検証可能報酬とも、実行時の自己修正ループとも相性がよい。代表製品・システムに Claude Code・SWE-agent・Devin・Cursor など（各詳細は概説。専用原典は未 ingest）。

## 構成要素

- **ツール（ACI）**: エージェントが使うツールは人間向け CLI の流用では最適でない。ツール群をエージェントの認知に合わせて設計し直す考え方が **ACI**（agent-computer interface）で、**SWE-agent**（[[summaries/2024-swe-agent]], NeurIPS 2024）が確立した（概念の本体は [[agent-computer-interface]]、本ページの要点は下記の節）。興味深いことに、フロンティアモデルの評価ハーネスは最小構成に収斂している。[[summaries/2026-deepseek-v4]] の SWE 評価は「bash＋ファイル編集」の 2 ツール、[[summaries/2026-kimi-k2.5]] は bash / create_file / insert / view / str_replace / submit の 6 ツールで、豊富なツールより**少数の直交したツール**が好まれる（→ [[tool-use-and-function-calling]] の「ツールの弱さが推論を引き出す」の現代形）。
- **実行フィードバック**: 単体テスト・型検査・リンタ・開発サーバー・ブラウザ自動化。どの層まで検証するかが品質を決める（後述）。
- **状態管理**: **git が天然のチェックポイント機構**を提供する。コミットは進捗記録・ロールバック手段・次セッションへの引き継ぎ記録を兼ねる。エージェント設計で外部メモリをゼロから作る前に、リポジトリに既にある仕組みを使うのが定跡。

## ACI: インターフェースを設計変数にする

> **ACI の本体（定義・系譜・設計原則・編集インターフェースの比較・SWE-agent のアブレーション・評価駆動のツール改善）は 2026-10-25 に独立した概念ページ [[agent-computer-interface]] へ移した。** 本節はコーディングエージェントにとっての要点と、コーディング固有の失敗分析に絞る。

**SWE-agent**（[[summaries/2024-swe-agent]], NeurIPS 2024）は、LM を「第 3 のエンドユーザー」とみなしてツール群を作り直し、**重みを変えずに SWE-bench の解決率を 3.8% → 12.47%** にした。アブレーションの決定打は、人間の検索 UI を模したツール（12.0%）が検索ツールなし（15.7%）より悪かったことである。

その 8 か月後、**Claude 3.5 Sonnet の足場**（[[summaries/2025-swe-bench-sonnet]], 2025-01）は同じ SWE-agent フレームワークをもとにしながら、専用コマンド群を **bash と `str_replace_editor` の汎用 2 ツール**に置き換え、ワークフローを固定せずに制御をモデルへ渡して SWE-bench Verified 49%（当時の SOTA）を出した。労力を注いだのはツールの説明文と、**絶対パスの強制・一意一致でしか置換しない編集**といった「誤りにくい」入力形式である。同じ足場で 22 → 33 → 49% とモデルの世代差がそのまま出ており、**強いモデルには制御を渡すほど伸びる**設計だと読める。

2 つは「ツールを作り込むか、最小にするか」で逆を選んだが、フィードバックの簡潔さ・誤りの構造的な防止・説明文で使い方を教える点では一致する。**弱いモデルほどツールで底上げでき、強いモデルほど足場を薄くできる**。[[summaries/2026-harness-design]] の「剥がす」と ACI は同じ軸の両端である（詳細な比較は [[agent-computer-interface]]）。

**コーディングエージェントに固有の教訓**として残るのは、(1) 編集は**一意一致の文字列置換**が最も信頼でき、事実上の標準になったこと、(2) 編集後に**リンタで検査して差し戻す**ガードレールが効くこと（SWE-agent で −3.0pt の差）、(3) 隠しテストで採点されるタスクでは、エージェントは**失敗しているのに成功したと思い込む**ので、自分で再現・検証させる手順が要ること（[[summaries/2025-swe-bench-sonnet]]。→ 下記「検証の設計」）、(4) ツールの出力が履歴の大半（SWE-agent では 1 ターンのトークンの約 84%）を占めるので、**古い観測を置き換え文に替えるだけで、コストが半分前後になり解決率も落ちない**こと（[[summaries/2025-complexity-trap]]。LLM による要約はこれを上回らなかった。残す窓の大きさは足場ごとに違い、OpenHands では SWE-agent の 10 ターンでは足りなかった → [[context-engineering]]）である。

### 編集は連鎖して壊れる

SWE-agent の軌跡分析はコーディングエージェントの失敗の形を数字にしている。**2,294 インスタンスのうち 1,185（51.7%）が失敗した編集を 1 回以上含む。** そして**回復確率は失敗が積み重なるほど落ちる**。編集のどんな試みも最終的に成功する確率は **90.5%** だが、**1 回失敗した直後には 57.2%**、つまり **1 回の編集エラーで 42.8% はもう回復しない**。リンタのガードレールはこの連鎖を断つために置かれている。

失敗の内訳も示唆的で、**Incorrect Implementation 39.9% ＋ Overly Specific Implementation 12.1% = 52.0%** が「妥当な場所を触ったが解が正しくない／一般的すぎない」。**位置特定より実装が難所**である（Failed to Find Relevant File はわずか 2.4%）。

「**エージェントは速く成功し、ゆっくり失敗する**」という観察も運用に役立つ。解決できたものは中央値 $1.21・12 ステップ、できなかったものは平均 $2.52・21 ステップで、**解決できたインスタンスの 93.0% は予算を使い切る前に提出**している。**予算やトークン上限を上げても性能はさほど伸びない**、というのが著者らの結論である。

## 検証の設計: 「コードだけ見て完了宣言」問題

コーディングエージェントの品質は**どこまで検証させるか**で決まる。実務で繰り返し観測される失敗が「単体テストや curl は通したが、end-to-end では動かないのに完了とマークする」であり、対策は**人間のユーザーと同じ経路での検証**である。Web アプリならブラウザ自動化（Puppeteer 等。ブラウザ操作という意味で [[computer-use-agents]] の技術の検証用途への転用）で実際に操作させる。ただし次の 3 つの罠が残る。

1. **検証ツールの盲点は品質の穴になる**: Puppeteer MCP から見えない alert モーダルに依存する機能はバグが残った（[[summaries/2025-effective-harnesses]]）。エージェントが観測できない場所は検証されない。
2. **自己検証の偽陽性は致命傷**: [[summaries/2023-reflexion]] の実測どおり、誤った実装を通してしまうテスト（偽陽性）は「確信を持った誤り」を生む。長時間ハーネスの feature list（全機能を `"passes": false` で列挙し、エージェント自身が passing にしていく完了定義。→ [[harness-engineering]]）の self-verify も同じ構造を持ち、検証手段が弱いドメインでは機能しにくい。評価側の対応物は [[agent-evaluation]] の終了状態評価。
3. **隠しテストでは「成功の思い込み」が起きる**: Claude 3.5 Sonnet の SWE-bench 実行（[[summaries/2025-swe-bench-sonnet]]）では、採点用テストが見えないため、モデルが**実際には失敗しているのに成功したと思い込む**ことがよくあった。原因は 2 種類あり、誤った抽象度での修正（根本的なリファクタリングでなく応急処置）と、問題は解いたが元の単体テストと合わない解である。足場のプロンプトが「再現スクリプトを作って実行 → 修正 → 再実行 → エッジケースを考える」を手順として明記しているのは、この思い込みを自分の検証で減らすためと読める。

## ハーネス: 本ページから切り出した層

コーディングエージェントの成熟は**ハーネス（モデルの外側にある編集可能な構成要素の総体で、システムプロンプト・ツール・ミドルウェア・記憶・サブエージェント設定を指す）** を独立した設計対象へ押し上げた。**その設計・縮小・自動探索・自動進化・仮想化は 2026-08-03 に [[harness-engineering]] へ切り出した**（本 wiki のハーネス系の原典が 7 本に達し、しかもその議論がコーディングに固有でなくなったため）。本ページには**コーディング固有の話**を残す。

あちらで扱う要点だけ挙げておく。

- **長時間タスクの二部構成**（[[summaries/2025-effective-harnesses]]）: initializer が feature list JSON・進捗ログ・`init.sh`・初期 commit で環境の足場を作り、coding agent が毎セッション 1 機能ずつ進めてクリーンに終了する。**引き継ぎ媒体を「要約」でなく検査可能な構造化 artifact にした**のが要点。
- **generator / evaluator / planner の分業と、ハーネスの縮小**（[[summaries/2026-harness-design]]）: 「**すべての部品は『モデルが単独でできないこと』への仮定であり、モデルの改善で陳腐化する**」。1 部品ずつ外して確認する。
- **ハーネスの自動探索**（[[summaries/2026-meta-harness]]）: コーディングエージェント自身を proposer にしてハーネスコードを探索させる。**原典の脚注は、このワークフローが「2026 年初頭のコーディングエージェント能力の大幅改善で初めて実用的になった」と述べている**。これは本ページの主題の成熟が、自分自身の実行基盤の改善という**再帰的な仕事**を可能にした記録である。
- **ハーネスの自動進化**（[[summaries/2026-agentic-harness-engineering]]）: 観測された失敗から編集を導き、**すべての編集に「直すタスク」と「壊すタスク」を自己申告させて次ラウンドで採点する**。Terminal-Bench 2 で 69.7% → 77.0%。**層別の価値が定量化されており、長期記憶 +5.6 / ツール +3.3 / ミドルウェア +2.2 に対しシステムプロンプトは −2.3 pp** であり、**事実としてのハーネス構造は転移するが、散文レベルの戦略は転移しない。**

## Claude Code という設計点: ハーネスが 98.4% を占める

本ページの他の節が「どう設計すべきか」の指針だったのに対し、[[summaries/2026-dive-into-claude-code]]（VILA Lab / MBZUAI・UCL, 2026）は**実際に出荷されている本番系を、公開された TypeScript ソース（v2.1.88、約 1,884 ファイル・51.2 万行）から解剖した**第三者の分析である。Anthropic の刊行物ではない。**証拠を 3 階層（Tier A = 公式ドキュメント／Tier B = コード検証済み／Tier C = 再構成・推論）でラベル付けしている**点で、リバースエンジニアリング系の資料としては珍しく誠実な形をしている。

**この論文の要約を一言にすると次の比率である。**

> **コードベースのうち AI の意思決定ロジックは推定 1.6%、残る 98.4% は運用ハーネスである。**

**ただしこれは Tier C（コミュニティ解析からの推定）であり、Tier B の主張と同じ強さでは読めない。** それでも本ページの他の原典と方向は一致する。**中核のエージェントループは「モデルを呼び、ツールを実行し、繰り返す」だけの while ループで、複雑さのすべてはその周囲にある**。著者らの言い方では「**工学的な複雑さは、モデルの決定を制約するためではなくそれを可能にするために存在する**」。

### 4 つの設計上の問い

著者らは、あらゆる本番コーディングエージェントが答えなければならない問いを 4 つに整理した。**本ページの他の系（SWE-agent・Aider・Devin）と比較する軸としてそのまま使える。**

| 問い | Claude Code | SWE-agent / OpenHands | Aider | Devin / LangGraph |
|---|---|---|---|---|
| **推論はどこに宿るか** | モデルが推論、ハーネスが実行。**モデルは FS・シェル・ネットワークに直接触れない** | 同様（コンテナ内） | 同様 | **スキャフォールディング側**に計画構造・状態グラフを持つ |
| **実行エンジンは何個か** | **1 個**（`queryLoop()`）。変わるのはレンダリングだけ | — | — | モード固有のエンジンもありうる |
| **既定の安全姿勢** | **deny-first ＋人間へのエスカレーション**、独立層の並列適用 | **コンテナ隔離** | **git ロールバック** | — |
| **拘束的な資源制約** | **コンテキストウィンドウ**（200K / 1M） | — | — | 計算予算、明示的スクラッチパッド |

**「推論はどこに宿るか」への答えにはセキュリティ上の帰結がある**。推論と強制が別々のコードパスを占めるので、**危殆化したモデルでもハーネスの権限チェックやサンドボックスを上書きできない**。モデルの外界への唯一のインターフェースは `tool_use` プロトコルであり、ハーネスが実行前に検証する。→ [[agent-safety-and-guardrails]]

### コーディングエージェントに固有の設計判断

上表の外で、**この論文がコーディングエージェント固有の教訓として読めるもの**が 3 つある。

- **git worktree を隔離機構に使う。** subagent の隔離モードは worktree / remote / in-process の 3 つで、**worktree は一時的な git worktree を作って subagent に自分用のリポジトリのコピーを与える**。コンテナのオーケストレーションを導入せず、**外部依存ゼロでファイルシステム水準の分離**が得られる。これは本ページ冒頭の「git が天然のチェックポイント機構」の延長にある。SWE-agent / OpenHands の Docker 隔離、AutoGen のコンテキストのみの隔離との中間に位置する。
- **エージェントチームの調整はファイルロックで行う。** メッセージブローカーも分散調整サービスも使わず、**共有タスクリストからロックファイルによる排他制御で主張する**。スループットを**依存ゼロの配備**と**プレーンテキスト JSON を読むだけのデバッグ可能性**と引き換えにしている。
- **CLAUDE.md はシステムプロンプトでなく user メッセージとして届く。** 著者らはこの含意を「**会話的なコンテキストとして届けられるため、これらの指示へのモデルの遵守は保証されたものではなく確率的である**」と明記する。決定論的な強制は権限ルールが担う。**指針（確率的）と強制（決定論的）の意図的な分離**であり、CLAUDE.md に何を書き、何を書いてはいけないかの判断基準になる。

### 弱点として記録に値するもの

- **多層防御の独立性の仮定が破れる。** Claude Code の安全性の層は**共通の性能・経済上の制約を共有している**（分類器は追加の LLM 呼び出し、AST チェックは解析遅延）。実例として**50 を超えるサブコマンドを持つコマンドは、解析が UI をフリーズさせたため、サブコマンドごとの deny チェックを飛ばして単一の汎用承認プロンプトへフォールバックする**。→ [[agent-safety-and-guardrails]]
- **compaction がユーザーに見えない。** とくに **context collapse はユーザーに見える出力なしに動作する**。何が失われたかを検査する手段がない。→ [[context-engineering]]
- **リバースエンジニアリングの限界。** 著者らが自ら書くとおり、**ソースは実装された構造を明らかにするが、設計の意図・本番で有効なフラグ・ランタイムでの出現頻度・出荷されていない挙動は確認できない**。機能フラグはビルド時の可変性を作り、`TRANSCRIPT_CLASSIFIER` が false のビルドでは **auto-mode 分類器全体が除去される**。**「異なるビルドターゲットは機能的に異なるアプリケーションを生成しうる」。**

### OpenClaw との対比が示すこと

論文は Claude Code を **OpenClaw**（約 2 ダースのメッセージング表面をエージェントランタイムへ繋ぐ local-first の WebSocket ゲートウェイ）と 6 次元で比較する。**同じ問いに正反対の答えが出るのが要点**で、信頼境界は「モデルと実行環境の間」対「ゲートウェイの境界」、エージェントループは「系の中心」対「制御平面の中の 1 コンポーネント」、拡張は「単一エージェントのコンテキスト」対「ゲートウェイ全体の能力面」となる。

**そして 2 つは合成できる**。**OpenClaw は ACP（Agent Client Protocol）を通じて Claude Code を外部のコーディングハーネスとしてホストできる**。著者らの結論は本 wiki にとって有用で、「**エージェントの設計空間は平坦な分類ではなく層状のものであり、ゲートウェイ水準の系とタスク水準のハーネスが合成できる**」というものである。→ [[agent-frameworks]]

### 大規模コードベースでの運用: 利用者が手を入れる側の記録

上の解剖がソースから見た Claude Code なら、[[summaries/2026-claude-code-large-codebases]]（Anthropic, 2026）は**利用者が手を入れる側**から見た記録である。数百万行のモノレポやレガシーシステムへの導入経験から、次を勧める。

- **索引を作らず、agentic search で辿る。** 埋め込み索引は大規模な開発現場の更新に追いつかず、古い情報を兆候なしに返す。代わりに、どこを見ればよいかの手がかり（CLAUDE.md の階層、コードベースの地図、生成物の除外）を人が整える → [[context-engineering]]。
- **7 つの部品を順に作る。** CLAUDE.md → フック → スキル → プラグイン → MCP サーバーの 5 つの拡張ポイントに、LSP 連携とサブエージェントを足す。LSP（Language Server Protocol, IDE の「定義へ移動」を支える言語サーバーとの標準プロトコル）は C・C++ のような言語でもシンボル単位の探索を可能にし、記事は多言語のコードベースで最も価値の高い投資の 1 つと呼ぶ。
- **探索と編集を分ける。** 読み取り専用のサブエージェントにサブシステムの地図を作らせてファイルに書き出させ、メインのエージェントはそれをもとに編集する → [[multi-agent-systems]]。
- **設定を 3〜6 か月ごとに見直し、担当者（DRI, その件に最終責任を持つ 1 人）を置く** → [[harness-engineering]]。

定量データのない提供者自身の記事だが、上の「指針と強制の分離」を「守らせたいことはフックへ」と実務の言葉で言い直しており、ソースの解剖と運用の記録が同じ方向を向いている。

## 短期の増幅と長期の損耗: 使った結果、人間側に何が起きるか

**本ページはここまで「どう作るか」だけを扱ってきた。しかし [[summaries/2026-dive-into-claude-code]] は、コーディングエージェントを*使った結果*についての懐疑的な実証を集めており、本 wiki にはこの軸の記述が 1 つも無かった。** 論文はこれを 5 つの価値と対等な設計価値ではなく「**評価的レンズ**」（アーキテクチャを横断して当てる問い）として扱っている。その理由も明記されており、**長期的な人間の能力の保全は Claude Code のアーキテクチャにも Anthropic の表明された設計価値にも、設計の駆動因として顕著には反映されていない**からだという。

### 実証されているもの

| 研究 | 規模 | 知見 |
|---|---|---|
| **RCT**（becker2025measuring） | 経験豊富な開発者 **16 名・246 タスク** | **AI ツール使用時に 19% 遅くなった。本人たちは 20% 速くなったと知覚していた** |
| **Cursor 導入の因果分析**（he2026cursor） | **807 リポジトリ** | **複雑度 +40.7%（p < 0.001）**。速度スパイクは初月 +281% だが**3 か月目でベースラインへ**。複雑度の上昇は将来の速度低下と比例——**利得は自己相殺的** |
| **AI コミットの監査**（liu2026techdebt） | **30.4 万コミット・6,275 リポジトリ** | **AI が導入した問題の約 1/4 が最新リビジョンまで持続**。セキュリティ関連はさらに高率で持続 |
| **理解度テスト**（shen2026skill） | — | AI 支援条件の開発者は**理解度テストで 17% 低いスコア** |
| **EEG 研究**（kosmyna2025brain） | **54 名** | LLM 利用者は**神経結合の弱まりを示し、AI を取り除いた後も持続** |

| Anthropic 内部調査（anthropic2025internal） | エンジニア・研究者 **132 名** | **タスクの約 27% はツールがなければ着手されなかった**。同時に「**監督のパラドックス**」——AI への過度の依存が、それを監督するのに必要なスキルを萎縮させるリスク——を記録 |

**最初の 1 行が最も重要だと思う。「19% 遅くなったのに 20% 速くなったと感じていた」は、主観的な生産性の報告が測定の代わりにならないことの直接の実証**であり、[[agent-evaluation]] が繰り返し扱ってきた「判定器と人間の一致」問題の、人間自身が判定器になった場合の変種として読める。

### アーキテクチャ側の予測と、それを支持するデータ

**論文の構成が良いのは、外部の実証を持ち出す前に、アーキテクチャからの予測を先に立てていることである。**

> 有界なコンテキストウィンドウは**コードベース全体の同時把握を妨げる**。したがって**エージェント生成コードはパターンの重複と規約違反の率が高くなる**とアーキテクチャ的に予測される。**subagent の隔離がこれを増幅する——並列のエージェントは、他所に既に存在する解を独立に再実装しうる。**
>
> **設計哲学はモデルが良い局所的な決定をすることを信頼するが、モデルが大域的な文脈を欠くとき、良い局所的な決定は悪い大域的な帰結を生みうる。**

上表の複雑度 +40.7% と技術的負債の持続は、**この予測と整合する外部データ**という位置づけになる。**著者らは正直に留保も付けている。** それによれば、Claude Code の 5 層 compaction・キャッシュ意識・読み取り時の射影・subagent の要約隔離は**まさにこれらの効果を緩和するよう設計されており、それが十分かは「ソースレベルの解析では解決できない、直接測定可能な実証的な問い」である**。上表の研究はいずれも隣接ツール（Cursor 等）を標的にしている。

### 測れないという問題

**論文が最後に置く問いが、本 wiki にとっては最も実務的である。**

> 既存の引用はセッションから数か月の尺度で動作する**が、ハーネスは理解や規約のドリフトについてセッションごとの信号を一切露出していない。**

つまり「**短期の増幅と長期の損耗のトレードオフを、開発者が自分のセッションで観測する手段が今は存在しない**」。著者らは (a) セッション粒度で測定可能にすることと、(b) 測定が存在したときアーキテクチャがそれに応答できるかを、別々の未解決問題として分けている。そして「**ハーネスがそもそもその行動の正しい場所なのか（IDE、組織、人間の開発ループではなく）はアーキテクチャの分析では裁定できない**」と留保する。

**設計上の教訓は 3 つある。**

1. **速度の自己申告を成果指標にしない。** 19% 対 +20% の乖離は、**主観的な速さの感覚が測定と逆を向きうる**ことを示す。ベロシティを測るなら実測する。
2. **複雑度と技術的負債を継続的に測る。** 初速のスパイクは 3 か月で消え、複雑度は残る。**導入の効果は 1 か月では評価できない。**
3. **エージェントに大域的な文脈が無いことを前提に設計する。** 規約の集約（CLAUDE.md 等）・重複検出・レビュー段の分離は、**アーキテクチャの構造的な限界に対する緩和であって、モデルが賢くなれば消える問題ではない**。

## 手続き型とエージェント型: 足場の 2 つの流儀

GitHub のイシュー解決の足場は、**エージェント型**（agentic）と**手続き型**（procedural）に分けられる（[[summaries/2025-swe-effi]] が引くサーベイの分類）。エージェント型は LLM が自分で計画し、ツールを選んでループを回す（SWE-agent、OpenHands）。手続き型は決まった手順の決まった箇所で LLM を呼ぶ固定パイプラインで、[[agent-frameworks]] の用語では agent ではなく **workflow** にあたる。**AutoCodeRover** は抽象構文木にもとづくツールで疑わしい関数を特定してから、パッチを生成して選ぶ。

**手続き型の一次資料が Agentless**（[[summaries/2024-agentless]], Xia ら, 2024）である。「当時の LLM にツールの使い分けと次の手の判断を任せると、ツールの誤用・無駄な探索・誤りの増幅が起きる」として、LLM には各段階の小さな仕事だけをさせ、手順は人間が固定した。

1. **位置の特定**：リポジトリの木構造 → ファイル（埋め込み検索と併用）→ クラス・関数（宣言だけを残したスケルトン形式で見せる）→ 編集位置、と段階的に絞る。
2. **修復**：編集位置の候補 4 組 × 10 本で、Search/Replace 形式の候補パッチを 40 本作る。
3. **パッチの検証**：LLM に再現テストを書かせ、回帰テスト → 再現テスト → 正規化したパッチの多数決の順で 1 本に絞る。

GPT-4o で SWE-bench Lite 32.0%（1 件 $0.70）と、同じモデルの SWE-agent（18.3%、$2.53）を大きく上回り、当時のオープンソースのエージェントをすべて超えた。OpenAI が GPT-4o・o1 の SWE-bench の成績を示す既定の手法に採用し、Kimi K2 も評価条件の 1 つに「Agentless」設定を置いている。**手順を固定する利点は段ごとに失敗を測れることにもある**。同論文のアブレーションは、ファイル全体ではなくスケルトンを見せると位置の正解率が上がり費用は 1/7 になること（58.3% 対 53.7%）、パッチの選び方を「多数決だけ」から「回帰テスト＋再現テスト」にすると 77 件 → 96 件になることを、段ごとに切り分けて示した。

**同じ論文が手続き型の限界も示している**。イシューに位置の手がかり（ファイル名・スタックトレース・キーワード）が一切ない問題では、コード検索のツールを自分で使って探し回れるクローズドソースのエージェント型ツールのほうが良かった。手順の外にある種類の問題には、固定のパイプラインは弱い。さらに、同じ表に載っている Claude 3.5 Sonnet（2024-10）の 49.0%（Verified）は Agentless の 38.8% を上回っており、Anthropic はこの数字を最小構成のエージェントで出したと報告している（[[summaries/2025-swe-bench-sonnet]]）。**モデルが強くなるにつれ、手順を固定する利点は薄れていった**。

SWE-Effi は 5 つの足場を 3 つのモデル（GPT-4o-mini、Llama-3.3-70B、Qwen3-32B）で SWE-bench Verified の 50 問にかけ、**足場の良し悪しはモデルとの相性で決まる**ことを示した。エージェント型の SWE-agent と OpenHands は、Qwen3-32B ではそれぞれ 28%・34% だが、GPT-4o-mini では 10%・11.9% に落ち、SWE-agent は入力 810 万トークン超を使った。手続き型の AutoCodeRover はどのモデルでも安定して競争力があり、Agentless は解決率首位（Qwen3-32B で 48%）だがテストを大量に回すので CPU 時間が重い。**弱いモデルでは手順を固定したほうが安定し、強いモデルには制御を渡したほうが伸びる**。[[agent-computer-interface]] の「作り込むか、最小にするか」と同じ軸が、足場の流儀でも現れている。最小構成の極には bash 1 ツール・約 100 行の **Mini-SWE-Agent** もある。どちらの流儀でも、**失敗した試行は成功の数倍の資源を使う**（→ [[agent-cost-efficiency]]）。

> 注: AutoCodeRover・OpenHands・Mini-SWE-Agent の原典は wiki に未取得で、これらの記述は SWE-Effi と Agentless を通した二次情報である。

**足場の流儀は訓練での伸び方も変える。** SWE-Gym（[[summaries/2024-swe-gym]]）は同じ Qwen2.5-Coder を 2 つの足場で訓練した。手順の決まった Moatless Tools では、素の 32B が SWE-bench Lite で 19.0% と高いが、自分の成功軌跡で訓練しても 19.7% で頭打ちになった。汎用の OpenHands では素の 32B が 3.0% しか解けないが、強いモデルの成功軌跡 491 本で SFT すると 15.3% になった。**手順を固定した足場は素のモデルを助けるが、訓練で伸ばす余地も狭める**。これは上の「弱いモデルには手順を固定したほうが安定する」と表裏の関係である。

**2 つの流儀を「段階」として並べる見方もある。** Kimi-Dev（[[summaries/2025-kimi-dev]], Moonshot, 2025-09）は、手続き型を「完成品」ではなく「エージェントの下ごしらえ」として使った。Qwen2.5-72B を Agentless の形式（ファイルの特定 → 編集、パッチを書く役とテストを書く役）で中間訓練・コールドスタート・RL まで鍛えると、それだけで Verified 60.4%（パッチ 40 本・テスト 40 本を実行して選ぶ設定）になる。そのモデルを SWE-smith の公開軌跡 5,016 本で軽く SFT するだけで、エージェント型の足場で 1 回の試行 48.6% になった。素のモデル・中間訓練後・SFT 後・RL 後を出発点にして比べると、エージェント用のデータが少ないほど RL 後のモデルが有利で、70 ターンを超えても解ける問題が増え続けた。ただし 5,016 本すべてを使うと出発点の差はかなり縮み、中間訓練だけで差の大半が説明できる（本 wiki の図の読み取り）。SWE-Gym の「手順の決まった足場は訓練で伸びにくい」とは矛盾しない。固定手順の**足場で**伸ばすのではなく、固定手順で**モデルを**鍛えてから自由な足場に移す、という順序の提案である。

## モデルを訓練する: 足場の外側の改善

ここまでの節はモデルを固定して足場とツールを工夫する話だった。2024 年末から、**オープンなモデルそのものを SWE エージェントとして訓練する**研究が続いている。SWE-Gym（[[summaries/2024-swe-gym]]）は、実行環境つきのタスク 2,438 件の上で強いモデルの成功軌跡を集め、Qwen2.5-Coder-32B を SWE-bench Verified で 7.0% → 20.6%（検証器で 16 本から選ぶと 32.0%）にした。Golubev ら（[[summaries/2025-swe-rl-long-context]]）は、教師モデルを使わず、自分の成功軌跡での SFT（RFT）と多ターンの強化学習だけで Qwen2.5-72B を 11.4% → 39.0% にした。同時期の DeepSWE-32B（42.2%）・SWE-agent-LM-32B（40.2%）なども含め、**オープンな中規模モデルは 2025 年夏に Verified 40% 前後まで来た**。

2025 年後半から 2026 年初めにかけて、**データを大量に作る**方向が続いた。SWE-smith（[[summaries/2025-swe-smith]]）は環境を先に作ってテストを壊すバグを合成し（5 万件）、Claude 3.7 Sonnet の軌跡で SWE-agent-LM-32B を 40.2% にした。SWE-Lego（[[summaries/2026-swe-lego]]）は実際の PR と合成バグを混ぜ、**強化学習なしの SFT だけで** Qwen3-32B を 52.6%（検証器で 16 本から選ぶと 58.8%）にした。同じ規模で RL を使ったモデルと並ぶ水準である。ただし SWE-Lego は、古い SWE-bench Verified の環境では `git log` で正解を覗けたことも示しており、この時期の数字の比較には注意が要る（→ [[agent-evaluation]]）。

訓練したモデルに残る弱点として、SWE-smith は**同じ行動の繰り返し**を挙げる。SWE-agent-LM-32B の軌跡の 25% 超に長さ 10 以上の繰り返し（多くは検索せずにファイルの別の部分を表示し続ける）があり、Claude 3.7 Sonnet では 4% 未満だった。足場で繰り返しを抑えても解決率は上がらず、繰り返しは難しい問題に当たったときの症状だと解釈されている。訓練データの側で繰り返しを減らす試みもある。SWE-Prime（[[summaries/2026-swe-prime]]）は、隣り合う同じツール呼び出しを含む成功軌跡を減点し、無関係な探索の区間を損失から外して訓練すると、成功軌跡すべてで訓練した場合より繰り返しが減り、平均ターン数も 4〜13 ターン減ったと報告している。

こうした訓練のもとになるデータの集め方も自動化が進んだ。SWE-rebench（[[summaries/2025-swe-rebench]]）は、実際の PR からインストール手順の推測とテストの確認まで人手なしで行い、3,468 リポジトリの 21,336 件を公開した（→ [[agent-environments]]）。

訓練で使うツールは小さい。RL 論文のエージェントはシェル・行範囲指定の edit・submit の 3 つだけで、SWE-agent の ACI（→ [[agent-computer-interface]]）に近い。素のモデルの失敗の多くは**ツール呼び出しの書式違反とループ**で、訓練でまず直るのもこの 2 つである（SWE-Gym では SFT でループに陥る軌跡の割合が下がった）。訓練の段取り（蒸留・RFT・多ターン RL・検証器）と落とし穴は [[agent-training]] にまとめた。

## 評価

**この領域で主に競われるのが SWE-bench**（[[summaries/2023-swe-bench]], Jimenez ら, ICLR 2024）である。実際の GitHub イシューと、それを解決したマージ済み PR の対から **2,294 件**（12 の Python リポジトリ）を自動収集し、**リポジトリ自身の単体テストで実行ベースに採点する**。詳しい設計は [[agent-evaluation]] に置いた。

**出発点の水準を押さえておく価値がある。** 2023 年当時、**編集すべきファイルを教える「オラクル」設定でさえ Claude 2 が 4.8%、GPT-4 が 1.7%**、普通に BM25 で検索させると 1.96% / 0.00% だった。翌年の [[summaries/2024-swe-agent]] が 12.47% へ、その後さらに大きく伸びる。**この領域の進歩の速さを測る基準線**として使える。

当時の失敗の質も記録されている。**モデルは gold より短く単純な編集を書き**（19.6 行 対 44.1 行）、**ほぼ単一ファイルしか触らない**（1.0 対 1.7 ファイル）。**パッチ形式で出させるほうがファイル全体を書き直させるより成績が良い**（Claude 2: 4.8% 対 2.2%）一方で、**整形式のパッチを出すこと自体に苦労する**（GPT-4 はオラクル設定で適用成功 150/472、うち 68.7% が自動修復を要した）。ファインチューニングした SWE-Llama は適用率が高く修復率が低く、**書式の遵守は微調整で改善する種類の問題**であることを示した。

興味深いのは、**成績が同程度でも解けている問題が重ならない**ことである。オラクル設定で Claude 2 は 110 件、SWE-Llama 13b は 91 件を解くが、**Claude 2 は SWE-Llama が解いた問題の 42% しか解けていない**。単一のスカラーがモデルの能力を代表しない。



標準は **SWE-bench 系**（実 GitHub イシューの解決率。Verified / Pro / Multilingual）・Terminal Bench（端末操作）・LiveCodeBench（競技・汚染対策つき）など → 詳細は [[agent-evaluation]]。実務上の注意として、同じモデルでもハーネスでスコアが大きく動く（ハーネス差・step 上限・コンテキスト管理の開示が比較の前提）ことと、フロンティアの到達点（2026 年時点で SWE-bench Verified 80 前後 → [[summaries/2026-deepseek-v4]] 表6。**ただし Verified は 2026-02 に作成者の OpenAI 自身が報告をやめた**。監査した難問の 59.4% はテストが正しい解を落とし、主要なフロンティアモデルはどれも正解パッチを記憶していた。この水準の数字は汚染とテストの欠陥を含む → [[summaries/2026-swe-bench-verified-retired]]、[[agent-evaluation]]。OpenAI は代わりに SWE-bench Pro を勧める）に対し、**長時間の自律構築タスクには標準ベンチマークがまだ無い**（Anthropic の記事も定量評価なし）ことが挙げられる。汚染を避ける方法としては、モデルの公開より後に作られたイシューだけで、全モデルを同じ足場で測る SWE-rebench のリーダーボードがある（[[summaries/2025-swe-rebench]]）。そこでは、コード生成のベンチマークで強い Qwen2.5-Coder-32B が 3% 前後にとどまり、ツールの実行結果を自分ででっち上げたり書式エラーを繰り返したりしていた。**コードを書く力と、決まった形式でツールを使い続ける力は別物**である。

## 設計論点

- **単一汎用 vs 特化分業**: テスト専任・QA・クリーンアップ等の特化エージェント分業が単一 coding agent に勝るかは**未解決**（[[summaries/2025-effective-harnesses]] が明示的にオープンクエスチョンとした）。[[multi-agent-systems]] の一般論（Anthropic Research の自己申告によれば、依存の密なコーディングは並列分業に不向き）と、Agent Swarm 系（並列化を学習で解く）の間で、コーディング領域の答えはまだ出ていない。
- **エージェントの書きやすさに環境を寄せる**: init.sh・機能リスト・進捗ログは「エージェントのための開発者体験（DX）」であり、人間の新人オンボーディングと同じ投資が役立つ。モデル訓練側でも同じ力学が働く。[[summaries/2025-kimi-k2]] のツール利用データ合成や [[summaries/2026-deepseek-v4]] の R&D 実タスク評価は、エージェントが働く環境・課題の整備がモデル性能と同じくらい結果を左右することを示す。
- **セッションの型化**: 「状況把握 → 健全性確認 → 1 単位 → クリーン終了」はコーディング以外の長時間タスク（研究・分析）にも流用可能な汎用テンプレート。
- **安全性**: コード実行はサンドボックス内で（→ [[agent-safety-and-guardrails]] の DSec が本番規模の実例）。リポジトリ書き込み・デプロイ権限は最小化し、不可逆操作（force push・本番反映）は人間の承認を挟む。
- **生成コードの静的解析をループに組み込む**: 上のリンタ・ガードレールの発想は**セキュリティ**にもそのまま延長できる。**CodeShield**（[[summaries/2025-llamafirewall]], Meta）は Semgrep と正規表現のルールで 50 超の **CWE**（Common Weakness Enumeration, 脆弱性の型を番号で分類した業界標準）を検査し、危険なパッチを差し戻してエージェントに書き直させる。リンタが構文の門番なら、こちらは**脆弱性の門番**である。レイテンシ設計も参考になり、**60ms の軽い層で入力の約 90% を捌き、疑わしいものだけを 300ms の本格解析へ回す**二層構成でエンドツーエンド 70ms 未満に収めている。エージェントのループに毎回挟むガードレールは、この程度まで安くないと成立しない。ただし**再現率は 79%**（適合率 96%）である。**危険なコードの 5 本に 1 本は通る**ので、単独の関門にはできない。
- **脅威は「攻撃」だけではない**: LlamaFirewall のシナリオ 2 が良い例で、エージェントが高評価の投稿から**文字列連結の SQL**（インジェクション脆弱性の典型）を学んで真似るのは、悪意ある攻撃者が存在しない失敗である。**コーディングエージェントの脅威モデルには、汚染された学習・参照ソースからの「善意の脆弱性伝播」を含める**必要がある。
