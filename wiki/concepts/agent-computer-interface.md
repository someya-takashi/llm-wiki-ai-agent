# Agent-Computer Interface（エージェント–コンピュータインターフェース, ACI）

**エージェントが使うツールを、エージェントの認知に合わせて設計するという考え方と、その設計原則の集まり**を扱うページ。ACI（agent-computer interface）は SWE-agent（[[summaries/2024-swe-agent]], 2024）が名付けた概念で、主張の核は次の 1 文にある——**言語モデルは「独自の必要と能力を持つ新しいカテゴリのエンドユーザー」であり、ソフトウェア向けの API・人間向けの UI に続く第 3 のインターフェースを必要とする**。

エージェントの性能は、モデルの重みが同じでもツールの作りで大きく変わる。SWE-agent は重みを一切変えずにインターフェースだけで SWE-bench の解決率を 3 倍以上にし、Anthropic は同じモデルのツールを Claude 自身に最適化させて社内タスクの正解率を 67.4% から 80.1% へ上げた（[[summaries/2025-writing-effective-tools]]）。**ツールはモデルの外側にある、最も安く動かせる性能のレバーの 1 つ**である。

## なぜ人間向けの道具では足りないのか

人間とエージェントの違いが、設計の指針を分ける。

- **コンテキストは有限で、すべてに課金される**。人間は不要な情報を読み飛ばせるが、エージェントにとっては**すべての出力がメモリと計算の固定コスト**であり、気を散らす文脈は性能を下げる（[[summaries/2024-swe-agent]]）。アドレス帳の例がわかりやすい——全連絡先を返すツールを渡されたエージェントは、1 件ずつトークンとして読むしかなく、ページを最初から順にめくって探す人と同じになる（[[summaries/2025-writing-effective-tools]]）。
- **とりうる行動の見え方（アフォーダンス）が違う**。人間に自然な「`next` で 1 件ずつ送る」検索は、エージェントには全件を網羅しようとする罠になる（下の SWE-agent のアブレーション）。
- **使われ方が確率的である**。従来の関数は決定論的なシステム同士の契約だったが、ツールは**決定論的なシステムと非決定論的なエージェントの間の契約**である（[[summaries/2025-writing-effective-tools]]）。エージェントはツールを呼ばないかもしれないし、誤った引数で呼ぶかもしれない。だから**仕様書どおりに作るだけでなく、実際に使わせて誤用を観察する**工程が要る。

一方で、IDE が人間に与える機能（構文検査・ナビゲーション）は、**形を変えればエージェントにも有用**である。人間に使いやすいツールは、結局エージェントにも直観的であることが多い、とも報告されている（[[summaries/2025-writing-effective-tools]]）。

## 2 つの設計路線 — 作り込むか、最小にするか

ACI の実装には、一見正反対の 2 つの路線がある。

| | SWE-agent（2024） | Claude 3.5 Sonnet の足場（2025） |
|---|---|---|
| ツール | 専用コマンド群（`find_file`・`search_dir`・`open`・`scroll`・`goto`・`edit <n>:<m>` など） | 汎用の 2 つ（bash・`str_replace_editor`） |
| 制御 | 思考と行動を毎ターン交互に生成させる | モデルが完了を宣言するまで自由に任せる |
| 工夫の置き場所 | ツールの種類と出力の形（100 行の窓、検索 50 件上限、リンタによる差し戻し、古い観測の折り畳み） | ツールの説明文と入力形式（環境の制約の明記、絶対パスの強制、一意一致の置換） |
| 前提のモデル | GPT-4 Turbo / Claude 3 Opus（2024 前半） | Claude 3.5 Sonnet new（2024 後半） |

**両者は対立しているようで、同じ軸の両端と読める**。ツールの数と抽象度については逆を選んだが、**フィードバックを簡潔にする・誤りを構造的に防ぐ・説明文で使い方を教える**という細部ではまったく一致している。どちらを選ぶかはモデルの強さで決まる——[[harness-engineering]] の「部品はモデルが単独でできないことについての仮定」であり、**弱いモデルほどツールの作り込みで底上げでき、強いモデルほどツールを汎用・最小にして制御を渡せる**。実際、フロンティアモデルの評価ハーネスは最小構成に収斂している（DeepSeek-V4 は bash＋ファイル編集の 2 ツール、Kimi K2.5 は bash / create_file / insert / view / str_replace / submit。→ [[coding-agents]]）。

## 設計原則（原典横断の整理）

### (1) 何をツールにするか — ワークフロー単位で、少なく

- **API を 1 対 1 で包まない**。頻繁に連鎖する操作を 1 つのツールにまとめる（`list_users`＋`list_events`＋`create_event` → `schedule_event`）。中間出力がコンテキストを消費しなくなり、エージェントの計算がツール側へ移る（[[summaries/2025-writing-effective-tools]]）。SWE-agent の原則「重要な操作は可能な限り少ない行動へ統合する（高次の操作を複数ターンの合成に分解させない）」と同じである。
- **少数の、目的の重ならないツール**。最頻の失敗はツール集合の肥大化で、判定基準は「**人間のエンジニアがどのツールを使うべきか断言できないなら、エージェントにもできない**」（[[summaries/2025-effective-context-engineering]]）。Manus は「重武装したエージェントはより愚かになる」と表現した（[[summaries/2025-manus-context-engineering]]）。
- **列挙でなく検索**。`list_contacts` でなく `search_contacts`、`read_logs` でなく関連行と周辺だけを返す `search_logs`。

### (2) 名前と引数 — 曖昧さを残さない

- **名前空間**：`asana_search` / `jira_search` のように共通のプレフィックスでまとめる。ただし**プレフィックス方式かサフィックス方式かで結果が変わり、効き方はモデルによって違う**ので評価で決める（[[summaries/2025-writing-effective-tools]]）。Manus では、一貫したプレフィックス（`browser_`・`shell_`）がロジットマスクでツール群をまとめて制御する単位にもなっている。
- **引数名**：`user` でなく `user_id`。入出力は厳格なデータモデルで強制する。

### (3) 応答 — 信号を強く、量を少なく

- **下流の判断に効くフィールドを返す**。`uuid`・`mime_type` より `name`・`file_type`。**UUID を自然言語や 0 始まりの ID に置き換えるだけで幻覚が減り、検索精度が大きく上がる**（[[summaries/2025-writing-effective-tools]]）。
- **詳しさをエージェントに選ばせる**：`response_format` 引数（`concise` / `detailed`）。Slack 検索の例では 206 トークンが 72 トークン（約 ⅓）になる。ID が要るときだけ詳細版を使う。
- **量の上限を既定値で持つ**：ページネーション・範囲指定・フィルタ・切り詰め。Claude Code はツール応答を既定で 25,000 トークンに制限する。SWE-agent はファイルビューアを 100 行の窓に、検索結果を最大 50 件にした。**窓には両側に最適点がある**（30 行でも全文でも下がる）。
- **書式も評価で選ぶ**：XML・JSON・Markdown のどれが良いかはタスクとモデルしだい。[[summaries/2024-building-effective-agents]] は、モデルが自然に見てきたテキストに近い書式を選び、diff の行数勘定や JSON 内のエスケープのような**書式オーバーヘッドを避けよ**と述べる。

### (4) 失敗の扱い — 構造で防ぎ、次の一手を返す

- **誤りにくい入力形式にする（error-proofing / Poka-yoke）**。絶対パスの強制、`old_str` がちょうど 1 か所に一致したときだけ置換する（[[summaries/2025-swe-bench-sonnet]]）。注意喚起でなく構造で防ぐ。
- **検証を通らない操作は適用せず差し戻す**。SWE-agent は編集後にリンタを走らせ、構文エラーなら編集を取り消して「エラー・編集後にどう見えたはずか・編集前の内容」の 3 点を返す。3 点すべてが要る——元の内容がないと、エージェントは**より新しいという理由だけで誤ったファイル内容に対して編集を生成する**。
- **エラーと切り詰めは「次に何をすべきか」を書く場所**。不透明なエラーコードでなく、何が誤りか・正しい形式の例・解決の手段（「`user_search()` を呼べ」）を返す。切り詰めたら絞り込み方や次ページの呼び方を添える。SWE-agent の「50 件を超えたら結果を出さず、より具体的なクエリを促す」も同じ型である。
- **操作のあとに結果を見せる**。SWE-agent は編集後に更新後のファイルを自動表示し、確認のための追加ターンをなくした。

### (5) 説明文 — プロンプトとして書き、誤用から直す

- **スキーマより説明文が効く**。Claude 3.5 Sonnet の Bash ツールはスキーマが `command` 1 つだけで、説明文に環境の制約（ネットなし・状態の持続・大量出力を避ける・長時間コマンドはバックグラウンドで）を書き込んだ（[[summaries/2025-swe-bench-sonnet]]）。
- **新しく入った同僚に説明するつもりで書く**。専用のクエリ形式・用語・リソース間の関係といった暗黙の前提を明示する（[[summaries/2025-writing-effective-tools]]）。
- **誤用を観察して直す**。Web 検索ツールで Claude が `query` に不必要に「2025」を付けていた問題は、説明文の改善で直った。

## 編集インターフェースの比較 — コーディングエージェントで最も研究された ACI

ファイルをどう書き換えさせるかは、ACI の設計判断のうち最も多くの比較がある。

| 方式 | 原典での扱い | 長所 | 短所 |
|---|---|---|---|
| **ファイル全体の書き直し** | SWE-bench 原論文：パッチ形式 4.8% に対し全体書き直し 2.2%（入力長を揃えても 7.8% 対 3.9%） | 単純 | 長く、無関係な部分まで壊しやすい |
| **diff / パッチ** | Building Effective Agents：diff はヘッダの行数を先に数える必要があり、書式オーバーヘッドが大きい | 変更が小さい | 行数勘定と書式の誤りが多い |
| **行範囲の置換（`edit <n>:<m>`）** | SWE-agent：リンタの差し戻しと組み合わせて 18.0%（編集コマンドなしは 10.3%） | 1 ステップで複数行を置換 | 行番号の算術が要る。直前の編集で行がずれる |
| **一意一致の文字列置換（`str_replace`）** | Claude 3.5 Sonnet の足場：試した方式のうち最も信頼性が高かった | 行番号が要らない。曖昧な一致は実行前に弾ける | `old_str` の空白まで正確に書く必要がある |

その後、一意一致の文字列置換はコーディングエージェントの事実上の標準になった（Claude Code の Edit、Kimi K2.5 の評価ハーネスの `str_replace` など）。ただし**どの方式でも編集は失敗し、失敗は連鎖する**——SWE-agent では 1 回の編集失敗のあと最終的に成功する確率が 90.5% から 57.2% に落ちた（→ [[coding-agents]]）。インターフェースの選択は失敗をなくすのでなく、失敗の起きにくさと回復のしやすさを決める。

## 根拠 — SWE-agent のアブレーション

ACI が単なる言い換えでないことを示す、この領域で最も引用に値する数字である（SWE-bench Lite・GPT-4 Turbo・既定 18.0%）。

| 軸 | 既定 | 代替 | 落差 |
| --- | --- | --- | --- |
| Editor | `edit` ＋ linting **18.0** | linting なし 15.0 / `edit` なし **10.3** | **−7.7** |
| Search | Summarized **18.0** | **Iterative 12.0** / 検索なし 15.7 | −6.0 |
| File Viewer | 100 行 **18.0** | 30 行 14.3 / ファイル全体 12.7 | −5.3 |
| Context | 直近 5 観測 **18.0** | 全履歴 15.0 / 実演なし 16.3 | −3.0 |

**最も重要なのは Search の行で、人間の検索 UI を模した Iterative search（12.0）は検索ツールを一切与えない場合（15.7）より悪い**。Vim や VSCode のように結果を `next` / `prev` で 1 件ずつ送る設計だと、エージェントは全一致を網羅しようと `next` を呼び続け、予算とコンテキストを使い果たす。**人間にとって良い UI がエージェントには積極的に有害でありうる**ことの、最も直接的な証拠である。

## 評価駆動でツールを改善する

[[summaries/2025-writing-effective-tools]] がまとめた手順は、ツールを「書いて終わり」でなく、評価で測って直す対象として扱う。

1. **プロトタイプを作り、自分で使ってみる**（ローカルの MCP サーバーとして接続するなど）。
2. **現実の用途から多段の評価タスクを作る**。強いタスクは数十回のツール呼び出しを要し、弱いタスクは 1 回で済んで引数まで指示に書いてある。検証器は厳しすぎないようにし、期待するツール経路は指定しすぎない。
3. **単純なエージェントループで回し、正解率以外も集める**（実行時間・呼び出し回数・トークン・エラー）。ツール呼び出しの前に推論を書かせると、なぜそのツールを選んだかを後で読める。
4. **生のトランスクリプトを読む**。エージェントが書かなかったことのほうが重要なことが多い。
5. **エージェントに改修させ、held-out テストで確かめる**。Slack 用ツールは 67.4% → 80.1%、Asana 用は 79.6% → 85.7%。

この手順は、[[summaries/2025-multi-agent-research-system]] のツールテスト用エージェント（説明文の書き直しでタスク完了時間 −40%）を一般化したものであり、ハーネス全体に広げると [[harness-engineering]] の Meta-Harness・AHE になる。共通する教訓は、**要約でなく生のトレースを読ませること**と、**改善に使わなかったテスト集合で最終判断すること**である（→ [[agent-evaluation]]）。

## 設計論点

- **原則はモデル依存である**。名前空間の方式・応答の書式・ツールの作り込みの度合いは、モデルによって最適が違う。「Claude が Claude のために最適化した」ツールが別のモデルでも最適とは限らない。原則は出発点で、最終判断は使うモデルでの評価に置く。
- **MCP 時代には説明文の品質を自分で統制できない**。外部の MCP サーバーから品質のばらつく説明文のツールが入ってくる（→ [[model-context-protocol]]、[[tool-use-and-function-calling]]）。対策は、選択の指針をプロンプトに書くこと、ツールテスト用エージェントで説明文を書き直すこと、そして使わないツールは定義を消さずにマスクすること（KV cache を壊さないため。→ [[summaries/2025-manus-context-engineering]]）。
- **ツールからスキルへ**。ツールが「何ができるか」を公開するのに対し、スキルは「どう遂行すべきか」を包装する（→ [[agent-skills]]）。手順をツールの説明文に詰め込むか、スキルとして分けるかは、コンテキストへのロード量の設計でもある。
- **安全性はツールの形で決まる部分が大きい**。危険な行動を行動空間に入れない、権限を最小にする、MCP のツールアノテーションで「外部へアクセスする」「破壊的な変更をする」ツールを開示する（→ [[agent-safety-and-guardrails]]）。Claude Code では、モデルの外界への唯一のインターフェースが `tool_use` であり、ハーネスが実行前に検証する（[[summaries/2026-dive-into-claude-code]]）。
- **効果量の証拠は偏っている**。構成要素ごとの効果を測ったのは SWE-agent（2024 年のモデル）と AHE だけで、2025 年の Anthropic の 2 記事は全体の効果か定性的な報告にとどまる。原則ごとの効果を今のモデルで測った公開データはまだない。
