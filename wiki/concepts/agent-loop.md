# Agent Loop（エージェントループ）

LLM（Large Language Model, 大規模言語モデル）エージェントの実行の骨格となる、**観測（observation）→ 思考（thought）→ 行動（action）を繰り返すループ**。1 回のプロンプトで答えを返す通常の LLM 利用と違い、エージェントは行動の結果を環境から受け取り、それを踏まえて次の一手を決める。この「結果を見てから考え直せる」性質が、幻覚（hallucination）の抑制と多段タスクの遂行を可能にする。

## 定式化

[[summaries/2022-react]]（ReAct, 2022）による定式化が現在も標準的である。時刻 $t$ でエージェントは環境から観測 $o_t$ を受け取り、方策 $\pi(a_t|c_t)$ に従って行動 $a_t$ を選ぶ。ここで $c_t = (o_1, a_1, \cdots, o_{t-1}, a_{t-1}, o_t)$ は**それまでの履歴すべて＝コンテキスト**であり、LLM エージェントでは文字通りコンテキストウィンドウ（モデルが一度に読める最大トークン数）に積まれたテキストがこれにあたる。

ReAct の核心は、行動空間を $\hat{\mathcal{A}} = \mathcal{A} \cup \mathcal{L}$（$\mathcal{L}$ は言語空間）に拡張したことである。言語空間に属する「行動」= **thought** は環境に作用せず観測も返さないが、コンテキストに追記されて以後の判断を支える。thought はいわば**書き出されたワーキングメモリ**（scratchpad）であり、これが [[agent-memory]] の最も原始的な形になっている。エージェントが辿った観測・思考・行動の列は trajectory（軌跡）と呼ばれ、デバッグ・評価・ファインチューニングの基本単位となる。

## 設計変数

### thought の密度: dense vs sparse

- **dense thought**: 毎ステップ思考を挟む。1 手ごとの判断が重い知識集約タスク（マルチホップ QA 等）向き。
- **sparse thought**: 要所でだけ思考し、挟むタイミングはモデル自身に決めさせる。行動数が多い意思決定タスク（ALFWorld のような 50 ステップ級の環境）向き。

ReAct はこの両モードを示し、sparse thought だけでも「目標の分解／部分目標の完了追跡／次の部分目標の決定／常識による所在推論」が働けば成功率が激変することを実証した（ALFWorld で思考なし 45% → あり 71%）。

### 何がループを起動し、いつ制御を返すか — イベント駆動と heartbeat

ReAct 型のループは「ユーザーの課題を受けて回り、答えたら止まる」1 本道だが、[[summaries/2023-memgpt]]（MemGPT, 2023）はこの起動と停止を一般化した。推論のトリガーを**イベント**として抽象化し（ユーザーメッセージだけでなく、コンテキスト容量警告のようなシステムメッセージ、ログイン等の通知、定時イベントも含む）、エージェントが「促されずに」動けるようにした。逆方向の制御——**続けるか、制御を返すか**——は、function call に付ける `request_heartbeat=true` フラグでモデル自身が宣言する: フラグ付きなら関数実行の直後に次の推論が走り（多段の検索・照合が可能になる）、フラグなし（yield）なら次の外部イベントまで停止する。「ループを回し続ける判断」自体をモデルの出力にした設計であり、現在のエージェントフレームワークの「ツール呼び出しが続く限りループする」実装の明示的な原型といえる。

### 停止条件

ループには打ち切りが要る。ReAct では `finish[answer]` という明示的な終了行動と、タスクごとのステップ上限（HotpotQA 7 / FEVER 5。それ以上は性能が伸びないため）を併用し、上限に達したら別手法（CoT-SC）へフォールバックした。**「解けないと判断したら戦略を切り替える」**という設計は現在のエージェントでも重要である。実務指針（[[summaries/2024-building-effective-agents]]）も、完了による終了に加えて最大反復回数などの停止条件を持たせること、チェックポイントや障害時に人間のフィードバックへ戻れることを標準形とし、各ステップで環境から ground truth（ツール実行結果等）を得て進捗を評価することを「決定的に重要」と位置づけている。

## 本番のループを解剖する — Claude Code の `queryLoop()`

上の節が ReAct 由来の**最小構成**を扱ってきたのに対し、[[summaries/2026-dive-into-claude-code]]（2026）は**出荷されている本番系のループを公開ソース（Claude Code v2.1.88）から解剖**している。**骨格は驚くほど素朴である**——「モデルを呼び、ツールを実行し、繰り返す」だけの while ループで、著者らの推定では**コードベースのうち意思決定ロジックは 1.6%、残り 98.4% はその周囲の運用ハーネス**（この比率は Tier C = 再構成された推定である）。

**すべての入口（対話 CLI・headless CLI・Agent SDK・IDE）が単一の `queryLoop()` 関数に収束し、変わるのはレンダリング層だけ**という設計も特筆に値する。モード固有のエンジンを持つ系（IDE と CLI で別コードパス）とは対照的で、統一性を表面固有の最適化と引き換えにしている。

### 1 ターンの構造

```
1. 設定の解決（不変パラメータの分解）
2. 可変状態の初期化（単一の State オブジェクト）
3. コンテキストの組み立て（最後の compact 境界以降）
4. モデル呼び出し前の 5 つの context shaper  → [[context-engineering]]
5. モデル呼び出し（ストリーミング）
6. tool_use の振り分け
7. 権限ゲート                                  → [[agent-safety-and-guardrails]]
8. ツール実行と結果収集
9. 停止条件（tool_use が無ければターン完了）
```

**実装の細部で真似る価値があるものが 2 つある。**

- **単一の `State` オブジェクトを「1 回の全体代入」で上書きする。** ループには **7 つの `continue` 地点**があり、そのすべてでフィールドを個別に変更するのではなく**状態オブジェクトごと置き換える**。多数の分岐から可変状態を触る系で、**部分更新の取りこぼしを構造的に防ぐ**書き方である。
- **ループを `AsyncGenerator` にする。** `StreamEvent`・`Message` 等を yield しながら進む。**ループ内部は単一の同期的な制御フローを保ったまま、UI 層へストリーミングできる。**

### ツールの振り分け — concurrent-read / serial-write

ツール実行の並列化には**中間の設計点**がある。Claude Code は**読み取り専用の操作を並列に、状態を変更する操作（シェルコマンド等）を直列に**実行する。加えて 2 つの調整機構を持つ。

- **兄弟の abort コントローラ**——いずれかの Bash ツールがエラーを起こしたら、**他の実行中のサブプロセスを最後まで走らせず即座に終了させる**。
- **結果は受け取った順序でバッファして発する**。並列に走っても出力順は保たれる——**モデルは tool-use 要求と同じ順序で結果を期待する**ため。

論文はこれを、完全に直列な振り分けと、モデルが生成している間に予測されたツール呼び出しを先行実行する投機的アプローチ（PASTE）との**中間**に位置づけている。

### 停止条件と回復 — 「静かに回復するが、回数は数える」

**停止条件は 5 つ**: (1) tool_use なし（**主要な停止条件**）、(2) `maxTurns` 到達、(3) `prompt_too_long`、(4) PostToolUse フックが `hook_stopped_continuation` を設定、(5) `abortController` の発火。

**回復機構も 5 つ**あり、**そのうち 2 つに明示的な回数制限が埋め込まれている**のが設計として重要である。

| 回復機構 | 制限 |
|---|---|
| 最大出力トークンのエスカレーション | **1 ターン 3 回まで**（`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`） |
| 反応的 compaction | **1 ターン 1 回まで**（`hasAttemptedReactiveCompact` フラグ） |
| `prompt_too_long` の扱い | context-collapse のオーバーフロー回復 → reactive compaction → **それでも駄目なら終了** |
| ストリーミングのフォールバック | 別戦略で再試行 |
| フォールバックモデル | 主要モデルが失敗したら別モデルへ |

**Table 1 の原則で言う *graceful recovery and resilience*（「エラーで強く失敗するか、静かに回復して人間の注意を回復不能な状況のために取っておくか」）の実装**である。上の「反復ループ」の失敗モードへの構造的な対策としても読める——**無制限のリトライは静かな無限ループになる**ので、回復は自動化しつつカウンタを持つ。

### ループの中の 3 つの注入点

論文が抽出した一般化が、自作のエージェントにそのまま使える。

> **あらゆるエージェントループは 3 つの注入点を持つ。`assemble()` はモデルが*何を見るか*を、`model()` は*何に手を伸ばせるか*を、`execute()` は行動が*実行されるか／どう実行されるか*を制御する。**

Claude Code の 4 つの拡張機構（フック・スキル・プラグイン・MCP）はこの 3 点に配置されており、**それぞれのコンテキストコストが挿入点と対応している**（→ [[agent-frameworks]]）。ループを設計するときの**拡張点のチェックリスト**として使える。

## 典型的な失敗モード

[[summaries/2022-react]] の失敗分析から、ループ構造に固有の失敗が整理できる。

- **反復ループ**: 直前と同じ思考・行動を繰り返して抜け出せなくなる（ReAct の reasoning error の主要因）。貪欲デコードが一因とされ、現在も loop detection として対策される。マルチエージェントでも消えない——[[summaries/2025-masft]] の実測では「ステップの反復」（FM-1.3, 11.5%）と「会話履歴の喪失」（FM-1.4）が MAS の主要失敗モードとして残った。
- **状態の見失い**: 思考を持たない行動のみのループ（Act）は、「自分はいまナイフを持っている」「まだ流しに行っていない」といった状態を追跡できず、無効な行動を繰り返す。thought はこれを防ぐ最小の仕掛けである。
- **観測の質への依存**: 検索が有益な情報を返さないとその後の推論全体が脱線する（ReAct のエラーの 23%）。ループは自己修復もするが、悪い観測に引きずられもする。

## 位置づけと発展

ReAct のループは「LLM 呼び出し 1 回 = 1 ステップ」の最小構成であり、後のエージェントはこの骨格の上に、ツールの構造化（[[tool-use-and-function-calling]]）、長期記憶（[[agent-memory]]）、コンテキストへの情報の積み方の最適化（[[context-engineering]]）、失敗の振り返り（[[self-reflection]]）、複数エージェントへの分業（[[multi-agent-systems]]）を積み増していった。ループの入れ子構造も生まれた——[[summaries/2023-reflexion]] は、episode 内の観測→思考→行動ループの**外側に「試行（episode）をまたぐ改善ループ」**を重ね、失敗した軌跡の反省文を次の試行のコンテキストに注入することで、重み更新なしの試行間学習を実現した。さらに、ループの各ターンで「**どのモデルがそのステップを担当するか**」自体を学習対象にする段階にも到達している——[[summaries/2026-sakana-fugu]] の Fugu は、ハーネスの相互作用状態からターンごとに担当ワーカーを選び直すオーケストレータで、「GPT が構築し、決定的なデバッグ地点で Opus に交代する」といった役割交代を学習で獲得した。人間がループの途中に介入する点（HITL, Human-in-the-Loop）としては、ReAct が示した「thought を編集して軌道修正する」方式が先駆けである。

**ループを「どこで動かすか」への分解**も、長時間運用が現実になるにつれて設計対象になった。Managed Agents（[[summaries/2026-managed-agents]], Anthropic, 2026）は、ループの構成要素を **session**（起きたことすべての append-only なイベントログ）・**harness**（Claude を呼びツール呼び出しを配線するループ本体）・**sandbox**（行動が実際に実行される環境）の 3 つに切り分け、それぞれを差し替え可能なインターフェースにした。含意は素直で、**ループの状態をループの外に置けば、ループ自体は落ちてよいものになる**——session が外にあるので、ハーネスが死んでも `wake(sessionId)` で新しいものを起こし、`getSession(id)` でイベントログを取り戻して最後のイベントから再開できる。ReAct 以来「1 プロセスの中で回るもの」と暗黙に想定されてきたループが、**永続化された状態＋使い捨ての実行体**へと分解された形である → [[agent-frameworks]] のランタイム分離。
