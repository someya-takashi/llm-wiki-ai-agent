# Context Engineering（コンテキストエンジニアリング）

LLM（Large Language Model, 大規模言語モデル）の**限られたコンテキストウィンドウに、いま何をどの形で積むか**を設計する営みの総称。プロンプトエンジニアリングが「指示文の書き方」に焦点を当てるのに対し、context engineering はより広く、**システム指示・ツール定義・検索結果・会話履歴・作業メモ（scratchpad）・few-shot 例示といった構成要素の全体を、トークン予算の中でどう配分し、いつ入れ替えるか**を扱う。エージェントは多ターンにわたって動くため、この配分は一度きりでなく**毎推論ごとの継続的な管理問題**になる。

この営みを名づけ、定式化したのが [[summaries/2025-effective-context-engineering]]（Anthropic, 2025）である。同記事は context engineering を「**LLM の推論中に最適なトークン（情報）の集合を精選し維持する戦略**、プロンプト以外の経路でそこに入るあらゆる情報を含む」と定義し、プロンプトエンジニアリングの自然な発展形と位置づけた。違いは対象範囲だけでなく**時間の構造**にもある——プロンプトを書くのが離散的なタスクなのに対し、**モデルに何を渡すか決めるたびに「精選（curation）」の局面が発生する**ので、コンテキストエンジニアリングは本質的に反復的である。ループの中のエージェントは次のターンで関連しうるデータを自分で生成し続けるので、精選の対象は絶えず膨らむ。

同記事はこの営み全体を貫く指導原理を 1 行で置いている。本ページの各節はその各論として読める:

> **望ましい結果の尤度を最大化する、可能な限り最小の高信号（high-signal）なトークンの集合を見つけること。**

[[agent-memory]] との棲み分け: memory は「**何を保存し、どう取り出すか**」（永続化の側）、context engineering は「**取り出したものを含め、いまウィンドウに何を載せるか**」（積載の側）。両者は表裏で、MemGPT のような階層記憶は「積載の判断を自動化する仕組み」と読める。この営みをコードとして実装したものが **harness（ハーネス）**である——Meta-Harness 論文（[[summaries/2026-meta-harness]], 2026）はハーネスを「**何を保存し、取り出し、モデルに提示するかを決めるコード**」と定義しており、これは本ページの主題のプログラム的実体に他ならない。同論文は固定モデルの周囲のハーネス差だけでベンチマーク性能が最大 6 倍変わることを引きつつ、この積載設計そのものを探索対象にした（後述の設計論点を参照）。

## 基本制約 — なぜ「全部入れる」では駄目か

まとめの枠組みとして有用なのが **注意予算（attention budget）** という言い方である（[[summaries/2025-effective-context-engineering]]）——限られたワーキングメモリしか持たない人間と同じく、LLM も大量のコンテキストを解釈するときに引き出す有限の予算を持ち、**新しいトークンはそれを消費する**。ゆえにコンテキストは容量ではなく「**限界効用が逓減する有限資源**」として扱うのが正しい。以下の 3 つはこの予算がどう目減りするかの各論である。

1. **有限性**: どれだけ延びてもウィンドウは有限で、あふれれば切り詰められる。切り詰めで**計画や初期の指示を失うのが典型的な最悪ケース**（[[summaries/2025-multi-agent-research-system]] は 200k での切り詰めに備えて計画を最初に外部メモリへ保存する）。この有限性には物理的な実体がある——ウィンドウ内の全トークンは KV cache として GPU メモリを占有し、系列長 O(N) で成長してメモリ帯域を律速する（[[summaries/2026-gpt2-to-kimi3]] → [[llm-inference-optimization]]）。固定状態アーキテクチャ（linear attention 系ハイブリッド）の台頭はこのコスト構造を変えつつあるが、「入れたものが等しく保持される保証はない」という制約はむしろ強まる方向にある。
**最も直接的な実測が [[summaries/2023-swe-bench]]（2023）にある。**同論文は BM25 検索の最大文脈を 13k → 27k → 50k と広げたときの、**オラクルのファイルに対する recall** と **タスクの解決率**を並べて測った。

| 最大文脈 | BM25 recall（平均） | Claude 2 の解決率 |
| --- | --- | --- |
| 13k | 29.58 | **1.96** |
| 27k | 44.41 | 1.87 |
| 50k | 51.06 | 1.22 |

**recall は素直に上がるのに、解決率は下がる。**著者らの説明は端的で、モデルは「**トークンの海の中で問題のあるコードを位置特定すること**」に無効なので、正しいファイルが入る確率の上昇より**気を散らすコードが増える害のほうが勝つ**。裏返しの実験がさらに効く——オラクル設定で、**実際に編集された行の ±15 行以外を畳む**だけで **Claude 2 は 4.8 → 5.9、GPT-4 は 1.3 → 3.4 へ上がる**。**同じ情報を含んだまま、無関係な部分を削るだけで性能が上がる。**注意予算という枠組みが「たとえ話」ではないことの、2023 年時点での数量的な裏づけになっている。

同じ現象を別の断面から見たのが [[summaries/2024-swe-agent]] の**ファイルビューアの窓サイズ**（30 行 14.3 / 100 行 18.0 / ファイル全体 12.7 と**両側に最適点がある**）と、**人間の UI を模した検索インターフェースが検索ツールなしより悪い**という結果である。**「取れる情報を全部渡す」は設計ではなく怠慢**、というのが 3 つの実測に共通する含意になる。

2. **想起の劣化（lost in the middle / context rot）**: 長いコンテキストでは、モデルは先頭と末尾の情報の想起は得意だが**中間が苦手**になる（**一次資料は [[summaries/2023-lost-in-the-middle]]**, Liu ら, TACL 2024。[[summaries/2023-memgpt]] が設計動機として引く知見。専用原典は未 ingest）。より一般的な形が **context rot（コンテキストの腐敗）**——**トークン数が増えるほど、そこから正確に想起する能力が低下する**現象で、劣化の緩急はモデルによるが**すべてのモデルに現れる**（needle-in-a-haystack 型ベンチマークの研究。[[summaries/2025-effective-context-engineering]] が Chroma の研究として引く）。「入れた＝読める」ではない。

   同記事はこれをアーキテクチャから説明しており、丸暗記でなく理由から使える形になっている。(a) transformer は全トークンが全トークンに注意を向けられるので、$n$ トークンで **$n^2$ の対関係**が生じる——長くなるほどこれを捉える能力が薄く引き伸ばされ、**コンテキストのサイズと注意の集中の間に自然な緊張**が生まれる。(b) モデルは訓練データの分布から注意パターンを獲得するが、そこでは**短い系列のほうが一般的**なので、コンテキスト全体にわたる依存関係については経験が乏しく専用パラメータも少ない。(c) 位置符号化の内挿（arXiv:2306.15595）は長い系列を扱えるようにするが、**トークン位置の理解に劣化を伴う**。帰結の言い方が実務的に重要で、これらが生むのは**「明確な崖ではなく性能の勾配」**である——長窓でもモデルは高機能だが、情報検索と長距離推論の精度が相対的に落ちる。「窓に入るかどうか」の二値でなく、**入れるほど少しずつ薄まる**という前提で設計する。さらに一部のモデルは **context anxiety**——自分の文脈限界が近いと感じると仕事を早々に畳み始める挙動——を示す（[[summaries/2026-harness-design]] の観察。Sonnet 4.5 で顕著、Opus 4.5/4.6 でほぼ消滅）。これは compaction（履歴のその場要約）では治らない: 連続性は保つが**まっさらな状態を与えない**ため不安が持ち越される。対策は **context reset**（文脈の完全クリア＋構造化引き継ぎで新エージェントを起動）だが、引き継ぎ artifact の設計コストとオーケストレーションの複雑さを伴う——そしてモデル世代が変わればこの部品ごと不要になりうる（実際に 4.6 で外された）。「文脈の使い方」がモデルの心理的（挙動的）特性にまで依存するという、コンテキスト設計の新しい変数の記録である。
3. **コスト**: コンテキストはトークン課金と遅延に直結する。長い履歴の持ち回りはそれ自体が浪費で、[[summaries/2025-multi-agent-research-system]] は大きな成果物を履歴にコピーして回すことを「伝言ゲーム」のトークンオーバーヘッドとして名指しした。コスト構造の実務データは Manus（[[summaries/2025-manus-context-engineering]]）が具体的で、エージェントの入力:出力トークン比は平均 **100:1**（毎ステップ伸びる履歴 vs 短い関数呼び出し）、KV cache のヒット有無で入力単価は **10 倍**違う（Claude Sonnet で $0.30 vs $3/MTok）。ゆえに同記事は **KV cache ヒット率を本番エージェントの最重要指標**と位置づけ、プレフィックスの安定（冒頭のタイムスタンプ禁止）・**追記専用**のコンテキスト・決定的なシリアライズ（JSON キー順の非決定はキャッシュを静かに壊す）を第一の設計規律とした——「何を積むか」だけでなく「**積んだものを動かさない**」こともコンテキスト設計の一部である → [[llm-inference-optimization]]。

## この制約の系譜 — 2023 から 2025 への追試

本ページの基本制約 2（想起の劣化）は、**同じ現象が領域を変えて何度も再発見されてきた**ことに支えられている。散らばりがちなので、ここに一本の系譜としてまとめる。

| 年 | 原典 | 領域 | 測ったこと |
| --- | --- | --- | --- |
| 2023 | [[summaries/2023-lost-in-the-middle]] | 一般 QA・合成検索 | **位置だけを変える**と U 字カーブ。GPT-3.5-Turbo は中間に置くと **closed-book（56.1%）を下回る**。拡張コンテキスト版は元版と**ほぼ同じ曲線** |
| 2023 | [[summaries/2023-swe-bench]] | コード（実 GitHub イシュー） | BM25 の文脈を 13k→50k に広げると **recall は 29.58→51.06 と上がるのに解決率は 1.96→1.22 と下がる**。編集行の ±15 行以外を畳むと **4.8→5.9 へ上がる** |
| 2024 | [[summaries/2024-graphrag]] | 長文要約（センスメイキング） | 8k / 16k / 32k / 64k を比較し、**最小の 8k が網羅性で一様に優れた**（平均勝率 58.1%）。gpt-4-turbo は 128k を扱えるにもかかわらず |
| 2024 | [[summaries/2024-swe-agent]] | コード（インターフェース設計） | ファイルビューアの窓サイズに**両側の最適点**（30 行 14.3 / 100 行 18.0 / 全体 12.7）。人間の UI を模した検索は**検索ツールなしより悪い** |
| 2025 | [[summaries/2025-effective-context-engineering]] | 定式化 | **context rot** として命名。機構として $n^2$ のペア関係・訓練分布の偏り・位置内挿を挙げる |

**この並びから読み取れることが 3 つある。**

**第一に、古びたのは数字であって命題ではない。**一次資料のモデルは 2023 年世代（GPT-3.5-Turbo・Claude-1.3・MPT-30B）で、needle-in-a-haystack 型の単純な想起はその後大きく改善した。しかし**「量と位置がタスク性能を動かす」という命題は、2024 年・2025 年の別々の領域で繰り返し確認されている。**「最近のモデルは長文脈に強いから関係ない」は、少なくとも 2025 年時点では成り立っていない。

**第二に、「検索が良くなる」と「成果が良くなる」は別である。**[[summaries/2023-lost-in-the-middle]] は retriever-reader 構成で **reader が retriever の recall より遥か手前で飽和する**ことを示し（20→50 文書で GPT-3.5 は約 1.5%、Claude は約 1% しか伸びない）、SWE-bench はコード領域で **recall と成果が逆向きに動く**ところまで測った。→ [[retrieval-augmented-generation]]

**第三に、対処は「減らす」と「並べ替える」の 2 つに集約される。**畳む（SWE-bench の ±15 行、SWE-agent の観測の折り畳み）・切り詰める（ranked list truncation）・先頭寄りに寄せる（再ランキング）・末尾に置き直す（[[summaries/2025-manus-context-engineering]] の todo.md）。**いずれも「情報を足す」の逆方向**である。

一次資料の**原因調査**も押さえておく価値がある。[[summaries/2023-lost-in-the-middle]] は 4 つの容疑者を順に消していく——**decoder-only だから**ではない（encoder-decoder も**訓練長を超えると** U 字になる）、**クエリが後ろにあるから**だけでもない（クエリを前後に置くと合成検索はほぼ完璧化するが**推論を伴う QA は変わらない**）、**instruction tuning のせい**でもない（素のベースモデルも U 字）、そして **7B は recency のみで 13B・70B から U 字が出る**（primacy 側は規模とともに現れる）。**機構的な説明は与えられておらず、著者ら自身が「予備的」と呼んでいる**——この現象は 2025 年時点でも原理が解けていない。

## 代表的な設計パターン

### 各構成要素の絞り方 — システムプロンプトの「高度」とツールの数

積み方の前に、そもそも何をどれだけ具体的に書くかがある。[[summaries/2025-effective-context-engineering]] は構成要素ごとに絞り方の基準を与えている。

**システムプロンプトは「適切な高度（right altitude）」を狙う**——2 つの失敗モードの間のゴルディロックス・ゾーンである。一方の極端は、厳密な挙動を引き出そうとして**複雑で脆い if-else をハードコード**すること（脆弱で保守が重くなる）。もう一方は**漠然とした高水準の指針**だけを与え、具体的な信号を欠いたまま共有文脈があると誤って想定すること。狙うのは「挙動を導けるだけ具体的、かつ強いヒューリスティクスを与えられるだけ柔軟」な水準。同記事の図は、カスタマーサポートのプロンプトを 3 段階（意図を 5 分類して分岐を延々書き下したもの／役割・利用可能なツール・4 段の応答フレームワーク・判断指針を簡潔に述べたもの／「ブランドの原則と本質に沿って解決せよ」だけのもの）で並べて見せており、翻訳側にプロンプト全文を転記してある。

補助的な 2 点も実務で効く。**「最小」は「短い」ではない**——期待する挙動を完全に描き出す最小の情報集合という意味であって、必要な情報は最初に与える。そして**節への区切り**（`<background_information>` / `<instructions>` / `## Tool guidance` 等の XML タグや Markdown 見出し）は推奨されるが、**モデルが高機能になるにつれ書式の重要性は低下しつつある**とも明記されている。進め方の既定は「最良のモデルで最小プロンプトから始め、初期テストで見つかった失敗モードに応じて指示と例を足す」。

**ツールは実行可能な最小集合に絞る**。最頻の失敗モードはツール集合の肥大化で、機能が重なると「どれを使うか」の判断点が曖昧になる。判定基準が覚えやすい——**人間のエンジニアがどのツールを使うべきか断言できないなら、エージェントにそれ以上を期待することはできない** → [[tool-use-and-function-calling]]。

### just-in-time 取得と段階的開示 — 事前に集めず、実行時に引く

後述の「参照渡し」を取得戦略の側から一般化したのが、[[summaries/2025-effective-context-engineering]] の **just-in-time（ジャストインタイム）** である。多くのアプリは**埋め込みベースの推論前検索**で重要なコンテキストを先に集めるが、エージェント的アプローチではこれを補強する形で、**軽量な識別子（ファイルパス・保存済みクエリ・Web リンク）だけを保持し、実行時にツールで動的に読み込む**方式が増えている。Claude Code は大規模データベースの分析で、的を絞ったクエリを書き結果を保存し `head` / `tail` で切り出すことで、**データ全体をコンテキストに載せずに**分析する。人間もコーパスを暗記せず、ファイルシステム・受信箱・ブックマークという外部の索引を作って必要時に引く——という比喩がそのまま設計指針になっている → [[retrieval-augmented-generation]]。

副次的な効果が 2 つある。第一に、**参照のメタデータそのものが挙動の信号になる**: `tests` フォルダの `test_utils.py` と `src/core_logic/` の同名ファイルは目的が違い、階層・命名規約・タイムスタンプがすべて「いつどう使うべきか」の手がかりを与える。第二が **progressive disclosure（段階的開示）**——エージェントが探索を通じて関連コンテキストを漸進的に発見し、**理解を層ごとに組み立てながらワーキングメモリには必要なものだけを保つ**。ファイルサイズは複雑さを、命名は目的を、タイムスタンプは関連性を示唆する。

トレードオフも明記されている。**実行時の探索は事前計算された取得より遅い**。さらに適切なツールとヒューリスティクスがなければ、エージェントはツールを誤用し行き止まりを追ってコンテキストを浪費する。現実解は**ハイブリッド**で、Claude Code がその実例——`CLAUDE.md` は素朴に事前投入し、`glob` / `grep` で残りを JIT に取得することで**陳腐化した索引や複雑な構文木の問題を回避**する。内容の動的さが低い領域（法務・財務）ほどハイブリッド寄りが適するとされる。

方向性としては「**賢いモデルに賢く振る舞わせる**」——モデルの能力向上につれ人間による精選を漸進的に減らす、というのが同記事の見立てで、助言は「うまくいく最も単純なことをせよ（do the simplest thing that works）」。

### 区画化 — MemGPT の main context 3 分割

[[summaries/2023-memgpt]]（2023）は、コンテキストを性質の違う 3 区画に分けた: **読み取り専用の system instructions**（制御規則）、**読み書き可能な working context**（常に見えているべき要点。固定サイズ）、**FIFO queue**（流動する履歴。先頭に追い出し分の**再帰的要約**が常駐）。「不変の規則」「更新される要点」「流れる履歴」を区別するこの構造は、現在のエージェント実装（システムプロンプト＋メモリブロック＋会話履歴）の原型である。容量の 70% で警告 → 退避、100% でフラッシュ＋要約更新、という**閾値駆動の入れ替え**も含めて、コンテキスト管理を明示的なプロトコルにした最初期の例。

### 圧縮と引き継ぎ — フェーズ要約・フレッシュコンテキスト

**compaction**（限界に近づいた会話を要約し、その要約で新しいウィンドウを初期化し直すこと）は、長時間タスクにおける「第一のレバー」と位置づけられる（[[summaries/2025-effective-context-engineering]]）。Claude Code の実装では、**アーキテクチャ上の決定・未解決のバグ・実装の詳細を保持し、冗長なツール出力やメッセージを破棄**して、圧縮済みコンテキスト＋**直近アクセスした 5 ファイル**で継続する。

同記事はチューニングの手順まで書いており、そのまま流用できる: **複雑なエージェントのトレース上でプロンプトを調整し、まず再現率（recall）を最大化して関連情報を取りこぼさないことを確認してから、余計な内容を削って適合率（precision）を上げる方向へ反復する**。いきなり簡潔さを狙うと、後で効く情報を落とす。また「**最も安全で最も軽い形の compaction**」として **ツール結果の消去**が挙げられている——「あるツールが履歴の深いところで呼ばれた後、エージェントが生の結果を再び見る必要がなぜあるだろうか」。要約による圧縮に手を出す前に、まずここから削るのが定石になる。

長時間タスクでは「全履歴の持ち回り」から「**フェーズごとに要約して本質だけ残す**」へ移行する。[[summaries/2025-multi-agent-research-system]]（2025）の本番運用パターン: 完了した作業フェーズを要約して外部メモリへ保存し、コンテキスト限界が近づいたら**クリーンなコンテキストを持つ新しいサブエージェントを生成して引き継ぐ**（handoff）。保存済みの計画は失わずメモリから取り戻す。MemGPT の recursive summary を、マルチエージェントの分業に持ち上げた形と読める。

### 参照渡し — コンテキストに実体を入れない

大きな成果物（コード・レポート・データ）は履歴に貼らず、**外部（ファイルシステム等）に置いて軽量な参照だけをコンテキストに入れる**（[[summaries/2025-multi-agent-research-system]] 付録）。情報劣化とトークン浪費を同時に防ぐ。検索結果も同様で、一度に大量に注入せず**ページネーションで少しずつ引く**（[[summaries/2023-memgpt]]）のが、コンテキスト予算と網羅性を両立させる基本手筋。

この路線の製品側の到達点が Manus の「**ファイルシステム＝究極のコンテキスト**」（[[summaries/2025-manus-context-engineering]]）である。要約・切り詰めのような不可逆圧縮は「どの観測が 10 ステップ後に効くか予測できない」以上つねにリスクを孕むため、圧縮は**復元可能（restorable）**な形——Web ページ本文は URL を残して落とす・文書はパスを残して省く——に限定し、サイズ無制限・永続・エージェント自身が読み書きできるファイルシステムを外部化メモリとして使う。研究側の MemGPT・本番マルチエージェントの Anthropic Research・ハーネス探索の Meta-Harness（proposer に全履歴をファイルシステムで渡す）が同じ結論へ独立に収束しており、「**実体は外部・文脈には復元可能な参照**」は現在もっとも合意の固い設計原則の 1 つといえる。

### session はコンテキストウィンドウではない — 保存と積載を分ける

前項の「復元可能な参照」を、**ランタイムの契約**として固定したのが Managed Agents（[[summaries/2026-managed-agents]], Anthropic, 2026）である。出発点の診断は Manus と同じ——compaction（履歴のその場要約）・memory ツールへの書き出し・context trimming（古いツール結果や思考ブロックの選択的除去）は**どれも「何を残すか」の不可逆な決定を伴い**、そして**どのトークンが将来のターンで必要になるかは事前に分からない**。compaction されたメッセージはコンテキストウィンドウから取り除かれ、**どこかに保存されていない限り復元できない**。

解は、**session（起きたことすべての append-only なイベントログ）をコンテキストウィンドウの外に生きるコンテキスト・オブジェクトとして扱う**こと。`getEvents()` でイベントストリームの**位置指定スライス**を取れるので、最後に読んだところから再開する・ある瞬間の数イベント前まで巻き戻して前段を見る・ある行動の直前の文脈を読み直す、といった読み方ができる。同記事はこの着想の先行研究として **Recursive Language Models**（Zhang・Kraska・Khattab, arXiv:2512.24601。REPL 内のオブジェクトを LLM がコードで filter/slice する形）を挙げている（本 wiki 未 ingest）。

設計上の要点は**関心の分離**である。session が保証するのは「永続的で、問い合わせ可能」であることだけ。取り出したイベントを**どう変換してウィンドウに積むか**——プロンプトキャッシュのヒット率を上げる整列を含む、あらゆるコンテキスト設計——は**ハーネス側の裁量**に残す。理由は「**将来のモデルにどんなコンテキスト設計が要るか予測できない**」から。本ページの主題である「積載の判断」は、この分離のもとでは**ハーネスの仕事として明示的に切り出された**ことになる（→ [[agent-frameworks]] のランタイム分離）。

ただしこれで難しさが消えたわけではなく、**場所が移った**だけである点は見ておく必要がある。長期タスクでイベントが際限なく積み上がったとき、`getEvents()` で何を引くかを賢くする責任は依然ハーネスにあり、それはまさに本ページが扱ってきた問題そのものである。

### 復唱（recitation）— 末尾への再掲で注意を操縦する

長いループでは、序盤に立てた計画が文脈中間に沈んで lost in the middle の餌食になる。Manus の解は **todo.md を絶えず書き直す**こと（[[summaries/2025-manus-context-engineering]]）: グローバルな計画をコンテキスト**末尾**＝モデルの直近の注意範囲へ毎ステップ押し出し続け、アーキテクチャ変更なしに自然言語で自分の注意をバイアスする（平均 50 ツール呼び出しのタスクでの漂流対策）。「重要なものは先頭か末尾へ」という位置の設計を、**動的に末尾を更新し続ける**形で実装したものであり、[[summaries/2025-effective-harnesses]] の進捗ファイル・feature list とも同型の「計画の外部化＋定期再掲」パターンである。

### 分割（sharding）— 溢れる前に分ける

長い trajectory（エージェントの行動列）がコンテキストを溢れさせるとき、事後的に削る方式——**Hide-Tool-Result**（直近以外のツール結果を隠す）・**Summary**（要約に置換）・**Discard-all**（閾値超過で全履歴を破棄。[[summaries/2025-deepseek-r1]] 系の DeepSeek が提案）——は reactive（受動的）であり、構造情報や中間推論を犠牲にする。Kimi K2.5 の Agent Swarm（[[summaries/2026-kimi-k2.5]]）はこれを**proactive（能動的）な分割**として再定式化した: タスクを分解する時点で、意味的に独立なサブタスクをそれぞれ**有界なローカルコンテキストを持つサブエージェント**に割り当て、完全な対話トレースではなく**タスクに関係する出力のみ**をオーケストレータへ還流する。切り詰め（truncation）でなく分割（**context sharding**）——各断片は汚染されない独立の作業記憶を持ち、グローバル側には調整シグナルと要点だけが残る。BrowseComp では同一モデルの Discard-all 運用を精度・ステップ効率の両方で上回っており、「溢れてから削る」前に「分解できるなら分ける」を先に検討すべき直接証拠になっている。分割した分の引き継ぎ設計が新たな積載問題になる点は下記のとおり。

### 保持 — 窓が伸びたら捨てない選択肢が生まれる

切り詰め・分割はどちらも「窓が足りない」ことへの応答だが、窓自体が伸びると第三の選択肢——**捨てずに持ち続ける**——が現実的になる。DeepSeek-V4 の **Interleaved Thinking**（[[summaries/2026-deepseek-v4]]）はその最初期の運用例で、ツール呼び出しを含むエージェントタスクでは**推論トレース（thinking）をユーザーターン境界を越えて全ラウンド保持**する方針へ転換した。前世代（V3.2）は新しいユーザーメッセージのたびに思考を全破棄しており、モデルは問題解決の状態をゼロから再構築していた——1M トークン窓と KV cache 効率化（同モデルで V3.2 比 10%）が、この「再構築コスト vs 保持コスト」の損益分岐を動かした形である。ただし一般会話では従来どおり破棄する（持ち続ける利益が薄い）、ツール相互作用をユーザーメッセージで模倣するハーネス（Terminus 型）では保持経路が発動しない、という適用条件の但し書きも実務的に重要。関連して同モデルの **Quick Instruction**（補助タスクを本体の計算済み KV cache を再利用する専用トークンで実行）は、「コンテキストの再 prefill を避ける」という積載コスト削減を推論システム側から行う例である → [[llm-inference-optimization]]。

### 例示の積み方 — 世代で反転した設計

few-shot 例示はコンテキスト積載の古典で、CoT（[[summaries/2022-chain-of-thought]]）は「⟨入力, 思考連鎖, 出力⟩ の 8 例示」で推論を引き出した。しかし推論モデル世代では反転し、[[summaries/2025-deepseek-r1]] は **few-shot 例示がむしろ性能を下げる**としてゼロショット直書きを公式推奨する。「何を積むと効くか」はモデル世代依存であり、コンテキスト設計は定期的な棚卸しが要る。

エージェントではさらに、**自分自身の履歴が意図せぬ few-shot になる**問題がある（[[summaries/2025-manus-context-engineering]] の「Don't Get Few-Shotted」）: 類似の行動–観測ペアが並ぶ反復タスク（履歴書 20 件のレビュー等）では、モデルがそのリズムを模倣して漂流・過剰一般化・幻覚に至る。対策はシリアライズテンプレート・言い回し・順序に**構造化された小さな変動**を入れてパターンの惰性を断つこと——「一様なコンテキストほどエージェントは脆い」。

### 失敗の痕跡は消さない

エラーのトレースを掃除してリトライする衝動は「証拠を消す」ことでもある。Manus は**失敗した行動とスタックトレースをコンテキストに残す**ことを最も効果的な改善の 1 つに挙げる（[[summaries/2025-manus-context-engineering]]）: 失敗を見たモデルは暗黙に事前分布を更新し、同じ誤りを繰り返しにくくなる。[[summaries/2023-reflexion]] が反省文の生成として形式化した「失敗からの文脈内学習」の、最小介入版（消さないだけ）にあたる。エラー回復を「真の agentic な振る舞いの最も明瞭な指標」としながら理想条件のベンチマークでは測られていない、という同記事の批判は [[agent-evaluation]] のギャップ指摘でもある。

### 長時間タスク — 3 手法の使い分け

上記のパターンは多いが、**トークン数がウィンドウを超える長時間タスク**に絞れば、[[summaries/2025-effective-context-engineering]] の 3 分類がそのまま見取り図になる。前提の置き方が重要で、**より大きなウィンドウを待つのは策にならない**——当面、あらゆるサイズのウィンドウが context pollution（無関係・陳腐化した情報の堆積）と情報の関連性の問題を免れないからである。

| 手法 | 中身 | 適する状況 | 本ページの該当節 |
| --- | --- | --- | --- |
| **compaction** | 履歴を要約して新しいウィンドウを初期化し直す | 広範なやり取りを要し、**会話の流れ**を保ちたいタスク | 圧縮と引き継ぎ |
| **構造化されたノート取り** | ウィンドウ外にノートを永続化し、後で引き戻す | **明確なマイルストーン**を伴う反復的な開発 | 参照渡し・復唱／→ [[agent-memory]] |
| **サブエージェント** | 専門化されたエージェントがきれいなウィンドウで作業し、要約だけ返す | **並列の探索**が見合う複雑な研究・分析 | 分割（sharding）／→ [[multi-agent-systems]] |

ノート取りの効き方の実例として、同記事は **Claude によるポケモンのプレイ**を挙げる: 記憶の構造について何もプロンプトされていないのに、探索済み地域の地図・解除した実績・相手別に有効な技といった戦略ノートを自ら作り、「直近 1,234 ステップの間 1 番道路で訓練しており、ピカチュウは目標の 10 レベルに向けて 8 レベル上がった」といった集計を数千ステップにわたって維持する。**コンテキストのリセット後は自分のノートを読んで継続する**——要約のステップをまたいだこの一貫性が、全部をウィンドウに保つだけでは不可能な長時間戦略を成立させている。

サブエージェント側の目安になる比率も出ている——**各サブエージェントは何万トークン以上を使って探索しうるが、返すのは 1,000〜2,000 トークンに蒸留した要約だけ**。返却が長いなら分業の利点（詳細な探索コンテキストの隔離）が消えている、という点検基準として使える。

## 設計論点

- **予算配分から考える**: システム指示・ツール定義・検索結果・履歴・スクラッチパッドの各構成要素に、どれだけのトークンを割くか。ツール定義や検索結果は無自覚に肥大しやすい（[[retrieval-augmented-generation]] の「文書数を増やせば単調に良くなるとは限らない」も同型の知見）。
- **位置を設計する**: lost in the middle を前提に、重要な指示・要点は先頭か末尾に置く。「中間に埋めた制約は読まれない」つもりで配置する。
- **切り詰めに備える**: 何が切られても復元できるよう、計画・要点は外部化しておく（→ [[agent-memory]]）。切り詰めが起きてから対処するのではなく、閾値駆動（MemGPT）かフェーズ境界駆動（Anthropic Research）で先手を打つ。**数日級の長時間タスク**では外部化が主役に昇格する——compaction（要約圧縮）は「次セッションへの指示として不完全」であり、Anthropic の長時間ハーネス（[[summaries/2025-effective-harnesses]]）は引き継ぎを**検査可能な構造化 artifact**（git 履歴・進捗ログ・全機能を `"passes": false` で列挙した feature list JSON）に置いた。要約は劣化するが git log と JSON は劣化しない。フォーマット選択も設計の一部で、**JSON は Markdown よりモデルに改変されにくい**——「変えてほしくない状態」の置き場所として機能する → [[coding-agents]]。
- **サブエージェントはコンテキスト分離の手段でもある**: 別々のウィンドウで並列に読む・考えることは、単一ウィンドウの限界を超えてトークンを使う仕組みそのもの（[[summaries/2025-multi-agent-research-system]] の「性能分散の 80% はトークン量」→ [[multi-agent-systems]]）。K2.5 の context sharding はこれを「実効コンテキスト長を伸ばす追加のアーキテクチャ次元」と明示的に位置づけた（[[summaries/2026-kimi-k2.5]]）。分離した分、引き継ぎの設計（何を渡すか）が新たな積載問題になる。
- **事前取得か、実行時取得か**: 埋め込みで先に集める（速いが陳腐化・無関係の混入リスク）か、識別子だけ持って実行時に引く（新鮮で絞れるが遅い）か。[[summaries/2025-effective-context-engineering]] の実務解はハイブリッドで、境界は「内容の動的さ」で引く——動的なコードベースは JIT 寄り、法務・財務のように安定した資料は事前取得寄り。JIT を採るなら**メタデータが読める構造（一貫した命名規約・階層・タイムスタンプ）を先に作る**のが前提条件になる。それらが揃っていて初めて、段階的開示が機能する。
- **この記事の各論は「剥がされる候補」でもある**: 同記事自身が「**より賢いモデルほど規定的なエンジニアリングを必要としなくなる**」「エージェント設計は人間による精選を漸進的に減らす方向へ進む」と書いている。プロンプトの書式・ツールの絞り込み・compaction の必要性はいずれもモデル能力への仮定を含んでおり、[[summaries/2026-harness-design]] の「ハーネスの部品はモデル能力への仮定である」・[[summaries/2026-managed-agents]] の「仮定は陳腐化する」と同じ枠組みに乗る。実際、1 年後には context anxiety 対策の部品がモデル世代交代で不要になっている（上記の基本制約 2 を参照）。**コンテキスト設計は定期的に「まだ要るか」を問い直す対象**である。
- **観測して直す**: どの積載が効いているかは事前には分からない。実トレースを見て「読まれていない区画」「肥大した区画」を特定して削る——プロンプトと同様、コンテキスト構成も反復改善の対象。この「トレースを見て直す」ループ自体の自動化が Meta-Harness（[[summaries/2026-meta-harness]]）で、コーディングエージェントに過去候補の実行トレースを検分させてコンテキスト構築コードを書き直させた結果、テキスト分類で人手最先端（ACE）を **+7.7 ポイント上回りながらコンテキストトークンを 1/4** にするハーネスを発見した——「多く積むほど良い」わけではないこと（few-shot 例を 32 超に増やすと 9 タスク中 7 つで悪化、という同論文の実測も同型）、そして精度とコンテキストコストは Pareto フロンティアとして**両方を狙って設計できる**ことの直接証拠である。
- **積載戦略はモデル非依存の資産になりうる**: 同論文の数学検索ハーネス（分野別に検索件数・再ランキングを変える 4 ルート BM25）は、探索で一度も見ていない 5 つのモデルにそのまま転移して平均 +4.7 ポイントを得た。良い積載設計はモデルを乗り換えても持ち運べる——ただし何が効くかがモデル世代依存で反転する例（上記 few-shot の教訓）もあるため、転移を仮定せず測るのが安全。
