# Multi-Agent Systems（マルチエージェントシステム）

複数の LLM（Large Language Model, 大規模言語モデル）エージェントを協調させ、**単一エージェントでは届かない性能・信頼性・分業**を実現するシステムの総称。背景には集合知（collective intelligence, 限られた個体の集団が相互作用を通じて個体を超える振る舞いを生むという考え方）の系譜があり、フロンティアモデルの得意分野がプロバイダごとに分化してきたこと（GPT 系=数学、Opus 系=ソフトウェア工学・セキュリティ、Gemini 系=事実想起・科学、など）で実用的な意味を持つようになった。

最も基本的な構成は **orchestrator-worker**（オーケストレータ・ワーカー）——親エージェント（指揮役）がタスクを分解して子エージェント（実働役）に割り当て、結果を統合する形——である。この用語と「サブタスクを事前定義せず、オーケストレータが入力に応じて動的に決める」という定義は Anthropic の実務指針（[[summaries/2024-building-effective-agents]]）が広めた。単一エージェントの [[agent-loop]] が「観測→思考→行動」を回すのに対し、マルチエージェントではさらに「**誰に**やらせるか」「**何を共有させる**か」という次元が加わる。

分野の初期整理は 2023 年サーベイ（[[summaries/2023-llm-agents-survey]]）が与えた。思想的な源流は Minsky『The Society of Mind』（1986,「知能は特定機能を持つ多数の小さなエージェントの相互作用から生まれる」）と分業論で、LLM 以前の MAS（KQML 等の専用通信言語・深層 RL ベース）に対する LLM 世代の質的変化は**自然言語がエージェント間通信になった**ことにある。同サーベイの分類——協調的相互作用を**無秩序（disordered, 自由発言＋統合役や多数決）**と**秩序だった協調（ordered, 規則・逐次発言。CAMEL の役割対・MetaGPT の SOP 符号化が代表）**に分け、**敵対的相互作用**（討論・tit-for-tat）を対置する——は現在のパターン語彙の原型である。また同サーベイは 2023 年時点で既に 3 つの構造的課題——幻覚が相互作用で際限なく増幅する・長い討論はコンテキスト限界を超える・**交渉が誤った合意へ収束し全員がその正しさを確信する**——を警告しており、後の MASFT（下記）が実測で裏づける失敗類型の先取りになっている。エージェント数のスケーリング（事前決定型 vs 動的型）と、複数エージェント＋環境からなる**エージェント社会**（open/persistent/situated/organized の 4 性質。Generative Agents の町シミュレーション・社会ネットワーク伝播・政策シミュレーション）という研究線もこのサーベイが整理した。

## 類型と代表手法

### (a) 固定パターン型 — debate と Mixture-of-Agents

複数エージェントに独立に解かせ、**固定された相互作用構造**で統合する初期の系譜。multi-agent debate（複数モデルが数ラウンド互いの答えを批評し合って収束させる手法）や **Mixture-of-Agents（MoA）**（複数モデルの出力を集約層のモデルが統合する手法）が代表。実装が簡単で効果も出るが、[[summaries/2026-sakana-fugu]] が指摘するとおり**集約役（aggregator）が固定される**ため、集約役の専門外のタスクではその実力に律速されるという構造的ボトルネックを抱える。

### (b) ルーティング型 — 学習された単発ルータ

クエリを見て**最適な 1 モデルへ振り分ける**ルータを学習する系譜（RouterDC など）。協調はしないが、モデルごとの得意分野を活かす最小構成であり、コストはほぼ単一モデル並み。現在の LLM プロダクトの「自動モデル選択」はおおむねこの型にあたる。

### (c) 学習されたオーケストレータ型 — Trinity → Conductor → Sakana Fugu

**オーケストレーション自体を訓練対象にする**最新の系譜（[[summaries/2026-sakana-fugu]], 2026）。代表は Sakana AI の Fugu ファミリーで、系譜としては Trinity（進化的に学習されたコーディネータ）→ Conductor（強化学習でワークフローを自然言語生成）→ Fugu / Fugu-Ultra と発展した。

- **Fugu**（ルーティング型の発展形）: バックボーン LM の隠れ状態に軽量な選択ヘッドを載せ、**テキスト生成なしのロジットだけ**でターンごとに 1 ワーカーを選ぶ。ソフト報酬分布への KL 損失による SFT → 実世界マルチターン軌跡上の進化戦略（sep-CMA-ES）の 2 段訓練。単発でなく**ターンごとに担当を替えられる**のが (b) との違いで、「GPT が構築し、要所で Opus がデバッグに入る」といった交代戦略が創発した。
- **Fugu-Ultra**（ワークフロー生成型）: サブタスク・担当ワーカー id・access list（前ステップのどの成果を見せるか）の 3 つ組の列として**ワークフローそのものを自然言語で出力**し、GRPO（グループ相対の強化学習）で訓練。best-of-N から並列ツリーまで任意のトポロジーを問題ごとに生成でき、**集約役すら問題ごとに変える**（数学問題では GPT を、トリビア問題では Gemini を木の根に置く）ことで (a) のボトルネックを回避した。

この型は「オーケストレーションはモデルスケーリングと直交する**新しいスケーリング軸**」という主張を伴う。重みにアクセスできない閉源 API モデルでも合成できる点で、モデルマージ（重みレベルの合成）のマクロ版＝**挙動レベルの機能的合成**と位置づけられる。

### (d) 本番の orchestrator-worker — Anthropic Research 機能

orchestrator-worker を**実プロダクトとして本番運用**した最初期の公開記録が Anthropic の Research 機能（[[summaries/2025-multi-agent-research-system]], 2025）である。リードエージェント（Opus 4）がクエリを分解して 3〜5 体の検索サブエージェント（Sonnet 4）を並列生成し、引用の帰属は専門の CitationAgent が担う。計画は最初に外部メモリへ保存する（200k トークンでの切り詰めに備える）。内部評価で**単一エージェント比 +90.2%**。

この記事の価値は、**なぜ効くかの定量分析**と**経済性の率直な開示**にある:

- BrowseComp 評価の性能分散の **80% をトークン使用量が説明**する（＋ツール呼び出し数・モデル選択で 95%）。つまりマルチエージェントの効果の正体は、別々のコンテキストウィンドウで「並列に考える容量」を追加し、単一エージェントの限界を超えてトークンを費やせるようにすることにある——**MAS は本質的にトークンのスケーリング機構**という見方を与えた。
- ただしトークン消費は**チャットの約 15 倍**（単一エージェントで 4 倍）。この倍率を正当化できる高価値なタスクにしか適さず、全エージェントがコンテキストを共有すべきタスクや依存の密なタスク（多くのコーディング）は不向きと明言している。「幅優先で並列化でき、単一コンテキストを超える情報を扱う高価値タスク」が適用条件。

統制の手段は (c) と対照的に**学習でなくプロンプト**である（委任指示の 4 要素——目的・出力形式・ツール・境界——や労力のスケーリング規則を明文化して埋め込む）。この「プロンプトによる統制」の限界（重複調査の発生、同期実行のボトルネック）も記事自身が自認しており、(c) の学習されたオーケストレーションが解こうとしている問題の実務側の証言として読める。

### (e) Agent Swarm — 並列化の意思決定を RL で学習する（PARL）

Kimi K2.5（[[summaries/2026-kimi-k2.5]], 2026）は、(c) の「学習されたオーケストレーション」を**モデル本体の RL（強化学習）に統合**し、フロンティア級の性能で実証した現時点の代表例である。**Parallel-Agent Reinforcement Learning（PARL）** の設計は次のとおり:

- **凍結サブエージェント**: 訓練されるのはオーケストレータのみ。サブエージェントは固定チェックポイントから起動され、その trajectory（行動列）は最適化対象から除外し「環境からの観測」として扱う。マルチエージェント RL 最大の難所である credit assignment（最終成果の功罪をどの行動に帰属させるかの割り当て）の曖昧さと訓練不安定を、共同最適化を諦めることで構造的に回避する。
- **最小のツール API**: オーケストレータが持つ委任手段は `create_subagent`（システムプロンプトと名前を与えて特化エージェントを定義）と `assign_task`（並行起動可の委任）の 2 つだけ。サブエージェントの種類は事前定義せず、リサーチャー・ファクトチェッカー・Web 開発者といった異種の編成がタスクごとに**創発**する。
- **報酬の 3 項構成**: タスク成果 r_perf に、*serial collapse*（並列化せず単独実行に退化する局所最適）を防ぐ r_parallel と、*spurious parallelism*（中身のないサブエージェント大量生成で並列指標だけ稼ぐ reward hacking）を防ぐ r_finish（サブタスク完遂率）を加える。補助 2 項の係数は訓練終盤にゼロへアニーリングし、最終ポリシーは純粋に成果を最適化する。
- **critical steps**: 資源制約を総ステップ数でなく「各並列グループの**最長**ブランチ」の和（計算グラフのクリティカルパスに相当）で課し、並列度でなく **end-to-end レイテンシの短縮**に直接インセンティブを与える。
- **並列化は教えない**: プロンプトで並列化を指示せず、逐次実行では予算内に完了できない wide search / deep search 型のタスク分布を作ることで、並列分解が自然に有利になるよう仕向ける。

結果は BrowseComp 60.6→78.4%（発表時点の比較では GPT-5.2 Pro 超え）・WideSearch item-F1 72.7→79.0%・実行時間 3〜4.5 倍短縮で、**タスクが難しいほど並列化の利得が拡大**する（単一エージェントの実行時間が線形に伸びる領域で Swarm はほぼ一定）。なお絶対値はモデル世代とともに動く——半年後の [[summaries/2026-deepseek-v4]]（表6）では**単一エージェント**の V4-Pro 83.4・Opus 4.6 83.7・Gemini-3.1-Pro 85.9 が Swarm の 78.4 を超えており、「並列化による同一モデル内の利得（+17.8pt・レイテンシ 1/4.5）」と「絶対値の SOTA」は分けて読む必要がある。(d) の Anthropic Research が「プロンプトによる統制」で残した課題——いつ・いくつ・どう分けるかのヒューリスティクス依存——を、環境フィードバックからの学習に置き換えた形であり、[[summaries/2025-masft]] の失敗分類のうち FC1（役割仕様・分解の失敗）に対する構造的応答とも読める。一方、凍結ゆえに**協調の共進化**（サブエージェント側が委任のされ方に適応する）は起きない——これは [[summaries/2026-sakana-fugu]] の全体最適化と対照的な設計選択である。Agent Swarm は同時に、コンテキストの側から見ると「reactive な切り詰めに対する proactive な分割（context sharding）」でもある → [[context-engineering]]。

### (f) subagent 委譲の本番実装 — Claude Code

[[summaries/2026-dive-into-claude-code]]（2026）が公開ソース（Claude Code v2.1.88）から解剖した subagent の系は、上記 (d) の orchestrator-worker の**具体的な実装の中身**にあたる。**設計上の判断が 4 つ、はっきり読み取れる。**

**(1) subagent の生成は「ツール呼び出し」である。** `AgentTool` は他のすべてのツールと**同じ `buildTool()` ファクトリを通じて振り分けられ**、基本ツールプールの中に `SkillTool` と並んで置かれる。**両者の違いが本質的で——SkillTool は現在のコンテキストウィンドウへ指示を注入し、AgentTool は新しい隔離されたウィンドウを生成して `queryLoop()` へ再入する。** 「委譲」を特別な制御構造ではなく**ツールの 1 つ**として実装すると、権限系もツールプールの組み立てもそのまま再利用できる。

**(2) 隔離は 3 段階から選ぶ。**

| モード | 中身 | 対応する外部の系 |
|---|---|---|
| **worktree** | **一時的な git worktree**。subagent が自分用のリポジトリのコピーを持つ | — |
| **remote**（内部専用） | リモート環境で起動。常にバックグラウンド | — |
| **in-process**（既定） | ファイルシステムは共有、**会話コンテキストのみ隔離** | AutoGen 等の会話ベース枠組み |

**worktree が興味深いのは、コンテナのオーケストレーションを一切導入せずにファイルシステム水準の分離が得られる**点である。SWE-agent / OpenHands の Docker 隔離（強い資源境界だがインフラが要る）と、会話ベース枠組みのコンテキストのみの隔離（軽いがファイルは共有）の**中間**を、Git の既存機能で埋めている。→ [[coding-agents]]

**(3) 返すのは要約だけ。履歴は sidechain へ。** 各 subagent は自分の `.jsonl` ＋ `.meta.json` を書き、**親へ返るのは最終応答テキストとメタデータだけ**。**デバッグと監査のために履歴は残るが、親のセッションファイルもコンテキストウィンドウも膨らまない。** 論文の言い方では「完全なトランスクリプトの履歴を共有する会話ベースの枠組みはこのコストを避けるが、**エージェントの数が増えるにつれてコンテキストの爆発を招くリスクがある**」。

**代償も明記されている**——**既定のパスは親の会話履歴を継承しないので、ほとんどの subagent 呼び出しは自己完結したプロンプトを必要とする**（fork-subagent のパスは例外）。**上記 (d) の「タスク記述の詳細さが分業の成否を決める」と同じ制約が、実装の構造から出てくる**ことが分かる。

**(4) 権限は継承と上書きの規則で決まる。** subagent が `permissionMode` を宣言していても、**親が既に `bypassPermissions`・`acceptEdits`・`auto` にある場合は上書きされない**——「これらのモードは、安全性と自律性のトレードオフについてのユーザーの明示的な決定を表すので常に優先される」。**ツールについては 2 層のスコープ**で、SDK 水準の権限（`--allowedTools`）は保存されるが**セッション水準のルールは subagent の宣言で置き換えられる**。加えて、subagent が親のターミナルへ権限をエスカレートするための内部専用モード `bubble` がある。→ [[agent-safety-and-guardrails]]

#### 並列化のコストが数字で出ている

**本ページで繰り返し扱ってきた「マルチエージェントは高い」に、具体的な倍率が付いた。**

> **Claude Code のエージェントチームは、plan モードでの標準セッションの約 7 倍のトークンを消費する。**

論文はこれを**要約のみの返却がより決定的になる理由**として挙げる——**subagent が隔離されたコンテキストにあってなお 7 倍なのだから、履歴まで共有したらどうなるか**、という話である。上記 (d) の Anthropic Research（単一チャットの約 15 倍）と併せて読むと、**分業の倍率は構成によって 7〜15 倍のレンジにある**と見ておける。

#### 調整はファイルロックで足りる

**インフラの選択として記録に値する。** 複数インスタンスの調整に**メッセージブローカーも分散調整サービスも使わない**。

> **タスクは共有リストからロックファイルベースの排他制御を通じて主張され、ロックファイルは予測可能なファイルシステムのパスに保存される。**

**スループットを 2 つの性質と引き換えにしている**——**依存ゼロの配備**（外部インフラが要らない）と、**完全なデバッグ可能性**（どのエージェントの状態もプレーンテキストの JSON を読めば分かる）。本ページ「運用側で決まること」の観点では、**分散システムの道具立てを持ち込む前に、ファイルシステムで足りないかを先に問う**べき、という実例になる。

#### 未解決として残されているもの

論文は**エージェント間の一貫性**を、5 価値の緊張表（Capability × Reliability）でも第 12 節の未解決問題でも繰り返し挙げている。

> 有界なコンテキストがコードベース全体の把握を妨げ、**subagent の隔離がエージェント間の一貫性を制限する**。**並列のエージェントは、他所に既に存在する解を独立に再実装しうる。**

**隔離は文脈の汚染を防ぐが、同時に「他の subagent が何をしたか」も見えなくする。** 本ページ (d) の「依存の密なタスクは並列分業に不向き」を、**アーキテクチャの構造から説明したもの**として読める。論文は「**with whom の拡張は Capability 対 Reliability に部分的に対応するが、表がカバーしていないエージェント間の一貫性の懸念を提起する**」と、自らの枠組みの穴として明示している。

## デプロイ形態の類型 — 実務側の分類

上の (a)〜(e) が「**どう協調させれば賢くなるか**」という研究側の類型なのに対し、企業が本番投入するときに使われるのは「**制御をどこに置くか**」で切る別の分類である。ベンダーの実務ガイド（[[summaries/2026-agent-orchestration-guide]], Databricks, 2026）が整理する 6 パターンは、制御・回復力・スケーラビリティのトレードオフの取り方で分かれる。

| パターン | 構造 | 向く場面 | 弱点 | 研究側の対応物 |
| --- | --- | --- | --- | --- |
| **中央集権型**（centralized） | 単一のオーケストレータが全タスクを割り当て、全結果を受け取る | 規制対象。全判断を 1 点に追跡したい | 単一障害点。エージェント数が増えるとスループットのボトルネック | (d) orchestrator-worker、(b) ルーティング型 |
| **分散/非中央集権型**（decentralized） | 中央の制御役なしにエージェント同士が直接通信・交渉 | 独立したチームやシステムをまたぎ、1 つの制御層を共有できない | 競合解決（同一タスクの取り合い、矛盾出力）の仕組みが別途要る | (a) debate 系の水平な相互作用 |
| **階層型**（hierarchical） | 監督エージェントが下位に委譲し結果を統合。段を重ねられる | 人間の組織構造に写像したい | 段数が増えるほど伝言劣化とレイテンシが累積 | (d) の多段化、(e) Agent Swarm の親子構造 |
| **ハイブリッド型**（hybrid） | 機微な処理は中央統制、大量処理は分散に委ねる | 実際の企業の大半 | 統制と委譲の**境界の設計**が最も難しい | (c) 学習されたオーケストレータが暗黙に学ぶもの |
| **フェデレーション型**（federated） | 生データを 1 箇所に集めずに組織をまたいで協働 | 医療・金融など、データを持ち出せない組織横断 | ネットワーク越しの文脈交換が攻撃面になる | — |
| **創発型**（emergent） | 協調の型を固定せず相互作用から発達させる | サンドボックス研究のみ | 出典自身が「本番で使うな」と明言 | (e) の編成創発、エージェント社会の研究線 |

**選択の起点はリスク許容度**である——監査可能性を最優先するなら中央集権型、単一障害点を避けたいなら非中央集権型やフェデレーション型。実務では単一パターンに寄せず、同一のエージェント・エコシステム内で複数を組み合わせるのが普通とされる。

注意すべきは、この分類が**制御の置き場所しか語っていない**ことである。(a)〜(e) が扱う「協調が実際に賢さを生むか」——どのタスクで並列化が効くか、どこで orchestration collapse が起きるか、コストが見合うか——は別の軸であり、デプロイ形態を選んでも解決しない。両方を独立に設計する必要がある。

### 運用側で決まること

デプロイ形態を選んだ後、本番で効いてくるのは協調のアルゴリズムではなく運用の作り込みである（同ガイド）。

- **暴走コストの上限**: エージェントが互いをループ状に呼び出したり無限にリトライしたりするため、**呼び出しの深さ・最大実行時間・リトライ回数**に上限を置く。これは監視ではなく制限側の責務である。
- **デッドロックの検知**: 2 エージェントが互いの出力を待って停止する。停滞を検知してタイムアウトや再割り当てを強制する**ウォッチドッグ**を置く。厳密な引き継ぎ順に依存する逐次型ほど陥りやすく、MASFT の FC3（検証と終了の失敗, 31.4%）と同じ場所で顕在化する。
- **共有モデルの連鎖障害**: 全エージェントが同じ基盤モデルに乗っていると、その 1 つの劣化が系全体に波及する。**モデルを混在させる**ことでリスクを分散する——(c) 学習されたオーケストレータがモデル間の得意分野の違いを利用するのと同じ事実を、可用性の側から使う発想である。
- **入出力契約**: エージェント間で受け渡すデータのスキーマを文書化しておくと、上流の出力形式の変更が下流を壊した瞬間を機械的に検知できる。型のない引き継ぎは、壊れても静かに壊れる。
- **段階的な配備**: 稼働中のエージェントを壊さないための **rainbow deployment**（新旧バージョン並走で漸進切り替え）は Anthropic の本番実例（[[summaries/2025-multi-agent-research-system]]）でも採られている。

これらの前提として、全エージェントの行動をトレースし指標をオーケストレーション層で集約する基盤が要る → [[agent-observability]]。権限の最小化と承認ゲートの設計は [[agent-safety-and-guardrails]]。

### many brains, many hands — 実行環境を共有可能にする

上の分類が「**エージェント同士の制御関係**」を切るのに対し、もう 1 つ独立した軸として「**エージェントと実行環境の結びつき**」がある。Managed Agents（[[summaries/2026-managed-agents]], Anthropic, 2026）は、ハーネス（brain）を実行環境（hands）から切り離し、各 hand を `execute(name, input) → string` という単一のツール口として扱う設計を採った。結果として **どの hand もどの brain にも結合しないので、brain 同士が hands を受け渡せる**——ハーネスは自分が繋がった sandbox が「コンテナなのか、電話なのか、ポケモンのエミュレータなのか」を知らない。

ここで示唆的なのは**能力と設計の順序が反転した**経緯である。多数の実行環境を扱い「どこへ仕事を送るか」を決めるのは、単一シェルで動くより難しい認知タスクなので、当初は**モデルにそれができなかったから**単一コンテナに閉じ込めていた。ところがモデルの知能が伸びると、今度は単一コンテナのほうが制約になった（そのコンテナが落ちると brain が手を伸ばしていた全 hand の状態が消える）。**モデル能力の向上がアーキテクチャ上の制約を反転させる**——(c) の学習されたオーケストレータや (e) の PARL が「協調の仕方を学習させる」方向で同じ現象に触れているのと対応する、インフラ側からの観測である。

## 共有基盤は何か — ハーネス表現の 4 水準と "The Central Gap"

MASFT が「なぜ失敗するか」を**症状**の側から分類したのに対し、[[summaries/2026-code-as-agent-harness]]（UIUC / Meta / Stanford のサーベイ, 2026）は同じ問題を**基盤の形式性**の側から切る。「これらのエージェントが住まう基盤とは何か」を問い、コード中心の MAS 20 本以上を**共有状態をどれだけ形式的に表現しているか**で 4 水準に分けた。

| 水準 | 何を共有基盤とみなすか | 代表系 | 構造的な弱点 |
|---|---|---|---|
| **暗黙／ファイルのみ** | 現在のコードファイル（群）。共有状態は各呼び出しで**会話履歴から暗黙に再構成される** | ChatDev, MetaGPT, FlowGen, MapCoder, CodeCoR, SEW, CodePori | エージェントの信念が真の状態から乖離しても**系にとって不可視**。検出も訂正もできない |
| **リポジトリにもとづく** | ディレクトリ構造・依存グラフ・呼び出し階層・版履歴を持つナビゲート可能なリポジトリ | MAGIS（進化記憶）, HyperAgent（`get_tree_structure` 等のナビゲーション・ツール）, Lingma SWE-GPT（AST 骨格で圧縮）, SyncMind | **静的な構造**しか見えない |
| **実行にもとづく** | コードが「どう見えるか」ではなく「**何をするか**」——コンパイル可否・テスト・fuzzer の発見・速度・仕様との一致 | AgentCoder, AutoSafeCoder, QualityFlow, MACRO, EvoMAC, CANDOR, MAGE | **動的な振る舞い**しか見えない |
| **黒板／共有状態** | すべてのエージェントが読み書きする明示的で大域的なデータ構造 | Self-Collaboration, **L2MAC**（永続ファイルストア＋Control Unit）, GameGPT, Cogito（3 層記憶） | 権威と一貫性の問題を新たに作る |

**同サーベイの立場表明が "The Central Gap"** である——**文献の大多数は最下層（暗黙／ファイルのみ）に位置し、共有ハーネス基盤の形式的なモデルを一切欠いている。プログラムはマルチエージェントの諸領域の中で唯一、*実行される*成果物であり、形式的な共有基盤を錨づけできる客観的で非言語的な信号を生む。にもかかわらず、ほとんどの系はこの性質をアーキテクチャの水準で活用できていない。**

**MASFT との接続**: MASFT の FC1（会話履歴の喪失・終了条件の不認識）と FC2（情報の抱え込み・他者の入力の無視）は、この 4 水準で言えば**最下層に留まったことの帰結**として読み直せる。SyncMind はこれを形式化し、**真の状態 $S_k$ とエージェントの信念状態 $B_k$ の乖離 $|B_k - S_k|$** として測る唯一の仕事だと同サーベイは指摘する。**「情報を抱え込む」は行儀の問題ではなく、抱え込みを検出できる共有表現がないという設計の問題である。**

### トポロジの複雑さは「症状」かもしれない

同サーベイが引き出した最も反直観的なパターンが、**トポロジの複雑さとハーネス状態の形式性が逆相関する**というものである。

- **最も明確な形式的基盤を持つ L2MAC**（永続ファイルストア＋明示的なコンテキスト・スケジューリング）は、**単純な逐次連鎖**で足りている。凝っているのは状態管理の側であってトポロジではない。
- **暗黙状態の EvoMAC / SEW** は、動的 DAG・ワークフロー変異・エージェントプールのスケーリングという**手の込んだ適応的トポロジ**を発達させる。

**「基盤が形式的に表現され問い合わせ可能なとき、エージェントは単純で透明なプロトコルで協調できる。基盤が暗黙のとき、エージェントは欠けた状態情報を補うためにより豊かな相互作用のパターンを必要とする。」** 上記 (c)〜(f) の学習されたオーケストレータやワークフロー最適化の系譜は、この観点からは**共有表現の不在を協調の複雑さで補償している**可能性を疑ってみる価値がある。

**関連して同サーベイは、文脈管理を「暗黙の共有状態が払う税」と呼ぶ。** L2MAC の Control Unit・MetaGPT の publish-subscribe プール・SoA のエージェントプール・スケーリング・Cogito の 3 層記憶は、**すべて同じ背後の問題への応答**——どのコンテキストウィンドウにも収まらない大きさのコードハーネスに、首尾一貫したビューをどう与えるか——である。成熟した基盤があれば、これらばらばらの解は「オンデマンドで問い合わせ可能な状態表現」へ統一できる、というのが同サーベイの見立てである。上の「隔離と共有の張力」（設計論点）に対する、基盤側からの答えにあたる。

**もう 1 つ、コードに媒介された協調への過信への釘も刺されている**——ファイル・API・diff・テスト・ログ・スキーマ・黒板・ワークフロー状態は**いずれも部分的なチャネル**で、忠実度・遅延・範囲をトレードオフする。「テストは意味論を合否へ圧縮し、要約は詳細を犠牲にして文脈を節約し、ログは接地されているがノイズ混じりで、共有黒板は永続性を改善する一方で権威と一貫性の問題を作る」。**中心的な設計問題は「コードが存在するか」ではなく「どの成果物が権威を持つか・どう圧縮されるか・チャネル間の衝突をどう解決するか」である。**

### いつ止めるのか — 収束の 6 パターン

MASFT の FC3（検証と終了の失敗が全体の 31.4%）に対応する、**設計側の分類**も同サーベイが与えている。

| パターン | 判定基準 | 代表系 |
|---|---|---|
| **正しさ（テストでゲート）** | 全テスト通過 | AgentCoder, L2MAC, SyncMind, CANDOR。PairCoder は**行き詰まり検出**を追加（同じバグ／フィードバックが履歴に再出したら次の候補計画へ切り替える） |
| **セキュリティ** | CWE の指摘ゼロ **かつ** fuzzer のクラッシュゼロ | AutoSafeCoder。多基準の収束で、どちらもエージェントの意見でなく客観的な振る舞いに接地 |
| **性能** | ユーザー定義のランタイム・メモリ閾値を満たす | MACRO（正しさでなく性能を主要な収束基準にした唯一の系） |
| **スコアにもとづく** | 品質スコアが閾値に達する／最良候補を選ぶ | MAGE（シミュレーション不一致スコア）, CodeCoR（4 基準の**軟らかい**収束——完璧を待たず最良を提出）, Trae Agent（候補パッチのアンサンブルからの選択） |
| **合意** | 複数レビュアーの多数決 | CANDOR（3 Panelist の多数決）, QualityFlow（品質検査器が収束オラクル兼コントローラ。**問題の 75〜84% が初回生成で収束**して早期脱出する） |
| **暗黙** | **固定回数の段／反復の後、客観的な品質基準なしで終了** | ChatDev（固定段数 or 連続 2 ラウンド同一 or 10 ラウンド）, MetaGPT（固定 SOP 完了）, Self-Collaboration（$n=4$ でフォールバック）, EvoMAC（固定 $K$ 回） |

**最後の「暗黙の収束」が文献で最も普及しており、この分野の最も重大な隙間である。** そしてそれは 4 水準の話と地続きで——**プログラム状態の客観的な表現がなければ、系は収束のための原理的な基準を持ちようがない。** MASFT が「早すぎる終了」「検証の欠落」を症状として数えたのに対し、これはその**原因の側**の記述になっている。

なお同サーベイは **FlowGen の落とし穴**も明示している——テストゲートの収束を**真のテストではなく LLM が生成したテスト**の上で行うと、**系は自分の偏ったテストは通るが外部の評価では失敗するコードに収束しうる**。AgentCoder が Test Designer をコードと独立に走らせ、Test Executor を（LLM ではなく）決定論的な Python スクリプトにしているのは、この**モード崩壊（mode-collapse）**への対策である → [[agent-evaluation]]。

## なぜ失敗するか — MASFT

期待に反して、MAS の実測性能は単一エージェントや best-of-N を明確に上回れていない（SOTA 級 OSS の ChatDev で正答 25%）。[[summaries/2025-masft]]（2025）は 5 つの人気 MAS の 150+ トレースを人手分析し、**14 失敗モード × 3 カテゴリ**の分類法 MASFT を確立した:

- **FC1 仕様とシステム設計**（37.2%）— タスク仕様・役割仕様の不遵守、ステップの反復、会話履歴の喪失、終了条件の不認識
- **FC2 エージェント間の不整合**（31.4%）— 会話リセット、明確化を求めない、タスク脱線、**情報の抱え込み**、他者の入力の無視、推論と行動の乖離
- **FC3 検証と終了**（31.4%）— 早すぎる終了、検証の欠落・不完全、誤った検証

中心的な主張は「**失敗の原因は個々の LLM の能力不足ではなく組織設計の欠陥**」であること。失敗モードは高信頼性組織（HRO）研究が示す設計原則（階層分化・専門性への敬意）の違反とちょうど対応し、プロンプト改善やトポロジー変更といった「自明な修正」では +14 ポイント止まりで実用水準に届かなかった。処方箋として挙げられる**構造的戦略**——包括的検証、標準化された通信プロトコル、MAS 向け強化学習、信頼度の定量化、メモリと状態の管理——は、下記の設計論点と直接対応する。トレース分析・LLM-as-a-judge という評価方法論の側面は [[agent-evaluation]] を参照。なお同じ MAST 研究（5 フレームワーク・150 タスク・14 失敗モード・3 カテゴリ）は横断サーベイ（[[summaries/2025-llm-reasoning-to-agents]] §V-B, Pan et al. の名で）でも未解決課題の筆頭に挙げられており、「マルチエージェントの失敗は組織設計の問題で、役割定義やオーケストレーションの調整だけでは不十分」という診断が複数のサーベイに引かれて定着したことがわかる。

## 設計論点

- **隔離と共有の張力**: 並列に動く複数エージェントに同じ軌跡を見せると、先行エージェントの道筋に後続が引きずられて多様性が失われる（**orchestration collapse**）。一方で完全隔離は同じ環境調査の重複を生む。Fugu-Ultra の解は「**現在のワークフロー内は隔離、過去のワークフローのツール呼び出し履歴は共有**」という切り分け → [[agent-memory]]。MASFT の FC2（情報の抱え込み・他者の入力の無視）と FM-1.4（会話履歴の喪失）は、この設計を誤ったときに実際に起こる失敗の実測である。Anthropic Research の付録が挙げる「**サブエージェントの成果物はファイル等に永続化し、参照だけをリードに渡す**」パターンは、多段の伝言ゲームによる情報劣化とトークン浪費を同時に防ぐ実務解（[[summaries/2025-multi-agent-research-system]]）。
- **同期か非同期か**: リードがサブエージェント群の完了を待つ**同期実行**は協調が単純だが、途中で操縦できない・サブエージェント同士が協調できない・1 体の遅延で全体がブロックされる、というボトルネックを作る。非同期化は並列性を上げる代わりに結果調整・状態一貫性・エラー伝播が難題になる——Anthropic Research は同期設計を選び、この制約を公開の技術的負債として明示した（[[summaries/2025-multi-agent-research-system]]）。
- **function call の帰属**: どのエージェントが発行したツール呼び出しかを追跡し、応答を正しい発行元に返すルーティングが必要になる。単一エージェントでは自明だった前提が崩れる → [[tool-use-and-function-calling]]。
- **分業の目的はコンテキストの隔離である（そして返却の細さが指標になる）**: サブエージェントを立てる理由は「並列で速い」だけではない。[[summaries/2025-effective-context-engineering]]（Anthropic, 2025）は、長時間タスクでコンテキストウィンドウの制限を回避する 3 手法（compaction / ノート取り / マルチエージェント）の 1 つとしてこれを位置づけ、**専門化されたサブエージェントがきれいなコンテキストウィンドウで焦点の絞られたタスクを扱い、メインエージェントは高水準の計画で調整する**という関心の分離として説明する。**詳細な検索コンテキストはサブエージェント内に隔離されたままで、リードは統合と分析に集中する**——これが分業の本体である。
  - 実務上の目安になる比率も出ている: **各サブエージェントは何万トークン以上を使って広範に探索しうるが、返すのは 1,000〜2,000 トークンに蒸留した要約だけ**。この比率は点検基準として使える——**返却が長いなら隔離の利点が消えている**。[[summaries/2025-multi-agent-research-system]] の「トークン 15 倍」という経済性の議論に対して、**なぜそれでも分業が成立するのか**（大量に読むのはサブエージェント側で、リードのウィンドウには要約しか戻らないから）という理由側の数字にあたる。また同記事は使い分けの基準も示しており、マルチエージェントが適するのは「**並列の探索が見合うだけの複雑な研究と分析**」で、広範なやり取りを要するタスクは compaction、明確なマイルストーンを伴う反復開発はノート取りが向くとされる → [[context-engineering]]。
- **コスト・レイテンシと品質のトレードオフ**: 多段オーケストレーションは常に得ではない。Fugu の評価でも、複数のベンチマークで単一選択の Fugu がワークフロー型の Fugu-Ultra を上回った。**タスクに応じて協調の深さを選ぶ**こと自体が設計変数。
- **上限はワーカーが決める**: オーケストレータは自分では解かないため、全ワーカーが失敗する問題は解けない。またワーカーのバージョン更新で得意分野の地図が変わると、学習済みルーティングが陳腐化するリスクがある。
- **検証の設計**: MASFT では検証と終了の失敗だけで全体の 31.4% を占める。verifier を「置く」だけでは足りず、何を検証するか（コンパイル可否でなく仕様準拠・エッジケース）と、誰が終了権限を持つか（例: verifier のみが会話を終了できる）の設計が要る。ただし「すべては verifier の責任」ではない——仕様・伝達の失敗は検証の手前で起きる（[[summaries/2025-masft]] §4.3）。
- **推論時計算との関係**: 複数エージェントの並列試行・debate・集約は、推論時に計算量を積んで精度を買う [[test-time-compute]] の一形態と見ることもできる。
