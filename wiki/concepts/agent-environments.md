# Agent Environments（エージェントの訓練環境）

**エージェントを強化学習（RL）で鍛えるための*環境*そのもの**を主題とするページ。[[reinforcement-learning-from-human-feedback]] が「どう学習則を回すか（アルゴリズム側）」、[[agent-evaluation]] が「能力をどう*測る*か」を扱うのに対し、本ページは「**エージェントに何を経験させるか**」、つまりタスクの分布・報酬の接地・サンドボックスの隔離を扱う。

**なぜ環境が第一級か。** モデルレポートが繰り返し述べる観察は「**RL の効果は、豊かで・多様で・頑健に検証可能な環境に律速される**」（[[summaries/2026-kimi-k3]]）である。同じ RL アルゴリズム・同じベースモデルでも、環境の質（報酬が客観的に接地されているか、タスクが本当に長期ホライズンの能力を要求するか、サンドボックスが探索を安全に許すか）で得られる能力が変わる。だから環境設計は報酬設計 ＋ タスク分布 ＋ サンドボックスの合成問題として、独立した工学の対象になる。

### (1) white-box modular harness: ハーネスを訓練時の変数にする

**K3 の最も概念的に新しい点。** 主張は端的である。

> **単一の固定されたエージェントハーネスで訓練すると、モデルは特定のツールスキーマ・システムプロンプト・コンテキスト管理機構・相互作用プロトコルへ*過適合*しうる。**

そこで K3 は**ハーネスを設定可能で合成可能なモジュールの集合**（ツールインターフェース・システムプロンプト・コンテキスト管理戦略・スキル・記憶・サブエージェント）として表現する統一 white-box 環境を作る。設定を通じてこれらを合成することで、環境は **Kimi Code / Claude Code / Codex / OpenClaw / Hermes** のような主流ハーネスや、まったく新しいものを具現化できる。**RL 中はタスクグループごとに異なるハーネス構成を動的に構築し、単一ハーネスの慣習ではなく多様な組み合わせにモデルを晒す。**

これは [[harness-engineering]] の視点を訓練側から裏返したものである。同ページは「**ハーネスのすべての部品はモデルが単独でできないことへの仮定であり、モデルの改善で陳腐化する**」と述べ、部品を*剥がす*側から論じた。K3 は逆に、**訓練時にハーネスを撹乱（randomize）することで、特定の部品への依存を最初から作らない**。そのため、配備時に別のハーネスへ載せ替えても頑健になりやすい。「**ハーネスは固定の容れ物ではなく、訓練分布に含める変数である**」という見方は、[[summaries/2026-code-as-agent-harness]] の *agent-initiated code artifacts* や AHE の自動進化（[[summaries/2026-agentic-harness-engineering]]）と同じ「ハーネスを第一級の対象にする」流れにある。

### (2) KG-guided task synthesis: 自己進化する知識グラフ

タスクの品質と多様性は**源材料**に左右される。K3 は**自己進化する階層的な DAG（有向非巡回グラフ）知識グラフ**を、エージェントが Web 規模の探索を通じて再帰的に拡張する。

- **構築**: 粗粒度のシードノードから始め、各ノードにエージェントを割り当てて複数の Web 検索で概念を調べる。新ノードを加える前に既存グラフを探索して重複を最小化する。**辺は常に粗い概念から細かい概念へ向く**。枝は概念が十分「原子的」になったら止まる。
- **合成**: 望ましい領域・タスク型の分布を狙って様々な粒度のノードをサンプリングし、キーワードと祖先ノードの文脈を組み合わせて Web クエリを作り、検索した実世界材料からタスクを合成する。

**K2 のツール合成が「ツールと軌跡を作る」だったのに対し、K3 の KG 合成は「タスクの源となる知識空間そのものを育てる」**。KG 合成は粒度 × 網羅を制御して、専門的で過小表現の知識まで届かせる。

### (3) AET（Autonomous Execution Tasks）: verify-in-the-loop

<figure>

![](../../raw/assets/2026-kimi-k3/fig10.png)

<figcaption>図10（再掲, Kimi K3）: Camera Repair Management System の完了曲線。ブラックボックスのシステム複製タスクで、エージェントは隠された 3D カメラ修理システムをオラクルへの問い合わせを通じて Web アプリとして再構築する。完了度は検証器が評価した進捗。</figcaption>
</figure>

各 AET は **初期状態 ＋ 制約付き目標 ＋ ツールベースの行動空間 ＋ 実行予算 ＋ 独立した検証器**を指定する。エージェントは目的・文脈・制約・検証インターフェースだけを見て、**参照軌跡や事前定義された手続きなしに**、タスク分解・ツール選択・計画・エラー回復・終了を自律的に行う。

**設計の核心は報酬の接地である**。

> **報酬はエージェントの*自己申告の完了*ではなく、検証器による*最終環境状態*の評価に接地される。**

検証器は多様化されており、black-box システム複製（図 10）・定量的ファクター発見・税務監査などがある。これは [[agent-loop]] の「途中までは正しくても最後の一手で失敗する」問題に対する訓練側の答えであり、[[agent-evaluation]] の oracle adequacy（検証器が意図したタスクを捉えているか）と表裏である。

### (4) モックアプリ: 再現可能な持続的環境

長期ホライズンのパーソナルアシスタントのタスクのため、**Gmail・Notion・Slack・Canvas** の現実的なモック実装を作る。核心的な意味論を保ちつつ、**外部 API やレート制限なしで**再現可能で大規模な相互作用を可能にする。エージェントは複数のシミュレートされた日にわたる持続的で進化する環境で動作し、**1 ロールアウトが最大で数千のツール呼び出しと数百万のコンテキストトークン**を含みうる。各イベントは決定論的な規則あるいは LLM ベースの評価器で評価される。

### (5) AgentENV: 再開可能な microVM サンドボックス

エージェント AI ワークロードのために設計された microVM ベースのサンドボックスランタイム。3 つの設計目標を持つ。

- **高忠実度の隔離**: **エージェントが有能になるほど積極的に探索し reward hacking を試みる**。伝統的なコンテナベースのランタイムでの初期実験では、意図しないエージェント操作が **kernel panic やデッドロック**を引き起こした。microVM 隔離が「できるだけ多くの探索を許す」と「安全」の緊張を解く。
- **柔軟なライフサイクル**: 漸進的なチェックポイント（前回以降に汚れたメモリページのみ保存）で、**チェックポイント/再開の遅延をそれぞれ 133ms/49ms** まで下げる。Pause/Resume など高水準操作を提供。partial rollout で軌跡が複数反復にまたがる agentic RL に不可欠。
- **高効率・高密度**: OverlayBD イメージ形式 ＋ カスタム ublk ドライバ ＋ P2P 転送でサブ秒起動。**訓練・評価を通じて 150 万イメージにわたる 5,121 万個のサンドボックスが作られた。**

これは [[summaries/2026-deepseek-v4]] の **DSec**（4 実行基盤・全コマンドを trajectory ログに記録）の次の世代にあたり、「**エージェント RL・評価のインフラは安全性インフラを兼ねる**」という観察の続きである → [[agent-safety-and-guardrails]]。

## SWE の訓練環境: 実行できるリポジトリを用意する

モデルレポートの環境が非公開の社内基盤であるのに対し、SWE（Software Engineering）では**公開された訓練環境**が先に整った。課題は「GitHub のイシューと正解パッチ」なら大量にあるのに、**それを実行してテストできる環境**がないことだった。SWE-bench の訓練用分割（19,008 件）は正解パッチしかなく、エージェントのパッチが正しいかを自動で採点できない。

| 環境 | 規模 | 作り方 | 特徴 |
|---|---|---|---|
| **SWE-Gym**（[[summaries/2024-swe-gym]]） | 11 リポジトリ・2,438 件（Lite 230 件）＋実行環境なしの Raw 66,894 件 | イシューが立った時点の requirements.txt・CI スクリプトを読み、**依存関係を手で設定**。正解パッチで元より多くのテストが通ることを確認。約 200 人時・1 万 CPU コア時間・Docker イメージ 6 TB | SWE-bench と重ならないリポジトリを選び汚染を避ける。依存の難しいタスクも捨てない |
| **SWE-rebench**（[[summaries/2025-swe-rebench]]。[[summaries/2025-swe-rl-long-context]] が使用） | 3,468 リポジトリ・21,336 件 | **環境づくりまで全自動**。`git tag` のバージョンでタスクをまとめて環境を共有し、Qwen2.5-72B に README や setup.py からインストール手順の JSON を書かせ（タスクあたり最大 3 案、失敗したらエラーログを見せて直させる）、実際にテストを走らせて確かめる。45 万件の候補から 15 万件に絞り、インストールと検証で 14% が残る | 規模が大きい。各タスクに LLM が付けた品質ラベル（イシューの明確さ・難しさ・テストの正しさ）が付く。**月ごとの分割**があり、訓練データに含まれない最新の分割（2025 年 5・6 月）を汚染のない評価に使える |
| **R2E-Gym**（[[summaries/2025-r2e-gym]]） | 8,135 件。SWE-bench と重ならない 10 リポジトリ・4,578 件の部分集合を訓練に使う | **イシューのないコミットからもタスクを作る**。小さなコード変更のコミットを選び、Docker の中で依存関係の組み合わせを順に試して環境を作り（半手動）、修正前に落ち修正後に通るテストを既存のテストから探すか LLM に書かせる。問題文は、コード変更と失敗するテストの実行結果を LLM に見せて逆に書かせる（逆翻訳） | 人間のイシューに頼る方法の 2.5 倍を集めた。合成したイシューで訓練しても実際のイシューとほぼ同じ効果（28.0% 対 27.8%）。部分集合の 6 割が pandas・numpy・pillow |
| **SWE-smith**（[[summaries/2025-swe-smith]]） | 128 リポジトリ・50,137 件、環境は 125 イメージで 290.54 GB | **環境を先に作り、その中でバグを合成する**。最新のコミットだけを SWE-agent にインストールさせ、LM による関数の書き換え・AST の機械的な変換・バグの組み合わせ・PR の取り消しの 4 つの戦略で候補を作り、既存のテストを壊したものを残す。人手は約 20 時間、費用は 1,360 ドル | 同じリポジトリのタスクが 1 つの環境を共有する。**訓練専用**（隠しテストがなく、壊れたテストが見えている） |
| **SWE-Lego**（[[summaries/2026-swe-lego]]） | 3,251 リポジトリ・32,119 件（実 18,409 ＋ 合成 13,710） | SWE-rebench の実際の PR と、SWE-smith の方法の合成バグを混ぜる | 実データが「深さ」（複雑さ）、合成データが「幅」（量と網羅）を受け持つ |

環境の作り方には選択がある。SWE-Gym の付録は、汎用のセットアップスクリプトで 6,415 件を集めた並行研究（Nebius の 2 本の連続したブログ記事、Badertdinov ら・Golubev ら 2024。後者は [[summaries/2025-swe-rl-long-context]] と同じ著者群）との違いを次の点に置いている。**手作業は偏りを避けるが数が増えない。自動化は数が取れるが、セットアップに失敗する（依存が難しい）タスクが系統的に抜ける**。

この並行研究を全自動化・大規模化したのが SWE-rebench（[[summaries/2025-swe-rebench]], Nebius, 2025）である。人手を LLM に置き換える場所は 2 つある。1 つはインストール手順で、Agentless（[[summaries/2024-agentless]]）にならった決まった手順で LLM を呼び、レシピを書かせて実行し、失敗したらログを見せて直させる。人手の環境がある SWE-bench の 18 タスクで比べると、この方式は候補 1 案で 6 件、3 案で 8 件、10 案で 9 件に成功し、Docker の中で自分で試行錯誤する対話型のエージェントは 1 回で 8 件だった。対話型は資源を大きく食うので、大量処理には固定手順を選んでいる。もう 1 つは SWE-bench Verified が人手で行ったタスクの点検で、その人手のラベルで学習したモデルに「イシューは明確か」「テストは正しいか」「難しいか」を予測させる（正解率は 67〜81%）。それでも**動く環境を作れたのはリポジトリの 31%** で、検証で落ちる主な原因は、flaky なテスト（何度か走らせて 1 回でも落ちたら除く）、途中のエラーを見ながら依存を足す対話的なインストールが要るプロジェクト、バージョンが固定されていないか公開されなくなった依存関係だった。上の「自動化するとセットアップの難しいタスクが抜ける」という偏りの、規模の大きい実例である。同論文は RL に使うデータとしての細部も直している。PR の差分を `head_commit` との間でとって無関係なマージの混入を防ぐ、テストをエラー出力を省略せずに走らせて「まだない関数名を当てさせる」タスクを見つける、依存関係のバージョンを凍結する、の 3 つである。

**人間が書いたイシューがなくてもタスクは作れる。** SWE-bench・SWE-Gym・SWE-rebench は「イシューとそれを直した PR」の組から出発するので、イシューの立っていない修正は使えない。R2E-Gym（[[summaries/2025-r2e-gym]]）は出発点をコミットに移し、問題文を LLM に逆に書かせた（逆翻訳, back-translation）。コード変更だけを見せると中身のない一般的な文になるので、修正前に落ちるテストとそのエラーメッセージも見せる。人間のバグ報告にも失敗するテストや実行の痕跡が含まれていることが多い、という観察にもとづく。軌跡 400 本ずつで比べると、実際のイシューで訓練して 28.0%、合成したイシューで 27.8% だった。ただし環境づくりは半手動のままで、著者ら自身がスケールさせにくいと書いている。

**もう 1 つの軸は「環境が先か、タスクが先か」である。** SWE-bench・SWE-Gym・SWE-rebench は、まず実際の PR（タスク）を集め、PR ごとに当時の依存関係の環境を作る。SWE-smith（[[summaries/2025-swe-smith]]）はこの順序を逆にした。リポジトリの最新のコミットについて環境を 1 つだけ作り、その中でテストを壊すバグを合成する。古い依存関係を設定する手間（SWE-bench の収集で最も高くつくステップ）が消え、同じリポジトリのタスクは 1 つの環境を共有できるので、5 万件でも 295 GB に収まる（同じ数を SWE-bench の方式で作ると 50〜150 TB と見積もっている）。事例研究では、pallets/flask で SWE-bench の方式が 1 件あたり約 207 分の人手を要したのに対し、SWE-smith は約 10.6 秒・0.006 ドルだった。合成したタスクはリポジトリのテストの 89% を少なくとも 1 回壊し（SWE-bench の同じリポジトリでは 7%）、実際の PR には現れない部分の機能にもモデルを触れさせる。

ただし合成バグには偏りもある。LM に「バグを入れて」と自由に頼むと単純な代入の入れ替えに偏り、訓練の効果も低かった。AST の機械的な変換（コストゼロ）と、関数を一から書き直させる方法は、実際の PR を取り消す方法に近い効果があった。SWE-Lego（[[summaries/2026-swe-lego]]）は実際の PR と合成バグを混ぜ、**バグの種類が補い合う**ことを示した。実データは API の不一致・入力の検証・プロトコルへの準拠が多く、合成データはロジックの誤り・import の欠落が多い。正解パッチの大きさも、実データは平均 3.7 ファイル・138 行、合成データは 1 ファイル・19 行と大きく違う。

**環境には答えが残っていることがある。** SWE-Lego は、エージェントがリポジトリの Git の履歴（将来のコミット）を `git log` で覗いて正解を読む「Git ハッキング」を、訓練の軌跡の生成でも評価でも観察した。訓練環境では、イシューより後のコミットとログを消す（合成タスクは、バグを入れたバージョンが元のバージョンより「新しい」ので履歴を丸ごと消す）必要がある（→ [[agent-evaluation]]）。

環境があっても、**そのまま報酬に使えるとは限らない**。[[summaries/2025-swe-rl-long-context]] は 21,336 件から、次の基準で 7,249 件に絞った。

- **テストを 50 回走らせて結果が揺れるタスクを除く**（外部サービスの呼び出しや浮動小数点の誤差による flaky test）。報酬のノイズを減らすためである。
- 解に固有の識別子名を当てさせるようなタスク（テストが AttributeError・ImportError で落ちる）を除く。イシューの文面からは解けないので、報酬が能力ではなく偶然を測ってしまう。
- イシューの記述が不明瞭なもの、テストパッチに欠陥があるものを LLM の品質スコアで除く。

**報酬の検証可能性は、環境を作っただけでは保証されない**。検証器（ここではテストスイート）そのものの監査が要る。これは下記の設計軸の「検証可能性」の具体例であり、訓練の段取りの側から見た話は [[agent-training]] に置いた。

## 設計軸

環境設計を比較・点検するための軸を、上記の系譜から抽出する。

| 軸 | 問い | 例 |
|---|---|---|
| **検証可能性**（verifiability） | 報酬が客観的に接地されているか | テスト合格率（実行）・独立検証器（AET）・LLM ジャッジのルーブリック（GRM）。**自己申告の完了を信じない** |
| **ハーネスのモジュール性** | 単一ハーネスへ過適合していないか | K3 の white-box 環境が構成を動的に撹乱する |
| **タスク合成** | タスクの分布をどう制御するか | K2 のツール合成／K3 の KG 合成（粒度 × 網羅） |
| **サンドボックスの隔離と再開性** | 探索を安全に許し、中断から再開できるか | AgentENV の microVM ＋ 漸進チェックポイント／DSec の 4 基盤 |
| **報酬設計** | reward hacking をどう防ぐか | K3 の予算ペナルティ（冗長性・過剰思考）／K2.5 PARL の r_finish（spurious parallelism 対策） |

**環境と足場の速さは、訓練の試行回数を直接決める。** SWE タスクの RL では、1 回のロールアウトごとに環境の準備・推論・コード実行・テストが走る。SWE-Effi（[[summaries/2025-swe-effi]]）は、DeepSWE が低レイテンシの独自足場を作り、SkyRL が OpenHands を大きく最適化し、SWE-RL が軽量な Agentless-Mini を使ったうえで実行フィードバックを避けた例を挙げ、**行き詰まった試行が予算の上限まで走る「高くつく失敗」は、推論時だけでなく RL の失敗ロールアウトのコストも押し上げる**と指摘した。AgentENV のチェックポイントと再開の速さ（上記 (5)）は、この訓練側のコストへの対処でもある（→ [[agent-cost-efficiency]]）。

## 訓練する環境と測る環境は別物

**同じ「環境」でも、訓練用と評価用では要件が違う。**

- **訓練環境**は、報酬信号が RL の勾配を歪めない程度に頑健で、タスク分布が能力の成長を駆動し、サンドボックスが探索を安全に許せばよい。多少ノイズがあっても大量に回せば平均化される。
- **評価環境**（[[agent-evaluation]]）は、**汚染されておらず・再現可能で・意図したタスクを捉える**必要がある。ここでの検証器の弱さは「解けたつもりのスコア」を生む（oracle adequacy）。

K3 はこの区別が曖昧になる例でもある。**内製ベンチ（Swarm Bench・Deep Research Bench）で強みを主張する一方、それらは外部再現不可**で、ハーネス割り当ても評価をまたいで不均一である。**「モデルの能力」と「環境・ハーネスの寄与」が混ざる**というのは、[[summaries/2026-code-as-agent-harness]]（ハーネス水準の 6 指標）と [[summaries/2026-externalization]]（転移可能性）が独立に指摘した問題そのものである。**環境を作り込むほど、その寄与を切り分ける評価が必要になる。**
