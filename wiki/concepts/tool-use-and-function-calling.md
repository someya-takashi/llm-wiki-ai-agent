# Tool Use and Function Calling（ツール利用とツール呼び出し）

LLM（Large Language Model, 大規模言語モデル）が**外部のツール——検索 API、計算機、コード実行環境、ブラウザなど——を呼び出して、自分の知識と能力の限界を補う**仕組み。モデル単体では最新情報を知らず、正確な計算が苦手で、外部世界に作用できない。ツール利用はこの 3 つの限界を一度に破る手段であり、[[agent-loop]] における「行動（action）」の具体的な中身にあたる。

歴史的には、(1) プロンプトでテキスト形式の行動を出力させる時代（ReAct 等）、(2) モデル自身にツール呼び出しを学習させる時代（Toolformer 等）、(3) API レベルで構造化された function calling が標準機能になる時代、と発展してきた。

## 代表手法

### ReAct の Wikipedia API — プロンプト時代のツール定義

[[summaries/2022-react]]（2022）は、ツールを **`search[entity]` / `lookup[string]` / `finish[answer]` の 3 つだけ**に絞った Wikipedia API を設計し、few-shot プロンプトの例示だけでモデルにその使い方を教えた。特筆すべきは、このツールが**意図的に弱く**作られていることである。検索は正確なページ名でしか引けず（最先端の検索器よりはるかに弱い）、それゆえモデルは「見つからなかったから類似候補の film の方を検索しよう」のように**言語での推論によって検索を導く**ことを強制される。ツールの弱さが推論を引き出すというこの設計は、ツールとエージェントを一体で設計する後の agent-computer interface の考え方（SWE-agent 等 → [[coding-agents]]）の源流にある。

得られた教訓も具体的である: 検索が有益な情報を返さないことがエラーの 23% を占め、悪い検索結果は推論全体を脱線させる。**ツールの出力の質がエージェントの上限を決める**。

### Toolformer — ツール利用を重みに埋め込む（自己教師あり学習）

[[summaries/2023-toolformer]]（Meta AI, 2023）は、**ツール利用能力をプロンプトでなくモデルの重みに埋め込む**方向を確立した。ReAct が推論時にプロンプトの例示でツールを呼ぶのに対し、Toolformer は**訓練時**にツール使用を学習する——同じ目的への逆の層からのアプローチである。

核心は「どの API 呼び出しを訓練データに残すか」の**自己採点**にある。(1) 各 API の数例デモを含むプロンプトで LM に大量の候補呼び出しをテキスト中へサンプリングさせ、(2) 実行して結果を得、(3) 「呼び出しと結果を与えたときの後続トークンの損失 $L^+$」が「呼ばない/入力だけの損失 $L^-$」より閾値以上小さい（＝**その呼び出しが実際に将来トークンの予測を助けた**）ものだけを残す。残った呼び出しを元テキストに挿入した拡張データで標準の言語モデリング目的でファインチューニングする。人手注釈もタスク固有プロンプトも要らず、訓練信号は**モデル自身のフィードバック（パープレキシティ改善）だけ**。

結果は象徴的で、6.7B の GPT-J をこの方式で鍛えた Toolformer が、**25 倍大きい GPT-3 (175B) を zero-shot の LAMA・数学で上回った**（計算機を 97.9%・QA ツールを 98.1% の例で自発的に使う）。素の言語モデリング能力は劣化せず（API 無効時のパープレキシティは素の GPT-J と同等）、ツール活用は**約 775M パラメータで創発**する（小モデルでは効かない——CoT の創発性と同型）。

設計上の重要な限界が、後のエージェント化の動機を先取りしている: **ツールの連鎖ができない**（各呼び出しが独立サンプリングなので、あるツールの出力を別のツールに渡す例が訓練データにない）・**対話的に使えない**（検索結果が悪くてもクエリを直せない——GPT-3 に QA で負けた主因）・入力あたり最大 1 回。これらは [[agent-loop]] の反復ループと [[reasoning-and-planning]] の計画がまさに解いた問題であり、「単発・独立の呼び出し」から「観測して次を決めるループ」への発展の必然性を示す。なお「行動を目的改善で選別する」フィルタリングの発想は、後の検証可能報酬（[[reinforcement-learning-from-human-feedback]] の RLVR）やツール利用データ合成（[[summaries/2025-kimi-k2]] の棄却サンプリング）の直接の祖先である——Toolformer は勾配でなく**データ選別**でこれを行った。

### Function calling — 構造化されたツール定義

現在の主流は、**ツールを JSON スキーマ（名前・説明・引数の型）で宣言し、モデルが構造化された引数付きの呼び出しを生成する** API レベルの機構である（OpenAI function calling、Anthropic tool use 等。原典未 ingest のため概説のみ）。ReAct の `search[entity]` のような文字列規約と比べ、引数の型検証・複数ツールの並列呼び出し・呼び出し失敗のハンドリングが体系化された。ツールとデータソースの接続を標準化するプロトコルとしては [[model-context-protocol]]（MCP）が登場している。

実装の内側は [[summaries/2025-kimi-k2]]（2025）の付録が具体的に公開している: ツール宣言は特殊トークンで区切られたテンプレートに埋め込まれ、宣言言語には **JSON スキーマより簡潔な TypeScript** を採用（型と制約を短いテキストで表現でき、トークンも節約）。並列ツール呼び出しは 1 応答ターン内の複数呼び出しブロックとして表現され、各呼び出しは `functions.{tool}:{counter}` の一意 ID を持つ。書式エラーは **enforcer**（制約付きデコーディング）で構造的に防ぐ——呼び出し開始トークンが出たら、以降のトークンをテンプレートと宣言スキーマに強制する。

同じ「トークナイザレベルで書式を規定する」設計のオープンな実例が Gemma 4（[[summaries/2026-gemma-4]]）の制御トークン群である: 関数宣言は `<|tool>declaration:...<tool|>`、呼び出しは `<|tool_call>call:...<tool_call|>`、思考トレースは `<|channel>thought ...<channel|>` と、**それぞれ専用の制御トークンで区画化**され、引数内の文字列すら `<|"|>` で括られる。ターン管理（`<|turn>user` / `<turn|>`）や thinking の有効化（`<|think|>`）まで含めて語彙に焼き込まれており、「関数呼び出しはプロンプト規約でなくトークナイザの仕様」という現代の実装形を、公開重みモデルの書式表（テクニカルレポート表11）として確認できる。

3 例目が DeepSeek-V4 の **DSML**（[[summaries/2026-deepseek-v4]]）で、こちらは**書式の構文自体を JSON から XML 型へ変えた**点が特徴的である: `<|DSML|invoke name="$TOOL_NAME">` の中に `<|DSML|parameter name="..." string="true|false">値</|DSML|parameter>` を並べる形式で、文字列はそのまま・その他の型は JSON 値として渡し `string` 属性で区別する。動機は実測に基づく——**「XML フォーマットはエスケープ失敗を効果的に緩和し、ツール呼び出しエラーを減らす」**（JSON では引数内の引用符・改行のエスケープ崩れが定番の失敗源）。K2 が enforcer（制約付きデコード）で書式エラーを**強制的に防ぐ**のに対し、DSML は**エスケープが壊れにくい構文を選ぶ**という予防側の解であり、宣言言語（K2 の TypeScript）・制御トークン（Gemma 4）・呼び出し構文（DSML）という 3 つの設計変数がそれぞれ独立に最適化されている現状がわかる。

### ツール利用能力の製造 — 大規模データ合成

自然データにはツール呼び出しの軌跡がほとんど存在しないため、現代のモデルは**ツール利用を合成データで教えられている**。[[summaries/2025-kimi-k2]] のパイプラインが公開レシピの代表例: GitHub から**実 MCP ツール 3000+** の仕様を取得し、ドメイン階層の進化で**合成ツール 20,000+** を生成 → システムプロンプト×ツール構成で数千のエージェントを作り、**成功基準ルーブリック付き**のタスクを生成 → LLM ユーザーペルソナと**状態を保持するツールシミュレータ**（成功・部分失敗・エッジケースを確率的に生成）で多ターン trajectory を作り、LLM ジャッジがルーブリック採点で合格分だけを残す（＝大規模な棄却サンプリング）。真正性が重要なコーディング系は実行サンドボックス（テスト合格率が ground truth）で補完する。この合成 SFT＋検証可能報酬 RL の組み合わせが、τ²-Bench 66.1・ACEBench 76.5 という当時（2025）の非思考ツール利用 SOTA を支えた。

## 設計上の論点

- **ツールの粒度と数**: ReAct は 3 ツールで足りたが、ツールが増えるほどモデルの選択誤りも増える。ツール説明文の書き方は一種のプロンプト設計である。Manus の実務観察（[[summaries/2025-manus-context-engineering]]）は端的で「**重武装したエージェントはより愚かになる**」——MCP でユーザーが数百の未知ツールを差し込める設計なら特に。
- **削除するな、マスクせよ**: 増えたツールを RAG 的に動的ロード・アンロードするのは 2 重に危険——ツール定義はコンテキスト前方にあるため変更で以降の KV cache が全滅し、過去の行動が「もう存在しないツール」を参照してスキーマ違反・幻覚を招く（[[summaries/2025-manus-context-engineering]]）。Manus の解は**定義を残したままロジットマスクで選択を制御**すること: response prefill の 3 モード（Auto=`<|im_start|>assistant` / Required=`...<tool_call>` / Specified=関数名の先頭まで prefill）を使い分け、**ツール名の一貫したプレフィックス**（`browser_`・`shell_`）で状態機械からグループ単位の制約を可能にする。ツールの命名は表示名でなく**制約の単位**でもある、という設計知見。K2 の enforcer・DSML と同じ constrained decoding の系譜のうち、「可用性の動的制御」に特化した応用形。
- **作用先が自分自身のコンテキストであるツール**: ツールは外界に向くとは限らない。[[summaries/2023-memgpt]]（MemGPT, 2023）は、**自分のコンテキストの編集（working context への書き込み）・外部記憶への退避・履歴のページング検索**をすべて function call として実装し、記憶管理をツール利用の一種に還元した。関数実行のランタイムエラーをそのままモデルへフィードバックして適応させる設計や、`request_heartbeat=true` フラグで**関数実行後に続けて推論するかをモデル自身が宣言する** function chaining も、ここで定式化された（現在の「ツール呼び出しが続く限りループする」実装の原型 → [[agent-loop]]）。ReAct の外向きツール（Wikipedia API）と対をなす「内向きのツール」の系譜であり、発展先は [[agent-memory]]。
- **ACI（Agent-Computer Interface）**: Anthropic の実務指針（[[summaries/2024-building-effective-agents]]）は「ツールの定義と文書に、プロンプト本体と同等のエンジニアリングを注げ」と定式化した。具体策——モデルが「考える」余地のある形式を選ぶ（diff の行数勘定や JSON 内エスケープのような**書式オーバーヘッドを排す**）、モデルが自然に見てきたテキストに近い形式にする、ジュニア開発者向け docstring のつもりで説明を書く、実際の誤用を観察して反復する、Poka-yoke（誤りを構造的に犯しにくくする）する。研究では推論を引き出すために意図的に弱いツールを使った（ReAct）のに対し、本番では誤りを減らすためにツールを磨く、という対照も設計判断の参考になる。
- **説明文の品質が外部化される — MCP 時代の課題**: [[model-context-protocol]]（MCP）でツールが外部サーバーから供給されるようになると、エージェントは**品質の激しくばらつく説明文を持つ見たことのないツール**に遭遇する——ACI のエンジニアリングを自前で統制できなくなる。Anthropic Research の実務（[[summaries/2025-multi-agent-research-system]]）はこれに 2 段で対処した: (1) 「まず全ツールを確認する」「ユーザーの意図にツールを合わせる」「汎用より専門ツールを優先する」等の**選択ヒューリスティクスをプロンプトに明記**する。(2) 欠陥のあるツールを何十回も試して**説明文を書き直す「ツールテスト用エージェント」**を作る——書き直された説明文を使う後続エージェントのタスク完了時間は **40% 減**った。ツール説明文の改善がプロンプト改善と同等以上のレバーであることの定量的な実証である。
- **検索ツールとの関係**: 「検索して結果を根拠に答える」というツール利用の最頻出パターンは、[[retrieval-augmented-generation]]（RAG）をエージェントのループに埋め込んだものと見なせる。RAG の原典（[[summaries/2020-rag]], 2020）は検索を**訓練時の潜在変数**として組み込み、幻覚の減少と索引差し替えによる知識更新を実証した——ReAct はその 2 年後、同じ目的を**推論時のループ内ツール呼び出し**として実現しており、「同じ目的、逆の層」の対になっている。「内部知識で足りるか、検索すべきか」の切り替えは ReAct のフォールバックが原型。
- **安全性**: ツールは外部世界への作用を意味するので、危険な行動を行動空間に含めない設計（ReAct は閲覧のみで Wikipedia を編集できない）、権限の最小化、実行前の人間の承認が基本になる → [[agent-safety-and-guardrails]]。
- **マルチエージェント下の function call loop**: 単一エージェントでは「呼び出し → 結果 → 続きを生成」のループはトランスクリプトが 1 本なので自明だが、複数エージェントが同じ環境に対してツールを呼ぶ構成では、**どのエージェントが発行した呼び出しかを追跡し、結果を正しい発行元に返す**ルーティングと、エージェント間でツール呼び出し履歴をどこまで共有するかの設計が必要になる。[[summaries/2026-sakana-fugu]] の Fugu-Ultra は「現在のワークフロー内は隔離（orchestration collapse 防止）・過去のワークフローの履歴は共有（重複探索の防止）」という切り分けでこれを解いた → [[multi-agent-systems]]。
- **並列ツール呼び出し**: 複数の独立な検索・取得を逐次に発行するのは、エージェントの体感速度を最も悪化させる要因のひとつ。Anthropic Research は「サブエージェント 3〜5 体の並列生成 × 各エージェント 3 つ以上のツールの並列呼び出し」の 2 段の並列化で、複雑なクエリの所要時間を**最大 90% 削減**した（[[summaries/2025-multi-agent-research-system]]）。function calling の API 設計（複数呼び出しの同時発行）が性能に直結する例である。
