# LLM Programming Systems（LLM プログラミングシステム）

**LLM プログラミングシステム**とは、**LLM の生成過程を制御するプログラムを書くための言語・実行系**である。SGLang・LMQL・Guidance・DSPy・LangChain がこの層に属する。

このページが独立して立つのは、**LLM の使われ方が変わったから**である。[[summaries/2023-sglang]] の言い方を借りれば——

> **こうした複雑なパターンの出現は、LLM との相互作用における転換を意味する——単純なターン制のチャットから、より洗練された LLM のプログラム的利用への転換である。**

**「LLM のプログラミング（Programming LLMs）」とは、LLM の生成過程を制御するコンピュータプログラムの開発を指す。** そこには 3 段階ある。

1. **単純なプロンプト技法** — few-shot・chain-of-thought・検索拡張生成。これも LLM プログラミングの基本要素である。
2. **高度なプロンプト技法** — meta-reasoning（複数解を生成してメタ推論）、skeleton-of-thought（骨格を作って並列に肉付け）、tree-of-thought（LLM 呼び出しを木探索へ組み込む）。→ [[reasoning-and-planning]]
3. **エージェント** — ReAct のように、**制御フローがループと条件文で決まり、各反復で行動の種類を選び、パラメータを生成し、外部環境からの観測を処理する**。→ [[llm-agents]]

**決定的なのは、これらがいずれも複数の——しばしば依存し合う——生成呼び出しを要し、しかも制御フローが LLM の出力に依存しうる**という点である。

## なぜ独立した層なのか — フロントエンドとバックエンドの分断

[[summaries/2023-sglang]] の診断が、この層が存在する理由を最もよく説明している。

> **フロントエンドとバックエンドの技術はどちらも急速に進歩しているが、別々の軌道で進化している。フロントエンドは LLM の推論の過程をほとんど意識せず、バックエンドはしばしばアプリケーションの構造を認識できず複数の呼び出しにまたがる最適化ができない。**

| | 代表 | 問題 |
|---|---|---|
| **フロントエンド** | LangChain・LMQL・Guidance・DSPy | 主眼が言語設計にあり、**ランタイムの性能が犠牲になる** |
| **バックエンド** | TensorRT-LLM・TGI・Orca・vLLM | 設計が**単一生成呼び出し**のインターフェースに根ざし、**ステートレス**に応答を返す |

**この分断が、逃されている最適化の正体である。** 具体的には 5 つ（[[summaries/2023-sglang]] §2.3）:

| 機会 | 内容 |
|---|---|
| **Caching** | 連鎖した呼び出しにまたがって計算済み KV キャッシュを再利用する。ただし追加の記憶域と複雑なメモリ管理を要する |
| **Batching** | decode はメモリ律速なので、多数のプログラムをバッチで走らせるとスループットが伸びる |
| **Sharing** | 単一プロンプトからの複数出力、状態からの fork。**不規則な木構造の共有**のような高度なパターンもある |
| **Parallelism** | 依存グラフから独立な呼び出しを同定して並列実行する（**プログラム内並列性**） |
| **Compilation** | プログラムを最適化された IR へコンパイルする。**プロンプト自体の自動調整**まで射程に入る |

そして——**「既存システムのいずれも、（KV キャッシュ共有の 4 つの典型パターン）すべてを自動的に扱うことはできない」**。

**バックエンド側の最適化は [[llm-serving-systems]] が扱う。本ページは「プログラムの構造をどう表現し、その構造をどうランタイムへ伝えるか」を扱う。**

## 層の地図

[[summaries/2023-sglang]] 自身が層を描いている。

| 層 | 代表 | 粒度 |
|---|---|---|
| **最上層** | **LangChain** | あらかじめ組まれたモジュールを持つ高水準のアプリケーション開発ライブラリ |
| **中間層** | **DSPy** | より柔軟なパイプラインプログラミングのフレームワーク |
| **中間〜最下層** | **SGLang** | 言語とランタイムの協調設計 |
| **最下層** | **LMQL・Guidance** | 単一のプロンプトの制御のための DSL |

**LangChain と DSPy の高水準パイプラインを SGLang へコンパイルすることは可能である**と論文は述べており、層が互いに排他でないことを示している。

エージェントの構築フレームワーク（LangGraph・AutoGen・CrewAI・Claude Agent SDK）はさらに上の層にあり、[[agent-frameworks]] が扱う。**本ページはその下、「1 つの LLM プログラムをどう書き、どう速く実行するか」の層**である。

### 3 つの DSL の比較

| | LMQL | Guidance | SGLang |
|---|---|---|---|
| 構文 | **カスタム**（SQL 風） | Python | Python |
| プリミティブ | extend, gen, select | extend, gen, select | extend, gen, select, **fork, join** |
| バックエンド | HF Transformers, llama.cpp, OpenAI | ＋ VertexAI | **SGVM**, OpenAI, Anthropic, TGI\*, llama.cpp\* |
| 実行モード | コンパイラ | インタプリタ | **インタプリタとコンパイラの双方** |

（\* は実験的。出典: [[summaries/2023-sglang]] の Table 1）

**SGLang の独自性は `fork` / `join` と、インタプリタ＋コンパイラの両モードにある。** Guidance は当初 Handlebars のテンプレート言語を使い、後に Python 埋め込みへ移行した。SGLang のフロントエンドは Guidance に着想を得ており、Guidance の新版と並行して開発された。

## プリミティブ — 何を言語にするか

SGLang のプリミティブは 5 つしかない。**少なさが設計の主張である。**

| プリミティブ | 役割 |
|---|---|
| `gen` | LLM の生成を呼び、結果を変数に格納する |
| `select` | 選択肢の一覧から**最も確率の高いものを選ばせる**（logit bias を自動構築） |
| `+=` / `extend` | 現在のプロンプトを拡張する |
| **`fork`** | プロンプトの状態を並列に分岐させる |
| **`join`** | 分岐した状態を再結合する |

これらを**任意の Python の制御フローとライブラリと交錯させられる**ことが、DSL を埋め込みにした理由である。

**`select` が地味に効く。** 生産性の比較（OpenAI API 206 行 → SGLang 91 行、**55% 削減**）で挙げられた 3 つの理由のうち 2 つがプリミティブに由来する——(1) 応答から内容を手で抽出して連鎖させる代わりに文字列連結の演算子が使える、(2) **true/false や整数のような制限された答えのために logit bias を手で構築する代わりに、許容されるデータ型と選択肢を指定するだけでよい**、(3) **`fork` が自動的にリクエストを並列化する**のでスレッドプールを書かなくてよい。

> **(2) は [[tool-use-and-function-calling]] と直結する。** ツール呼び出しの引数を型と列挙値で縛ることは、正しさの機能であると同時に、**制約で一意に定まるトークンを LLM に予測させずに済ませる高速化**でもある（→ [[llm-serving-systems]]）。

## インタプリタ — プロンプトを非同期ストリームとして扱う

SGLang のインタプリタの設計が、この層で最も転用しやすい着想である。

**プロンプトを非同期のストリームとして扱う。** `extend`・`gen`・`select` の実行は、そのストリームへ演算を**投入**することであり、**ノンブロッキング**である。Python 側は生成の完了を待たずに次のコードを実行できる。各プロンプトはバックグラウンドスレッド内のストリーム実行器が管理する。

論文の比喩がそのまま分かりやすい——**「CUDA のカーネルを CUDA のストリームへ非同期に起動するのに似ている」**。

結果を取得するときだけブロックする（イベント機構で、生成呼び出しが出力を作った時点でイベントを設定する）。これで**プログラム内並列性と同期がユーザーの手を離れて管理される**。

**ユーザーが `threading` や `asyncio` を書かなくてよくなる**のが実利で、論文は公平な比較のために「SGLang のプログラムを threading や asyncio を明示的に使わずに等価な Python へ翻訳した」結果、**翻訳版は並列化可能なリクエストを並列化せずレイテンシが高くなった**と報告している。

## コンパイラ — プログラムをグラフにする

もう 1 つの実行方法が、**プログラムをトレースして計算グラフへコンパイル**し、グラフ実行器で走らせることである。

**IR ノード**: ConstantText・Argument・Gen・Select・Variable・Fork・GetForkItem・Join。

**依存関係は 2 種類**:
- **ストリーム内依存** — `+=` で投入された演算は、そのストリーム内の先行するすべての演算の後に実行される
- **ストリーム間依存** — あるストリームが別のストリームから変数の値を取得するときに生じ、同期を要する（`fork` が導入する）

<figure>

![](../../raw/assets/2023-sglang/x5.png)

<figcaption>図2: SGLang プログラムに対応する計算グラフ。3 つのストリームが 3 つの関数呼び出しに対応する。出典: [[summaries/2023-sglang]] の Figure 5。</figcaption>
</figure>

**コンパイルの利点**は、グラフ書き換えの最適化・ランタイムのオーバーヘッド削減・**プログラムの直列化**である。

**限界も明確である——トレースはデータ依存の制御フローを持つプログラムに使えない。** これは著者自身が §7 で挙げる制限であり、**エージェントの制御フローは定義上 LLM の出力に依存する**ので、緊張がある。本論文のエージェントの成果（後述の 5.6 倍）は**インタプリタ側の成果**であって、コンパイラのものではない。

### GPT-4 にコンパイラ最適化をさせる

**この層で最も異色な着想である。**

最適化そのものは古典的な**コード移動**で、**グラフのノードを並べ替えて定数 prefix を長くする**。

```
変更前: "Here is a question + {question}. Please act as a math expert and solve the given question"
変更後: "Please act as a math expert and solve the given question. Here is a question + {question}."
```

後者のほうが共有可能な prefix が長い。**なぜ GPT-4 が要るのか**の理由が本質的である。

> **この最適化が興味深いのは、SGLang には自然言語の指示が含まれるため、伝統的なプログラム解析では達成できないからである。**

並べ替えが意味論を保つかは、**プロンプトの自然言語としての意味を理解しないと判定できない**。だから GPT-4 に few-shot で SGLang の IR の概念を教えて並べ替えさせる。

**結果**: 15 テンプレート中 **12 件成功**、共有可能 prefix が**平均 +60 トークン**。失敗の型も具体的で、**「積極的すぎて、順序の変更が元の意味論を変える場合であってもすべての定数を前へ持ってきてしまう」**。

**この最適化は元の計算を厳密には保存しない**ので、著者は「積極的な（aggressive）」最適化に分類し、「信頼できるものにするにはさらなる作業が必要」と留保している。**本番で自動適用するには早い。**

もう 1 つの最適化 **プリフェッチの注釈**は、頻繁に使う長いプロンプトを CPU にキャッシュしておき、コンパイラがプリフェッチノードを挿入する。ランタイムはそのノードで radix tree からノードを退避し、キャッシュされた prefix を swap in する。**退避のコストは大幅に重ね合わせられる**ので、**4k の prefix で最初のトークンのレイテンシが 1 秒 → 0.2 秒（80% 削減）**。

## 何が速くなるのか — 協調設計の効果

言語側の設計がランタイムに伝わることで何が起きるかが、実測で示されている（対 vLLM。→ [[summaries/2023-sglang]]）。

| ワークロード | 効果 | 効いた仕組み |
|---|---|---|
| **ReAct エージェント** | **スループット 5.6 倍・レイテンシ 13%** | 状態の追記による prefix 再利用 |
| few-shot（MMLU / GSM-8K） | **4.4 倍 / 4.5 倍** | 共有 prefix の自動再利用 ＋ batching |
| HellaSwag | **2 倍** | `select` プリミティブ（vLLM は各選択肢をプロンプトと連結して冗長計算する） |
| 推論（multi-chain / ToT） | 改善するが幅は小さい | **ゼロショットは共有可能 prefix が短い** |
| 長文書処理 | 1.2 倍 / 2.9 倍 | KV キャッシュ再利用（バッチサイズ 1 なのでレイテンシ改善＝スループット改善） |
| 生産性 | **206 行 → 91 行（−55%）** | 文字列連結・`select` の logit bias 自動構築・`fork` の自動並列化 |

**「vLLM の API では支えられない」という指摘が繰り返し出る。** multi-chain reasoning で誘導プロンプト（"Think step-by-step"・"Take a deep breath"）を変えながら複数解を生成する場合、**単純な並列サンプリングと違って柔軟な prefix 共有が要る**ので、vLLM の API では表現できない。**言語側で表現できないものは、ランタイムが最適化できない**——これが協調設計の主張の核である。

## 構造化出力 — 正しさと速度の両方

`select` や JSON スキーマ・正規表現・文脈自由文法による**制約付きデコーディング**は、この層の主要な機能である。

- **正しさの側面**: ツール呼び出しの引数を型・列挙値で縛る（→ [[tool-use-and-function-calling]]）
- **速度の側面**: **制約で次のトークンが一意に確定する箇所は LLM を呼ぶ必要がない**（→ [[llm-serving-systems]]）

**なお SGLang 論文の時点では文法制約付きデコーディングは未実装である**（§7 の限界に明記）。[[llm-serving-systems]] が構造的デコーディングの高速化の根拠として引く compressed-FSM は、**本論文より後**の仕事である。**この層は動きが速く、論文の時点と現在の実装が乖離しやすい。**

## 設計論点

- **プログラムの構造をランタイムへ伝えられているか。** 本ページの中心的な問いである。フロントエンドが構造を知りバックエンドが知らないなら、**キャッシュ・共有・並列化の機会は落ちる**。
- **「自動的に扱えるか」を機能の評価軸にする。** SGLang が vLLM に対して立てた差は速度でなく**自動性**だった——vLLM の prefix 共有は手動設定を要し、公開コードでは動かなかった（→ [[summaries/2023-pagedattention]] の限界）。**手動で設定すれば同じことができる、は同じではない。**
- **定数を前、可変を後ろ。** コンパイラ最適化として自動化されたが、手で書く場合も同じ原則が効く。**プロンプトの並べ替えが直接コストになる**（→ [[context-engineering]]）。
- **プリミティブは少なく、宿主言語の制御フローに任せる。** SGLang が 5 つのプリミティブで済ませ Python の制御フローと交錯させたのは、DSL 設計として学ぶところが多い。カスタム構文（LMQL）は表現力を上げるが可搬性と学習コストを損なう。
- **自然言語を含むプログラムには従来のプログラム解析が効かない。** これは SGLang 固有でなく、**プロンプトを含むコードベース全般**に当てはまる観察である。静的解析・リファクタリング・テストのいずれもこの制約を受ける。
- **コンパイラとエージェントは相性が悪い。** データ依存の制御フローを持つプログラムはトレースできない。**エージェントの制御フローは定義上 LLM の出力に依存する**ので、当面はインタプリタ側の最適化が主戦場になる。
- **この層の記述は陳腐化しやすい。** LMQL・Guidance・SGLang はいずれも活発に開発されており、論文時点の比較表は半年で古びる。**層の分け方と設計原則のほうが持ちが良い。**

## 本 wiki における根拠の薄さ

**現時点で一次資料は [[summaries/2023-sglang]] の 1 本だけである。** LMQL・Guidance・DSPy・LangChain についての記述はすべて、SGLang 論文が §2.4 と Table 1 で述べた範囲に依拠しており、**競合が自己申告する内容とは照合していない**。とくに:

- **DSPy** は「柔軟なパイプラインプログラミングのフレームワーク」としか書かれておらず、その中心的な着想（プロンプトの自動最適化）は本 wiki に入っていない。
- **LangChain** は [[agent-frameworks]] と [[model-context-protocol]] で言及されるが、原典は未取得である。
- **Guidance / LMQL** の比較は SGLang 側の記述であり、**利害関係がある**（SGLang は自らを両者の改良として位置づけている）。
