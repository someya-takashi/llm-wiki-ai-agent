# Agent Skills（エージェントのスキル）

**スキルとは、あるタスクの*クラス*をどう遂行すべきかという手続き的な専門性（procedural expertise）を、発見・ロード・改訂・合成できる明示的な成果物へ包装したもの**である。`SKILL.md`・`AGENTS.md`・指示ファイル・マニフェスト・組織の SOP（Standard Operating Procedure, 標準作業手順）テンプレートがその具体的な形にあたる。

**このページを独立させる理由は、スキルがツールでもプロンプトでもない固有の層だからである。** 最も明快な線引きは [[summaries/2026-externalization]]（上海交通大学ほか, 2026）が与えた。

> **ツールは*操作*を露出させ、プロトコルはそれらの操作が*どう記述され呼び出されるか*を統べ、スキルはあるタスクの*クラス*がそれらを使って*どう実行されるべきか*を符号化する。**

**スキルが解こうとしている失敗は「能力の欠如」ではなく「*分散*（variance）」である。** モデルは原理的にはタスクの解き方を知っていても、同じプロンプトが実行をまたいで異なる分解・分岐の決定・停止条件を生む。**症状は、飛ばされたステップ・不安定なツール使用・一貫しない停止条件として現れる。** したがって表現の転換は「**反復的な合成から再利用可能な手続きへ**」——ランタイムにモデルが直面するタスクを、**ワークフローを発明することから、ワークフローを選んで従うことへ**変える（→ [[harness-engineering]] の「なぜ外部化が効くのか」）。

## スキルは何を包むのか — 3 つの成分

[[summaries/2026-externalization]] §4.1 の分解。**3 つすべてが揃って初めてスキルは再利用可能になる。**

| 成分 | 中身 | 落とすとどうなるか |
|---|---|---|
| **運用手順**（operational procedure） | タスクの骨格——ステップ・フェーズ・依存関係・**停止条件** | 過程が不安定になる。「多くの誤りは行動水準の無能力からではなく**過程の水準の不安定さ**から来る」 |
| **判断ヒューリスティクス**（decision heuristics） | 分岐での局所方策——**何を最初に試すか・いつ引き下がるか・どんな証拠で十分か・どのトレードオフが好まれるか** | 分岐のたびにモデルが局所方策を再発見する。ヒューリスティクスは**専門家のスタイル**を捉える主要な手段であり、二次的な便宜ではない |
| **規範的制約**（normative constraints） | 受け入れ可能性の条件——テストの要件・スコープの制限・アクセスの制約・追跡可能性・領域固有の運用ルール | 「ワークフローは技術的に有効でありながら、なお非準拠・非安全・運用上誤りでありうる」 |

**規範的制約の扱いが設計上とりわけ重要である。外部化されると、それは*事後の評価基準であることをやめてスキルの一部になる***——事前条件を形作り、安全でない分岐を遮断し、中間の検証を要求し、完了の前に生成されなければならない証拠を定義する。**これがスキルを、能力の担い手であると同時に*統治の担い手*にする** → [[agent-safety-and-guardrails]]。

## どこから来たのか — 3 段階の進化

**スキルはツール使用の言い換えではない。** それは 2 つの先行する発展の下流にあり、**単位が変わった**ところで始まる。

| 段階 | 単位 | 代表 | 達成したこと／しなかったこと |
|---|---|---|---|
| **1. 原子的な実行プリミティブ** | **行動プリミティブ** | [[summaries/2023-toolformer]]・function calling | いつ呼ぶか・引数をどう構成するか・結果をどう取り込むかを学習した。**タスクのクラスのための再利用可能な手続きは提供しない** |
| **2. 大規模なプリミティブの選択** | **ツール** | Gorilla・ToolLLM・ToolNet・ToolScope | 大きなツール群からの検索・順位づけ・動的な選択。**ノウハウはなおプロンプトかパラメータの中に暗黙のまま** |
| **3. 包装された専門性としてのスキル** | **手続き** | Claude Code の `SKILL.md`・SOP-Agent・プログラム的スキル帰納・PolySkill | 「**何ができるか**」ではなく「**どう遂行されるべきか**」を包装する |

> **「第 3 段階は単にツール使用をより複雑にするのではなく、エージェントの能力を*外部化された再利用可能な手続き的ノウハウ*として表現する方向への転換を反映している。」**

**この段階分けは [[tool-use-and-function-calling]] の内容の直接の続きである**——同ページが扱う Toolformer と Gorilla が段階 1・2 にあたり、本ページが段階 3 を引き受ける。

## どう外部化するのか — 5 つの機構

**「指示を書き下す」だけでは外部化は完了しない。** ランタイムが**いつロードするか・どの記憶に条件づけるか・どのツールへ束縛するか**を決められて初めてスキルは現実になる。

### (1) 仕様（Specification）

**スキルの仕様は API の実装というより API のドキュメントに似ている。** その価値は、手続き的な専門性を不透明な内的状態から、**検査され・議論され・改訂され・統治されうる明示的な対象**へ変えることにある。

**よく形成された仕様が覆うべき 5 種の情報**（そのままテンプレートの記入欄になる）:

1. **能力の境界** — 何をするスキルか
2. **適用可能性のスコープ** — どんな種類の問題を解くのか
3. **事前条件** — いつ安全に使えるか
4. **実行の制約** — どんな運用上の仮定のもとで作動するか
5. **例と反例** — 意図された使用パターンを具体例に錨づけし、**モデルによる過少規定された解釈を減らす**

### (2) 発見（Discovery）

スキルが明示的な成果物になると、**登録と発見**の問題が生じる。ローカルなリポジトリ・組織のレジストリ・プラットフォーム水準のマーケットプレイスへ公開し、タスクの目標・文脈の状態・環境の条件にもとづいて候補を探索する。

**ここでの設計上の勘所は、スキルの発見が単なる意味検索ではないことである。**

> **「スキルは、そのキーワードがタスクの記述と重なるからではなく、現在のタスクの意味的かつ運用的な構造と*真に両立するから*検索されるべきである。」**

考慮すべきは**トピックの類似度だけでなく、タスクの複雑さ・環境の仮定・運用上の制約・リスクの条件**である。**保存しただけでは外部化は不完全で、現実的なタスク条件のもとで検索可能でなければならない。**

### (3) 段階的開示（Progressive Disclosure）

**発見されたからといって全文を文脈へ入れてよいわけではない。長い文脈は確実により良い性能へ翻訳されないので、詳細な指示は指針の源ではなく*推論のノイズ*の源になりうる。**

産業実装の層構造は 3 段である。

| 水準 | 露出させるもの | 目的 |
|---|---|---|
| 最小 | **名前 ＋ 短い記述** | その能力が存在することを知らせる |
| 中間 | **マニフェスト的情報**——適用可能性の条件・必要な前提・主要な制約 | 適用可否を判断させる |
| 最深 | **完全なガイド**——詳細な手順・例外処理・例・補助ファイル | 実際に遂行させる |

> **「目的は単に文書を圧縮することではない。より根本的には、それは『さらなるスキルの詳細が必要か』という問いを、それ自体としてのランタイムの決定へ変える。」**

**この設計は Claude Code のスキル系で最も可視である**——[[summaries/2026-dive-into-claude-code]] の解剖によれば、`SkillTool` は**名前でスキルを起動してその指示を現在のコンテキストウィンドウへ注入する**メタツールで、**コンテキストコストは「低」（frontmatter の記述のみ）** に分類される。同じメタツールの形をとる `AgentTool`（新しい隔離されたウィンドウを生成する。コスト「高」）との対比が、段階的開示の実装上の意味を明確にする → [[agent-frameworks]] / [[context-engineering]]。

### (4) 実行のバインディング（Execution Binding）

**スキルは通常それ自体が行動の実行器ではない。** ツール・ファイル・API・サブエージェント・プロトコルのエンドポイントといった**より低水準のランタイム基盤へ束縛されなければならない**。

> スキルは「関連するコードを検索し、テストを走らせ、結果の diff を要約せよ」と規定しうるが、**行動そのものは検索ツール・ファイル操作・シェルコマンド・テストランナーによって遂行される。**

**このバインディングには中間の解釈層が要る**——現在の文脈でどのステップが活性化されるべきか・どのプリミティブが束縛されるべきか・どの条件が分岐を起こすべきか・どの制約が優先されるべきかを決める層である。**それがなければ、スキルは「原理的には読めるが実践では使えない静的な成果物」に留まる。** [[model-context-protocol]] のようなスキーマにもとづくインターフェースは、**スキルをツールやプロトコルへ畳み込むことなく**このバインディング層を支える。

### (5) 合成（Composition）

**合成できて初めてスキル系は本領を発揮する。** パターンは**直列実行・並列の分業・条件つきのルーティング・部分スキルの再帰的な呼び出し**。

**合成は単なる断片の連結ではなく、手続き的専門性そのものの高水準の再利用である。** データ分析レポートのスキルは、モノリシックな端から端までの手続きである必要はなく、**データのクリーニング・統計分析・可視化・叙述の統合**のより小さなスキルの協調として組織できる。得られるのは性能だけでなく**保守性・置換可能性・監査可能性**である。

> **「合成は、スキルが孤立したレシピの寄せ集めではなく*真の能力の層*になる点を印づける。」**

## どう獲得するのか — 4 つの経路

| 経路 | 中身 | 本 wiki の関連 |
|---|---|---|
| **Authored**（著される） | 人手による `SKILL.md`・`AGENTS.md`・SOP テンプレート。**「エージェントが配備で失敗のパターンを繰り返し示すとき、エンジニアは対応するスキルを更新して、観測された 1 つの失敗を明確化された手続きあるいは追加された制約へ変えられる」**——運用経験を再利用可能な行動の構造へ変える実践的インターフェース | [[harness-engineering]] の「人手で作る」 |
| **Distilled**（蒸留される） | 軌跡・実践のトレース・保存された経験から帰納。**「記憶は経験を保存し、スキルの帰納はその中の再利用可能な構造を抽出する」**。Skill Set Optimization は報酬のある部分軌跡から転移可能なスキルを抽出、MemSkill は記憶操作自体を学習可能なスキルとして再定式化 | [[agent-memory]] / [[self-reflection]] |
| **Discovered**（発見される） | 環境との相互作用からの自律発見。**Voyager** が Minecraft で**探索・実行フィードバック・自己検証・カリキュラム駆動のタスク選択**により実行可能なコードのスキルライブラリを成長させた。PolySkill は**抽象的な目標を具体的な実装から分離**して再利用を改善 | [[llm-agents]] のライフサイクル指向エージェント |
| **Composed**（合成される） | 既存スキルの組み合わせが繰り返し有効だと検証されると、**その組み合わせ自体が新しい高水準スキルとして包装される**。平坦なリストではなく**階層的なレパートリー**が育つ | 上記 (5) 合成 |

> **「成熟したスキル系は、それがどれだけ多くの指示を保存するかによってではなく、*どれだけ効果的に経験を再利用可能な外部化された専門性へ変えるか*によって定義される。」**

ハーネスの中では、この進化のループ自体が体系化される——**記憶が証拠を提供し、評価器が何が昇格に値するかを決め、プロトコル化された実行面が候補スキルが実際に配備されうるかを決める。**

## 何が壊れるのか — 4 つの境界条件

**スキルはひとたび書かれれば安定したままの自己充足的なモジュールではない。** ここは実務で最も効く節であり、[[summaries/2026-externalization]] が証拠の強さを段階的に自己申告している点でも信頼できる。

### (1) 意味的な整合（semantic alignment）

**モデルはスキルの文字どおりの文言に従いながら、なおタスクの真の目的を取り逃しうる。** 仕様は自然言語あるいは軽量な構造化形式で意図を表現するが、実行は具体的なツール・API・環境の制約に依存するからである。

**SkillProbe は「意味と振る舞いの不整合」を既存のスキル・マーケットプレイスにおける根本的な欠陥として同定している。** 関連するツール使用の意思決定の研究も、**鍵となる困難がしばしば「外部の能力を*呼べるか*」ではなく「タスクの現在の解釈のもとでそれを*呼ぶべきか*」である**ことを示す。

### (2) 可搬性と陳腐化（portability and staleness）

**スキルが内的に首尾一貫していても、環境をまたいだ妥当性は前提にできない。** Web サイト・API・依存・ワークフロー・ランタイムの慣習が変われば、かつて有効だったスキルは部分的に誤解を招くか完全に時代遅れになる。**さらにエージェントの枠組み・ツールの基盤・基盤モデルの異質性が、同じスキルが設定をまたいで一貫して振る舞わないことを意味する。** SkillsBench は**スキルの有用性が領域とモデル–エージェント構成をまたいで実質的に変わる**ことを示す。

> **「スキルの可搬性は、外部化の内在的な特徴としてではなく*条件つきの経験的な性質*として扱うのが最もよい。」**

これは [[harness-engineering]] の「**すべての部品はモデルが単独でできないことへの仮定であり、モデルの改善で陳腐化する**」の、スキル層における具体化である。

### (3) 危険な合成（unsafe composition）— 最も証拠が強い

**孤立して無害に見えるスキルが、組み合わされたときに危険に相互作用しうる。** とりわけ長文の指示・実行可能なスクリプト・外部の依存を束ねているときに。**問題は単一のスキル成果物に限定されず、複数の成果物とそれらを繋ぐインターフェースの間の相互作用から創発する。**

**ここは推測ではない。公開スキル・エコシステムの大規模な経験的研究が、プロンプトインジェクション・データ流出・権限昇格・サプライチェーンのリスクを含む脆弱性を実質的な割合で報告している。攻撃指向の研究はさらに、スキルのファイルそれ自体が現在のエージェントにとって現実的なプロンプトインジェクションの面になりうることを示している。**

> **スキルの合成は、純粋に無害なモジュール的再利用の形ではなく、*セキュリティに敏感な過程*として扱われるべきである。**

**[[summaries/2026-code-as-agent-harness]] が引く OpenClaw の「Lethal Trifecta」**——**機微なデータへのアクセス ＋ 制約のない外部通信 ＋ 検証されていない実行**——が、**手続きの指針そのものが健全でも制約のない実行はなお安全性の問題であり続ける**ことを例示する。**だからプロトコル水準の検証は、スキル自身の正しさとは独立の境界の検査として要る**——よく書かれたスキルでさえ、禁止された操作を試みれば遮断されるべきである → [[agent-safety-and-guardrails]] / [[llm-red-teaming]]。

### (4) 文脈依存の劣化（context-dependent degradation）

**2 方向の劣化がある。**

- **スキルのファイルを更新しても、エージェントは古い運用ロジックに従い続けうる**——残存するセッションの文脈・キャッシュされた要約・以前に強化された行動パターンのために。
- **詳細なスキルのガイドが大域的なタスクの追跡を妨げうる**——あまりに多くの局所的な手続きの詳細が文脈へ注入されると、**モデルは指示を注意深く実行しながら真の成功条件を見失う**。

**著者らはこの項目について「スキル固有の直接の証拠はまだ限られている」と明記しており**、多ターンのドリフト・長期ホライズンの信頼性・長文脈の推論に関する隣接の仕事からの推論であると断っている。**したがってスキルのロードは検索の問題としてだけでなく、*文脈の配分と実行の安定性*の問題としても扱われるべきである** → [[context-engineering]]。

## ハーネスの中のスキル — 4 つの結合

**スキルは単体の成果物として評価できない。** 稼働する系の内側でどう位置づけられるかが信頼性を決める。

- **記憶への条件づけ** — ハーネスが記憶にタスクの履歴・過去の結果・ユーザー固有の文脈を問い合わせ、**どのスキルをロードするか・どのパラメータを実体化するか・どの分岐を好むか**を決める。**この条件づけがなければ、スキルの選択はタスク記述に対するキーワード照合へ退化する。** → [[agent-memory]]
- **プロトコルを通じたバインディング** — 選択されたスキルは、ツールのスキーマ・サブエージェント委譲の契約・ファイル操作・承認のワークフローを通じて接地される。**「スキルは*何がなされるべきか*を規定し、プロトコルは*結果として生じる行動がどう記述され・呼び出され・統治されるか*を規定する。」** → [[model-context-protocol]]
- **ランタイムの統治** — 機微な操作の前の権限検査、高リスクなステップの承認ゲート、**どのスキルがロードされ何の行動を生んだかの監査ログ**、多段の途中で失敗したときのロールバック。**これらはスキルの成果物の一部ではなくハーネス環境の性質である**——サンドボックスで安全なスキルが本番では追加の制約を要しうる。 → [[agent-safety-and-guardrails]] / [[agent-observability]]
- **ライフサイクルのフィードバック** — 実行のトレース・成功率・失敗のパターン・ユーザーの訂正が記憶へ書き戻され、やがて**スキルの改訂・廃止・新しい候補の昇格**を起こす。**「ハーネスは単にスキルをホストするのではない。それはスキルが改善されるフィードバックのインフラを提供する。」** → [[harness-engineering]]

**この双方向の流れは [[summaries/2026-externalization]] の 6 結合のうち 2 本にあたる。** 特に「**スキル → 記憶（実行の記録）**」の指摘が重要である——**この流れこそがスキル層を単に自己拡張的なものではなく*自己訂正的*にする。記録がなければ、記憶からスキルへの蒸留の経路はますます古びた証拠の上で作動する。**

## 設計論点

- **3 成分を全部書く。** 運用手順だけ書いて判断ヒューリスティクスと規範的制約を落とすのが最もよくある不足である。**分岐での局所方策と受け入れ可能性の条件を落とすと、外部化の利得の半分を捨てることになる。**
- **仕様には反例を入れる。** 5 種の情報のうち**例と反例が最も省かれやすく、最も過少規定な解釈を減らす**。
- **発見を「意味検索」に留めない。** キーワードの重なりではなく、**タスクの複雑さ・環境の仮定・運用上の制約・リスクの条件との両立**で選ぶ。
- **段階的開示を「圧縮」でなく「ランタイムの決定」として設計する。** 3 層に分け、どこまでロードするかをその場で決める。**全部を最初から入れるのは、外部化のつもりで文脈の負荷を作っているだけである。**
- **スキルの合成をセキュリティ・レビューの対象にする。** ここは唯一、**大規模な経験的証拠が既にある**境界条件である。スキルのファイル自体がプロンプトインジェクションの面になる。
- **陳腐化を前提に運用する。** 可搬性は内在的な性質ではなく条件つきの経験的性質である。**モデルが更新されたら、スキルがまだ荷重を支えているかを 1 つずつ確認する**（→ [[harness-engineering]] の「剥がす」）。
- **実行のトレースを書き戻す経路を最初に作る。** これがないとスキル層は自己拡張的にはなっても**自己訂正的にはならない**。
- **スキルと記憶の境界を守る。** 記憶は**過去に何が起きたかの証拠**、スキルは**その証拠が明示的な再利用可能な手続きへ昇格されたもの**。反復する手続き的な規則性は最初エピソード的なトレースの中のパターンとして現れるが、**昇格された時点でそれは記憶の層ではなくスキルの層に属する。**
