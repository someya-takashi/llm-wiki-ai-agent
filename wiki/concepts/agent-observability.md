# Agent Observability（エージェントの可観測性）

**本番で動いているエージェントが、いま何をしていて、なぜそうしたのかを、外から見えるようにする仕組み**の総称。具体的には trajectory（トラジェクトリ, エージェントが辿った観測→思考→行動の系列）のトレース収集、ツール呼び出しの全件ログ、レイテンシ・成功率・コストの計測、そして改変不可能な監査証跡の保全を含む。

## [[agent-evaluation]] との境界

この 2 つは混同されやすいが、**問う時点と目的が違う**。

| | [[agent-evaluation]]（評価） | agent-observability（可観測性） |
| --- | --- | --- |
| いつ | 主に開発時・リリース前 | 主に本番稼働中・事後 |
| 問い | このエージェントは**良いか**（ベンチマークで何点か、どう失敗するか） | いま**何が起きているか**（どこで止まったか、コストはいくらか、方針から逸れていないか） |
| 一次データ | 用意したタスク集合とスコア | 実運用のトレース・ログ・指標 |
| 出口 | 採用・改善の判断 | アラート、インシデント調査、監査対応 |

ただし両者は循環する。可観測性が集めた本番トレースは、[[summaries/2025-masft]] が確立した**トレース分析型評価**の一次データそのものであり、そこから抽出された失敗分布が次の評価軸を決める。「可観測性は評価の入力を作り、評価は可観測性が何を測るべきかを決める」という関係にある。

## なぜエージェントでは固有に難しいのか

従来のソフトウェア監視（リクエスト数・エラー率・レイテンシ）がそのまま通用しない理由が 4 つある。

1. **非決定的である**: 同じ入力でも実行ごとに経路が変わる。[[summaries/2025-multi-agent-research-system]]（Anthropic, 2025）は本番運用の課題としてこれを筆頭に挙げ、**個々の会話内容ではなく「意思決定パターンと相互作用構造」をトレースする**設計に切り替えたと報告している。「同じ入力→同じ出力」を前提とした差分比較が使えないため、**分布として見る**しかない。
2. **エラーが複利で効く**: エージェントは状態を持って多段に進むため、序盤の小さな逸脱が後段で増幅する。同記事はこれに対し、失敗しても最初からやり直さず**エラー地点から再開できるチェックポイント**を置いた。可観測性の側から言えば、「どのステップの状態が保存されているか」自体が監視対象になる。
3. **失敗が静かである**: エージェントは例外を投げずに間違える。停滞（[[multi-agent-systems]] のデッドロック）、早すぎる終了、検証の省略——[[summaries/2025-masft]] の失敗分類のうち **FC3「検証と終了」だけで全体の 31.4%** を占める。スタックトレースは出ないので、**振る舞いの系列を見なければ検知できない**。
4. **多主体になると帰属が壊れる**: 誰のツール呼び出しか、誰の判断が結果を決めたかを追跡しないと、マルチエージェント系では原因の特定ができない（→ [[multi-agent-systems]] の function call の帰属）。

そして 5 つ目として、**アーキテクチャが可観測性を規定する**という点がある。Managed Agents の設計記録（[[summaries/2026-managed-agents]], Anthropic, 2026）は、可観測性を失った構成の実例を率直に書いている。session・ハーネス・sandbox を**単一のコンテナに同居**させていた時期、外から中を見る窓は WebSocket のイベントストリーム 1 本しかなく、それは障害が**どこで**起きたかを教えてくれなかった——**ハーネスのバグも、イベントストリームのパケット喪失も、コンテナのオフライン化も、すべて同じに見えた**。原因を突き止めるにはエンジニアがコンテナ内でシェルを開くしかないが、そのコンテナには顧客データも入っていたため、実質的に**デバッグする能力が無かった**。

ここから 2 つの教訓が引ける。(a) **「障害の種類がすべて同じ症状に見える」状態は、監視ツールの不足ではなく設計の失敗として扱ってよい**。構成要素が分離されていなければ、どんな計装を足しても障害は局在化できない。(b) **可観測性は可用性と同じ理由で分離を要求する**——同記事が brain / session / sandbox を切り離した動機には、落ちても直せるようにすることと並んで、**どこが落ちたか分かるようにすること**が含まれていた。分離後は、コンテナの障害がハーネスから見て**ツール呼び出しのエラー**という明示的な型で観測できるようになっている。

## 何を記録するか — 3 つの層

### (1) 行動ログ（最も硬い層）

**ツール呼び出しは全件ログできる**——エージェントが環境に対して実際に何をしたかは、モデルの内心と違って観測可能な事実である。[[agent-safety-and-guardrails]] はこれを「CoT より硬い監視面」と位置づける: 思考の記述は取り繕えるが、発行されたツール呼び出しとその引数・返り値は残る。環境と相互作用する脅威（ファイル書き込み、外部送信、権限昇格）は、この層で捕まえるのが基本になる。

### (2) 指標（集約して傾向を見る層）

エージェント単位で**レイテンシ・成功率・エスカレーション頻度・トークン消費とコスト**を計装し、**オーケストレーション層で集約する**（[[summaries/2026-agent-orchestration-guide]]）。個々のエージェントが健全に見えてもシステム全体が破綻していることがあるため、集約の粒度が要になる。マルチエージェントではコストが跳ねる——Anthropic Research の実測で**チャット比 15 倍のトークン**——ので、コストは事後の請求書ではなく**リアルタイムの監視項目**として扱うべきである。

関連して、**暴走の上限**は可観測性と一体で設計する。呼び出しの深さ・最大実行時間・リトライ回数に上限を置かないと、エージェントが互いをループ状に呼び出してコストが発散する。監視は「気づく」ためのもので、止めるのは制限側の仕事である。

### (3) 監査証跡（事後に説明するための層）

ここで、**永続ログはデバッグ用の副産物ではなく、実行の一次記録になりうる**。Managed Agents（[[summaries/2026-managed-agents]]）の session は append-only なイベントログとしてハーネスの外に置かれ、ハーネスが落ちても `wake(sessionId)` → `getSession(id)` で最後のイベントから再開できる——つまり**同じログが「事後に何が起きたか読む」ためと「処理を再開する」ための両方に使われる**。トレースを後付けの計装ではなく状態そのものとして設計すると、記録漏れは機能不全として即座に表面化するので、観測の網羅性が構造的に担保される。

**改変不可能（immutable）でタイムスタンプ付きの記録**を、すべてのエージェント行動について残す——何をしたか、なぜか、どのデータを使ったか。規制対象の領域では、後から規制当局や監査部門が「この判断はどう行われたか」を再構成できることが要件になる。通常のログとの違いは**事後に書き換えられないこと**にあり、これが担保されて初めて証跡として機能する。

## 実務で確立している型

- **意思決定パターンをトレースし、会話内容は見ない**（[[summaries/2025-multi-agent-research-system]]）。プライバシーと非決定性の両方に同時に対処する設計。何を話したかではなく、どう判断が分岐したかを構造として記録する。
- **rainbow deployment**（新旧バージョンを並走させ段階的に切り替える配備）。稼働中のエージェントを壊さずに更新するための実務解で、切り替え中は両バージョンの指標を並べて比較できる。
- **方針との定期突き合わせ**（[[summaries/2026-agent-orchestration-guide]]）。記録されたトレース上の**実際の**振る舞いと、文書化されたガバナンス方針を定期的に照合する。両者の乖離を、エージェントの**スコープ漂流**（当初の設計範囲から徐々にずれること）の早期兆候として扱う。これは「監視項目を決めて終わり」にせず、監視の妥当性自体を定期的に問い直す運用である。
- **契約違反の検知**: エージェント間に入出力契約（スキーマ）を定めておくと、下流のエージェントが受け取れない形式を上流が返した瞬間を機械的に検知できる。型のない引き継ぎは、壊れても静かに壊れる。

## トレースで「見えないもの」— 最重要の限界

トレースに thought（思考）が書かれていても、**それが行動の本当の理由とは限らない**。[[summaries/2025-cot-faithfulness]]（Anthropic, 2025）の実測では、答えを変えるほど効いたヒントを CoT（Chain-of-Thought, 思考過程を明示的に出力させる手法）が明かす率は **Claude 3.7 Sonnet で平均 25%・DeepSeek R1 で 39%** に留まり、不忠実な CoT はむしろ**長く、もっともらしい正当化**を構築する。合成 RL 環境では reward hack を 99% 超悪用しながら、6 環境中 5 つで**言語化率が 2% 未満**だった。

ここから導かれる、トレースを読むときの規律:

- **thought の記述より、行動と観測の系列を一次データとして扱う**。何を考えたと書いたかではなく、何を呼び、何が返ってきて、次に何をしたか。
- **CoT モニタリングは「気づくための層」であって「排除の保証」ではない**。高頻度・多段の逸脱ならどこかで言語化される確率は上がるが、CoT なしで実行できる脅威は素通りする。「そのタスクは CoT なしで実行できるか」が有効性の分水嶺になる（→ [[agent-safety-and-guardrails]]）。
- 行動ログと文脈の**突合**が要る。単体のツール呼び出しは正当に見えても、系列として見ると逸脱していることがある。

## 設計論点

- **記録の粒度とコストのトレードオフ**: 全ステップの全コンテキストを保存すると保管費用と機微データの露出が増える。一方で粒度を落とすと事後の再現ができない。実務解は「構造（判断の分岐・ツール呼び出し）は全件、内容（本文）は必要最小限」に寄せることが多い。
- **観測が挙動を変えないか**: トレースのためにモデルへ追加の出力を求めると、それ自体がタスク性能や思考の書き方に影響する。監視のための計装は、可能なら**モデルの外側**（ツール層・オーケストレーション層）に置く方が副作用が小さい。
- **可観測性は抽象化の代償として要求される**: [[agent-frameworks]] が指摘するとおり、高抽象なフレームワークは立ち上げが速い代わりに内部が見えにくい。**本番に向かうほど抽象化を剥がす**方向に力が働くのは、可観測性の要求が上がるためである。
- **共有コンテキストの可視化**: どの情報がどのエージェントに渡ったかが見えないと、[[summaries/2025-masft]] の FC2（情報の抱え込み、他者の入力の無視）は診断できない。コンテキストの流れ自体が観測対象になる（→ [[context-engineering]]）。

## この wiki でのカバレッジ

本ページは、既存原典に散在していた可観測性の記述（Anthropic の本番運用報告、MASFT のトレース分析方法論、CoT 忠実性の限界、フレームワークの抽象化トレードオフ）を集約して新設したもので、**可観測性そのものを主題とする一次資料はまだ ingest していない**。OpenTelemetry の生成 AI 向けセマンティック規約、トレーシング基盤（LangSmith・Langfuse・Arize 等）の設計文書、本番インシデントの事後報告といった原典が入れば、記述の解像度は上がる余地がある（`lint` のデータギャップとして追う）。現時点で最も運用寄りの根拠は [[summaries/2026-agent-orchestration-guide]] だが、これはベンダーブログであり、提示される数値には出典がない点に注意する。
