# Retrieval-Augmented Generation（検索拡張生成）

**外部知識を検索してモデルに与え、それを根拠に生成させる**手法の総称。LLM（Large Language Model, 大規模言語モデル）の 3 つの構造的弱点——知識を更新できない・出所を示せない・幻覚する——への最も広く使われる対処であり、エージェントにとっては「世界の最新の事実にどう接続するか」の基本部品である。

RAG には歴史的に **2 つの実装層**があり、混同しやすいので分けて理解する:

1. **訓練時に組み込む型**（原典型）— 検索器と生成器を単一の確率モデルとして end-to-end に訓練する。[[summaries/2020-rag]]（2020, 命名の原典）がこの型。
2. **推論時に注入する型**（現代の主流）— 既製の LLM のプロンプトに検索結果を入れるだけ。長コンテキストの LLM と in-context 学習の発達で、ファインチューニングなしのこの型が実務標準になった（chunking＝文書分割 → embedding＝ベクトル化 → 検索 → reranking＝再ランキング → プロンプト注入、のパイプライン。専用原典は未 ingest のため概説）。

層は違っても、原典が確立した設計原則——**知識はパラメータでなく索引に置く**——は共通している。

## 代表手法

### RAG（Lewis et al., 2020）— 命名の原典

[[summaries/2020-rag]]。パラメトリック記憶（BART の重み）と非パラメトリック記憶（Wikipedia 2100 万チャンクの密ベクトル索引）を、**検索文書を潜在変数として周辺化**する形で結合し、どの文書を使うべきかの教師なしで検索まで学習した。今日まで通用する 3 つの実証:

- **幻覚の減少**: 人手評価で「より事実的」42.7% vs BART 7.1%。パラメトリックと非パラメトリックの協働（検索が引き金を引き、モデル内部の知識が補完する）の分析も残した。
- **index hot-swapping**: 索引を差し替えるだけで再訓練ゼロの知識更新（2016/2018 年版 Wikipedia で世界指導者の正答が入れ替わる実証）。「ドキュメントを差し替えれば済む」という現代の RAG 運用の原型。
- **retrieval collapse**: 知識をあまり要さないタスクでは検索器が入力を無視して固定文書に崩壊し、生成器も文書を無視するようになる——RAG の適用境界の最初の記録。

### DPR / REALM — 検索側の土台

**DPR**（Dense Passage Retriever）は BERT の bi-encoder（クエリ用・文書用）で埋め込み、最大内積探索（MIPS, FAISS で近似）で文書を引く密検索器で、原典 RAG の検索部品。**REALM** は検索つき事前学習の先行（抽出型 QA まで）。いずれも概説（専用原典は未 ingest）。なお原典のアブレーションでは、**エンティティ中心のタスクでは古典的な BM25（単語の重なり）が密検索に勝つ**ことも示されており、「密検索一択にしない」は当時からの教訓である。

## 設計論点

- **検索の質が生成の上限**: 悪い検索結果は推論全体を脱線させる。[[summaries/2022-react]] でも検索失敗がエラーの 23% を占めた——層が違っても（訓練型でもループ型でも）この制約は同じ。
- **単発検索か、反復検索か**: 原典 RAG は 1 回の検索で生成する。「検索→読んで→足りなければ再検索」という反復は、[[summaries/2022-react]] がエージェントのループ内ツール呼び出しとして解いた（→ [[tool-use-and-function-calling]]）。「内部知識で足りるか、検索すべきか」のルーティング（ReAct ⇄ CoT-SC のフォールバック）も同系列の論点。本番プロダクトの側でもこの対比は明示されている: Anthropic Research（[[summaries/2025-multi-agent-research-system]]）は自らのアーキテクチャを「**静的検索**（類似チャンクを一度取って生成する従来型 RAG）に対する**動的な多段検索**——見つけたものに適応しながら検索を重ね、結果を分析して回答を組み立てる——」と位置づけ、さらに検索を並列サブエージェント群に分散した。エージェント時代の RAG は「1 回の検索」から「検索戦略の運用」へと重心が移っている。この発展形を横断サーベイ（[[summaries/2025-llm-reasoning-to-agents]], 2025）は **Agentic RAG** として体系化する: 従来の RAG に自律エージェントの設計パターン（planning・reflection・ツール利用・マルチエージェント協調）を埋め込み、検索と反復的洗練を動的にオーケストレートする枠組みで、同サーベイの比較表（Table VI）は LLM 事前学習／事後訓練／RAG／AI エージェント／Agentic RAG の 5 段階を自律性・学習・信頼性で対比し、「**RAG の事実接地（静的だが正確）× AI エージェントの動的適応性**」の掛け合わせと位置づける。また同サーベイ §V-E の **ReSearch** は、検索を「別個の検索ステップ」でなく**推論連鎖に織り込まれたトークン化された行動**として扱い、最終答えの精度と think/search/result 形式の遵守を報酬に強化学習で訓練する——注釈付き推論トレースなしでマルチホップ QA の強い性能を得る、agentic retrieval を訓練で作り込む方向である → [[reinforcement-learning-from-human-feedback]]。
- **agentic search vs RAG の実測**: この対比を**同一モデル・同一タスク群で定量比較**した最初期の公開データが DeepSeek-V4（[[summaries/2026-deepseek-v4]]）の本番評価である。同社チャットボットは non-think モードで RAG（検索結果の一括注入）、thinking モードで agentic search（モデルがクエリごとに検索・取得ツールを反復呼び出し）を使い分けており、ペアワイズ評価では **agentic search が全難度帯で優位、差は複雑なタスクほど拡大**した。注目すべきはコスト側で、agentic search の平均はツール呼び出し 16.2 回（**大半は並列**）・prefill 13,649 トークン・出力 1,526 トークン——RAG（prefill 10,453・出力 1,308）に対して**わずかな増分**に収まる。「反復検索は高くつく」という直感への反証であり、並列ツール呼び出しと KV cache 再利用が効く環境では、agentic search をデフォルトにしない理由はコストではなくレイテンシ要件になる。
- **top-K の上限を破る — ページング反復**: 単発検索には「retriever が top-K に正解を入れられなければ、生成側は決して正解を見られない」という構造的上限がある。[[summaries/2023-memgpt]]（MemGPT, 2023）はこれを実証つきで突いた: 文書 QA で固定コンテキストのベースラインは retriever の性能で頭打ちになるのに対し、MemGPT は archival storage（ベクトル検索つき文書 DB）への**ページネーション付き検索を function call で何度でも発行**でき、正解がランキングの深い位置にあっても原理的には到達できる——コンテキスト長を増やしても性能が変わらない平坦な曲線がその帰結である。ただし同論文は、モデルが**データベースを使い尽くす前に検索を打ち切ってしまう**ことも観察しており、「どこまで粘って引くか」という読み出し側の挙動が新しいボトルネックになることを示した。
- **agentic RAG と agentic memory の境界**: 「いつ・何を検索するかをモデルが決める」検索側の自律化（agentic RAG。Self-RAG や FLARE の系譜——概説）に対し、[[summaries/2025-a-mem]]（A-Mem, 2025）は**保存・組織化の側の自律化**を対置した: 検索がどれだけ賢くても、索引そのものが静的なら知識ベースは育たない。A-Mem は保存時に LLM が意味づけ（キーワード・タグ・文脈説明）を済ませ、記憶間のリンクを判断し、新しい記憶の到着で既存記憶を書き換える（memory evolution）。**「検索の agency」と「索引の agency」は独立した設計軸**であり、後者は本ページの範囲を超えて [[agent-memory]] の領域に入る——両ページの境界線がここにある。
- **知識の置き場所の経済学**: 原典は 626M パラメータで T5-11B（closed-book）を圧倒した。知識はパラメータに焼き込むより索引に置く方が安く、更新可能で、監査できる——[[agent-memory]] の外部記憶設計へ通じる原則。
- **文書数と合成の粒度**: 検索文書を増やせば単調に良くなるとは限らない（RAG-Token は 10 でピーク）。複数文書の内容を 1 つの答えへ合成する必要があるかどうかで、設計（原典なら Token/Sequence、現代ならプロンプトへの並べ方 → [[context-engineering]]）が変わる。
- **collapse の監視**: 検索結果が入力によらず似通ってきたら検索が死んでいるサイン。RAG パイプラインのヘルスチェック項目（→ [[agent-evaluation]]）。
- **索引のバイアス**: 検索で接地しても、索引が誤っていれば誤りに接地する。知識源の品質管理は RAG の外側で必要。
