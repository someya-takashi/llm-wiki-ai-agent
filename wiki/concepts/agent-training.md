# Agent Training（エージェントの訓練）

**エージェントとして働く力を、プロンプトや足場（scaffold, モデルの周りでツールとループを提供するプログラム）ではなく、モデルの重みそのものに入れる**方法を扱うページ。ここでの「エージェントとして働く力」とは、ツールを正しい書式で呼び、観測（コマンドの出力・テストのログ）を読み、数十ターンにわたって一貫して作業を進める力である。

2024 年ごろまで、SWE（Software Engineering）エージェントの進歩はほぼ**プロプライエタリなモデル＋足場の工夫**によるもので、オープンなモデルは素のままではほとんど解けなかった（SWE-bench Verified で 1 桁台）。その状況を変えたのが、**実行できる訓練環境**（→ [[agent-environments]]）と、その上で回す訓練の段取りである。どの方法も次の 3 つの問いへの答えの組み合わせとして読める。

1. **誰の軌跡（trajectory, エージェントが辿った行動と観測の列）から学ぶか**: 強い教師モデルか、自分自身か。
2. **どう採点するか**: テストの成否（0/1）、LLM ジャッジのルーブリック、学習した検証器。
3. **どう更新するか**: 成功例をまねる教師あり学習か、良し悪しの差から学ぶ強化学習（RL）か。

## 3 つのやり方: 教師をまねる、自分の成功をまねる、差から学ぶ

| やり方 | データ | 採点の使い方 | 代表例（本 wiki） |
|---|---|---|---|
| **(1) 教師の軌跡の蒸留**（SFT） | 強いモデルの軌跡 | 成功したものだけ残す（ことが多い） | SWE-Gym：GPT-4o・Claude 3.5 Sonnet の成功軌跡 491 本 → 32B が 7.0% → 20.6%。SWE-smith：Claude 3.7 Sonnet の 5,016 本 → 40.2%。SWE-Lego：公開モデル Qwen3-Coder-480B の 1.8 万本 → Qwen3-32B が 23.2% → 52.6% |
| **(2) 棄却サンプリングファインチューニング**（RFT） | **自分の**軌跡 | 成功したものだけ残して SFT | 72B が 11.4% → 20.5%（[[summaries/2025-swe-rl-long-context]]）、Moatless 7B が 7.0% → 10.0%（[[summaries/2024-swe-gym]]） |
| **(3) 多ターン RL** | 自分の軌跡（毎反復で引き直す） | 成功も失敗も使い、グループ内の差を advantage にする | 72B が 20.5% → 39.0%（DAPO の改変）、Kimi K2 の agentic rollout、DeepSeek-V4・Kimi K3 の専門家 RL |

**(1) 蒸留**は最も安く、効き目も大きい。SWE-Gym は数百本の成功軌跡でオープンモデルの解決率を 3 倍にした。推論の領域でも、DeepSeek-R1 は「小さなモデルに RL を直接かけるより、大きなモデルが RL で見つけた推論を蒸留したほうが強い」（Qwen-32B で 72.6 対 47.0）と報告している（[[summaries/2025-deepseek-r1]]）。ただし**教師より上には行きにくく**、教師がプロプライエタリならデータの出所に縛られる。さらに、SWE-bench の SWE-Llama は「編集すべきファイルが文脈に全部入っている」設定で訓練したため、検索で文脈を作る設定に移すと 3.00% → 0.70% に落ちた（[[summaries/2023-swe-bench]]）。**訓練時と使用時で文脈の作り方が違うと、まねた振る舞いは崩れる**。

**蒸留の伸びしろは、データの量と多様性で決まる**ことが分かってきた。SWE-smith（[[summaries/2025-swe-smith]]）は環境を先に作ってバグを合成する方式で 5 万件のタスクを作り、軌跡が 100 本から 5,000 本に増えるにつれて 14.3% → 40.2% と伸び、リポジトリの数を 4 → 100 に増やすと対数的に伸びることを示した。SWE-Lego（[[summaries/2026-swe-lego]]）は実際の PR と合成バグを混ぜた 3.2 万件で、**強化学習を使わず SFT だけで**同規模の RL のモデルに並んだ（Qwen3-32B で 52.6%）。寄与の大半はデータ（+25.6 ポイント）で、SFT の工夫は +3.8 ポイントだった。SWE-Lego の教師は**公開モデル**（Qwen3-Coder-480B）で、プロプライエタリなモデルの利用条件に縛られずにローカルで大量に軌跡を作れる点も、2026 年の蒸留の変化である。

**量だけでなく、どの軌跡のどの部分をまねさせるかも効果を左右する。** SWE-Prime（[[summaries/2026-swe-prime]], 2026-08）は、Qwen3-Coder-480B が SWE-rebench で解いた成功軌跡 32,161 本を、軌跡ごとの規則（調べてから編集し最後に確かめたか、ツールの成功率、同じ呼び出しの連続、Git ハッキング、正解パッチより広い変更）とイシューのクラスタで 10% に絞り、さらに LLM が 0〜10 点で採点した区間のうち 7 点未満を損失から外した（文脈としては残す）。3 つの 30B 級 MoE モデルのすべてで、成功軌跡すべての SFT を SWE-bench Verified と Pro の両方で上回り、ランダムに 10% を選ぶと素のモデル並みに落ちた。ただし差は多くが 2〜4 ポイントで、1 回の実行の数字であり、選別の設定は評価用の問題（Verified）で決めている。

**教師はオープンウェイトの強いモデルでもよい。** SWE-Master（[[summaries/2026-swe-master]], 2026-02）は、Verified で 7 割近くを解く MiniMax-M2 と GLM-4.6 を教師にし、4 つのデータセットのイシューを 1 件 3〜12 回解かせた。そのうえで、毎回解けるイシューと一度も解けないイシューを除いた約 6 万件の軌跡で SFT し、素の Qwen2.5-Coder-32B（6.2%）を 57.8% にした。データ量に対する伸びは対数的で 4.8 万件付近で飽和し、量が増えるほど平均ターン数と思考のトークンは減った。素のモデルから到達点までの伸びの大部分は SFT（強い教師の蒸留）で、後段の RL の上乗せは 3.6 ポイントだった。

**(2) RFT**（rejection sampling fine-tuning, filtered behavior cloning とも）は、「自分に何回も解かせ、成功した軌跡だけを学習データにする」方法である。成功を判定できさえすれば教師モデルが要らない。考え方は古く、Toolformer の「損失を下げたツール呼び出しだけを訓練例に残す」フィルタ（[[summaries/2023-toolformer]]）や、R1 の第 3 段（RL チェックポイントから正解だけを 60 万件集める）、Kimi K2 の「LLM ジャッジがルーブリックで合格とした多ターン軌跡だけ残す」大規模なツール利用データ合成（[[summaries/2025-kimi-k2]]）も同じ形をしている。エージェントでは **RL の前の準備運動**として役に立つ。素のモデルの失敗の多くがツール呼び出しの書式違反なら、まず RFT で書式を覚えさせるだけで大きく伸びる。

**(3) 多ターン RL**は成功した軌跡だけでなく**失敗した軌跡からも学ぶ**。同じタスクで複数（例: 10 本）の軌跡を引き、グループ内の平均より良かったものの確率を上げ、悪かったものの確率を下げる（GRPO・DAPO の考え方 → [[reinforcement-learning-from-human-feedback]]）。RFT では捨てていた失敗が負の信号になるので、RFT が頭打ちになったところからさらに伸びる。[[summaries/2025-swe-rl-long-context]] では、伸びの大半（20.5 → 35.7）が RL の第 1 段階で生まれた。

## 1 回答えて終わる RL と何が違うか

数学の RL（R1・DeepSeekMath）は、問題に 1 回答えると採点が返る。エージェントの RL は**状態を持つ環境と数十ターンやり取りした最後に、ようやく 1 ビットの採点が返る**。[[summaries/2025-swe-rl-long-context]] はこれを部分観測マルコフ決定過程（POMDP, 環境の本当の状態は見えず、観測の履歴から次の手を決める問題設定）として書き、次の違いを挙げる。

- **軌跡が長い**：1 本が数十ステップ・数万〜十数万トークンになる。文脈長そのものが訓練の設定値になり、65k → 131k のように段階的に広げる。
- **観測が情報を持つ**：テストのログやエラーを読み、次の手に反映する力が要る。
- **信用割当が難しい**：成功の信号は最後にしか来ないので、数十の行動のどれが効いたかを割り当てにくい。
- **1 回の採点が高く、ノイズを含む**：環境を立ち上げ、テストを走らせるたびにコストがかかり、不安定なテスト（flaky test）は報酬そのものを汚す。
- **ロールアウトのインフラが重い**：環境待ちで GPU が遊ぶ、軌跡の長さがばらつく。Kimi K2 の partial rollout（長い軌跡を一時停止して次の反復で再開する）や、DeepSeek-V4 の DSec（数十万の並行サンドボックス）は、この問題への大規模な回答である（[[summaries/2025-kimi-k2]]・[[summaries/2026-deepseek-v4]]）。足場の速さが訓練の試行回数を決める点は [[agent-cost-efficiency]] も参照。

## 実測された落とし穴

本 wiki の原典が実際に踏んだ失敗を、対策と組みにして並べる。

| 落とし穴 | 何が起きたか | 対策 |
|---|---|---|
| **簡単なタスクへの偏り** | 何回も解かせると、成功は簡単なタスクに集中する。成功軌跡を全部使うと訓練データが簡単なタスクで埋まる（[[summaries/2024-swe-gym]] 図 3） | **1 タスクあたりの本数に上限**（SWE-Gym では上限 2 が最良） |
| **学習信号のないタスク** | 10 本全部成功・全部失敗のタスクは、グループ内に差がなく advantage が 0 になる | advantage 0 のサンプルを捨てる（DAPO）。累積解決率が **2/3 超と 0 のタスクを除いて**、中くらいの難しさに絞る（[[summaries/2025-swe-rl-long-context]] で 7,249 → 2,028 タスク） |
| **自己改善で悪化する** | 教師の軌跡で SFT したモデルに、自分の成功軌跡 868 本を足して訓練し直すと Lite で **15.3% → 8.7%**（SWE-Gym・OpenHands）。手順の決まった足場でも 32B は 19.0 → 19.7 で頭打ち | 成功例をまねる RFT の限界と見て、失敗からも学ぶ RL に進む（後続の研究が DAPO で 39% に到達） |
| **成功軌跡の中の失敗した手までまねる** | 成功した軌跡にも、書式エラーを起こしたターンや失敗した試みが混じる | **エラーを返した手の応答を損失から外す**（マスク）。Golubev らは書式エラーのターンを、SWE-Lego は端末が返したエラーメッセージを正規表現で見つけて直前の応答を外し、+2 ポイント前後（ただしバグの再現やテストの実行で出るエラーは目的どおりの手なので外さない）。SWE-Prime（[[summaries/2026-swe-prime]]）はこれを「意味的な区間」の単位に広げ、エラーのない無関係な探索も LLM の採点で外した |
| **直せなかった軌跡を全部捨てる** | テストに通らなかった軌跡にも、正しいファイルに辿り着いた手本が含まれる | SWE-Lego は、正解パッチが変更したファイルを正しく開いた「半解決」の軌跡 4,000 本を足して 41.0% → 42.2% |
| **軌跡がカンニングを含む** | 教師が Git の履歴（将来のコミット）を覗いて正解を読む「Git ハッキング」や、テストを書き換えて通す軌跡が混じる | 環境からイシューより後のコミットを消し（合成タスクは履歴を丸ごと消す）、テストを変更した軌跡を捨てる（SWE-Lego）。→ [[agent-evaluation]] |
| **教師がツールを誤用する** | 引数の型の誤り（行範囲に文字列を渡す）や、うまく使えないツール（タスク管理の `task_tracker`）が、無駄なターンと誤りを手本に混ぜる | 誤りを事後に補正し、使えないツールを外す（SWE-Lego で有効な軌跡の率 27% → 30%）。→ [[agent-computer-interface]] |
| **イシュー文に答えを書いてしまう** | 壊れたテストをイシュー文に載せると、成功軌跡は増えるが、モデルが再現スクリプトを書かなくなる（500 問中 379 回 → 127 回） | イシュー文は LM に書かせ、テストそのものは見せない（SWE-smith）。LM が書いた文面は本物のイシューと同等の効果だった |
| **長すぎる軌跡を捨てるとループが増える** | 文脈長を超えた軌跡はたいていループに陥ったものなので、捨てるとループが罰されなくなる | 捨てずに**長さの罰**で抑える |
| **打ち切られた軌跡を報酬 0 にすると崩れる** | 長い SFT のあとの RL で、確認を繰り返して提出しないまま予算を使い切る軌跡が約 20% 出た。報酬 0 で平均報酬が下がり続け、訓練が崩れた。打ち切られた軌跡の約 24.3% は、後から採点すると解決していた（SWE-Master） | その時点の状態を**強制的に提出**して採点し、報酬を割り引く（α = 0.5）。打ち切りを報酬 0 にしてマスクする DeepSWE の方式は、SFT 済みの SWE-Master では崩れた（[[summaries/2026-swe-master]]） |
| **インフラの失敗が報酬を汚す** | コンテナの起動失敗やサーバーのエラーで終わった軌跡に報酬 0 を与えると、方策と無関係なノイズを学ぶ | その軌跡を**損失の計算から丸ごと外す**（SWE-Master） |
| **文脈を書き換えるエージェントを、全履歴を前提に訓練する** | 履歴を途中で要約するエージェントは、圧縮後の行動を圧縮後の文脈を見て生成している。圧縮前の全履歴を前提に訓練すると、推論時と状態がずれる | **圧縮の時点で軌跡を部分軌跡に切り**、それぞれを実際に見ていた圧縮後の文脈から始める。長さのばらつきに備え、ロールアウトごとに平均してからバッチで平均する（SWE-MeM, [[summaries/2026-swe-mem]]） |
| **サンプリング設定のずれ** | vLLM の更新で既定の top_k・min_p が有効になり、5〜10 反復後に性能が落ちた。重要度サンプリング比が前提とする「旧方策から引いた」が崩れたため | ロールアウトは温度 1.0 だけにし、他のデコーディング設定を切る。同じ系統の問題として、K2.5 は訓練側と推論側の数値の不一致にトークン単位の対数比クリップで、K3 は量子化をロールアウトと訓練でそろえることで対処している |
| **報酬のノイズ** | 外部サービスや浮動小数点誤差で、テストの結果が実行ごとに揺れる | **テストを 50 回走らせて揺れるタスクを除く** |

## 検証器を訓練する: 生成と選別を分ける

テストで採点できる環境では、**成功・失敗のラベルつきの軌跡**が副産物としてたまる。これで**検証器**（verifier, 軌跡や出力が正しいかを判定するモデル）を訓練すると、推論時に K 本の候補から 1 本を選べる（→ [[test-time-compute]]）。SWE-Gym の検証器は ORM（Outcome-supervised Reward Model, 最終結果だけを見て成功確率を出す報酬モデル）で、軌跡を読ませて YES／NO を答えさせ、YES の確率をスコアにする。

指標は 2 つを並べて見る。**Pass@K**（K 本中に 1 本でも正解があるか、選び方が完璧なときの上限）と **Best@K**（検証器が選んだ 1 本が正解か）である。

| 原典 | 1 本だけ | K 本から検証器で選ぶ | K 本中に正解がある（上限） |
|---|---|---|---|
| SWE-Gym・32B（Verified） | 20.6% | 32.0%（Best@16） | 42.8%（Pass@16） |
| SWE-Gym・Moatless 32B（Lite） | 19.7% | 26.3%（8 本から） | — |
| R2E-Gym・32B（Verified） | 34.4% | 51.0%（Best@26、テスト＋ORM の組み合わせ） | 64.4%（Pass@26） |
| RL 論文・72B（Verified） | 39.0% | —（検証器なし） | 58.4%（Pass@10） |

**上限と実際の差は「よい候補は出ているのに選べていない」部分**であり、そこを埋めるのは検証器の仕事である。DeepSeekMath の「RL は Maj@K（多数決）を上げるが Pass@K を上げない」という観察（[[summaries/2024-deepseekmath]]）と合わせると、**RL で 1 本目の精度を上げることと、検証器で選ぶことは、同じ上限を取り合う関係にある**とも読める。

SWE-Gym が見つけた検証器の訓練のこつは次のとおり。

- **教師の軌跡と自分の軌跡を混ぜ、成功と失敗を同数にする**。教師の軌跡だけだと 22% 前後で頭打ちになり、失敗例を 2 倍にすると検証器が慎重になりすぎる。
- **LoRA のほうが全パラメータより良かった**（Best@8 で 29.8% 対 27.2%。正則化として効いたと推測 → [[parameter-efficient-fine-tuning]]）。
- **検証器も大きいほうが伸び続ける**（7B は 4 本で頭打ち、32B は 8 本でも伸びる）。

**検証器は生成型のほうが伸び続ける**（[[summaries/2026-swe-lego]]）。軌跡を読んで「yes／no」を答えさせ、その確率をスコアにする生成型（SWE-Gym の ORM と同じ形）と、スコア用の出力層を足して二値分類で訓練する回帰型を、同じデータ（解決 5k・未解決 13k）で比べると、候補が少ないうちは同程度だが、16 本では生成型 49.6% 対 回帰型 46.8% と差が開いた。公開の回帰型の検証器は、候補を増やすとむしろ下がった。事前学習の次トークン予測と形が合うので、モデルの知識を使いやすいという仮説である。検証器の訓練データを 6k → 18k に増やすと 47.6% → 49.6%、大きなエージェントの候補には大きな検証器が効いた。それでも Pass@16 の 66.0% に対して選べたのは 49.6% で、選べていない部分は大きい。

**テストで選ぶ検証器と、軌跡を読んで選ぶ検証器は、別の理由で頭打ちになる**（[[summaries/2025-r2e-gym]]）。R2E-Gym は、再現テストを書く専用のエージェント（Qwen2.5-Coder-32B を SFT）と回帰テストで選ぶ実行ベースの検証器と、SWE-Gym と同じ形の ORM（14B）を、同じ 26 本の候補で比べた。どちらも 43% 前後で止まる（Pass@26 は 64.4%）。テストで選ぶ側の問題は**区別できない**ことで、大半の問題で正しいパッチと誤ったパッチを分けるテストは 20% 未満しかなく、誤ったパッチだけを通す「毒性のあるテスト」も一部の問題で最大 10% 出た。ORM の側の問題は**パッチ以外を見てしまう**ことで、パッチだけを見せると 42.8% → 37.6% に下がり、注意の重みはエージェントの「修正はうまくいった」という自己申告に集まっていた。ORM の上位 n 本に絞ってからテストの通過数で選び、同点を ORM の連続値で割ると 51.0% になった。回帰テストだけでも 47.4%、テストを Agentless のものに替えると 48.8% である。SWE-Lego の比較では、この 14B の ORM（R2E-Gym-Verifier-14B）は 16 本から選ぶ設定で 47.0% と、SWE-Lego の 8B の生成型の検証器（49.6%）にわずかに及ばなかった。

この ORM の偏りは、**報酬モデルとして使うと問題が大きくなる**（本 wiki の読み）。自己申告に高い点を付ける検証器を報酬にすれば、正しく直すより自信のある報告を書く方向へ訓練が進みうる。

検証器は推論時の選別に使うだけでなく、そのまま RL の報酬モデルにもなる。Kimi K2 の自己批評ルーブリックや DeepSeek-V4 の「actor 自身が GRM（Generative Reward Model, 文章で評価を生成する報酬モデル）を兼ねる」設計は、判定する力と生成する力を同じモデルの中で育てる方向である（→ [[reinforcement-learning-from-human-feedback]]）。

## 難しさをどう扱うか: 原典によって答えが違う

訓練データの「難しさ」の扱いは本 wiki の原典で食い違っている。

| 原典 | やり方 | 結果 |
|---|---|---|
| SWE-Gym（[[summaries/2024-swe-gym]]）・RFT | 易しいタスクの軌跡が増えすぎないよう、1 タスクあたり 2 本までに制限 | 上限なしよりわずかに良い |
| SWE-smith（[[summaries/2025-swe-smith]]）・RFT | 1 タスクあたり 3 本までに制限。さらに難しさ別に 500 本ずつで訓練 | **難しさと訓練の効果は相関しない**（12.4〜13.6% で揺れるだけ） |
| SWE-Lego（[[summaries/2026-swe-lego]]）・SFT | ターン数を難しさとみなし、易しい → 中程度 → 難しいの順に学ぶカリキュラム | +0.4〜0.8 ポイント（エラーマスキングと組み合わせて最大） |
| Golubev ら（[[summaries/2025-swe-rl-long-context]]）・RL | 解決率が 2/3 超（易しすぎる）と 0（解けない）のタスクを除く | 中くらいの難しさに計算を集中させた |
| SWE-Master（[[summaries/2026-swe-master]]）・SFT | 教師に 3〜12 回解かせ、毎回解けるイシューと一度も解けないイシューを除く（RL も同じ分布） | 選別なしの 54.2% → 57.8%。平均ターン数と思考のトークンはほぼ変わらない |

SWE-Master の +3.6 ポイントは SFT での選別としては大きいが、成功軌跡だけを使う SFT では「一度も解けないイシュー」はもともと軌跡がないので、実質的に除いたのは「毎回解ける易しいイシュー」である。SWE-Gym・SWE-smith の「易しいタスクに偏らせない」と同じ方向の操作と読める。

これらは矛盾というより、**学習の仕組みの違い**として読める。RL では、全部成功・全部失敗のタスクはグループ内に差がなく学習信号がゼロになるので、難しさの選び方が直接効く。成功例をまねる SFT・RFT では、どの難しさの成功例も同じように手本になるので、効くのは「易しいタスクに偏りすぎない」ことくらいで、難しさそのものの効果は小さい。SWE-Lego のカリキュラムの利得も 1 ポイント未満で、試行のばらつきを考えると誤差の範囲に入りうる（→ [[summaries/2024-error-bars-evals]]）。

## SWE エージェントの訓練の到達点（2025 年夏時点）

[[summaries/2025-swe-rl-long-context]] の表 2 が、同時期の SWE 特化のオープンモデルをまとめている（SWE-bench Verified、Pass@1）。

**表**: 訓練した SWE エージェントの比較（原典の表 2 を再構成）

| エージェント | 基盤モデル | 訓練前 | 訓練後 | 教師からの蒸留 |
|---|---|---|---|---|
| DeepSWE-32B | Qwen3-32B | 23% | **42.2%** | なし |
| SWE-agent-LM-32B（SWE-smith） | Qwen2.5-Coder-32B-Instruct | 14.3% | 40.2% | あり |
| Golubev ら（RFT → DAPO） | Qwen2.5-72B-Instruct | 11.4% | 39.0% | なし |
| Skywork-SWE-32B | Qwen2.5-Coder-32B-Instruct | 6.4% | 38.0% | あり |
| R2EGym-Agent-32B | Qwen2.5-Coder | 7.0% | 34.4% | あり |
| SWE-Fixer-72B | Qwen2.5-72B-Base | – | 30.2% | あり |
| SWESynInfer-72B | Qwen2.5-72B-Instruct | 25.4% | 30.2% | あり |
| SkyRL-Agent-14B-v0 | Qwen3-14B | 18.0% | 21.6% | なし |
| SWE-Gym-32B | Qwen2.5-Coder-32B-Instruct | 7.0% | 20.6% | あり |

読み取れることは 2 つある。第一に、**半年で 20% 台から 40% 前後まで上がった**。第二に、**蒸留ありとなしで到達点に大差がない**。教師に頼らない RL でも、強いモデルの蒸留と同じ水準に届くようになった。なお、同じ時期のフロンティアのプロプライエタリモデルや後の世代のモデルは SWE-bench Verified で 60〜80% 台にあり（[[coding-agents]] の評価節。ただし Verified は 2026-02 に OpenAI が「汚染とテストの欠陥のため、もはや能力を測れない」として報告をやめた → [[summaries/2026-swe-bench-verified-retired]]）、この表はあくまで「オープンな中規模モデルを訓練でどこまで持ち上げられるか」の記録である。

**2026 年初めの続き**（[[summaries/2026-swe-lego]] の表 7 から）：SFT だけの SWE-Lego-Qwen3-32B が 52.6%（検証器で 16 本から選ぶと 58.8%）、SFT の SWE-Mirror-LM-32B が 52.2%、継続事前学習＋SFT＋RL の CWM-32B が 53.9%、8B でも SWE-Lego-Qwen3-8B が 42.2% に達した。**オープンな中規模モデルは半年でさらに 10 ポイント以上伸び、SFT だけでも RL と同じ水準に届いている**。ただし SWE-Lego は 2025 年 9 月 3 日より前の SWE-bench Verified の Docker イメージでは `git log` で正解を覗けたことを示しており（自分たちの 32B で 57.6% 対 52.6%）、この時期の他のモデルの数字には 2〜5 ポイントの水増しが含まれている可能性がある。

**2026 年前半の続き**：SWE-Master（[[summaries/2026-swe-master]], 2026-02）は、オープンウェイトの教師の蒸留（SFT）と、打ち切られた軌跡を強制的に提出させる RL で、Qwen2.5-Coder-32B を 61.4%（候補 8 本から模擬テストで選ぶと 70.8%）にし、データの作り方から RL の報酬までを公開した。SWE-MeM（[[summaries/2026-swe-mem]], 2026-06）は別の軸から攻め、**文脈の管理そのものを訓練する**ことで、文脈を 32K に絞ったまま Qwen3-4B を 43.4%、Qwen3-Coder-30B-A3B を 60.2% にした。4B でも、文脈 128K の SWE-Master-4B（33.4%）や 8B の SWE-Lego（42.2%）を上回った。ただしどちらの表も他手法の値は各論文の報告値で、足場や文脈の上限は揃っていない。

**手続き型で鍛えてからエージェントにする道**（[[summaries/2025-kimi-dev]], 2025-09）：Kimi-Dev は Qwen2.5-72B-Base に GitHub の PR から作った約 1,500 億トークンの中間訓練、DeepSeek-R1 の長い推論でのコールドスタート、コード編集の段だけの RL（報酬は実行結果のみ、解ける見込みのある 1,200 問から始めて 100 ステップごとに 500 問を戻すカリキュラム、終盤は成功例を混ぜる）を、すべて Agentless の形式で行った。その後 SWE-smith の軌跡 5,016 本の SFT だけで、エージェント型の足場で 48.6% になった（同じデータの SWE-agent-LM-32B は 40.2%）。同じ Qwen2.5-72B から、エージェント型のまま RFT と多ターン RL で 39.0% にした Golubev らとは別の道である。出発点（素・中間訓練後・SFT 後・RL 後）を比べた実験は、**エージェント用のデータが少ないときほど、どこから始めるかが効く**ことを示した。

> 注: DeepSWE・SkyRL・Skywork-SWE の原典は wiki に未取得で、上の数字は [[summaries/2025-swe-rl-long-context]] と [[summaries/2026-swe-lego]] を通した二次情報である（SWE-smith は 2026-10-26、SWE-rebench と R2E-Gym は 2026-10-28 に取り込んだ → [[summaries/2025-swe-smith]]、[[summaries/2025-swe-rebench]]、[[summaries/2025-r2e-gym]]）。R2EGym-Agent-32B の 34.4% は原典の値と一致する。原典では SWE-Gym と同じ Qwen2.5-Coder で比べ、7B・14B・32B のすべてで SWE-Gym を 8〜14 ポイント上回った。Kimi K3 の評価表にある「DeepSWE」はベンチマーク名で、この表のモデルとは別物である。

## 設計論点

- **どこから始めるか（初期化）**。素のモデルからエージェントの RL を始めると、ツールをうまく使えずループに陥りやすい。Kimi-Dev（[[summaries/2025-kimi-dev]]）では、エージェントの軌跡での更新を 1 回だけにした状態から end-to-end の RL をかけると、中間訓練だけのモデルは 8 回試して 1 度でも解ける問題が 6,202 問中 260 問しか残らず、10 ステップで崩れた。Agentless の RL まで済ませたモデルは 2,062 問が残り、300 ステップ安定して伸びた。**最初に解ける問題がどれだけあるかが、RL を回せるかどうかを決める**。
- **教師に頼るか、自力で育てるか**。蒸留は安く強い（R1 の 72.6 対 47.0、SWE-Gym の 491 本で 3 倍）が、教師の能力と利用条件に縛られる。自力の RL は高い（H200 ノード 16 台・100 反復超）が、出発点のモデルがある程度解ける（72B で 11%）なら教師なしで蒸留と同じ水準に届く。実際の大規模モデルの訓練（DeepSeek-V4・Kimi K3）は、**専門家を RL で育て、それを 1 体に蒸留する**という両方の組み合わせに収束している（→ [[reinforcement-learning-from-human-feedback]]）。
- **足場と訓練の相性**。手順の決まった足場（Moatless・Agentless → [[summaries/2024-agentless]]）は素のモデルでも点が高いが、訓練で伸びにくい。汎用の足場（OpenHands・SWE-agent 型）は素のモデルでは弱いが、訓練でよく伸びる（[[summaries/2024-swe-gym]]）。SWE-Effi の「弱いモデルは手順を固定したほうが安定し、強いモデルには制御を渡したほうが伸びる」（[[summaries/2025-swe-effi]]）と合わせると、**訓練でモデルを強くする計画があるなら、最初から汎用の足場で訓練データを作る**ほうが筋がよい（→ [[coding-agents]]）。
- **何が律速か**。SWE-Gym は訓練軌跡を 491 本の 25%・50%・100% と増やしても飽和せず、タスク数やリポジトリの多様性ではなく**軌跡をサンプリングする計算量**が律速だと結論した。RL の側でも、ロールアウトの速さが訓練の試行回数を決める（→ [[agent-cost-efficiency]]）。
- **環境の作り方がデータの偏りを決める**。SWE-Gym は依存関係を手で設定して 2,438 件にとどまり、並行研究（Nebius の 2 本の連続したブログ記事、Badertdinov ら・Golubev ら 2024。後者は [[summaries/2025-swe-rl-long-context]] と同じ著者群）は汎用のセットアップスクリプトで 6,415 件を集めたが、セットアップに失敗した（依存の難しい）タスクは捨てている。**自動化して数を取るか、手間をかけて偏りを避けるか**の選択である（→ [[agent-environments]]）。その並行研究を全自動化した SWE-rebench（[[summaries/2025-swe-rebench]]）は 21,336 件まで増やしたが、動く環境を作れたのはリポジトリの 31% だった。また、RL の報酬が「タスクの欠陥」でなく「エージェントの力不足」だけを反映するように、差分の取り方・テストの走らせ方・依存関係の凍結を SWE-bench の方法から直し、イシューの明確さやテストの正しさを LLM に予測させたラベルを各タスクに付けている。
- **評価の汚染を分けて見る**。SWE-bench Verified だけで訓練の効果を語ると過大評価になりうる。2026-02 には OpenAI が、主要なフロンティアモデルがどれも Verified の正解パッチを記憶していたと報告している（[[summaries/2026-swe-bench-verified-retired]]）。[[summaries/2025-swe-rl-long-context]] では、第 2 段階の RL の +3.3 ポイントが、訓練データより後に集めた SWE-rebench の月次分割では再現しなかった（→ [[agent-evaluation]]）。
- **報酬が 1 ビットだけであることの副作用**。成功／失敗しか返さない報酬では、「確信がなくても何かを提出する」振る舞いが育ちやすく、途中のどの行動が効いたかも学びにくい。SWE-Master では逆に、確信が持てずに提出しない振る舞いが RL の初期に増えた（上の表）。報酬を 1 ビットのまま、**ステップ単位で学習に使う行動を選ぶ**のが SWE-MeM の Memory-aware GRPO である。成功した軌跡でも質の悪い圧縮や遅すぎる圧縮は学習から外し、上限を超えて失敗した軌跡では「残りがわずかなのに圧縮しなかったステップ」だけを罰する。プロセス報酬や途中の検証は、この限界に対する今後の論点として残っている。
- **残り予算を見せる**。SWE-Master は残りのターン数を、SWE-MeM はステップ数と文脈の残りを、毎ターンの観測に添えて訓練した。方策が予算を条件に判断できるようにする工夫で、MemGPT の容量の警告（→ [[agent-memory]]）を訓練の側に持ち込んだ形である。
