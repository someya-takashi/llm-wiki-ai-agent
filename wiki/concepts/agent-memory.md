# Agent Memory（エージェントの記憶）

LLM（Large Language Model, 大規模言語モデル）エージェントが**過去のやり取り・獲得した知識・作業の途中状態を、コンテキストウィンドウ（モデルが一度に読める最大トークン数）の限界を超えて保持し、必要なときに取り出す**ための仕組みの総称。LLM 自体はステートレス（推論のたびにコンテキストに入っているものしか「覚えて」いない）なので、エージェントの記憶はすべて**設計で外付けする**ことになる。慣例的に、コンテキスト内に載っているものを**短期記憶**、外部ストアに永続化されたものを**長期記憶**と呼ぶ。

記憶の実装層は大きく 3 つに分けられる:

1. **コンテキストそのもの** — 会話履歴・スクラッチパッドをそのまま持ち回る最も単純な形。限界に達したら要約か切り捨てになる。何をどう積むかの設計は [[context-engineering]] の領域。
2. **検索で引く非パラメトリック記憶** — 知識を外部索引（ベクトル DB 等）に置き、必要なときに検索して注入する。[[retrieval-augmented-generation]]（RAG）が確立した「知識はパラメータでなく索引に置く」原則の延長で、索引の差し替え（hot-swap）による更新可能性を持つ（[[summaries/2020-rag]]）。
3. **エージェントが自己管理する記憶** — 何を覚え、何を退避し、何を呼び戻すか、さらにはどう意味づけ・接続するかの判断まで**エージェント自身**に委ねる形。配置の自己管理が MemGPT、組織化・進化の自己管理が A-Mem。

## 何を外部化しているのか — 4 つの内容と 4 つのアーキテクチャ

上の 3 層は**実装の層**による分け方だが、[[summaries/2026-externalization]]（上海交通大学ほか, 2026）は同じ空間を**保存される内容**と**設計の成熟度**の 2 軸で切り直しており、本ページの代表手法を並べ直すのに有用である。

### 4 つの内容

| 内容 | 何を保存するか | 性質 |
|---|---|---|
| **作業文脈**（working context） | 開いているファイル・一時変数・能動的な仮説・部分的な計画・実行のチェックポイント | **急速に変化し、古びると価値を失う**。外部化されなければコンテキストのリセットや中断で消える |
| **エピソード的経験**（episodic experience） | 決定点・ツール呼び出し・失敗・結果・反省 | 具体的な**先例**として働き、既知の誤りの繰り返しを避け、後の抽象化の原材料になる |
| **意味的知識**（semantic knowledge） | 領域の事実・一般的なヒューリスティクス・プロジェクトの慣習・安定した世界知識 | **「エピソード的記憶は*ある事例で*何が起きたかを語り、意味的記憶は*事例をまたいで*何が成り立つ傾向にあるかを語る」** |
| **パーソナライズされた記憶**（personalized memory） | 特定のユーザー・チーム・環境の選好・習慣・反復する制約 | **一般的な自己改善のストアへ畳み込んではならない**——ユーザー固有のトレースは**異なる保持・検索・プライバシーの規則に従う** |

**4 番目の分離が実務で効く。** 「ユーザーの好み」と「タスクの知識」を同じストアに入れると、**削除要求・保持期間・アクセス制御の要件が混ざる**。→ [[agent-safety-and-guardrails]]

**そして記憶とスキルの境界も同サーベイが明示している**——反復する手続き的な規則性は最初エピソード的なトレースの中のパターンとして現れるが、**ハーネスがそれを明示的な再利用可能な指針へ*昇格*させた時点で、それはもはや記憶ではなく [[agent-skills]] の層に属する**。**記憶は「過去に何が起きたかの証拠」であって、それ自体は手続き的な指針ではない。**

### 4 つのアーキテクチャ — 保存から制御へ

| 段階 | **何を解くか** | 代表 |
|---|---|---|
| **モノリシックな文脈** | **存在**（そもそも履歴を持てるか） | 全履歴／要約をプロンプトへ。透明でプロトタイプは容易だが、**状態はセッションとともに消える** |
| **検索ストアつきの文脈** | **容量** | 本ページの (2) 非パラメトリック記憶。**容量を解く代わりに記憶の品質を*検索の問題*へ変える**（GraphRAG・ENGRAM・SYNAPSE が平坦な類似度検索を置き換えようとする） |
| **階層的な記憶とオーケストレーション** | **組織** | [[summaries/2023-memgpt]]・Mem0・Memory-R1・Mem-α。**抽出・統合・忘却**の明示的な操作を導入し、記憶を受動的なストアから**管理されたライフサイクル**へ変える |
| **適応的な記憶系** | **方針** | MemEvolve（符号化・保存・検索・管理のモジュールが独立に進化）・MemVerse／MemRL（ノンパラメトリック RL で検索の振る舞いを更新）・GAM |

> **「これらの段階にわたる主要な移行は*保存から制御へ*である。モノリシックな文脈は存在を解き、検索ストアは容量を解き、階層的な系は組織を解き、適応的な系は方針を解き始める。（…）成熟したエージェントにおいては、記憶は*モデルがどの過去に対して実効的に行動できるかを決めるハーネスの制御面*の一部になる。」**

**階層化には 2 つの独立した系統がある**（この 2 項目はクリップで欠落しており原ページから復元した）。

- **時空間的な資源の分離** — **OS の論理**を借り、記憶を能動的に管理されなければならない制約された資源として扱う。**熱い作業状態と冷たいロングテールのストレージを分け、タスクの要求に応じて階層をまたいでスワップする**（[[summaries/2023-memgpt]]・MemoryOS）。**利得は「固定のコンテキスト予算のもとでの実効容量の向上」**。
- **認知的機能による意味の分離** — **機能あるいは内容の型**で組織し、異種の記録が同じチャネルを通らないようにする。MemoryBank・MIRIX が**イベント／ユーザープロファイル／世界知識**を、MemOS が**明示的記憶と暗黙記憶**を、xMemory が**トピック–イベントの階層**を分ける。**「目標は単にきれいな分類法ではなく、複雑なタスク条件のもとでのより精密な検索である。」**

**本ページの [[summaries/2023-memgpt]] は前者、[[summaries/2025-a-mem]] は後者に近い**——同じ「階層的記憶」でも**分離の軸が違う**ことが、この整理で初めて見える。

### 成功基準を「保存量」から「変換」へ

**同サーベイの最も持ち帰る価値のある主張が評価基準の置き換えである。**

> **記憶の成功基準は「どれだけ保存したか」ではなく「*現在の決定を読み取り可能にしたか*」である。**

理由は Norman の認知的人工物の枠組みから来る（→ [[harness-engineering]]）——**記憶の外部化は、内的な*想起*の問題を外的な*再認と検索*の問題へ変換する。「膨大なストレージを持つが検索が弱い系は、なお誤った問題表現をモデルへ提示している——履歴は存在するが、タスクは変換されていない。」**

**ここから失敗モードが「実装のバグ」ではなく「表現設計の失敗」として整理される。** これはデバッグの分岐としてそのまま使える。

| 失敗 | 症状 | 何が壊れているか |
|---|---|---|
| **古びた記憶** | 時代遅れの問題表現を提供する | 鮮度の管理 |
| **過度に抽象化された記憶** | 現在の決定に必要な**運用上の詳細**を失う | 抽象の粒度（高すぎ） |
| **過少に抽象化された記憶** | プロンプトをノイズで溢れさせ、**外部化が単純化するはずだった再認のタスクそのものを劣化させる** | 抽象の粒度（低すぎ） |
| **汚染された／矛盾する記憶** | 誤った前提を検索されたスライスへ埋め込み、将来の推論を汚染する | 出所と整合性の管理 |

**いずれも「保存が少なすぎた／多すぎた」ではなく「*履歴を使える現在へ変換しなかった*」である。** 最後の 1 つは安全性の問題でもある——**記憶の汚染（memory poisoning）** は、同サーベイが挙げる 3 大脅威の 1 つで、**破損したエピソード的トレースが将来の推論を静かに歪める** → [[agent-safety-and-guardrails]]。

## 代表手法

### MemGPT — OS 的な階層記憶と自己管理

[[summaries/2023-memgpt]]（2023, ICML 2024）は、コンテキストを OS の物理メモリに、外部ストレージをディスクに見立て、**仮想メモリのページングに倣った virtual context management** を定式化した。この分野の基本語彙の多くはここで定義されている:

- **main context の 3 分割**: 読み取り専用の system instructions ／ 読み書き可能な **working context**（ユーザーの事実・好みなど「常に見えているべき要点」）／ 流動履歴の **FIFO queue**（先頭に追い出し済み履歴の**再帰的要約**が常駐）
- **external context の 2 種**: **recall storage**（全メッセージ履歴の DB）と **archival storage**（任意テキストの読み書き DB）
- **自己管理**: queue manager がコンテキストの 70% で **memory pressure 警告**を挿入し、LLM は function call で重要情報を退避する。100% でフラッシュし再帰的要約を更新。検索は**ページネーション**付きで、コンテキストをあふれさせずに何度でも引ける。
- 効果の実証: 過去セッションの詳細を問う Deep Memory Retrieval で GPT-4 単体 32.1% → MemGPT 92.5%。文書 QA では「retriever の top-K が上限」という固定コンテキストの構造をページング検索で破り、コンテキスト長に性能が影響されなくなった。

重要な含意は 2 つ。第一に、**記憶管理はツール呼び出しの一種**として実装できる（作用先が外部世界でなく自分のコンテキストである「内向きのツール」→ [[tool-use-and-function-calling]]）。第二に、記憶の取捨選択をモデルに委ねる以上、**退避し損ねた情報は静かに失われる**——自己管理の信頼性が新しい失敗モードになる。

### A-Mem — 記憶の組織化と進化の自己管理

MemGPT が「どこに置くか」（階層間の配置）を自己管理したのに対し、[[summaries/2025-a-mem]]（A-Mem, 2025）は「**どう意味づけ、どう繋ぐか**」（構造の側）を自己管理の対象にした。着想源は Zettelkasten（ツェッテルカステン, 原子的なメモを相互リンクさせて知識網を育てるノート術）で、中核操作は 3 つ:

- **ノート構築**: 保存時に LLM がキーワード・タグ・文脈的説明を付与した構造化ノートを作り、属性込みのテキストから埋め込みを計算する——生ログの蓄積でなく、**書き込み時に意味づけを済ませる**。
- **リンク生成**: 新ノートの埋め込みで top-k の近傍を粗く絞り、**接続すべきかは LLM が判断**する（埋め込み類似度では見えない因果・概念的つながりを拾う 2 段構え）。
- **記憶進化（memory evolution）**: 新しい記憶の到着を引き金に、**近傍の既存記憶の文脈・タグを LLM が書き換える**。記憶は書いたら終わりでなく、後続の経験によって再解釈され続ける——固定スキーマ（グラフ DB 等）では表現できない動的な組織化。

長期会話ベンチマーク LoCoMo の multi-hop 質問（セッションをまたぐ情報の接続）で既存手法の 2 倍超の F1 を、**全履歴注入や MemGPT 比 約 1/10 のトークン**（約 1,200〜2,500 vs 16,900）で達成し、アブレーションでリンク生成（土台）と記憶進化（上積み）の補完関係も示した。一方で、**既存記憶を書き換える設計は誤った改変が静かに蓄積するリスク**と表裏であり（下記「忘却と監査」）、書き込みのたびに LLM 呼び出しが走るコストは読み出し節約と別勘定になる。

### Reflexion — エピソード記憶に「反省」を蓄える

[[summaries/2023-reflexion]]（2023）は、何を記憶するかという観点で対照的な設計を示した: 保存するのは事実や履歴ではなく、**失敗試行から言語化した反省文**である。エピソード記憶（episodic memory, 個別の経験の記録）に反省を蓄えて次試行のコンテキストに注入することで、重み更新なしの試行間学習を実現した。MemGPT が「何でも保存して検索で取り出す」汎用記憶なら、Reflexion は「教訓だけを蒸留して保存する」目的特化記憶であり、**記憶の内容（事実 vs 反省 vs 計画）は独立した設計軸**であることを示す → [[self-reflection]]。

### 本番運用の記憶 — Anthropic Research

[[summaries/2025-multi-agent-research-system]]（2025）は、MemGPT 型の設計が本番プロダクトでどう使われるかの実例を与えた:

- リードエージェントは**最初に立てた計画を外部メモリへ保存**する（200k トークンでの切り詰めで計画を失うのが最悪の失敗だから）
- 長い作業は**フェーズごとに要約して外部メモリへ書き、クリーンなコンテキストの新サブエージェントに引き継ぐ**（MemGPT の recursive summary + フラッシュに相当する運用）
- サブエージェントの成果物は**ファイルシステム等に直接永続化し、参照だけを渡す**——多段の「伝言ゲーム」による情報劣化とトークン浪費を防ぐ

### ファイルシステム＝究極のコンテキスト — Manus

製品側の到達点が Manus（[[summaries/2025-manus-context-engineering]], 2025）の設計である: **ファイルシステムを「サイズ無制限・永続・エージェント自身が読み書きできる」外部化メモリ**として扱い、モデルがオンデマンドにファイルへ書き・読むことを学ぶ。切り詰め・要約のような不可逆圧縮は「どの観測が 10 ステップ後に効くか予測できない」ためリスクと断じ、圧縮は**復元可能な参照**（Web ページは URL・文書はパスを残して本文を落とす）に限定する。また **todo.md を絶えず書き直してコンテキスト末尾へ計画を復唱（recitation）**し続けることで、長ループ（平均 50 ツール呼び出し）での目標喪失を防ぐ——「計画の外部化＋定期再掲」の最初期の製品実装記録であり、MemGPT の階層記憶・Anthropic Research の構造化 artifact と同じ結論への独立の収束である → [[context-engineering]]。

### 構造化されたノート取り — 最小のエージェント的記憶

上の 2 節（MemGPT の階層記憶・Manus のファイルシステム）が「仕組み」を作り込むのに対し、**最も少ない実装で同じ効果を得る形**が [[summaries/2025-effective-context-engineering]]（Anthropic, 2025）の **structured note-taking（構造化されたノート取り）**である。同記事はこれを **agentic memory** と呼び、「エージェントが定期的にノートを書き、コンテキストウィンドウの外側の記憶へ永続化し、後の時点で引き戻す」技法と定義する。実装は Claude Code の to-do リストや、自作エージェントが維持する `NOTES.md` ファイル程度でよく、それだけで**何十回ものツール呼び出しの間に失われるはずのコンテキストと依存関係**を維持できる——長時間タスクの 3 手法（compaction / ノート取り / サブエージェント）の中で「最小のオーバーヘッドで永続的な記憶を提供する」と位置づけられている → [[context-engineering]]。

効き方を示す事例として挙げられるのが **Claude によるポケモンのプレイ**である。**記憶の構造について何もプロンプトされていない**にもかかわらず、エージェントは探索済み地域の地図・解除した実績・相手別に有効な技といった戦略ノートを自ら作り、「直近 1,234 ステップの間 1 番道路で訓練しており、ピカチュウは目標の 10 レベルに向けて 8 レベル上がった」といった集計を数千ステップにわたって維持する。そして**コンテキストのリセット後は自分のノートを読んで数時間の作業を継続する**。A-Mem が保存時の意味づけとリンク判断を作り込んだのに対し、こちらは**書式も構造もモデルに任せて場所だけ与える**——それでも要約のステップをまたいだ一貫性が成立する、という観察である。同記事の時点で Claude Developer Platform にはファイルベースのメモリツールがベータ提供されており、この形が製品機能として標準化されつつある。

### マルチエージェントでの記憶共有 — Fugu-Ultra

複数エージェント構成では「誰の記憶を誰に見せるか」が加わる。[[summaries/2026-sakana-fugu]] の Fugu-Ultra は「**現在のワークフロー内は隔離**（先行者の道筋に引きずられる orchestration collapse を防ぐ）・**過去のワークフローのツール呼び出し履歴は共有**（同じ環境調査の重複を防ぐ）」という切り分けを採った → [[multi-agent-systems]]。

### CLAUDE.md — 4 階層のファイルベース記憶と、埋め込みを使わない選択

[[summaries/2026-dive-into-claude-code]]（2026）が Claude Code v2.1.88 の公開ソースから解剖した記憶の系は、**本ページの他の手法とは正反対の賭けをしている**——**埋め込みもベクトルインデックスも使わない**。

**階層は 4 水準**で、優先度と可視性が対応している。

| 水準 | 場所 | 性格 |
|---|---|---|
| **Managed** | `/etc/claude-code/CLAUDE.md` 等 | OS 水準のポリシー（全ユーザー） |
| **User** | `~/.claude/CLAUDE.md` | 私的な大域の指示 |
| **Project** | `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` | **コードベースにチェックインされる** |
| **Local** | `CLAUDE.local.md` | gitignore される、私的なプロジェクト固有の指示 |

発見は現在のディレクトリからルートまで遡り、**読み込みは「優先度の逆順」——後から読み込まれたファイルほどモデルの注意を受ける**。CWD より下の入れ子ディレクトリのルールは**遅延して読み込まれる**ので、**モデルの指示集合は会話の途中で、探索が進むにつれて増えていく**（→ [[context-engineering]]）。モジュール化のための **`@include` ディレクティブ**（`@path`, `@./relative`, `@~/home`, `@/absolute`）もあり、循環参照は処理済みパスの追跡で防がれ、**存在しないファイルは静かに無視される**。

#### 検索に埋め込みを使わないという判断

**記憶の検索は、記憶ファイルのヘッダを LLM でスキャンして最大 5 ファイルを選ぶ方式で、エントリ粒度ではなくファイル粒度である。** 論文はトレードオフを明示している。

> **埋め込みベースの系は個々のエントリをより選択的に検索できるが、検査可能性とインデックス維持に必要なインフラのコストを払う。**

**得ているのは監査可能性である**——「ユーザーはエージェントが見るいかなる指示も読み、編集し、バージョン管理し、削除できる」。本ページの [[summaries/2025-a-mem]] や [[summaries/2020-rag]] 系が採る**埋め込み検索の対極**にあり、**[[summaries/2025-manus-context-engineering]] の「ファイルシステム＝究極のコンテキスト」と同じ側**に立つ。本 wiki の記憶の設計空間は、この 2 極の間に広がっていると読める。

#### 最も重要な含意 — 記憶は「指針」であって「強制」ではない

**この論文が記録した中で、記憶設計に最も効く一節がこれだと思う。**

> **CLAUDE.md の内容はシステムプロンプトの内容としてではなく、ユーザーコンテキスト（user メッセージ）として届けられる。**（中略）**会話的なコンテキストとして届けられるため、これらの指示へのモデルの遵守は保証されたものではなく確率的である。** 権限ルール（deny-first の順序で評価される）が決定論的な強制の層を提供する。**これは指針（CLAUDE.md、確率的）と強制（権限ルール、決定論的）の間の意図的な分離を作る。**

**つまり「記憶に書いたことは守られるとは限らない」ことが、届け方の構造として設計に埋め込まれている。** エージェントの記憶を設計するとき、**守らせたい制約を記憶に書くのは誤り**であり、それは決定論的な層（権限・スキーマ検証・フック）へ移すべきである——という判断基準になる。→ [[agent-safety-and-guardrails]]

なお実装上の細部として、CLAUDE.md のローダーは読み込んだ内容を **auto-mode 分類器のためにキャッシュする**（`setCachedClaudeMdContent()`）。これは**ローダーと権限系のインポート循環を避けるため**だが、副作用として**分類器の挙動が、会話中に遅延ロードされる新しいルールに影響されうる**（論文が「単一の設定ファイルからは予測が難しい創発的な挙動」の例として挙げている）。

#### 欠けている層 — 経験の記憶

論文は Claude Code の記憶を **2 層しか持たない**と整理する——**事実の層**（CLAUDE.md、auto memory）と**作業の層**（会話ウィンドウ）である。**欠けているのは経験の層**（過去のセッションから学ばれた戦略の、蓄積され自動的に整備されるプレイブック）で、著者らはこれを「**自然な次のステップ**」と呼ぶ。

**本ページの [[summaries/2023-reflexion]]（反省をエピソード記憶に蓄える）や [[summaries/2025-a-mem]]（記憶の組織化と進化）が扱ってきたのがまさにこの層**であり、**本番系にはまだ入っていない**というのが 2026 年時点の状況である。論文が引く記憶サーベイ（hu2025memory）も、エージェントの記憶が「**コンテキストウィンドウ管理の副作用ではなく独立した認知的な基層**」になりつつあると論じ、自動化された記憶管理・RL 駆動の記憶・信頼できる記憶（プライバシー・説明可能性・幻覚への頑健性）を未解決のフロンティアに挙げている。

**セッションをまたぐ永続性の問い**も未解決として残されている——CLAUDE.md（静的な指示）とトランスクリプト（単一セッションの記録）の**間**に何が属するか、そして**単一の基層が「ユーザーの個人的な指示階層」と「共有される組織的な文脈」の双方を、ファイルベースの透明性を保ちながら運べるか**である。

## 設計論点

- **何を残すか**: 事実・好み（MemGPT の working context）／教訓・反省（Reflexion）／計画・進捗（Anthropic Research）は性質が違う。「何でも残す」は検索ノイズと化すため、記憶の**種類ごとに置き場と形式を分ける**のが共通解。
- **いつ書くか**: 容量警告に駆動される退避（MemGPT）と、作業のフェーズ境界での要約（Anthropic Research）の 2 パターンが実証済み。どちらも「あふれてから」では遅い、という点で一致する。
- **どう取り出すか**: 書いた記憶は検索できなければ存在しないのと同じ。ベクトル検索なら [[retrieval-augmented-generation]] の設計論点（検索の質が上限・collapse の監視）がそのまま適用される。MemGPT の「検索を途中で打ち切る」観察は、**読み出し側の根気もモデル能力に依存する**ことを示した。A-Mem の実証——保存時の意味づけ（属性込み埋め込み）が検索の質を底上げし、top-k は増やしても頭打ちになる——は、読み出しの改善が**書き込み側の設計**で決まることを示す。
- **忘却と監査**: 自己管理記憶は退避漏れ・誤要約で静かに壊れる。何が失われたかを検出する仕組み（履歴の完全保存＝MemGPT の recall storage はその保険）と、記憶の監査可能性が実務では重要。**記憶を書き換える**設計（A-Mem の memory evolution）はこのリスクをさらに強め、進化の巻き戻し・監査の仕組みは未解決の論点として残っている。
- **共有境界**: マルチエージェントでは隔離／共有の張力（上記 Fugu-Ultra）。会話履歴の喪失や情報の抱え込みは MASFT（[[summaries/2025-masft]]）が実測した頻出失敗モードでもある。
- **アーキテクチャ内部にも同型の問題がある**: 「固定容量のメモリに、何を書き・何を上書きし・何を減衰させるか」という本ページの中心問題は、モデルの重み・状態の内部でも独立に進化してきた。attention の系譜（[[summaries/2026-gpt2-to-kimi3]]）では、KV cache の無限成長 → 固定状態への加算（干渉が発生）→ delta rule による選択的上書き → ゲートによる減衰 → チャネル別の細粒度減衰、と発展しており、これは生ログ蓄積 → 上書き型記憶（A-Mem の memory evolution）→ 退避・要約（MemGPT）というエージェント側の系譜の**内側版**である。原記事の結語——「固定容量の連想メモリには追い出しポリシーが要り、学習された選択（ゲート・ルーティング・減衰）が必須」——は、そのままエージェント記憶の設計原則としても読める → [[transformer-architecture]]。
