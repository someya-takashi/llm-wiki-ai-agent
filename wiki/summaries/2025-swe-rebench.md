# SWE-rebench：実際の PR から動くタスクを自動で集め続け、訓練と汚染のない評価に使う

> 原典: [[translations/2025-swe-rebench]] ・ `raw/papers/SWE-rebench_ An Automated Pipeline for Task Collection and Decontaminated Evaluation of Software Engineering Agents.md`
> 著者・年・会議: Ibragim Badertdinov・Alexander Golubev（同等の貢献）ほか 9 名（全員 Nebius）・arXiv:2505.20411（v1: 2025-05、v2: 2025-11）・NeurIPS 2025。`raw/` のクリップは途中で切れた v1 なので、翻訳と本ページは全文がそろった v2 にもとづく。

## 一言まとめ

GitHub のイシューと修正 PR から、**依存関係を入れてテストまで走る「実行できるタスク」を人手なしで集める仕組み**を作り、Python の 3,468 リポジトリから 21,336 件の訓練用データセットを公開した。同じ仕組みで毎月新しい問題を作り、全モデルを同じ足場で 5 回ずつ走らせる**汚染のないリーダーボード**も運営し、SWE-bench Verified の点数の一部が水増しされている可能性を示した。

## 背景と問題意識

SWE-bench（[[summaries/2023-swe-bench]]）以降、コーディングエージェントの評価と訓練には「イシュー＋正解パッチ＋採点用テスト＋そのテストを走らせられる環境」の組が要る。訓練では、エージェントのパッチが正しいかを自動で判定できないと強化学習（RL, Reinforcement Learning, 試行錯誤の結果に報酬を与えて行動を強める学習）の報酬が作れないからである。ところが、PR ごとに当時の依存関係をそろえた環境を作る作業はこれまで人手に頼っていた。SWE-Gym（[[summaries/2024-swe-gym]]）は約 200 人時をかけて 11 リポジトリ・2,438 件にとどまった（→ [[agent-environments]]）。

評価の側にも 4 つの問題があると著者らは整理する。

1. **汚染**（contamination, 評価問題とその答えがモデルの訓練データに入ってしまうこと）。SWE-bench は 2023 年末から公開されており、その後のモデルは問題を見ている可能性がある。
2. **足場**（scaffold, モデルを包んでツールやループを提供する周辺のプログラム）**がばらばら**。作り込んだプロンプト、マルチエージェント、リトライ、best-of-N（N 本作って 1 本選ぶ）でモデル単体の力が見えない。足場自体が SWE-bench の部分集合で調整されていて、暗黙に過適合している。
3. **報告が自己申告**。pass@N を pass@1 として報告する、最終テストの情報を使う、といった誤った報告を外から確かめられない。
4. **1 回の実行は揺れる**。エージェントの軌跡は確率的なので、何回か走らせて一番良い回だけを報告すると能力を過大に見せられる。

著者らは 2024 年に SWE-bench Extra という自動収集のデータセットを出しており（SWE-Gym の付録がこれを並行研究として挙げていた）、本論文はそれを全自動化・大規模化したものにあたる。同じ著者群が後に、このデータセットで Qwen2.5-72B を RL で訓練した論文が [[summaries/2025-swe-rl-long-context]] である。

本論文には 2 つの成果物がある。訓練用の**データセット**と、評価用の**ベンチマーク（リーダーボード）** である。どちらも同じ収集パイプラインから作る。

### 1. 収集パイプライン：45 万件から 2 万 1,000 件へ

**表**: データ収集のファネル（原典の付録 L の表 6）

| 段階 | 入力 | 出力 | 残る割合 |
|---|---|---|---|
| PR とイシューの照合 | 1,000 万 PR・600 万イシュー・3 万 2,000 リポジトリ | 45 万の候補 | 5%（PR に対して） |
| 条件による絞り込み | 45 万 | 15 万 | 33% |
| インストールと検証 | 15 万 | 2 万 1,000 | 14% |
| 品質ラベルの付与 | 2 万 1,000 | 2 万 1,000 | 100% |

**(a) 予備的な絞り込み。** GitHub Archive（GitHub の公開イベントを毎日 JSON で公開しているアーカイブ）からイシューと PR のメタデータを集め、リポジトリは履歴ごと手元に clone する。2025-05-01 より前のイシューにリンクした PR を対象に、寛容なライセンス（MIT・Apache-2.0・BSD など）でコードの 75% 超が Python のリポジトリに限る。さらに「イシューが解決済み」「PR がマージ済み」「1 つの PR が 1 つのイシューに対応」「**PR がテストを追加か変更していて、テスト以外のコードも変えている**」「変更は 1〜15 ファイル」などの条件で絞る。テストを必須にするのは、パッチの正しさを自動で判定するためである。PR の差分はテスト以外の変更（解のパッチ）とテストの変更（テストパッチ）に分ける。

**(b) インストール手順の自動生成。** ここが本論文の中心である。人手でやっていた 2 つの作業を自動にする。

- **バージョンでまとめる**: `git tag` からプロジェクトのバージョンを推定して `major.minor` にそろえ（1.2.3 → 1.2）、同じバージョンのタスクは 1 つの環境を共有する。環境の基準にはグループ内で最も新しい `base_commit` を使う。マイナーバージョンの中では依存関係の互換性が保たれやすく、後のコミットほど環境の修正が入っているからである。約 95% のタスクにバージョンが付いた。
- **手順を LLM に書かせる**: エージェントに自由に試させるのではなく、Agentless（[[summaries/2024-agentless]]）にならった**決まった手順**で LLM を呼ぶ。まず Qwen2.5-72B-Instruct にファイル一覧を見せて、README や setup.py のようなインストール情報がありそうなファイルを最大 10 個選ばせる。次にその中身を読ませて、Python のバージョン・インストールのコマンド・テストのコマンドなどを並べた JSON の「レシピ」を書かせる。レシピはタスクごとに最大 3 つ作る。スクリプトがそれを実行し、失敗したらエラーログを LLM に見せてレシピを直させる。

この方法で、**全リポジトリの 31% について少なくとも 1 件は動く環境が作れた**。人手で環境を作ってある SWE-bench の 18 タスクで試すと、Agentless 型は候補 1 つで 6 件、3 つで 8 件、10 個で 9 件に成功し、対話型のエージェント（Docker の中で自分でコマンドを打って試す方式）は 1 回で 8 件だった。エージェント型のほうが上手なこともあるが計算資源を大きく食うため、大規模な処理には Agentless 型を選んだ。

**(c) 実行による検証。** 環境をコンテナに入れ、PR のテストパッチを走らせて、SWE-bench と同じ 3 条件を確かめる。(1) 解のパッチを当てる前に少なくとも 1 つのテストが落ちる。(2) 落ちていたテストが当てたあとはすべて通る。(3) 通っていたテストは当てたあとも通る。成功した環境では `pip freeze` と `conda env export` で依存関係のバージョンを凍結して記録し、後で同じ環境を作り直せるようにする。

検証で落ちる主な原因（付録 B.5）は次の 3 つである。

- **flaky なテスト**（実行するたびに結果が変わるテスト）。外部 API の呼び出しや浮動小数点の厳密な比較が原因になる。何度か走らせ、1 回でも落ちたら除く。
- **インストールに対話が要る**。途中のエラーを見て依存関係を足していくような古いプロジェクトは、決まった少数の手順では入らない。
- **依存関係のバージョンが固定されていないか、もう公開されていない**。凍結と社内のパッケージミラーで対処した。

**(d) SWE-bench の作り方からの改良（付録 G）。** RL に使うなら、タスクが解けないのは「エージェントの力不足」のときだけであるべきだ、という考えから、元の SWE-bench の方法を 4 点直している。

- PR の差分を `base_commit` と `merge_commit` の間ではなく、PR のブランチの最後のコミット（`head_commit`）との間でとる。間に入った別のマージが無関係なテストを差分に混ぜるのを防ぐためで、SWE-bench Verified から除かれた `sympy__sympy-14821` はこの問題の例である。
- 削除されたテストファイルを、テストを走らせるコマンドから外す。
- テストが「まだ存在しない属性や import」で落ちるタスク（エージェントが正確な関数名を当てるしかない）を見つけるため、エラー出力を省略せずに走らせ、メタデータに記録する。
- 依存関係のバージョンを凍結する。

**(e) 品質ラベルの自動付与。** SWE-bench Verified は人がタスクを 1 件ずつ点検したが、2 万件では無理なので、その人手のラベル（3,800 件超）で Qwen2.5-72B-Instruct をファインチューニングし、3 つの二値ラベルを予測させる。**イシューの明確さ**（開発者が読んで解けるだけの情報があるか）、**タスクの複雑さ**（解くのに 1 時間を超えるか）、**テストパッチの正しさ**（特定の実装に依存しすぎずに修正を確かめているか）である。検証用の 413 件での正解率は複雑さ 81%（素のモデルは 68%）、テストの正しさ 67%（同 60%）、明確さ 79%（同 80%）だった。ラベルは各タスクのメタデータとして配布し、利用者が絞り込みに使う。著者らは変更ファイル数（SWE-bench Lite の基準）より細かく難しさを選べると主張する。ファイル数も粗い目安にはなり、DeepSeek-V3-0324 の解決率は変更ファイルが 1 つで 28.6%、2 つで 20.6%、3 つ以上で 17.5% だった。

データセットのタスクは、イシューが平均 142 語（中央値 91 語）、変更は平均 3.46 ファイル・142 行（中央値 2 ファイル・37 行）、修正前に落ちて修正後に通るテスト（fail-to-pass）は平均 14.6 本（中央値 2 本）である。

### 2. ベンチマーク：同じ条件で、新しい問題だけで測る

データセットから、**2025 年に作られたイシュー**で、解のパッチが 3 ファイル以下・500 語以下、イシューが英語で 16〜1,000 語、LLM が付けた難易度が 3 未満、fail-to-pass のテストが 50 本以下、修正前のテスト実行に AttributeError や ImportError がない、といった条件を満たす **169 リポジトリの 294 問**を選んだ。評価は次の 3 つの原則で行う。

- **評価は著者らが一元的に行い、条件を固定する。** 全モデルを、同じ最小限の ReAct 型の足場（ReAct は「考える → 行動する → 結果を見る」を繰り返す方式 → [[reasoning-and-planning]]）・同じシステムプロンプト・開発元が勧める生成の設定・128K トークンのコンテキストで動かす。ツールは SWE-agent（[[summaries/2024-swe-agent]]）に似たファイルビューアと行範囲の編集コマンド（`open`・`goto`・`scroll_down`・`edit`・`search_file`・`submit` など）で、応答は「推論の文章＋1 つのコマンド」の形で書かせる。**関数呼び出し（function calling, モデルが JSON の引数でツールを呼ぶ API の機能）は使わない**。対応しているモデルとしていないモデルの条件をそろえるためである。
- **問題を継続的に入れ替え、汚染の可能性を印づける。** イシューと PR の作成日をモデルの公開日と照らし、公開日より前のイシューを含む評価には、リーダーボード上で汚染の可能性を示す印を付ける。
- **ばらつきを数える。** 各モデルを 5 回走らせ、平均の解決率に加えて、平均の標準誤差（SEM, Standard Error of the Mean, 5 回の平均がどれくらい揺れるかの目安）と pass@5（5 回のうち 1 回でも解けた問題の割合）を報告する。

著者らはこの設定で測るものを「イシューを理解して計画し、正しいパッチを書く力」と「指示に従い、決まった枠組みの中で動く力」の 2 つだと説明している。オープンなモデルは vLLM（LLM の推論サーバ）で H200 GPU 8 枚のノード 2 台に載せて動かした。最大の DeepSeek-V3 は 294 問の 1 回分に約 7 時間かかった。

## 実験結果と知見

**表**: SWE-bench Verified と SWE-rebench（2025 年 3〜4 月の問題）の比較（原典の表 2 から。解決率は 5 回の平均、%）

| モデル | Verified 解決率 | Verified pass@5 | rebench 解決率 | rebench pass@5 |
|---|---|---|---|---|
| DeepSeek-V3-0324 | 39.7 | 57.4 | 21.3 | 32.4 |
| DeepSeek-V3-1226 | 35.2 | 51.0 | 21.9 | 31.4 |
| Llama-3.3-70B-Instruct | 18.1 | 31.6 | 11.2 | 22.9 |
| Llama-4-Maverick-Instruct | 16.0 | 39.2 | 12.2 | 27.6 |
| Qwen2.5-72B-Instruct | 11.3 | 27.8 | 9.3 | 19.0 |
| Llama-4-Scout-Instruct | 8.8 | 22.2 | 5.3 | 14.3 |
| Qwen2.5-Coder-32B-Instruct | 4.9 | 16.0 | 3.2 | 9.5 |

- **どのモデルも Verified より rebench のほうが低い**。DeepSeek-V3-0324 はほぼ半分（39.7% → 21.3%）になった。
- **DeepSeek-V3 の 2 つの版の差は Verified にしか出ない**。12 月版と 3 月版は rebench ではほぼ同じ（21.9% と 21.3%）なのに、Verified では 35.2% と 39.7% に分かれる。著者らはこれを、古いベンチマークでの汚染の影響の可能性として挙げている（v2 で加筆）。
- **時期で分けた比較**（表 1。2025 年 1 月の問題と 3〜4 月の問題）では、**GPT-4.1 だけが目立って下がった**（31.1% → 26.7%）。表 1 で最も解決率が高いのも GPT-4.1 である。
- **Llama-4-Maverick は pass@5 のわりに平均が低い**。難しい問題を解く力はあるが、毎回は解けない。
- **Qwen2.5-Coder-32B はコード生成のベンチマークでは強いのに、ここでは 3% 前後**。軌跡を見ると、**環境の応答を自分ででっち上げる**（ツールの実行結果が返る前に「ファイルを更新しました」という観測まで自分で書く）か、書式エラーを繰り返すかして、意味のある解の試みに至らない。コードを書く力と、決まった形式でツールを使い続ける力は別物だということである（→ [[coding-agents]]）。
- **Qwen3 は思考モードの有無でほぼ差がない**。235B・32B とも、思考なし（no-think）が思考あり（think）をわずかに上回ることさえあった。
- **解ける問題はモデルごとに違う**。5 モデルが 1 回以上解いた問題の重なりを見ると、5 モデルすべてが解いたのは 49 問で、GPT-4.1 だけが解いた問題が 19 問あった。

## 限界・批判的視点

- **Verified との差が汚染によるものかは切り分けられていない。** rebench の問題は Verified と作り方も分布も違う（Verified の 12 リポジトリより幅広い 169 リポジトリから取る、自動で集めたので記述が不十分な問題も混じる）。全モデルが一様に下がること自体は「rebench のほうが難しい」でも説明がつく。汚染の証拠としてより強いのは、DeepSeek-V3 の 2 版の順位が Verified でだけ開く点や、オープンなモデルの間で Llama-3.3-70B と Llama-4-Maverick の順位が入れ替わる点のような**相対的な変化**のほうである。著者らの表現も「水増しされている可能性がある」にとどまる。フロンティアモデルの汚染は、のちに OpenAI がより直接的な方法で確かめた（[[summaries/2026-swe-bench-verified-retired]]）。
- **SEM は「5 回の実行の揺れ」しか表さない。** 問題そのものを取り直したときの揺れ（[[summaries/2024-error-bars-evals]] が言う誤差）は含まれない。本 wiki での試算では、294 問・解決率 20% のとき問題数から来る標準誤差は約 2.3 ポイント（95% で ±4.6 ポイント）になる。表の SEM（0.3〜1.8）よりずっと大きい。しかも表 1 は 294 問をさらに時期で分けており、各期間の問題数は書かれていない。GPT-4.1 の 4.4 ポイントの低下も、Llama 同士の順位の入れ替わりも、この誤差の範囲に入りうる（→ [[agent-evaluation]]）。
- **品質ラベルはあまり当たらない。** テストの正しさは正解率 67% で、イシューの明確さはファインチューニングしても素のモデル（80%）から改善しなかった（79%）。明確なイシューを見つける再現率は 0.20 しかない。ベンチマークの「難易度 3 未満」の条件はこのラベルに頼っている。データセットの統計で、難易度・明確さのスコアの平均が 1 前後（大半が「易しく明確」）に偏っているのも、ラベルの精度と合わせて読む必要がある。
- **「インストールできたもの」だけが残る偏り。** 環境を作れたのはリポジトリの 31% で、インストールと検証の段階で残るのは 14% である。依存関係の古い・複雑なプロジェクトは系統的に抜ける。SWE-Gym が指摘していた「自動化すると、セットアップの難しいタスクが抜ける」という偏りがそのまま当てはまる（→ [[agent-environments]]）。ベンチマークではさらに 3 ファイル以下・難易度 3 未満に絞っている。
- **足場の固定は「この足場での能力」を測る。** 関数呼び出しを使わずテキストのコマンドで操作させるので、関数呼び出しで訓練されたモデルや、別の足場で力を出すモデルには不利になりうる。著者ら自身、別の足場ならより高い点が出うると認めている。足場をそろえる利点（[[harness-engineering]] でいう、モデルとハーネスの寄与の混同を避けること）と引き換えである。
- **インストール手順の生成は 18 リポジトリで調整しただけ**で、品質の自動評価も人の判断を完全には再現できない。著者らは、記述が不十分でイシューだけからは解けないタスクが混じりうることを限界として明記している。
- **Python だけ**。v2 では、他の言語に広げるには言語ごとの部品の実装が要ると書き直された。
- **評価用の問題もいずれ公開されて汚染される。** 新しい問題を作り続けることでしか汚染を避けられないので、リーダーボードの価値は運営が続くことにかかっている。

## 実装・運用上の示唆

- **社内でエージェントを評価するなら、「モデルの公開日より後に作られた問題」を分けて持つ。** 本論文の要点はリーダーボードそのものより、日付で汚染を管理する考え方である。自分たちのリポジトリの最近のイシューと PR から問題を作れば、どの公開モデルの訓練データにも入っていない評価になる。
- **同じ条件で複数回走らせ、平均と pass@k を両方見る。** 平均だけでは「解けるが安定しない」モデル（Llama-4-Maverick 型）を見落とし、最良の 1 回だけでは過大評価になる。問題数から来る誤差も別に計算する。
- **環境構築は「安い固定手順を何本か」から始める。** LLM にレシピを 3 本書かせ、失敗ログで直させるだけで、人手の環境がある 18 件の試験では 8 件が動いた（1 本だけなら 6 件）。対話型のエージェントはタスクの多い重要なリポジトリにだけ使う（付録 L の提案）。
- **評価環境を作るときの細部をまねる。** `head_commit` との差分をとる、テストは省略なしのエラー出力で走らせる、依存関係を凍結する、flaky なテストは何度か走らせて除く。どれも「正しい解が採点で落ちる」事故を減らす。
- **小さなモデルを評価に使うなら、まず書式とツール操作を見る。** Qwen2.5-Coder の例のように、コード生成が得意でもエージェントとしては動かないことがある。失敗した軌跡を読むと、能力の問題か形式の問題かが分かる。

## 用語と略称

- **SWE（Software Engineering）**: ソフトウェアエンジニアリング。ここでは実際のリポジトリでイシューを直す作業を指す。
- **LLM（Large Language Model）**: 大規模言語モデル。
- **PR（Pull Request）**: GitHub でコードの変更を取り込んでもらうための依頼。
- **RL（Reinforcement Learning）**: 強化学習。
- **汚染（contamination）**: 評価の問題や答えが訓練データに含まれていること。点数が実力より高く出る。
- **足場（scaffold）**: モデルを包み、ツール・プロンプト・ループを提供するプログラム。ハーネスとも呼ぶ（→ [[harness-engineering]]）。
- **ReAct（Reasoning + Acting）**: 推論の文章と行動（ツール呼び出し）を交互に出させる方式（→ [[summaries/2022-react]]）。
- **Agentless**: エージェントに自由に行動させず、決まった手順で LLM を呼ぶ方式（→ [[summaries/2024-agentless]]）。
- **fail-to-pass / pass-to-pass**: 修正前に落ちて修正後に通るテスト／修正の前後とも通るテスト。前者で「直ったか」、後者で「壊していないか」を判定する。
- **flaky なテスト**: 同じコードでも実行のたびに結果が変わるテスト。
- **SEM（Standard Error of the Mean）**: 平均の標準誤差。
- **pass@k**: k 回試したうち 1 回でも正解した問題の割合。
- **best-of-N**: N 本の候補を作って 1 本を選ぶ方式。
- **SPDX**: オープンソースのライセンスを識別子（MIT、Apache-2.0 など）で表す標準。
- **vLLM**: LLM の推論を高速に提供するオープンソースのサーバ。
- **GH Archive（GitHub Archive）**: GitHub の公開イベントを日ごとに記録して公開しているプロジェクト。
