# R2E-Gym：コミットから訓練環境を作り、テストと検証器を組み合わせて候補を選ぶ

> 原典: [[translations/2025-r2e-gym]] ・ `raw/papers/R2E-Gym_ Procedural Environments and Hybrid Verifiers for Scaling Open-Weights SWE Agents.md`
> 著者・年・会議: Naman Jain・Jaskirat Singh（同等の貢献）ほか 4 名（UC Berkeley, Australian National University）・arXiv:2504.07164（v1: 2025-04-09、版は v1 のみ）。`raw/` のクリップは図・表・脚注が多く欠けていたので、翻訳と本ページは arXiv の HTML 版 v1 にもとづく。

## 一言まとめ

人間が書いたイシューのない**コミットからも実行できる訓練タスクを作る方法**（SweGen）で 8,135 件の環境を集め、Qwen2.5-Coder-32B を SFT で SWE-bench Verified の 34.4% まで訓練した。さらに、同じ問題を 26 回解かせて 1 本を選ぶ場面について、**テストを走らせて選ぶ検証器と、軌跡を読んで選ぶ検証器はどちらも 43% 前後で頭打ちになるが、2 つを組み合わせると 51.0% まで伸びる** ことを、それぞれの弱点の分析とともに示した。

## 背景と問題意識

コーディングエージェントを訓練するには、「イシュー（問題文）＋正解のコード変更＋採点用のテスト＋そのテストを走らせられる環境」の組が大量に要る（→ [[agent-environments]]）。先行の SWE-Gym（[[summaries/2024-swe-gym]]）は、実際の GitHub のイシューとそれを直したプルリクエスト（PR）から 2,438 件の環境を作ったが、**人間がイシューを書き、テストを付けた PR しか使えない**ので数が増えない。リポジトリのコミットの大半には、対応するイシューがないからである。

もう 1 つの論点は、推論時に計算を増やして精度を上げる **test-time compute**（→ [[test-time-compute]]）の選び方である。同じ問題をエージェントに K 回解かせると、K 本のうちどれかが正解である割合（Pass@K）は大きく上がる。しかし提出できるのは 1 本なので、**K 本から正解を選ぶ検証器**（verifier, 出力の正しさを判定する仕組み）が要る。選び方には 2 つの流儀があった。

- **実行ベース**（execution-based）: テストを書いて各候補のパッチに走らせ、通った数で選ぶ。Agentless（[[summaries/2024-agentless]]）の「再現テスト＋回帰テスト」がこの例である。
- **実行なし**（execution-free）: 軌跡（trajectory, エージェントがたどった思考・行動・観測の列）とパッチを LLM に読ませ、正しそうかを点数にする。SWE-Gym の ORM（Outcome-supervised Reward Model, 最終結果の成否だけを見て成功確率を出す報酬モデル）がこの例である。

2 つは別々に研究されてきて、どちらが何を苦手とするかは比べられていなかった。本論文はこの 2 つの問い（データを増やす方法と、候補の選び方）を同じ環境の上で扱う。

## 提案手法 / 主張

### 1. SweGen: コミットから訓練環境を作る

<figure>

![](../../raw/assets/2025-r2e-gym/overview-p1-v10.png)

<figcaption>図1(a)（再掲）: 実行できる訓練環境の数。人間の PR に頼る方法（灰）に対し、SweGen（緑）は 2.5 倍を集めた。</figcaption>
</figure>

手順は 4 段ある。

1. **リポジトリとコミットを選ぶ**。コミット数の多い Python リポジトリを集め、ルールと LLM の判定で「小さくまとまったコード変更」のコミットに絞る。しきい値は、テスト以外のファイルの変更が 5 個まで、編集行が 100 行まで、パッチが 2,000 文字まで、などである。
2. **当時の環境を作る**。過去のコミットのコードは、今の依存ライブラリでは動かないことが多い。Docker の中で依存関係のバージョンの組み合わせを順に試し、最初にビルドが通った組み合わせを使う。この作業は**半手動**で、著者ら自身がスケールさせにくいと書いている。
3. **採点用のテストを用意する**。修正前のコードで失敗し、修正後のコードで通るテスト（F2P, Fail→Pass テスト）を、コミットに含まれる既存のテストから探す。テストがないコミットでは、正解のコード変更を見せたうえで LLM にテストを書かせる。
4. **問題文を逆に作る**（逆翻訳, back-translation）。コード変更から「このバグを直してほしい」というイシューを LLM に書かせる。コード変更だけを見せると一般的で中身のない文になるので、**失敗するテストとその実行結果（エラーメッセージ、失敗したアサーション）も見せる**。人間のバグ報告にも失敗するテストや実行の痕跡が含まれていることが多い、という観察にもとづく。プロンプトでは「解決策を明かさない」「テスト関数やファイル名に直接触れない」「人間が書くように平易に」などを指示している（翻訳の Listing 3）。

こうして 8,135 件（R2E-Gym）を集め、SWE-bench の評価用リポジトリと重なるものを除いた 4,578 件・10 リポジトリ（R2E-Gym-Subset）を実験に使う。部分集合の内訳は pandas が 31.5%、numpy が 17.1%、pillow が 13.5% で、上位 3 つで 6 割を占める。

### 2. エージェントと訓練

足場（scaffold, モデルを包んでツールとループを与える周辺のプログラム）は、OpenHands をもとにした最小限の ReAct 型（→ [[reasoning-and-planning]]）で、ツールはファイルの閲覧・編集、検索、bash の実行、提出の 4 つだけである。専用のワークフローはなく、再現スクリプトを書く・バグを探す・直す・確かめるまでをエージェントが自分で行う（→ [[coding-agents]]）。

訓練データは、Claude 3.5 Sonnet（v2）にこの足場で R2E-Gym-Subset を解かせ、テストに通った軌跡だけを残したもの（棄却サンプリング, rejection sampling）で、2,048 環境から 3,321 本になった。軌跡は 40 ステップ・32K トークン・10 分までに制限している。これで Qwen2.5-Coder の 7B・14B・32B を、思考と行動の両方を正解として全パラメータの SFT（Supervised Fine-Tuning, 教師ありファインチューニング）にかけた。

### 3. 2 種類の検証器と、その組み合わせ

**実行ベースの検証器**は 2 つの部品からなる。

- **テストエージェント**: イシューの再現テストを書く専用のエージェント。Qwen2.5-Coder-32B を、Sonnet が書いたテスト生成の軌跡 2,203 本で SFT した。1 回の実行で 10 個のテストを含むスクリプトを書く。Agentless のように 1 回の呼び出しでテストを書かせるのではなく、**既存のテストを読み、書いたテストを実行して直しながら**作る点が違う。
- **回帰テストのフィルタ**: リポジトリにもとからあるテストを走らせ、既存の機能を壊したパッチを落とす。

スコアは「回帰テストの成績が最も良いパッチのうち、生成したテストに通った数」で、それ以外のパッチは 0 点である。

**実行なしの検証器**は、SWE-Gym と同じ形の ORM である。Qwen2.5-Coder-14B に、イシュー・軌跡・パッチを読ませて「正しいか」を YES／NO で答えさせ、YES の確率をスコアにする。成功と失敗が同数になるようにそろえた 5,700 本の軌跡で、LoRA（Low-Rank Adaptation, 小さな追加行列だけを学習する手法 → [[parameter-efficient-fine-tuning]]）で訓練した。

**ハイブリッド検証器**は 2 つを順に使う。

1. 実行なしの検証器のスコアで、上位 n 本だけを残す。
2. 残った候補について回帰テストで絞り、実行ベースのスコアに実行なしのスコアを足して最も高い 1 本を選ぶ。

実行ベースのスコアは「通ったテストの数」なので同点が多い。実行なしのスコアは 0〜1 の連続値なので、**同点を割る役**になる。先に上位 n 本に絞ると、まれに出る「誤ったパッチだけを通すテスト」の影響が見込みのある候補の中だけに限られる。絞り込みが効いた理由を、著者らはおそらくこれだろうと推測している。

## 実験結果と知見

評価はすべて SWE-bench Verified（500 問）と SWE-bench Lite（300 問）で、指標は解決率である（→ [[agent-evaluation]]）。

### 訓練データの効果

**表**: 同じ Qwen2.5-Coder を SWE-Gym と R2E-Gym で訓練したときの解決率（%、Pass@1。原典の表 3 から Verified の列）

| モデルサイズ | 訓練前 | SWE-Gym | R2E-Gym | 差 |
|---|---|---|---|---|
| 7B | 1.8 | 10.6 | 19.0 | +8.4 |
| 14B | 4.0 | 16.4 | 26.8 | +10.4 |
| 32B | 7.0 | 20.6 | **34.4** | +13.8 |

- **データを増やすと伸びるが、小さいモデルは早く止まる**。軌跡を 100 本から 3,200 本まで倍々に増やすと、32B は最後まで伸び続けた（図では 3,200 本で約 34%）が、14B は約 800 本で頭打ちになった。SWE-Gym が調べた約 500 本の先まで延ばした結果である。
- **合成したイシューでも、実際のイシューとほぼ同じ効果がある**。軌跡 400 本ずつで比べると、実際の GitHub のイシューで 28.0%、SweGen で作ったイシューで 27.8% だった。
- **思考も一緒に学ばせたほうが良い**。行動だけで訓練すると 30.4%、思考と行動で訓練すると 34.4% だった（本文では 34.2% と書かれている）。

### 2 種類の検証器の弱点

R2E-Gym-32B に Verified の各問題を 26 回解かせる（温度 0 で 1 本、温度 0.8・0.9 で 25 本）。26 本のどれかが正解である割合（Pass@26）は 64.4% だが、検証器が選んだ 1 本が正解である割合（Best@26）は、実行ベースで 43.7%、実行なしで 42.8% にとどまり、どちらも候補が 10 本を超えたあたりから頭打ちになった。

<figure>

![](../../raw/assets/2025-r2e-gym/bestk_plot_agent.png)

<figcaption>図14（再掲）: 候補の数 K を増やしたときの Pass@K（青、選び方が完璧なときの上限）と各検証器の Best@K。K=26 で上限 64.4% に対し、実行ベース（緑）43.7%、実行なし（赤）42.8%、ハイブリッド（紫）51.0%。</figcaption>
</figure>

**実行ベースの弱点は「区別できない」こと**。テストは、正しいパッチと誤ったパッチで違う結果になってはじめて選別に使える。この割合（判別率）を調べると、大半の問題で区別に役立つテストは 20% 未満だった。生成したテストの多くは、修正前のコードでも通ってしまう（バグを再現していない）か、正解のパッチでも落ちる（テスト自体にバグや例外がある）。これは訓練したテストエージェントだけでなく、Claude 3.5 Sonnet にプロンプトで書かせたテストでも、Agentless-1.5 のテストでも同じ傾向だった。さらに一部の問題では、**誤ったパッチを通して正しいパッチを落とす「毒性のあるテスト」**（toxic test）がテスト全体の最大 10% 出た。

**実行なしの弱点は「パッチ以外を見てしまう」こと**。検証器にパッチだけを見せると Best@26 は 42.8% → 37.6% に下がり、軌跡から思考だけを抜くと 41.4% だった。正しさを決めるのはパッチだけなのに、検証器は**エージェントの思考に大きく頼っている**。注意（attention）の重みを調べると、誤ったパッチを「正しい」と判定した例で、検証器が最も注目していたのは「再現できた、修正した、エッジケースも確認した、後方互換性も保った」「修正はうまくいった」といった**エージェント自身の自己申告**だった。

### 組み合わせの効果

<figure>

![](../../raw/assets/2025-r2e-gym/hybrid-ablation-v3.png)

<figcaption>図8（再掲）: ハイブリッド検証器のアブレーション（SWE-bench Verified、26 本から選択）。実行なし 42.7%、実行ベース 43.8%、生成テストなし（回帰テストだけ）47.4%、テストエージェントの代わりに Agentless のテスト 48.8%、上位 n の絞り込みなし 49.8%、全部入り 51.0%。棒の値は本文の 42.8%・43.7% とわずかに違う。</figcaption>
</figure>

- ハイブリッドにすると **Best@26 が 51.0%**（16 本からなら 49.4%）になり、単独の検証器より 7〜8 ポイント高い。
- 部品ごとに見ると、回帰テストだけでも 47.4% まで上がる。生成した再現テストを加えると 51.0%、テストを Agentless のものに替えると 48.8%、上位 n の絞り込みを外すと 49.8% だった。
- **テストを増やすほうが、候補を増やすより安く効く場合がある**。編集エージェントの候補を 16 本から 21 本に増やすと 47.6% → 48.4% だが、テストエージェントを 5 回多く走らせると 49.3% になった。テストエージェントの実行は編集エージェントよりかなり安いと著者らは注記している。

### 他の手法との位置関係

原典の表 4 によれば、51.0% は当時のオープンなモデルの中で最も高い。同じ表の SWE-Gym は 16 本から選んで 32.0%、SWE-RL-70B は 500 本からテストで選んで 41.0%、DeepSeek-R1 を Agentless で使うと 49.2% である。プロプライエタリなモデルでは、o1 の Agentless が 48.0%、Claude 3.5 Sonnet（表では Claude-3.6-Sonnet と表記）のツールつきエージェントが 49.0%、同じモデルの OpenHands が 53.0%、Claude 3.7 Sonnet のツールつきエージェントが 62.3% である。

### なぜ重要か

この論文の価値は 2 つある。1 つは、**イシューのないコミットまで訓練に使えるようにした**ことで、訓練データの量の上限を「人間が書いたイシューの数」から「リポジトリのコミットの数」に移した。もう 1 つは、検証器の頭打ちを「どちらの検証器も精度が足りない」ではなく、「**それぞれ別の理由で失敗する**」と分けて示したことである。失敗の理由が違うので、組み合わせると互いの穴を埋められる。この分け方は SWE-Gym の「よい候補は出ているのに選べていない」（[[summaries/2024-swe-gym]]）という問題への、具体的な処方になっている。

## 限界・批判的視点

- **設計の選択と評価が同じ SWE-bench Verified の上で行われている**。ハイブリッドの組み合わせ方、上位 n の絞り込み、テストの数などのアブレーションは、すべて評価に使う Verified の 500 問で比べられており、別の検証用の問題集合で決めた形跡はない。上位 n の **n の値も本文に書かれていない**。最終の 51.0% には、設計を評価用の問題に合わせた分が含まれうる（本 wiki の読み）。
- **小さな差は誤差の範囲に入りうる**。500 問で解決率 51% のとき、問題の選ばれ方から来る標準誤差は約 2.2 ポイント（本 wiki の計算。√(0.51×0.49/500)。→ [[summaries/2024-error-bars-evals]]）である。同じ問題で比べる対の比較なら誤差は小さくなるが、上位 n の有無（1.2 ポイント差）や Agentless のテストとの差（2.2 ポイント差）は、この論文の結果だけでは確かとは言いにくい。7〜8 ポイントの主な効果は、この誤差より十分大きい。
- **「プロプライエタリなシステムと肩を並べた」の比較条件はそろっていない**。51.0% は 26 本から選んだ値で、比べている o1（48.0%）は Agentless の手順、Claude 3.5 Sonnet（49.0%）は 1 回の試行の値である。選択にかけた計算量、つまりエージェントを 26 回、テストエージェントを 7 回走らせ、各パッチにテストを実行する費用も報告されていない（→ [[agent-cost-efficiency]]）。1 回の試行で比べれば 34.4% で、同じ表のプロプライエタリなモデルとはまだ差がある。
- **数値と参照の食い違いが多い**。思考ありの成績が図の表で 34.4%、本文で 34.2%。実行なし・実行ベースの検証器が図 8 で 42.7%・43.8%、本文で 42.8%・43.7%。部分集合の件数が本文で 4,578、付録で 4,538。本文の「表 2」「図 3」「図 5（右）」は、実際には表 1・図 2・図 8 を指している（翻訳の冒頭の訳注）。結論を変えるほどの差ではないが、v1 のままで改訂版は出ていない。
- **Pass@1 の 34.4% は温度 0 での 1 回の値**と読める。26 本の中から 1 本を無作為に選んだときにあたる図 14 の K=1 の点は 32.0% である。表 3 の ± が何回の試行の標準偏差かも書かれていない（本 wiki の読み）。
- **データの多様性は小さい**。訓練に使った部分集合は 10 リポジトリで、pandas・numpy・pillow の 3 つが 6 割を占め、言語は Python だけである。環境づくりは半手動で、SWE-smith（[[summaries/2025-swe-smith]]）の比較では、部分集合 4.6k 件の Docker イメージが 4 TB に達する。
- **汚染の扱いは訓練データの側だけ**。SFT のデータからは SWE-bench のリポジトリを除いたが、軌跡を生成した教師の Claude 3.5 Sonnet が SWE-bench を見ているかは制御できない（→ [[summaries/2026-swe-bench-verified-retired]]）。テストエージェントの訓練データがどの環境から来たかは書かれておらず、テストエージェントに見せる手本のコードは SWE-bench の評価に含まれる Django のものである。また SWE-Lego（[[summaries/2026-swe-lego]]）は、2025 年 9 月より前の SWE-bench Verified の Docker イメージでは `git log` で正解を覗けたと報告している。本論文がこの影響を受けたかどうかは確かめられていない。
- **実行なしの検証器の偏りは、RL の報酬にすると問題が大きくなる**（本 wiki の読み）。検証器が「修正はうまくいった」という自己申告に高い点を付けるなら、それを報酬にして訓練したエージェントは、正しく直すより自信のある報告を書くことを覚えうる。いわゆる reward hacking（報酬の抜け道を突く振る舞い → [[reinforcement-learning-from-human-feedback]]）の一種である。著者らはこの検証器を推論時の選別にしか使っていない。

## 実装・運用上の示唆

- **K 本から選ぶなら、テストと LLM の判定を組み合わせる**。テストは「正しいかどうか」を直接見るが同点が多く、LLM の判定は差を付けられるが自己申告に引きずられる。片方だけを強くするより、テストで足切りし LLM で同点を割るほうが効いた。
- **LLM に正誤を判定させるときは、エージェントの自己申告を見せない工夫を考える**。この論文の分析では、検証器がエージェントの「直った」という文に注目していた。判定の入力をパッチと実行結果に寄せるか、自己申告の部分を除いて比べる価値がある（本 wiki の読み）。これは、[[coding-agents]] の「コードだけ見て完了宣言」問題を、判定する側から見たものでもある。
- **生成したテストは必ず検証してから使う**。生成したテストの多くは、バグを再現しないか、正解でも落ちる。修正前のコードで落ちること・候補の間で結果が分かれることを確かめてから、選別に使う。
- **イシューがないコミットも訓練データになる**。失敗するテストとエラーメッセージを見せて逆にイシューを書かせると、実際のイシューと同等の訓練効果が出た。テストが整ったリポジトリを持っていれば、社内のコードでも同じ方法でタスクを作れる。
- **後続の研究での使われ方**。Kimi-Dev（[[summaries/2025-kimi-dev]]）は、公開された R2E-Gym-Lite の Docker 環境（3,671 件）を RL の環境の 1 つに使った。SWE-Lego（[[summaries/2026-swe-lego]]）は、本論文の 14B の検証器（R2E-Gym-Verifier-14B）を比較相手にし、自分たちの 8B の生成型の検証器が 16 本から選ぶ設定で上回ったと報告している（49.6% 対 47.0%）。

## 用語と略称

- **SWE**（Software Engineering）: ソフトウェア工学。ここでは GitHub のイシューを解く課題を指す。
- **SWE-bench Verified / Lite**: SWE-bench（[[summaries/2023-swe-bench]]）から、人手で確認した 500 問 / 軽めの 300 問を選んだ部分集合。
- **SweGen**: 本論文の、コミットから実行できるタスクを作る方法。
- **R2E-Gym / R2E-Gym-Subset**: 本論文の 8,135 件のデータセット / SWE-bench と重なるリポジトリを除いた 4,578 件の部分集合（付録では R2E-Gym-lite・4,538 件、Hugging Face では R2E-Gym-Lite として公開）。
- **F2P テスト**（Fail→Pass）: 修正前のコードで失敗し、修正後のコードで通るテスト。
- **逆翻訳**（back-translation）: 出力（ここではコード変更）から、それを生む入力（ここではイシュー）を逆に作らせる手法。
- **ReAct**: 思考と行動を交互に出力して進めるエージェントの形式（→ [[reasoning-and-planning]]）。
- **SFT**（Supervised Fine-Tuning）: 正解の例をまねるように学習させる教師ありファインチューニング。
- **棄却サンプリング**（rejection sampling）: 生成した軌跡のうち、テストに通ったものだけを訓練に残すこと。
- **LoRA**（Low-Rank Adaptation）: 小さな追加行列だけを学習する、少ないパラメータでのファインチューニング（→ [[parameter-efficient-fine-tuning]]）。
- **ORM**（Outcome-supervised Reward Model）: 最終結果だけを見て成功確率を出す報酬モデル。ここでは実行なしの検証器。
- **Pass@K / Best@K**: K 本の候補の中に正解があるか（選び方が完璧なときの上限）/ 検証器が選んだ 1 本が正解か。
- **判別率**（distinguishability rate）: 正しいパッチと誤ったパッチで結果が分かれるテストの割合。
- **毒性のあるテスト**（toxic test）: 誤ったパッチを通し、正しいパッチを落とすテスト。
- **回帰テスト**（regression test）: 既存の機能が壊れていないかを確かめる、リポジトリにもとからあるテスト。
- **ロールアウト**（rollout）: エージェントに問題を 1 回最後まで解かせること。
