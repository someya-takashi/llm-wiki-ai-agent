# How Claude Code works in large codebases — 大規模コードベースでは、モデルよりハーネスの整え方が結果を分ける

> 原典: [[translations/2026-claude-code-large-codebases]] ・ `raw/articles/How Claude Code works in large codebases_ Best practices and where to start.md`
> 著者・年・出典: Anthropic（Applied AI チームの導入経験に基づく。署名なし）・2026-05-14・Claude 公式サイト Resources、連載「Claude Code at scale」の 1 本

## 一言まとめ

数百万行のモノレポや数十年来のレガシーシステムに Claude Code を入れてきた Anthropic の Applied AI チームが、うまくいった導入に共通するパターンをまとめた実務記事。主張は 3 つある。(1) 埋め込み索引を使う RAG はコードの更新に追いつけないので、Claude Code は grep とファイル読みで辿る **agentic search** を採り、その代わりに「どこを見ればよいか」の手がかりを人が整える必要がある。(2) 性能を左右するのはモデルよりも周りの**ハーネス**で、CLAUDE.md → フック → スキル → プラグイン → MCP サーバーの順に作り、LSP とサブエージェントで補う。(3) モデルが新しくなると古い指示がかえって邪魔になるので、**3〜6 か月ごとに設定を見直す**。数値の実験はなく、事例と経験則の記事である。

## 背景と問題意識

小さなリポジトリでは、コーディングエージェント（→ [[coding-agents]]）にリポジトリ全体を探させても大きな問題は起きない。大規模コードベースでは事情が変わる。サブディレクトリごとにビルドコマンドが違い、レガシーコードが共通のルートを持たないフォルダに散らばり、C・C++・C#・Java・PHP のように「AI コーディングツール向きではない」と思われがちな言語も混ざる。記事はこうした環境を「大規模コードベース」とまとめて呼ぶ。

ここでまず問題になるのが、**エージェントが必要なコードをどう見つけるか**である。多くの AI コーディングツールは RAG（Retrieval-Augmented Generation, 外部知識を検索してプロンプトに与え、それを根拠に生成させる手法 → [[retrieval-augmented-generation]]）を使う。コードベース全体を embedding（埋め込み, テキストを意味を保った数値ベクトルに変換したもの）にして索引を作り、質問のたびに関連するチャンク（分割した断片）を取り出す方式である。記事は、これが大規模な開発現場では失敗すると指摘する。数千人がコミットし続けるので埋め込みのパイプラインが追いつかず、索引は数時間〜数週間前のコードを反映したままになる。その結果、2 週間前に名前が変わった関数や、前のスプリントで消えたモジュールが返ってくる。しかも**古いという兆候がどこにも出ない**。

Claude Code はこの方式を採らない。エンジニアと同じようにファイルシステムを辿り、ファイルを読み、grep で探し、参照を追う。開発者のマシン上で動き、索引を作ったりサーバーに上げたりしない。これを **agentic search**（エージェントが自分でツールを使って探す検索）と呼ぶ。生きているコードベースを直接見るので、陳腐化は起きない。

この選択は、[[summaries/2025-effective-context-engineering]] が「just-in-time 取得」として整理した設計と同じである。そちらでも Claude Code は「CLAUDE.md は先に読み込み、残りは glob / grep で必要なときに引く」ハイブリッドの実例とされ、陳腐化した索引の問題を避けると書かれていた（→ [[context-engineering]]）。本記事はその理由を、大規模な開発現場の具体的な失敗として述べ直している。

ただし agentic search には代償がある。**最初にどこを見ればよいかの手がかりがないと、うまく働かない**。10 億行のコードベースで曖昧なパターンを全部探せと頼めば、作業が始まる前にコンテキストウィンドウ（context window, モデルが一度に読める最大トークン数）が尽きる。だから探索の質は、CLAUDE.md やスキルで手がかりをどれだけ整えたかで決まる。記事の残りはこの「整え方」の話である。

## 提案手法 / 主張

### ハーネスはモデルと同じくらい重要である

記事は、Claude Code の能力はモデルで決まる、という見方を「最もよくある誤解の 1 つ」と呼ぶ。チームはベンチマークやテスト課題での出来に目を向けがちだが、実際にはモデルの周りに作るエコシステム、つまり**ハーネス（harness, モデルの外側にある編集可能な構成要素の総体 → [[harness-engineering]]）がモデル単体よりも結果を左右する**という。

この主張そのものは本 wiki ではすでに何度も出てきた。[[summaries/2026-dive-into-claude-code]] は Claude Code のソースの 98.4% が運用ハーネスだと推定し、[[summaries/2026-meta-harness]] や [[summaries/2026-agentic-harness-engineering]] はモデルを固定してハーネスだけを変えても成績が動くことを示した。本記事の新しさは**大企業への導入という現場で、どの部品をどの順に作るか**を具体的に示した点にある。

### 7 つの部品（5 つの拡張ポイントと 2 つの補助機能）

記事はハーネスを **5 つの拡張ポイント**（CLAUDE.md、フック、スキル、プラグイン、MCP サーバー）と **2 つの補助機能**（LSP 連携とサブエージェント）に分ける。各層は前の層の上に積み上がるので、**作る順序に意味がある**という。

<figcaption>図1（再掲）: Claude Code のハーネス。横軸はセッションの時間。CLAUDE.md は開始直後から最後まで常に載り、フックは開始時と終了時に働き、スキル・LSP・MCP は必要なときだけ点で呼ばれ、プラグインはセッション前に入れておけばずっと使え、サブエージェントは途中の一区間で探索して発見をファイルに書き出す。</figcaption>
</figure>

| 部品 | 何を置くか | いつ載るか | 記事が挙げるよくある誤り |
|---|---|---|---|
| **CLAUDE.md** | コードベースの知識とプロジェクト固有の慣習。ルートに全体像、サブディレクトリにその場所の慣習 | 毎セッション（自動） | スキルに置くべき再利用できる専門知識を書き込む |
| **フック（hooks）** | 要所で自動実行するスクリプト | イベントで起動 | 自動で実行すべきことをプロンプトで頼む |
| **スキル（skills）** | 特定のタスク向けに包んだ指示とドメイン知識 | 必要なときだけ | 代わりに全部を CLAUDE.md に詰め込む |
| **プラグイン（plugins）** | スキル・フック・MCP 設定をまとめたパッケージ | 設定後は常に使える | よいセットアップを一部の人の暗黙知のままにする |
| **LSP 連携** | 言語サーバーによるシンボル単位の探索とエラー検出 | 設定後は常に使える | 自動で有効になっていると思い込む |
| **MCP サーバー** | 社内ツール・データ・API への接続 | 設定後は常に使える | 基本が動く前に MCP を作り始める |
| **サブエージェント** | 別のコンテキストウィンドウを持つ Claude のインスタンス | 呼び出したとき | 探索と編集を同じセッションでやる |

各部品の役割を、記事の説明に沿って補足する。

- **CLAUDE.md が最初に来る。** Claude が各セッションの開始時に自動で読むコンテキストファイルである（このファイルが 4 階層で管理され、user メッセージとして届く仕組みは → [[agent-memory]]）。タスクに関係なく毎回読まれるので、**広く当てはまることだけに絞らないと性能の足かせになる**。
- **フックは「止める道具」より「改善する道具」として使う。** 多くのチームはフックを誤った操作を防ぐスクリプトと考えるが、記事はもっと価値のある使い方として継続的な改善を挙げる。stop フックでセッションを振り返らせ、記憶が新しいうちに CLAUDE.md の更新を提案させる。start フックでチームごとのコンテキストを動的に読み込み、各開発者が手で設定しなくても自分のモジュールに合った状態で始められるようにする。リントやフォーマットのような自動チェックは、**Claude が指示を覚えていることに頼るより、フックで決定論的に強制したほうが結果がそろう**。
- **スキルは段階的開示（progressive disclosure, 最初は名前と短い説明だけを見せ、必要になったら本文を読み込ませる方式 → [[agent-skills]]）で使う。** 何十種類もの作業がある大規模コードベースで、全部の専門知識を毎回載せる必要はない。セキュリティレビューのスキルは脆弱性を調べるときだけ、文書処理のスキルはドキュメント更新が要るときだけ読み込まれる。さらに**スキルは特定のパスに紐づけられる**。決済サービスのチームが自分たちのデプロイスキルをそのディレクトリに結びつければ、モノレポの別の場所で作業している人のセッションには載らない。
- **プラグインはうまくいく設定を配る手段である。** 大規模な組織では、よい設定が一部の人の暗黙知にとどまりやすい。プラグインはスキル・フック・MCP 設定を 1 つにまとめるので、新人が初日に入れれば古参と同じ環境がすぐにそろう。更新は管理されたマーケットプレイスで組織全体に配れる。ある大手小売企業は社内の分析基盤に接続するスキルを作り、事業部門への展開前にプラグインとして配った。
- **LSP 連携で、文字列ではなくシンボルで辿らせる。** LSP（Language Server Protocol, エディタと言語ごとの解析サーバーをつなぐ標準プロトコル）は、IDE の「定義へ移動」「すべての参照を検索」を支えている仕組みである。これを Claude に開放すると、関数呼び出しを定義まで追い、ファイルをまたいで参照を辿り、別の言語にある同名の関数を区別できる。ないと、Claude はテキストのパターンマッチングに頼るので、誤ったシンボルにたどり着くことがある。あるエンタープライズソフトウェア企業は、C と C++ の探索を大規模でも信頼できるものにするため、Claude Code の展開前に LSP 連携を全社に入れた。記事は**多言語のコードベースで最も価値の高い投資の 1 つ**と呼ぶ。
- **MCP サーバーはほかでは届かない社内のツールとデータにつなぐ。** MCP（Model Context Protocol, ツールやデータソースをモデルに接続する標準プロトコル → [[model-context-protocol]]）である。最も進んだチームは、構造化検索を Claude が直接呼べるツールとして MCP で公開していた。
- **サブエージェント（subagent, 親から仕事を受けて独立したコンテキストで動く子のエージェント）で、探索と編集を分ける。** サブエージェントは最終結果だけを親に返す。読み取り専用のサブエージェントにサブシステムの地図を作らせてファイルに書き出させ、メインのエージェントはその全体像をもとに編集する、という使い方が紹介されている（→ [[multi-agent-systems]]）。

### どこに何を置くかを分ける 3 つの軸

上の表の「よくある誤り」は、どれも**置き場所の取り違え**である。記事の説明を整理すると、置き場所は次の 3 つの軸で決まる（軸の立て方は本ページの整理である）。

1. **毎回要るか、ときどき要るか。** 毎回要る知識は CLAUDE.md、特定の作業でだけ要る知識はスキル。CLAUDE.md に専門知識を詰め込むと、関係のない作業でも毎回コンテキストを食う。
2. **守らせたいのか、知っておいてほしいのか。** 毎回必ず実行してほしいこと（フォーマット、テストコマンド、セキュリティチェック）はフックで強制する。プロンプトに書いても、モデルが覚えていることに頼るだけになる。これは [[summaries/2026-dive-into-claude-code]] が指摘した「**CLAUDE.md は user メッセージとして届くので、遵守は確率的である。決定論的な強制は別の層が担う**」という指針と強制の分離と、同じ結論である（→ [[agent-safety-and-guardrails]]）。
3. **自分だけのものか、組織に配るものか。** 個人やチームの工夫をプラグインに包めば、組織全体で同じ設定を使える。

記事が示す作る順序（CLAUDE.md → フック → スキル → プラグイン → MCP）は、[[summaries/2026-dive-into-claude-code]] が示した**拡張機構のコンテキストコストの階層**（フックはゼロ、スキルは低、プラグインは中、MCP はツールスキーマのぶん高い → [[agent-frameworks]]）とほぼ同じ並びになっている。安い部品から先に整え、新しいツールの面が本当に要るときに高い部品を足す、という順序と読める。ただし、記事自身はこの順序の理由をコンテキストコストとしては説明していない。

### 大規模でもコードベースを探索しやすくする

成功した導入に共通する 3 つの設定パターンのうち、1 つ目がこれである。読み込むコンテキストが多すぎれば性能が落ち、少なすぎれば Claude は手探りになる。効果を上げた導入は、コードベースを Claude が読み取りやすい形に整えることに先行投資していた。記事が挙げる具体策は 6 つある。

- **CLAUDE.md を簡潔に、階層に分けて保つ。** Claude はディレクトリを移動するにつれて CLAUDE.md を足し合わせて読み込む。ルートの CLAUDE.md には**ポインタ（詳しい情報の在りか）と致命的な落とし穴だけ**を書く。それ以外はやがてノイズになる。記事末尾のチェックリストの図では、ルートは組織全体の文脈、サブディレクトリはチーム固有のルールとし、**それぞれ 200 行程度**という目安が示されている（本文にはない数字）。
- **リポジトリのルートではなく、サブディレクトリで起動する。** Claude は作業に関係する部分にスコープを絞ったときに最もよく働く。ディレクトリツリーを上へ辿って途中の CLAUDE.md をすべて読み込むので、ルートの文脈は失われない。
- **テストとリントのコマンドをサブディレクトリごとに決める。** 1 つのサービスを変えただけなのにテストスイート全体を走らせると、タイムアウトになり、関係のない出力でコンテキストが埋まる。サービスごとにテストとビルドのコマンドがあるコードベースではうまくいくが、ディレクトリをまたぐ依存が深いコンパイル言語のモノレポでは難しく、プロジェクト固有のビルド設定が要ることもある。
- **生成ファイル・ビルド成果物・サードパーティのコードを除外する。** `.ignore` ファイルを使い、`.claude/settings.json` に `permissions.deny` ルールをコミットしておけば、除外設定がバージョン管理され、チーム全員に同じ効果が出る。コードジェネレータの開発者のように生成ファイルそのものを扱う人は、ローカルの設定で上書きできる。
- **ディレクトリ構造が当てにならなければ、コードベースの地図を作る。** リポジトリのルートに、トップレベルのフォルダごとに「そこに何があるか」を 1 行で書いた軽い markdown を置けば、Claude はファイルを開く前に目次として読める。フォルダが数百ある場合は、ルートには最上位の構造だけを書き、次の階層の説明はサブディレクトリの CLAUDE.md に任せる。単純な場合は、参照してほしいファイルやディレクトリを @ でメンションするだけでよい。
- **LSP サーバーを動かし、文字列ではなくシンボルで探させる。** よくある関数名を grep すると何千件もヒットし、Claude はどれが本物かを確かめるためにファイルを開いてコンテキストを使う。LSP は同じシンボルを指す参照だけを返すので、**Claude が読む前に絞り込みが終わっている**。

ここで並んでいるのは、どれも「何をコンテキストに入れないか」を事前に決める工夫である。[[context-engineering]] の基本制約（コンテキストは有限の注意予算で、全部入れると性能が落ちる）を、大規模コードベースの日常の運用に落とした形になっている。とくにコードベースの地図は、「本体はコンテキストの外に置き、何がどこにあるかだけを先に見せる」という段階的開示の考え方（→ [[agent-skills]]）を、markdown 1 枚で実現する最も手軽な方法である。

記事は限界も認めている。数十万のフォルダと数百万のファイルを持つコードベースや、git 以外のバージョン管理を使うレガシーシステムでは、階層的な CLAUDE.md でも破綻する。これらは連載の今後の回で扱うとしている。

### モデルが変わったら設定を見直す

2 つ目のパターンは**モデルの進化に合わせて CLAUDE.md を手入れし続けること**である。今のモデルのために書いた指示が、次のモデルでは逆効果になりうる。

- **CLAUDE.md の例**: 「リファクタリングは必ず 1 ファイルずつに分ける」というルールは、以前のモデルが脱線しないためには役立ったかもしれない。だが新しいモデルが得意とする、複数ファイルをまたいだ協調的な編集を妨げてしまう。
- **フックの例**: Perforce（git とは別のバージョン管理システム）のコードベースで、`p4 edit`（Perforce でファイルを編集可能にする操作）を強制するためにファイル書き込みを横取りしていたフックは、Claude Code が Perforce モードを標準で備えた時点で不要になった。

モデルの推論の弱さであれ、Claude Code のツールの不足であれ、**特定の限界を補うために作ったスキルやフックは、その限界がなくなれば負担になる**。記事は 3〜6 か月ごとに本格的な見直しを行い、大きなモデルのリリース後に性能が頭打ちに感じられたときにも見直すよう勧める。

これは [[summaries/2026-harness-design]] の「**ハーネスの各部品は『モデルが単独でできないこと』への仮定であり、モデルの改善で陳腐化する**」という原則を、CLAUDE.md・スキル・フックという日常の設定ファイルに当てはめたものである（→ [[harness-engineering]] の「剥がす」）。harness-design では Opus 4.5 → 4.6 で context reset とスプリント分解が実際に不要になった。本記事は同じことが、チームが書いた CLAUDE.md の 1 行にも起きると言っている。

### 担当者を決め、組織の層に投資する

3 つ目のパターンは技術ではなく組織の話である。技術的な設定だけでは普及は進まない。

<figure>

![](../../raw/assets/2026-claude-code-large-codebases/f6aed9026a2db46aee2b02175e4bc20e7e67aac6.png)

<figcaption>図2（再掲）: Claude Code の展開の 3 段階。広く使わせる前に担当者が少しずつ基盤を組み（Quiet investment）、初日には基盤ができていて最初の開発者たちが生産的に使え（The rollout lands）、その評判がチームからチームへ広がる（Adoption spreads）。原ページにキャプションはなく、図の題と文言から説明を付けた。</figcaption>
</figure>

- **広く開放する前に、専任で基盤を整える。** 最も速く広がった展開では、小さなチーム（ときには 1 人）が先にツールをつなぎ込み、開発者が初めて触れたときにはもう Claude が普段のワークフローに収まっていた。ある企業では数人のエンジニアがプラグインと MCP の一式を初日から用意し、別の企業では AI コーディングツールの専任チームが展開前に基盤を整えていた。どちらも、開発者の最初の体験が苛立たしいものでなく生産的なものになり、そこから普及が広がった。
- **担い手は開発者体験（developer experience）や開発者生産性の部門。** 新人のオンボーディングと開発者向けツールを担う部門である。いくつかの組織では、Claude Code のエコシステムの管理に専念する、PM とエンジニアを兼ねた**エージェントマネージャー**という役割が生まれつつある。専任チームがない組織での最小限の形は **DRI（Directly Responsible Individual, その件に最終責任を持つ 1 人）** で、設定・権限ポリシー・プラグインのマーケットプレイス・CLAUDE.md の慣習を決める権限と、それらを最新に保つ責任を持つ。
- **ボトムアップの熱意を、誰かが集約する。** 現場から広がる普及は熱意を生むが、うまくいくものを集める人がいないと断片化する。標準化した CLAUDE.md の階層や、厳選したスキルとプラグインの一式をまとめて広める人がいなければ、知識は暗黙知のままで普及は頭打ちになる。
- **ガバナンスは小さく始める。** 規制産業ではとくに早い段階で問いが出る。どのスキルやプラグインを使えるようにするかを誰が決めるのか。何千人が同じものを作り直すのをどう防ぐのか。AI が書いたコードに、人間のコードと同じレビューをどう通すのか。記事は承認済みのスキルの限られた一式・必須のコードレビュー・限定的な初期アクセスから始め、確信が深まるにつれて広げることを勧める。エンジニアリング・情報セキュリティ・ガバナンスの代表者による部門横断のワーキンググループを早く作った組織で、導入が最も円滑だったという。

## 実験結果と知見

**定量的な実験や数値の比較はない。** 根拠は Anthropic の Applied AI チームが観察した導入事例で、具体例として次の 4 つが挙がる。

- ある大手小売企業: 社内の分析基盤に Claude を接続するスキルを作り、ビジネスアナリストがワークフローを離れずに業績データを取れるようにした。事業部門への展開前にプラグインとして配った。
- あるエンタープライズソフトウェア企業: C と C++ の探索を信頼できるものにするため、展開前に LSP 連携を全社に入れた。
- Perforce のコードベース: `p4 edit` を強制するフックが Claude Code の Perforce モードの追加で不要になった。
- 展開が速かった 2 社: 数人のエンジニア、または専任チームが、展開前にプラグインと MCP を用意していた。

ほかに記事が示す目安は、CLAUDE.md は各 200 行程度（チェックリストの図のみ）と、設定の見直しは 3〜6 か月ごと、の 2 つである。どちらも根拠となるデータは示されていない。C・C++ などの言語でも「多くのチームの予想を上回る性能を出す」という記述にも、数値はない。

## 限界・批判的視点

- **提供者自身による、成功例だけの報告である。** 著者は Claude Code を売る Anthropic で、記事の末尾は Enterprise 版への誘導で終わる。観察対象は「成功した導入」に限られ、失敗した導入や、同じ設定でうまくいかなかった例は出てこない。どのパターンがどれだけ効いたのかを切り分けたデータもない。
- **「ハーネスがモデルより結果を左右する」は、この記事の中では裏づけがない。** 本 wiki の他の原典はこの主張に条件を付けている。[[summaries/2026-agentic-harness-engineering]] では強いモデルほどハーネスの利得が小さく（GPT-5.4 で +2.3 pp に対し、deepseek-v4-flash では +10.1 pp）、[[summaries/2025-swe-effi]] では作り込んだ足場が弱いモデルでかえって崩れた（→ [[harness-engineering]]）。ハーネスの効き方はモデルとの組み合わせで変わる。
- **RAG との比較は片側だけである。** 索引の陳腐化は差分更新である程度は減らせるが、その議論はない。agentic search の側の代償（探索にかかる時間とトークン、行き止まりを追う無駄）も、[[summaries/2025-effective-context-engineering]] ほどには書かれていない。記事が認めるのは「手がかりがないと働かない」という点だけである。
- **プラグインとマーケットプレイスは、配布の経路であると同時に攻撃の経路でもある。** 記事は配布の利点を強調するが、悪意あるスキルや改ざんされたプラグインが組織全体に一度に届く危険には触れない。[[summaries/2026-externalization]] はスキルの「危険な合成」と悪意あるスキルの注入を、最も証拠の強い境界条件として挙げている（→ [[agent-skills]]、[[agent-safety-and-guardrails]]）。記事のガバナンスの節（承認済みのスキルから始める）が、事実上その対策になっている。
- **フックによる CLAUDE.md の自己更新にも、見張りが要る。** stop フックで CLAUDE.md の更新を提案させる運用は、放っておくと CLAUDE.md を膨らませ、記事自身が勧める「簡潔に保つ」と衝突しうる。[[summaries/2026-agentic-harness-engineering]] では、自己改善ループが自分の変更による後退をうまく予測できなかった。記事が「更新を適用する」ではなく「提案する」と書いている点は、人の確認を挟む前提と読める。
- **前提は「慣習的な環境」である。** 記事自身が、エンジニアが主な貢献者で、Git を使い、標準的なディレクトリ構造に従う環境を前提にしていると明記する。大きなバイナリアセットを持つゲームエンジン、git 以外のバージョン管理、エンジニア以外も書き込むコードベースでは追加の作業が要る。

## 実装・運用上の示唆

- **CLAUDE.md には「毎回要ること」だけを書く。** ルートはポインタと致命的な落とし穴に絞り、詳細はサブディレクトリの CLAUDE.md とスキルへ逃がす。目安は 1 ファイル 200 行程度。
- **必ず守らせたいことはプロンプトではなくフックや権限ルールに移す。** フォーマット・テスト・セキュリティチェックは、指示に書くより自動で実行させたほうが結果がそろう。これは [[summaries/2026-dive-into-claude-code]] の「指針と強制の分離」の実務版である。
- **探索の手がかりを先に用意する。** サブディレクトリで起動する、テストコマンドをディレクトリごとに書く、生成物を除外する、ルートに 1 行ずつの地図を置く。型のある言語や多言語のリポジトリなら LSP を入れる。どれも、コンテキストに入る無関係な情報を減らす工夫である。
- **探索と編集を分ける。** 広い範囲を調べるときは読み取り専用のサブエージェントに地図を作らせ、結果をファイルに書かせる。メインのコンテキストを探索の途中経過で埋めずに済む（ファイルを介した引き継ぎは [[summaries/2025-effective-harnesses]] の構造化 artifact と同じ発想）。
- **設定ファイルにも寿命があると考える。** モデルの更新時や 3〜6 か月ごとに、各ルールやフックが「どのモデルのどの弱点を補うために書いたか」を確かめ、不要になったものは外す。1 つずつ外して影響を確かめる、という [[summaries/2026-harness-design]] のやり方がそのまま使える。
- **配布と統制はセットで設計する。** よい設定はプラグインで配る。同時に、使ってよいスキルとプラグインの一覧、AI が書いたコードのレビュー手順、設定の責任者（DRI）を決めておく。

## 用語と略称

- **agentic search**: エージェントが grep・ファイル読み・参照の追跡といったツールを自分で使って必要なコードを探す方式。事前の索引を作らない。
- **RAG**: Retrieval-Augmented Generation。外部知識を検索してプロンプトに与え、それを根拠に生成させる手法。ここではコードを embedding にした索引から関連チャンクを取り出す方式を指す。
- **embedding**: 埋め込み。テキストやコードを、意味を保った数値ベクトルに変換したもの。
- **ハーネス（harness）**: モデルの外側にある編集可能な構成要素の総体。本記事では 5 つの拡張ポイントと 2 つの補助機能を指す。
- **CLAUDE.md**: Claude Code が各セッションの開始時に自動で読むコンテキストファイル。ルートとサブディレクトリに置け、ディレクトリを移動するにつれて足し合わされる。
- **フック（hooks）**: セッション開始・終了やツール実行の前後など、決まったイベントで自動実行されるスクリプト。
- **スキル（skills）**: 特定の作業向けに包んだ指示とドメイン知識。必要なときだけ読み込まれる。
- **段階的開示（progressive disclosure）**: 最初は名前と短い説明だけを見せ、必要になったときに本文を読み込ませる方式。
- **プラグイン（plugins）**: スキル・フック・MCP 設定を 1 つにまとめた、インストールできるパッケージ。
- **LSP**: Language Server Protocol。エディタと言語ごとの解析サーバー（言語サーバー）をつなぐ標準プロトコル。「定義へ移動」「すべての参照を検索」を支える。
- **IDE**: Integrated Development Environment。統合開発環境。
- **MCP**: Model Context Protocol。ツールやデータソースをモデルに接続する標準プロトコル。
- **サブエージェント（subagent）**: 親のエージェントから仕事を受け、独立したコンテキストウィンドウで動いて結果だけを返す子のエージェント。
- **モノレポ（monorepo）**: 複数のプロジェクトやサービスを 1 つのリポジトリにまとめて管理する方式。
- **Perforce / `p4 edit`**: git とは別のバージョン管理システムと、そこでファイルを編集可能にする操作。
- **DRI**: Directly Responsible Individual。その件に最終責任を持つ 1 人。
- **PM**: Product Manager。製品の方針と優先順位を決める役割。
- **API**: Application Programming Interface。ソフトウェア同士が機能を呼び出し合うための取り決め。
