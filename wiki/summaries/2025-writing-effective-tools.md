# Writing effective tools for AI agents — ツールを評価で磨き、エージェントに直させる

> 原典: [[translations/2025-writing-effective-tools]] ・ `raw/articles/Writing effective tools for AI agents.md`
> 著者・年: Ken Aizawa（Anthropic）・2025-09-11。原ページの見出しは "Writing effective tools for agents — with agents"。

## 一言まとめ

ツールを「**決定論的なシステムと非決定論的なエージェントの間の契約**」と定義し直し、エージェント向けツールを**評価駆動で作り・測り・エージェント自身に改修させる手順**と、その過程で得た 5 つの設計原則をまとめた Anthropic の実務記事。社内の Slack 用・Asana 用ツールでは、**Claude が最適化した版が人手で書いた版を held-out テストで上回った**（67.4% → 80.1%、79.6% → 85.7%）。

## 背景と問題意識

MCP（Model Context Protocol, ツールやデータソースをモデルに接続する標準プロトコル。→ [[model-context-protocol]]）によって、エージェントは数百ものツールを持てるようになった。だが多くのツールは、**既存の API エンドポイントを人間の開発者向けと同じ感覚で包んだだけ**のものになりがちである。

記事の出発点は、従来のソフトウェアとツールの違いにある。`getWeather("NYC")` は毎回同じように動くが、エージェントは同じ質問に対して天気ツールを呼ぶかもしれないし、一般知識で答えるかもしれないし、場所を聞き返すかもしれない。ツールの使い方を取り違えたり幻覚を起こしたりもする。つまり**ツールの「使われ方」が確率的**であり、関数や API と同じ設計手順では足りない。この問題意識は、SWE-agent（[[summaries/2024-swe-agent]]）が「LM は第 3 のエンドユーザーだ」と述べた ACI（agent-computer interface, エージェント向けに設計し直したツールとその接面。→ [[agent-computer-interface]]）の主張を、コーディング以外の業務ツール一般へ広げたものと読める。

## 提案手法 — 作る・測る・直させる

### 1. プロトタイプを作る

まず手を動かす。どのツールがエージェントにとって使いやすいかは、試さないと分からない。Claude Code でツールを書くなら、依存するライブラリや API のドキュメント（公式サイトの `llms.txt` など LLM 向けのもの）を渡す。ツールをローカルの MCP サーバーや Desktop extension（DXT）で包めば、Claude Code や Claude Desktop にそのまま接続して試せる。

### 2. 評価を作って回す

- **タスクは現実の用途から作り、多段にする**。強いタスクの例は「来週 Jane と Acme Corp の件で会議を設定し、前回の議事メモを添付し、会議室を予約して」。弱いタスクは「来週 jane@acme.corp と会議を設定して」のように、1 回の呼び出しで済み、引数まで指示に書いてあるもの。**数十回のツール呼び出しを要するタスク**が望ましい。単純すぎる「サンドボックス」環境は避ける。
- **検証器は厳しすぎないように**。書式・句読点・言い換えのような本質的でない差で正答を落とさない。期待するツール呼び出しを指定してもよいが、正しい経路は複数ありうるので**戦略を指定しすぎない**。
- **実行は単純な `while` ループで**。タスクごとに 1 つのエージェントループを回す。システムプロンプトで、ツール呼び出しの**前に**推論とフィードバックのブロックを書かせると、CoT（chain-of-thought, 思考過程を書き出させて推論を改善する手法）が働くうえに、エージェントがなぜそのツールを選んだかを後から読める。
- **正解率以外も集める**。ツール呼び出しとタスクの実行時間、呼び出し回数、トークン消費量、ツールエラー。冗長な呼び出しが多ければページネーションやトークン上限の調整、不正なパラメータのエラーが多ければ説明文や例の改善、というように、**指標が直す場所を指す**。

### 3. 結果を読み、エージェントに直させる

- **エージェントが書かなかったことに注意する**。LLM は思っていることを必ずしも言わない。CoT だけでなく**生のトランスクリプト**（ツール呼び出しと応答そのもの）を読み、CoT に現れない振る舞いを拾う。実例として、Claude の Web 検索ツールでは `query` に不必要に「2025」を付け足して検索結果を偏らせていたことが見つかり、説明文の改善で直した。
- **トランスクリプトを Claude Code に貼って改修させる**。Claude は多数のツールの実装と説明文を一括で、整合を保ったまま書き換えられる。記事の助言の大半はこの反復から得たものだという。
- **held-out テストで過適合を確かめる**。「訓練」用の評価とは別のテスト集合で測り、研究者が手で書いた「専門家」実装を超える改善が得られたことを確認した。

## 5 つの設計原則

| 原則 | 要点 | 例 |
|---|---|---|
| **作るツールを選ぶ** | API を包むのでなく、影響の大きいワークフロー単位でツールを作る。エージェントはコンテキストが有限で、総当たりの読み込みに弱い | `list_contacts` でなく `search_contacts`。`list_users`＋`list_events`＋`create_event` でなく `schedule_event`。`read_logs` でなく、関連行と周辺だけ返す `search_logs` |
| **名前空間を与える** | 関連ツールを共通のプレフィックスでまとめ、境界をはっきりさせる。**プレフィックス方式かサフィックス方式かで評価結果が無視できないほど変わり、効き方はモデルによって違う** | `asana_search` / `jira_search`、`asana_projects_search` / `asana_users_search` |
| **意味のある文脈を返す** | 低レベルの識別子（`uuid`・`mime_type`）より、下流の判断に効くフィールド（`name`・`file_type`）を返す。**UUID を自然言語や 0 始まりの ID に置き換えるだけで、幻覚が減り検索精度が大きく上がる** | `response_format` 引数で `"concise"`／`"detailed"` を選ばせる。Slack 検索の例では詳細版 206 トークンに対し簡潔版 72 トークン（約 ⅓） |
| **トークン効率** | 大きくなりうる応答には、ページネーション・範囲指定・フィルタ・切り詰めを既定値つきで実装する。Claude Code はツール応答を既定で **25,000 トークン**に制限している | 切り詰めたら「先頭 3 件のみ表示。取引先や金額範囲で絞れる、次ページはこう呼ぶ」と次の一手を添える。エラーは不透明なコードでなく、何が誤りで、正しい形式の例と解決手段は何かを返す |
| **説明文をプロンプトとして書く** | 新しく入った同僚に説明するつもりで、暗黙の前提（専用のクエリ形式、用語、リソース間の関係）を明示する。入出力は厳格なデータモデルで強制し、引数名は曖昧にしない | `user` でなく `user_id`。MCP のツールアノテーションで「外部へアクセスする」「破壊的な変更をする」ツールを開示する |

最後の原則の効果を示す例として、記事は**Claude 3.5 Sonnet が SWE-bench Verified で SOTA に届いたのはツール説明文を精密に直したあとだった**ことを挙げる（→ [[summaries/2025-swe-bench-sonnet]]）。

応答の書式（XML・JSON・Markdown）にも万能の正解はない。LLM は訓練データに近い形式でよく働くので、**どの書式が良いかはタスクとモデルしだいで、評価で決める**。

## 実験結果と知見

- 定量的な結果は Slack（67.4% → 80.1%）と Asana（79.6% → 85.7%）の 2 つの比較のみ。いずれも社内ワークスペース（実際のプロジェクト・文書・メッセージ）上の評価で、held-out テスト集合での値である。
- 「UUID を意味のある名前に置き換えると精度が大きく上がる」「名前空間の方式で結果が変わる」「Web 検索ツールの "2025" 問題」は、数値なしの定性的な報告である。

## 限界・批判的視点

- **原則ごとの効果量がない**。Slack・Asana の改善は「Claude による最適化」全体の効果で、5 原則のどれがどれだけ効いたかは分からない。タスク数・試行回数・ばらつきも示されていない。
- **社内評価で外部から再現できない**。評価タスクは社内ワークスペース上に作られている。
- **原則の一部はモデル依存**。名前空間の方式や応答の書式の効き方は「モデルによって違う」と記事自身が書いている。「Claude が Claude のために最適化した」ツールが別のモデルでも良いかは検証されていない。原則は出発点であって、最終判断は自分のモデルでの評価に委ねられている。
- **「エージェントが書かなかったこと」問題は評価全体に及ぶ**。CoT は忠実とは限らない（[[summaries/2025-cot-faithfulness]]）ので、トランスクリプト分析をエージェントに任せる工程にも同じ盲点が入りうる。記事が生トランスクリプトを人が読むことを勧めるのはこのためと読める。
- **提供元のベンダー記事**であり、自社製品（Claude Code・MCP・cookbook）での実践を前提にしている。

## 既存 wiki との接続

- **ACI の系譜の現在地**。SWE-agent（2024）が提唱し、[[summaries/2024-building-effective-agents]] が「ツールの定義にプロンプトと同等の労力を」と一般化し、[[summaries/2025-swe-bench-sonnet]] が SWE-bench で実証した流れの延長で、**評価で測ってエージェントに直させる**手順まで体系化した。詳しい整理は [[agent-computer-interface]] に置いた。
- **ツールの自己改善は、ハーネスの自己改善の一部**。[[summaries/2025-multi-agent-research-system]] の「ツールテスト用エージェント」（説明文の書き直しでタスク完了時間 −40%）の手順化であり、[[summaries/2026-meta-harness]] や [[summaries/2026-agentic-harness-engineering]] の「生トレースを読ませて改修させる」と同じ構造を持つ。AHE ではツールの差し替えだけで +3.3pt だった（→ [[harness-engineering]]）。どちらも**要約でなく生のトレースを読むこと**を重視している点が共通する。
- **トークン効率は [[context-engineering]] の注意予算の話**。応答の切り詰め・簡潔版の選択・ページネーションは、「最小の高信号なトークン集合」（[[summaries/2025-effective-context-engineering]]）をツール応答の側で実装する手段である。SWE-agent の「検索結果が 50 件を超えたら結果でなく再クエリを促す」も同じ発想。
- **評価設計は [[agent-evaluation]] に接続する**。強い／弱いタスクの区別、厳しすぎない検証器、期待経路を指定しすぎないこと、held-out テストは、ベンチマーク設計の一般的な規律として使える。

## 実装・運用上の示唆

- ツールは API の 1 対 1 の包装でなく、**タスクの自然な単位**で設計する。迷ったら「同じ資源を与えられた人間ならどう分割するか」を基準にする。
- 応答には **`response_format` 引数**（簡潔／詳細）を付け、ID が要る場面だけ詳細版を使わせる。
- 切り詰めとエラーの応答は「**次に何をすればよいか**」を書く場所として使う。
- ツールの評価は現実的な多段タスクで作り、**held-out テスト**を必ず分けておく。エージェントに改修させる場合も、最終判断はテスト集合の数字で行う。
- 生のトランスクリプトを読む工程を省かない。

## 用語と略称

- **MCP** = Model Context Protocol（ツールやデータソースをモデルに接続する標準プロトコル）
- **ACI** = Agent-Computer Interface（エージェント向けに設計したツールとその接面）
- **DXT** = Desktop Extension（Claude Desktop にツールを追加する拡張形式）
- **CoT** = Chain-of-Thought（思考過程を書き出させる手法）
- **interleaved thinking**：ツール呼び出しの合間に思考を挟む Claude の機能
- **held-out テスト集合**：改善に使わず、最後の検証にだけ使うテスト集合
- **affordance（アフォーダンス）**：ある主体にとって「とりうる行動」として知覚される性質
- **namespacing（名前空間）**：関連するツールを共通のプレフィックス（またはサフィックス）でまとめること
- **`response_format`**：ツール応答の詳しさをエージェントに選ばせる引数（concise / detailed）
