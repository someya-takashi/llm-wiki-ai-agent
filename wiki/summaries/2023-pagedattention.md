# PagedAttention — OS の仮想メモリを KV キャッシュへ持ち込む

> 原典: [[translations/2023-pagedattention]] ・ `raw/papers/Efficient Memory Management for Large Language Model Serving with PagedAttention.md`
> 著者: Kwon, Li, Zhuang ら（UC Berkeley / Stanford / UC San Diego）
> SOSP 2023（arXiv:2309.06180）

## 一言まとめ

**「LLM サービングのスループットはメモリ律速である」と診断し、その原因が KV キャッシュを連続メモリに置いていることだと突き止め、OS の仮想メモリとページングをそのまま持ち込んで解いた論文**である。vLLM の原典であり、**既存システムが KV キャッシュのメモリの 20.4〜38.2% しか実際に使えていなかった**ところを、ほぼ無駄ゼロにして**スループットを 2〜4 倍**にした。

## 背景と問題意識

本 wiki は昨日 [[llm-serving-systems]] を二次資料から作り、PagedAttention をその中心に据えた。**これはその原典**であり、位置づけを一次で確認できる。

### 診断が先にある

論文の構造で見事なのは、**手法の前に問題を定量したこと**である。13B のモデルを 40GB の A100 でサービングするときのメモリ配分は——**重み約 65%・KV キャッシュ約 30%・活性その他が残り**。重みは静的で活性は小さいので、**KV キャッシュの管理が最大バッチサイズを決める**。

そして KV キャッシュはふつうのテンソルと性質が違う。**動的に伸縮し、寿命と長さが事前に分からない。** ところが深層学習フレームワークはテンソルが連続メモリにあることを要求するので、既存システム（Orca・FasterTransformer）は**リクエストの最大長ぶんを事前確保**していた。

<figcaption>図3: 既存システムにおける KV キャッシュのメモリ管理。3 種類の無駄——予約（reserved）・内部断片化・外部断片化——が存在する。</figcaption>
</figure>

無駄が 3 種類に分解される。

| 種類 | 何が起きているか | いつ分かるか |
|---|---|---|
| **予約（reserved）** | 将来のトークンのために確保した分。最終的には使うが、その間ほかのリクエストが使えない | サービング前から |
| **内部断片化** | 最大長に合わせた過剰供給。実際の出力が短ければ丸ごと無駄 | **リクエストが終わって初めて**分かる |
| **外部断片化** | アロケータ（buddy allocation）に由来。**生成トークンに決して使われない** | サービング前から分かる |

**実測が痛烈である。「従来システムにおける実効的なメモリは 20.4% まで低くなりうる」**（Fig. 2 では 20.4〜38.2%）。

具体的な見積もりも置かれている。**13B の OPT では 1 トークンの KV キャッシュが 800KB**、最大 2048 トークンなので **1 リクエストで最大 1.6GB**。数十 GB の GPU では数十リクエストしか載らない。しかも**GPU の計算速度はメモリ容量より速く伸びている**（A100 → H100 で FLOPS は 2 倍超だがメモリは 80GB のまま）ので、この問題は悪化する。

## 提案手法 — OS の比喩を最後まで使い切る

<figure>

![](../../raw/assets/2023-pagedattention/x6.png)

<figcaption>図5: PagedAttention の図示。attention のキーとバリューのベクトルが非連続なブロックとして格納されている。クエリ "forth" に対し、3 つのブロックが物理メモリ上でばらばらの位置にある。</figcaption>
</figure>

対応関係が体系的である。

| OS | vLLM |
|---|---|
| ページ | **KV ブロック**（固定数のトークンぶんのキーとバリュー） |
| バイト | **トークン** |
| プロセス | **リクエスト** |
| ページテーブル | **block table**（論理ブロック → 物理ブロック） |
| スワップ空間（ディスク） | **CPU メモリ** |
| fork の copy-on-write | **参照カウント ＋ ブロック粒度の copy-on-write** |
| 共有ライブラリ | **共有 prefix**（提供者が予約した物理ブロック） |

**内部断片化はブロックを小さくして必要時に確保することで緩和し、外部断片化は全ブロックが同サイズなので消える。** vLLM はリクエストごとの無駄を **1 ブロック以内**に抑える。

### デコードアルゴリズムごとの共有

論文が丁寧なのは、共有が**デコード手法によって形を変える**ことを個別に扱っている点である。

- **並列サンプリング**: プロンプト部分の物理ブロックを共有し、参照カウントを持つ。分岐が起きた最後のブロックだけ copy-on-write する。
- **ビーム探索**: プロンプトだけでなく**途中のブロックも共有し、共有パターンがデコードの進行とともに動的に変わる**——「OS における複合的な fork が作るプロセスツリーと同様」。従来システムが必要とした候補間の頻繁なメモリコピーが、**1 ブロック分のコピー**に縮む。
- **共有 prefix**: 提供者が事前定義した prefix のために物理ブロックを予約する。
- **混合**: 異なるデコード選好のリクエストを**同時に**処理できる——既存システムにはできない。論理→物理の共通の写像層が複雑さを隠すので、**LLM と実行カーネルは物理ブロック ID のリストしか見ない**。

### スケジューリングと復旧

FCFS で公平性を保ち、メモリが尽きたら**最も遅いリクエストからプリエンプト**する。退避の方針が LLM 固有である——**all-or-nothing**（系列のブロックは全部使うか全部使わないかなので、まとめて退避する）で、1 リクエスト内の複数系列（ビーム候補など）は**系列グループ**としてギャングスケジュールされる。

復旧は 2 通り。**退避（swapping）** は CPU メモリへコピーする（**退避量が GPU の KV キャッシュ容量を超えないので、CPU 側のスワップ空間に上界がある**）。**再計算（recomputation）** は、生成済みトークンを元のプロンプトへ連結して**1 回のプロンプト相で全位置を作り直せる**ので、元のレイテンシよりずっと安い。

### 分散実行

Megatron-LM 型のテンソル並列を支える。着眼が良い——**モデル並列でも各シャードは同じ入力トークンを処理するので、同じ位置の KV キャッシュを必要とする**。したがって **KV キャッシュマネージャは中央に 1 つでよい**。GPU ワーカはメモリ管理について同期する必要がなく、各反復の冒頭に block table を受け取るだけでよい。

## 実験結果と知見

OPT 13B/66B/175B と LLaMA-13B を、**ShareGPT**（実際の ChatGPT の会話）と **Alpaca** のトレースで評価。ShareGPT は Alpaca より入力が 8.4 倍・出力が 5.8 倍長い。

| 場面 | 結果 |
|---|---|
| 基本サンプリング（ShareGPT） | Orca (Oracle) の **1.7〜2.7 倍**、Orca (Max) の **2.7〜8 倍**、FasterTransformer の**最大 22 倍**のリクエストレート |
| 同時処理数（OPT-13B） | Orca (Oracle) の **2.2 倍**、Orca (Max) の **4.3 倍** |
| ビーム探索（幅 6） | Orca (Oracle) 比の改善が基本の 1.3 倍から **2.3 倍**へ |
| メモリ節約（Alpaca） | 並列サンプリング **6.1〜9.8%**、ビーム探索 **37.6〜55.2%** |
| メモリ節約（ShareGPT） | 並列サンプリング **16.2〜30.5%**、ビーム探索 **44.3〜66.3%** |
| 共有 prefix | 1-shot で **1.67 倍**、5-shot で **3.58 倍** |
| チャットボット | 3 つの Orca すべてに対し **2 倍** |

**ベースライン Orca を 3 段階で実装した**のが誠実である——出力長を知っている **Oracle**（実現不可能な上界）、最大 2 倍まで過剰予約する **Pow2**、常に最大長を予約する **Max**。

### 正直なアブレーション

**PagedAttention の attention カーネルは FasterTransformer より 20〜26% 遅い。** block table へのアクセス・追加の分岐・可変系列長の処理という間接参照の税を払っているからである。**それでも端から端までは大きく勝つ**——より多くのリクエストが載るからである。

> **これは [[llm-serving-systems]] の Roofline の枠組みそのものである。** カーネルを速くするのでなく、**memory-bound の領域でバッチサイズを上げる**ことで勝っている。「カーネルが 20% 遅くてもシステムは 2〜4 倍速い」は、この層で何が効くかを端的に示す。

**ブロックサイズ**は既定 16。ShareGPT では 16〜128 が最良だが、Alpaca では**系列がブロックより短くなるので大きいブロックが大きく劣化する**。**再計算 vs 退避**は、小ブロックでは退避が PCIe 帯域を使い切れず不利、大ブロックでは退避が有利、**再計算のオーバーヘッドが退避のレイテンシの 20% を超えることは決してない**。

## 限界・批判的視点

- **「共有 prefix」は自動ではない。** §4.4 は「**提供者が事前定義した共有 prefix の集合のために物理ブロックを予約しておく**」と書いており、**手動の設定**である。しかも [[summaries/2023-sglang]] は「**vLLM の論文はこの機能を論じているが、信頼できる高性能なカーネルがないため公開されたコードは対応していない**」と明言している。**自動の prefix 再利用は SGLang の貢献であって vLLM のものではない**——本 wiki の [[llm-serving-systems]] の記述はここを訂正した。
- **Orca を自前で再実装している。** Orca が公開されていないためだが、buddy allocation を使うという仮定を含め、**比較相手の性能は著者の実装に依存する**。3 段階のベースラインを置いたのは緩和策だが、Oracle は「実現不可能」と自ら断っている。
- **チャットボットの実験で会話ラウンド間の KV キャッシュを保持していない**（「他のリクエストの空間を占有してしまうから」）。つまり**エージェントの多ターン trajectory で最も効くはずの再利用を、意図的に使っていない**。この設定でも 2 倍だが、SGLang が示したのはここに 5 倍以上の余地があるということである。
- **反復単位のスケジューリング自体は Orca の貢献**であり、vLLM はそれを前提にメモリ側を解いている（論文自身が「相補的」と明記）。**continuous batching を vLLM の発明と読まない**こと。
- **適用範囲が限定的だと著者自身が §8 で述べている。** DNN の訓練はテンソル形状が静的なので事前最適化でき、**LLM でない DNN のサービングは計算律速なのでメモリ効率の向上が性能につながらず、間接参照のオーバーヘッドでむしろ悪化しうる**。
- 評価は **OPT と LLaMA の 2 系列、A100 のみ**。2023 年時点なので GQA を持つモデルが対象外で、KV キャッシュのサイズ見積もり（800KB/token）は現代のモデルとは異なる。

## 実装・運用上の示唆

1. **手法の前に無駄を分解して測る。** 予約・内部断片化・外部断片化という 3 分類と「実効メモリ 20.4%」という数字が、この論文の説得力の大半を担っている。**最適化を提案する前に、何がどれだけ無駄になっているかを測る。**
2. **古典的な OS の技法をそのまま持ち込めないか考える。** ページング・参照カウント・copy-on-write・共有ライブラリ・スワップ——すべて 1960 年代からある道具である。**問題の構造（動的確保・容量律速）が一致すれば、解も再利用できる。**
3. **応用固有の意味論で OS から離れる。** all-or-nothing 退避（系列は全ブロックを同時に使う）と**再計算による復旧**（OS では不可能）は、汎用の仮想メモリにはない。**比喩を借りたら、どこで比喩を捨てるかも決める。**
4. **カーネル単体の速度とシステムの速度を混同しない。** attention カーネルが 20〜26% 遅くても、システムは 2〜4 倍速い。**最適化の対象を間違えないために、どの層で律速しているかを先に決める。**
5. **ベースラインを段階で置く。** Oracle（実現不可能な上界）・Pow2・Max の 3 段は、「相手の実装が悪いから勝った」という批判を封じる型として使える。
6. **ブロックサイズはワークロードの系列長分布で決まる。** 系列がブロックより短いと大きなブロックは破綻する。**既定値をそのまま使う前に、自分の入出力長の分布を見る。**

## 用語と略称

- **PagedAttention** = KV キャッシュを固定サイズの非連続ブロックに置いたまま attention を計算するアルゴリズム
- **vLLM** = PagedAttention の上に構築された高スループットの LLM サービングエンジン
- **KV キャッシュ** = decode で過去トークンのキーとバリューを再計算しないための保存領域
- **KV ブロック / ブロックサイズ $B$** = 固定数のトークンぶんのキーとバリューを保持する単位。vLLM の既定は 16
- **block table** = 論理 KV ブロックから物理 KV ブロックへの写像（OS のページテーブルに対応）
- **内部断片化 / 外部断片化** = 確保した領域の内側で使われない分 / アロケータに由来し確保単位の外側で使えない分
- **copy-on-write（書き込み時複製）** = 共有された領域へ書き込みが起きた時点で初めて複製する方式
- **参照カウント（reference count）** = ある物理ブロックを何本の論理ブロックが指しているかの数
- **FCFS** = First-Come-First-Serve（先着順）
- **all-or-nothing eviction** = ある系列のブロックを全部退避するか、まったくしないかのどちらかにする方針
- **sequence group（系列グループ）** = メモリ共有のためにまとめてスケジュール・プリエンプトされる系列の束
- **swapping / recomputation** = 退避したブロックを CPU メモリへ移す / 再計算し直す、2 つの復旧手法
- **SPMD** = Single Program Multiple Data（同じプログラムを異なるデータで並列実行する方式）
- **Orca / FasterTransformer** = 比較対象の先行サービングシステム。前者は反復単位スケジューリング、後者はレイテンシ最適化
- **ShareGPT / Alpaca** = 評価に使ったワークロードのデータセット。前者は ChatGPT の実会話、後者は指示データセット
- **正規化レイテンシ** = 各リクエストの端から端までのレイテンシを出力長で割った値
