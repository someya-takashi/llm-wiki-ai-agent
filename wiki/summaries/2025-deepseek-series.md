# DeepSeek シリーズ技術概観 — 4 本を「HPC 協調設計」の一本の弧として読む（と、原典との食い違い）

## 一言まとめ

DeepSeek の 4 本のテクニカルレポート（DeepSeek-LLM → V2 → V3 → R1）を、**「制約されたハードウェアの上でどう大きくするか」という単一の問い**への連続した回答として読み直した二次資料。wiki にとっての価値は、**V3・R1 の手前にある 2 本（scaling law と MLA/DeepSeekMoE の初出）を埋めること**にあるが、**V3 の MLA に関する記述 3 点は原典に存在しない**ので、そこは信用せずに読む必要がある（→ [原典との照合](#原典との照合)）。

## 背景と問題意識 — なぜ二次資料をわざわざ取り込むのか

wiki はすでに [[summaries/2024-deepseek-v3]] と [[summaries/2025-deepseek-r1]] という**一次資料を 2 本**持っている。ではこの解説記事は何を足すのか。3 つある。

**第一に、系譜の欠けた前半**。DeepSeek-V3 のレポートは「DeepSeek-V2 で十分に検証された MLA と DeepSeekMoE を採用する」と一行で済ませ、その MLA と DeepSeekMoE が**何を解決するために作られたのか**は書かない。V2 のレポートを読まないと分からないその文脈が、本記事にはある。さらにその手前の **DeepSeek-LLM**（2024-01）の scaling law の仕事は、wiki のどこにも入っていなかった。

**第二に、「HPC co-design（HPC 協調設計）」という括り**。著者はこれを 4 本を貫く主題として立てる。**モデルのアーキテクチャと、それを訓練するデータセンターのインフラを、切り離さずに一緒に設計すること**を指す語で、原典（V3 レポート）自身も使っている。「アーキテクチャの論文」と「システムの論文」を分けて読む習慣に対する反論になっている。

**第三に、二次資料そのものの検証**。DeepSeek は 2025 年初頭に市場を巻き込む形で騒がれ、その過程で主張が文脈から切り離されて広まった（著者自身が冒頭でそう書き、同僚の記事を紹介している）。**一次資料を持っている状態で二次資料を読むと、二次資料がどこで滑るかが分かる**——本記事はその実例としても機能する。

## 4 本を貫く弧

著者が立てる 3 つの弧:

| 弧 | 内容 | 主に効いた論文 |
| --- | --- | --- |
| **コストとメモリの効率** | MLA による KV 圧縮、MoE、FP8 訓練。超大規模の訓練と推論を「実行可能」にする | V2, V3 |

この並べ方の含意は、**R1 の「創発」は前 3 本の「効率」の上にしか立てなかった**ということである。RL（Reinforcement Learning, 強化学習）は生成を大量に回す手法なので、推論が安くなければ回数を稼げない。効率の仕事と能力の仕事は別々のトラックに見えて、実際には前者が後者の前提条件になっている。

## DeepSeek-LLM（2024-01）— 規模をパラメータ数で測るのをやめる

**wiki に初めて入る内容。** 問いは古典的である——**事前学習の計算予算が固定されているとき、モデルをどれだけ大きくし、データをどれだけ食わせるべきか**。scaling law（スケーリング則, モデル規模・データ量・計算量と性能の間に成り立つ経験的な冪乗則）の研究は当時すでにあったが、Chinchilla（DeepMind, 2022）と GPT-3 系で結論が食い違っていた。

DeepSeek-LLM の切り口は、**測り方を変えること**だった。従来は規模を**パラメータ数 $N$** で測っていたのに対し、**非埋め込み FLOPs/token $M$**（トークン 1 個を処理するのに、埋め込み層を除いた層が消費する浮動小数点演算数）で測る。すると計算予算 $C$ は

$$
C = M \times D
$$

と、データ量 $D$ との積で素直に書ける。**なぜこれが効くのか**——埋め込み層はパラメータ数としては大きいが、トークンあたりの計算量にはほとんど寄与しない（ルックアップだから）。パラメータ数で規模を測ると、語彙サイズの違いがそのまま「規模」の違いに化けてしまい、異なる設定のモデルを同じ曲線に乗せられない。計算量そのもので測れば、その歪みが消える。**「何を規模と呼ぶかを変えると、ばらついていた法則が揃う」**という、測定量の設計が結論を左右する好例である。

もうひとつの発見が**データ品質が最適比率を動かす**ことである。高品質なデータほど、同じトークン数に対してより大きなモデルが正当化される。記事の説明が直感的でよい——重複とスパムだらけの 1000 億トークンでは、パラメータを増やしても学ぶものがないので早々に収穫逓減にぶつかる。コード・数学・多言語対話が幅広く入った 1000 億トークンなら、1 トークンあたりの情報が濃いので、パラメータを増やす「余裕がある」。**scaling law は普遍定数ではなくデータに依存する**、という主張である。

実務的な成果としては、7B と 67B を英中 2T トークンで訓練し、SFT（Supervised Fine-Tuning, 教師ありファインチューニング）と **DPO**（Direct Preference Optimization, [[summaries/2023-dpo]]）で整合させ、67B が LLaMA-2 70B をコード・数学で上回った。**DeepSeek がこの時点で PPO ではなく DPO を使っていた**ことは、[[reinforcement-learning-from-human-feedback]] の系譜として押さえる価値がある——のちに [[summaries/2024-deepseekmath]] で GRPO を自作し、[[summaries/2025-deepseek-r1]] でそれを RLVR に載せるまでの助走にあたる。

## DeepSeek-V2（2024-06）— MLA と DeepSeekMoE の初出

**wiki に初めて入る内容。** V2（総 236B / 活性 21B、8.1T トークン、128K コンテキスト）は、Transformer の 2 大コストに正面から取り組む。

1. **attention の KV キャッシュ**——生成のたびに過去トークンの Key/Value を保持し続けるので、系列が伸びるほどメモリを食う。
2. **feed-forward の計算**——通常 Transformer の FLOPs の最大消費源。

**MLA（Multi-Head Latent Attention, 多頭潜在アテンション）**が (1) への答えである。Key と Value を**低ランク分解**——$(in, out)$ の行列 1 枚を $(in, rank)$ と $(rank, out)$ の 2 枚に分ける——で圧縮し、$c^{KV}_t = W^{DKV}\mathbf{h}_t$ という**単一の潜在ベクトル**にまとめる。キャッシュするのはこの潜在ベクトルだけで、各ヘッドの K と V はそこから**その場で復元する**。V2 の abstract の数字では **KV キャッシュ 93.3% 削減・最大生成スループット 5.76 倍・訓練コスト 42.5% 削減**（DeepSeek 67B 比）。

ここが重要な区別なのだが、**MLA はキャッシュの「追い出しポリシー」ではない**。長コンテキスト対策の多くは「どのトークンを捨てるか」を工夫する（sliding window, H2O 等）が、MLA は**捨てずに、そもそも 1 トークンあたりの占有量を下げる**。だから追い出し系の手法と直交して併用できる（→ [[transformer-architecture]]）。

**DeepSeekMoE** が (2) への答えである。MoE（Mixture of Experts, 入力ごとに一部の専門家サブネットのみを使う構造）自体は既存だが、DeepSeek 版の特徴は 2 つ:

- **細粒度エキスパート ＋ 共有エキスパート**。エキスパートを従来より細かく割り、そのうえで**共有エキスパート**（全トークンが必ず通る、普遍的なパターン担当）と**ルーティングされるエキスパート**（ゲートが動的に選ぶ、特化した部分問題担当）に分ける。共通の処理を全エキスパートに重複して学習させる無駄を、共有側に括り出す設計である。
- **device-limited routing（デバイス制限ルーティング）**。任意のトークンが任意のエキスパートへ飛べると、GPU 間の all-to-all 通信が爆発する。そこで**まずトークンごとに親和性の高い上位 $M$ 個のデバイスを選び、その内側でだけ上位 $K_r$ 個のエキスパートを選ぶ**。**ルーティングの自由度をハードウェアのトポロジーに合わせて意図的に削る**——これが HPC 協調設計の最も分かりやすい実例で、V3 の node-limited routing（$M=4$ ノード）に直接繋がる。

負荷の偏りには **3 つの均衡損失**を当てる。$L_{ExpBal}$（エキスパート水準・崩壊防止）、$L_{DevBal}$（デバイス水準・作業負荷）、$L_{CommBal}$（各デバイスの入出トークン量）。**「均衡」が単一の概念ではなく、計算・配置・通信の 3 層それぞれで別々に要求される**ことがここで明示される。V3 がこの補助損失群を捨てる（正確には粒度を変える）話は次節に繋がる。

## V3 と R1 — 既存の一次資料との関係

この 2 本は wiki に一次資料があるので、記事の読み方だけを拾う。

**V3 の MoE 側**の記述は概ね原典に沿う。補助損失の代わりに各エキスパートが動的なバイアス $b_i$ を持ち、過負荷なら下げ、負荷不足なら上げ、ゲート判定は $s'_{i,t} = s_{i,t} + b_i$ になる。トークン落としがゼロになり、ルーティングされるエキスパートが 6 → 8 に増えた、という記述も正しい。

ただし記事の解釈——**「補助損失を取り除くことで主目的への干渉を避けられる」**——は、原典自身の分析より粗い。V3 レポート §4.5.3 は**バッチ単位の補助損失**を自分で設計して比較しており、それが「補助損失なし」と同じ検証損失に達することを示している。つまり効いているのは損失の有無ではなく**均衡を要求する粒度**（系列単位 → バッチ単位）である。記事だけを読むと「補助損失は悪」という誤った教訓を持ち帰ることになる（→ [[mixture-of-experts]]）。

**FP8 の記述**も方向は合っているが、理由づけが違う。記事は FP32 への周期的な昇格を「オーバーフロー／アンダーフローを避けるため」とするが、原典の理由は**精度**である——H800 の Tensor Core の FP8 GEMM は仮数部の積の**上位 14 ビットしか使わない**ので、$K=4096$ で最大約 2% の相対誤差が出る。これを $N_C=128$ 要素ごとに CUDA Core へ昇格させて FP32 累積することで潰す（→ [[llm-inference-optimization]]）。

**R1 の記述は正確**である。R1・R1-Zero が V3 と**アーキテクチャ的に同一**で、V3-Base に異なる量の事後訓練を当てたものであること。GRPO の 4 手順と advantage の式。ルールベース報酬が正確性報酬と形式報酬（`<think></think>` / `<answer></answer>`）の重み付き和であること。R1-Zero の 3 つの欠点（可読性・非推論タスクの不安定・ドメインの限定）と、それを埋める R1 の 4 段階（コールドスタート SFT → 推論 RL → 棄却サンプリング＋SFT → 全シナリオ RL）。**段階 3 で「ベースモデルを再びファインチューニングする」**——段階 2 のチェックポイントからの継続ではなく V3-Base に戻る——という点まで正しく書けている。二次資料としては良い出来である。

## 原典との照合

**この記事の V3「洗練された MLA」節の 3 点は、DeepSeek-V3 テクニカルレポートに存在しない。** 現行版（2025-06-18 改訂）の原ページを取得して確認したので、クリップ不良ではない。

| 記事の主張 | 原典（[[translations/2024-deepseek-v3]]）の実際 | 根拠 |
| --- | --- | --- |
| **改善された RoPE の扱い** — V2 は key を部分的にしか decouple していない。V3 が拡張して 128K を安定化 | V2・V3 とも同一の decoupled key $\mathbf{k}^R_t = \operatorname{RoPE}(W^{KR}\mathbf{h}_t)$。**V2 の時点ですでに 128K 対応**。V3 の 128K は **YaRN による 2 段階のコンテキスト拡張**（§4.3、各 1000 ステップ）から来ており、MLA の変更とは無関係 | V3 §2.1.1 / §4.3、V2 abstract |
| **統合された KV の保存** — V2 は圧縮した key と value を別々に保存、V3 が統合 | V2 の時点で **$c^{KV}_t$ という単一の潜在**から $\mathbf{k}^C$ と $\mathbf{v}^C$ の双方を復元する。**記事自身の V2 節がその式を引用している** | 記事の V2 節 vs V3 節（内部矛盾） |
| **層ごとの適応的キャッシュ** — 深い層で古い KV エントリを刈る | **レポートに一切存在しない。** V3 §2.1 は「DeepSeek-V2 と比べた例外は、DeepSeekMoE に補助損失を使わない負荷分散戦略を導入したこと」と明記しており、**MLA の変更は例外として挙げられていない** | V3 §2.1 |

3 点目の根拠が特に強い。**原典が「V2 との違いは負荷分散だけ」と自ら書いている**以上、MLA に 3 つの改良が入っていたという記述は成り立たない。

細かいものが 2 点:

- **「Streaming Microcontrollers を動的に分割する」** — 正しくは Streaming **Multiprocessor**（SM）。記事の脚注 14 は "Streaming multiprocessors (SMs or 'microcontrollers')" と半分自己訂正しているが、本文は誤記のまま。また V3 は 132 SM のうち **20 個を通信に静的に割り当てる**のであって、動的分割ではない。
- **FP8 の FP32 昇格の理由**（前節のとおり、オーバーフロー回避ではなく仮数部 14 ビットの精度問題）。

**なぜこうなったかの推測**（記事の改訂履歴が手掛かりになる）。末尾の改訂ログに *「2025 年 6 月 18 日: DeepSeek の初期の講演／ブログには存在したが、公開された資料には存在しなかった詳細を削除した（Mark O'Connor に感謝する）」* とある。つまり著者は**一度この種の混入を掃除している**。それでも MLA の 3 点が残った。**二次資料は、著者が誠実に訂正を重ねていても、なお誤りを残しうる**——という、wiki の運用にとっての教訓の方が本体かもしれない。

## 限界・批判的視点

- **上記の事実誤り**が最大の限界。とくに MLA の 3 点は、V3 のレポートを読んでいない読者に「V3 で attention が作り直された」という誤った像を与える。実際には **V2 → V3 で attention は変わっていない**。
- **一次資料ではない**。数値・式・実験条件はすべて原典に当たって確認すべきで、本記事は地図として使うのがよい。
- **著者自身が前提知識を要求すると明言している**（「当サイトの記事としては通常よりも」）。冒頭に「今後数週間で概念の説明を加えたい」とあるが、2025-06-18 の最終改訂を見る限り**その拡充は行われていない**。
- **R1 以降がない**。最終改訂が 2025-06 なので、[[summaries/2025-kimi-k2]] 以降の joint RL、[[summaries/2026-deepseek-v4]] の CSA/HCA と OPD、DeepSeek-V3.2 の疎な attention はカバー範囲外。**「HPC 協調設計が唯一の道」という締めは、その後の系譜でむしろ強化されている**ので、結論自体は古びていない。
- **「創発的な推論」という語り口**には注意が要る。記事は自己検証・反省・探索的推論を「創発した振る舞い」として列挙するが、[[summaries/2025-cot-faithfulness]] が示すとおり、**出力された思考連鎖が実際の計算過程を忠実に反映しているとは限らない**。「反省しているように見えるテキスト」と「反省している」は別である（→ [[self-reflection]]）。

## 実装・運用上の示唆

- **scaling law を自分の設定に持ち込むときは、規模の測り方から疑う**。パラメータ数で測ると語彙サイズや埋め込み設計の違いが「規模」に化ける。非埋め込み FLOPs/token のような計算量ベースの指標なら、異なる構成のモデルを同じ曲線に乗せられる。
- **データ品質の改善は、モデルを大きくする許可証でもある**。データを綺麗にしたなら、同じトークン予算でモデルを一段大きくする方が合理的かもしれない——という読み替えができる。
- **ルーティングの自由度は削ってよい**。device-limited / node-limited routing の教訓は、**「理論上できること」を全部許すと通信で死ぬ**ということ。トポロジーに合わせて選択肢を先に絞るのは劣化ではなく設計である。
- **二次資料は一次資料への地図として使い、数値と機構は必ず原典で確認する**。本記事はまさにその手続きを踏んだ結果、3 点の誤りが見つかった。

## 用語と略称

- **LLM** = Large Language Model（大規模言語モデル）
- **HPC** = High Performance Computing（高性能計算）。**HPC co-design** はモデルのアーキテクチャと計算基盤を一体で設計すること
- **FLOPs** = Floating Point Operations（浮動小数点演算数）。**非埋め込み FLOPs/token** は埋め込み層を除いた層がトークン 1 個に費やす演算量
- **MLA** = Multi-Head Latent Attention（多頭潜在アテンション）。KV を低ランクの潜在ベクトルへ圧縮してキャッシュ量を減らす
- **KV cache** = Key-Value cache。生成済みトークンの Key/Value を保持して再計算を避ける機構
- **MoE** = Mixture of Experts（混合エキスパート）。トークンごとに一部のサブネットのみ活性化する構造
- **FFN** = Feed-Forward Network（Transformer 内の全結合ブロック）
- **RoPE** = Rotary Position Embedding（回転位置埋め込み）
- **YaRN** = Yet another RoPE extensioN。RoPE の周波数を補間してコンテキスト長を拡張する手法
- **SFT** = Supervised Fine-Tuning（教師ありファインチューニング）
- **DPO** = Direct Preference Optimization（報酬モデルも RL ループも使わない選好学習, [[summaries/2023-dpo]]）
- **RL** = Reinforcement Learning（強化学習）
- **PPO** = Proximal Policy Optimization（近位方策最適化）
- **GRPO** = Group Relative Policy Optimization（critic を排し群内の相対比較で advantage を作る, [[summaries/2024-deepseekmath]]）
- **CoT** = Chain-of-Thought（思考過程を明示的に出力させる手法）
- **FP8 / FP32** = 8 ビット／32 ビットの浮動小数点形式
- **GEMM** = GEneral Matrix Multiply（一般行列積）
- **PTX** = Parallel Thread eXecution。NVIDIA GPU の中間命令セット（CUDA より一段低い層）
- **SM** = Streaming Multiprocessor（GPU の演算ユニット）。**warp** はその上でまとめてスケジュールされるスレッドの束
- **IB** = InfiniBand（HPC クラスタで使われる高速・低遅延インターコネクト）
- **NVLink** = NVIDIA の GPU 間高速インターコネクト
- **all-to-all** = 全ノードが全ノードへデータを送る集団通信。MoE のトークン dispatch がこれにあたる
