# Kimi K2.5: Visual Agentic Intelligence（Kimi Team, 2026）

> 原典: [[translations/2026-kimi-k2.5]] ・ `raw/papers/Kimi K2.5_ Visual Agentic Intelligence.md`
> 著者・年・出典: Kimi Team（Moonshot AI）・2026・arXiv:2602.02276

## 一言まとめ

[[summaries/2025-kimi-k2]] の後継となるオープンソースのマルチモーダル agentic モデル。主張は 2 本柱——(1) **テキストと視覚は同時最適化すると相互強化する**（early fusion 事前学習・zero-vision SFT・視覚 RL がテキスト性能まで上げる双方向転移）、(2) **並列化そのものを RL で学習する Agent Swarm**（訓練可能なオーケストレータ＋凍結サブエージェントの PARL）で、BrowseComp 60.6→78.4%・実行時間 3〜4.5 倍短縮を達成。マルチエージェントの「いつ・何を並列化するか」を人手の設計からモデルの学習対象へ移した点で、[[multi-agent-systems]] のパラダイムを一段進めた原典である。

## 背景と問題意識

2 つの限界への応答である。第一に、従来の VLM（Vision-Language Model, 視覚言語モデル）構築の定石——テキストモデルの訓練後半に視覚を「後付け」する——は、言語か視覚のどちらかを犠牲にしがちだった。第二に、K2-Thinking のような数百ステップ級のエージェントでも**ツール呼び出しは逐次実行**であり、推論時間がステップ数に線形に伸びる。広い探索（wide search）を要するタスクでは、単一エージェントの推論深度とツール呼び出し予算が先に枯渇してしまう。[[summaries/2025-multi-agent-research-system]]（Anthropic）が示したように並列サブエージェントは有効だが、そこではオーケストレーションは**プロンプトと委任ヒューリスティクスの人手設計**だった。K2.5 はこの両方——モダリティ統合と並列オーケストレーション——を訓練問題として解く。

## 提案手法 / 主張

### 柱 1: テキスト×視覚の同時最適化——3 つの反直観的な知見

1. **early fusion・低 vision 比率が勝つ**（事前学習）: 視覚・テキストの総トークン予算を固定した対照実験で、「後半に視覚 50%」（従来の定石）より「最初から視覚 10%」が全指標で優位（表1）。late fusion はテキスト性能の「dip-and-recover」（視覚導入時に一度落ちて回復する）を起こすが、early fusion は安定に推移する。K2.5 は K2 チェックポイントから **15T トークン**の混合データで同時事前学習する。
2. **zero-vision SFT**（事後学習）: 視覚エージェント能力の発火（コールドスタート解消）に、**テキストのみの SFT で足りる**。画像操作は IPython（Python 実行環境）でのプログラム操作として代行させる——切り抜き・回転のような「視覚ツール」を用意する代わりに、二値化して数える・面積を測るといった操作をコードで書かせる。人手設計の視覚 trajectory（エージェントの行動列）を混ぜるとむしろ汎化が悪化した。
3. **視覚 RL がテキストを強くする**（joint RL）: 視覚必須タスク（グラウンディング・チャート読解・視覚 STEM）への成果ベース RL の後、テキストベンチマークが**上がる**（MMLU-Pro 84.7→86.4、GPQA-Diamond 84.3→86.4、LongBench v2 56.7→58.9）。これを受けて RL のドメイン編成を「モダリティ別」から**「能力別」（知識・推論・コード・agentic）**へ変更し、各ドメインがテキスト・視覚両方のクエリから学ぶ。

### 柱 2: Agent Swarm——並列化を学習する PARL

<figure>

![](../../raw/assets/2026-kimi-k2.5/multi-agent-rl-system.png)

<figcaption>図3（再掲）: 訓練可能なオーケストレータが凍結サブエージェントを動的に生成し、タスクを並列サブタスクへ分解・分配する。</figcaption>
</figure>

構成要素を書き下すと:

- **訓練対象はオーケストレータのみ**。サブエージェントは固定チェックポイントから起動される**凍結**モデルで、その trajectory は最適化対象から除外——出力は「環境からの観測」として扱う。これにより credit assignment（結果の功罪をどの行動に帰属させるかの割り当て）の曖昧さと訓練不安定を回避する。
- **ツールは 2 つだけ**: `create_subagent`（システムプロンプトと名前を与えて特化サブエージェントを定義）と `assign_task`（タスクを委任。並行起動可）。サブエージェント自身も検索・ブラウザ・コード実行を持つ。
- **PARL 報酬 = r_perf + λ1·r_parallel + λ2·r_finish**。r_parallel は *serial collapse*（並列化せず単独実行に退化する局所最適）を防ぎ、r_finish は *spurious parallelism*（意味のない大量サブエージェント生成で並列指標だけ稼ぐ reward hacking）を防ぐ。λ は訓練終盤にゼロへアニーリングし、最終ポリシーは純粋にタスク成果を最適化する。
- **critical steps**: 資源制約を総ステップ数でなく「メインのステップ＋各並列グループの**最長**サブエージェントのステップ」の和（クリティカルパス）で課す。並列度でなく**end-to-end レイテンシの短縮**に直接報酬を与える設計。
- **並列化は指示しない**: wide search / deep search 型の合成タスク分布を作り、逐次では予算内に完了できない状況に置くことで、並列分解が「自然に有利」になるよう仕向ける。訓練が進むと精度と並列度が同時に上昇する（図4）。

### Agent Swarm = 能動的コンテキスト管理（context sharding）

本論文の理論的に興味深い主張: サブエージェント分割は、Hide-Tool-Result・Summary・Discard-all（履歴を溢れた時点で圧縮・破棄する **reactive** な切り詰め）と違い、**分解の時点でコンテキストを意味的に分割し、要点のみをオーケストレータへ還流する proactive な方式**である。各サブエージェントは独立の作業記憶を持ち、グローバルコンテキストを汚染しない。BrowseComp では同じ K2.5 の Discard-all 運用を精度・critical steps の両方で上回る（図7）。[[context-engineering]] の圧縮 vs 分割の議論に直結する。

### その他の構成要素

- **MoonViT-3D**: SigLIP-SO-400M 初期化・NaViT の patch packing（可変解像度画像を 1 次元系列に詰める）を時間方向へ一般化。連続 4 フレームを時空間ボリュームとして同一エンコーダで処理し、時間プーリングで 4 倍圧縮——画像・動画で**完全重み共有**のまま長時間動画（2,000 フレーム超）を扱う。
- **Toggle（トークン効率 RL）**: 固定予算での訓練は length-overfitting（大きな推論予算に汎化しない）を起こすため、予算制約フェーズと通常スケーリングフェーズを m イテレーションごとに交互切替。K2 Thinking で出力トークン −25〜30%・性能劣化ほぼなし。
- **DEP（Decoupled Encoder Process）**: 視覚エンコーダを Pipeline Parallelism から切り離して全 GPU に複製し、forward → バックボーン訓練 → 再計算＋backward の 3 段に分ける。テキスト用に最適化済みの並列化戦略をそのまま再利用でき、マルチモーダル訓練効率はテキスト比 90%。
- **RL アルゴリズム**: token-level の対数比クリッピング（訓練・推論フレームワーク間の不一致による off-policy 乖離への対策）、視覚タスク特化報酬（IoU/ガウス距離のソフトマッチ F1・正規化編集距離・計数差）、GRM（Generative Reward Model, 生成型報酬モデル）の複数ルーブリック化。RL 基盤は Gym ライク環境＋最大 **10 万並行 rollout** の Rollout Manager。

## 実験結果と知見

- **単一エージェント**（表4・256k コンテキスト・temp 1.0）: SWE-Bench Verified 76.8%・LiveCodeBench v6 85.0%・AIME 2025 96.1%。agentic search が突出——BrowseComp 60.6%（管理なし）/74.9%（Discard-all）、DeepSearchQA 77.1%・Seal-0 57.4% は評価対象全モデル中トップ。HLE w/ tools 50.2% は GPT-5.2（45.5%）・Gemini 3 Pro（45.8%)超え。視覚は OCRBench 92.3%・MathVista 90.1%、長時間動画（LVBench 75.9%）で SOTA。
- **Agent Swarm**（表6）: BrowseComp 78.4%（+17.8pt、GPT-5.2 Pro 77.9 超え）・WideSearch item-F1 79.0%（Opus 4.5 の 76.2 超え）・内製 Swarm Bench 58.3%（+16.7pt）。目標 F1 を 30→70% に上げると単一エージェントの実行時間は約 1.8→7.0 倍に伸びるが、Swarm は 0.6〜1.6 倍でほぼ一定——**タスクが難しいほど並列化の利得が大きい**。

- **computer use**: OSWorld-Verified 63.3%（GUI 操作のみ。Operator 42.9% を上回り Opus 4.5 の 66.3% に肉薄）、WebArena 58.9%。→ [[computer-use-agents]]

## 限界・批判的視点

- **内製・引用ベンチの混在**: Swarm の利得が最大の「In-house Swarm Bench」は内製で外部再現不可。GDPVal は外部リーダーボードの引用。ベースラインの多くは自社再評価（\*付き）で、GPT-5.2 は API 不安定により視覚評価の約 10% が無出力＝誤答扱い——比較の非対称性がある。
- **凍結サブエージェントの二面性**: credit assignment 回避の代償として、サブエージェント側の実行能力は Swarm 訓練では向上しない。オーケストレーションと実行の**共進化**は未解決（[[summaries/2026-sakana-fugu]] の全体最適化と対照的な設計選択）。
- **並列化の適用範囲**: 利得が実証されたのは wide search 型（独立サブタスクに分解しやすい）が中心。サブタスク間依存が密なタスク（設計判断が連鎖するコーディング等）での有効性は本レポートでは示されていない。
- **安全性の議論が薄い**: 動的に生成されるサブエージェントへの権限委譲や prompt injection（外部入力に埋め込まれた指示による乗っ取り）耐性の分析はない。[[summaries/2025-masft]] が指摘した検証不足・情報隠蔽といったマルチエージェント固有の失敗様式が PARL でどこまで減るかも未検証。

## 実装・運用上の示唆

- **サブエージェント設計の最小 API**: `create_subagent`＋`assign_task` の 2 ツールで動的特化が成立している（付録 E.8 にスキーマ全文）。サブエージェント一覧を静的に用意する前に、この「定義もモデルに任せる」設計は検討に値する。
- **並列化の費用対効果は critical path で測る**: 総トークンでなく「最長ブランチ」で予算を切る発想は、自前のオーケストレータ評価にもそのまま流用できる。
- **報酬設計の教訓**: 並列化を直接報酬にすると spurious parallelism が出る。「補助報酬＋アニーリング」で探索だけ促し最終目的関数から消す、という手順が再現の要。
- **コンテキスト戦略の選択**: 溢れてから削る（Summary/Discard-all）前に、タスクが分解可能なら分割（sharding）を先に検討する——K2.5 の比較実験は分割優位の直接証拠。

## 用語と略称

- **VLM** = Vision-Language Model（視覚言語モデル）／ **LLM** = Large Language Model（大規模言語モデル）
- **early fusion**（視覚トークンを訓練の最初期から混ぜる方式。対義: late fusion＝後付け）
- **SFT** = Supervised Fine-Tuning（教師ありファインチューニング）／ **zero-vision SFT**（テキストのみの SFT で視覚能力を発火させる K2.5 の手法）
- **RL** = Reinforcement Learning（強化学習）／ **RFT** = Rejection-sampling Fine-Tuning（棄却サンプリングで良い trajectory のみ抽出して微調整）
- **PARL** = Parallel-Agent Reinforcement Learning（オーケストレータのみ更新し凍結サブエージェントを従える並列エージェント RL）
- **serial collapse**（並列化せず単独実行に退化する局所最適）／ **spurious parallelism**（見せかけの並列性。中身のないサブエージェント大量生成）
- **critical steps / critical path**（並列実行の所要時間を決める最長経路。K2.5 の資源制約指標）
- **context sharding**（コンテキストを事前に意味単位で分割してサブエージェントに持たせる方式。切り詰め＝truncation との対比）
- **GRM** = Generative Reward Model（生成型報酬モデル。ルーブリックに沿って自然言語で評価する報酬モデル）
- **MoE** = Mixture-of-Experts（→ [[transformer-architecture]]）／ **MuonClip**（K2 系のトークン効率オプティマイザ → [[summaries/2025-kimi-k2]]）
- **MoonViT-3D / NaViT packing**（可変解像度の画像パッチを 1 次元系列へ詰める方式の時空間拡張）／ **SigLIP**（対照学習ベースの視覚エンコーダ系列）
- **YaRN**（RoPE 補間による文脈長拡張手法）／ **PP / EP** = Pipeline / Expert Parallelism（→ [[llm-inference-optimization]]）
- **DEP** = Decoupled Encoder Process（視覚エンコーダを PP から分離する K2.5 の訓練インフラ）
- **Toggle**（予算制約と通常スケーリングを交互に切り替えるトークン効率 RL）／ **length-overfitting**（固定予算訓練が大きな推論予算に汎化しない現象）
- **CUA** = Computer-Use Agent（GUI を直接操作するエージェント → [[computer-use-agents]]）／ **OSWorld / WebArena**（computer use・Web GUI の代表ベンチマーク）
- **HLE** = Humanity's Last Exam ／ **BrowseComp / WideSearch / Seal-0**（agentic search 系ベンチマーク）／ **item-F1**（列挙型回答の項目単位 F1）
- **Avg@k**（k 回の独立実行の平均）／ **Hide-Tool-Result / Summary / Discard-all**（reactive なコンテキスト切り詰め 3 方式）
