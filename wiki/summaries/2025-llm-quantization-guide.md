# LLM 量子化の解説: 完全ガイド

> 原典: [[translations/2025-llm-quantization-guide]] ・ `raw/articles/LLM Quantization Explained_ A Complete Guide.md`
> 著者: Abhinaykrishna（Medium, 2025-03-27）

## 一言まとめ

LLM 量子化の**手法カタログ**。GPTQ・AWQ・GGUF・bitsandbytes をユースケース別に並べ、「どれを選ぶか」の判断表を与える実務者向けの記事で、最も価値があるのは末尾の **「量子化は必ずしもレイテンシを下げない」** という節である。

## 背景と問題意識

**量子化（quantization）**とは、高精度の数値を低精度の数値へ写像する圧縮技法である。LLM では重みや活性の精度を下げることを指す。動機は単純で、7B（70 億）パラメータのモデルは FP16（16 ビット浮動小数点）で **28GB** を要するが、4 ビットなら **7GB** に収まり、コンシューマ向け GPU に載る。

前提として、浮動小数点数は 3 つの部分からなる——**符号ビット**（正負）、**指数部（exponent）**（スケール。表現できる値の「広さ」を決める）、**仮数部（mantissa / significand）**（有効桁。「細かさ」を決める）。FP32 が完全精度、FP16 と BF16 が半精度にあたる。10 億パラメータなら FP32 で 4.0GB、INT8 で 1.0GB という単純な掛け算がメモリ見積もりの基本になる。

この記事の立ち位置は「原理の導出」ではなく「**現場で選べるようにする**」ことにある。同時期の [[summaries/2025-llm-quantization-explained]] が原理と実装を掘るのに対し、こちらは手法名とユースケースの対応づけに紙幅を割いている。

## 主張

### 何を量子化するのか——3 つの対象

「4 ビット量子化したモデル」と言うとき、ふつうは**重みの量子化**だけを指している。しかし対象は 3 つある。

| 対象 | 頻度 | 説明 |
|---|---|---|
| **重み（weights）** | 最も一般的 | 学習済みパラメータを圧縮。モデルサイズと VRAM が直接減る。GPTQ・AWQ・GGUF・bitsandbytes がこれ |
| **活性（activations）** | まれ | 推論中の中間値。**入力ごとに変わる**ので重みより難しい。主に QAT や特化した推論エンジンで |
| **KV cache** | 増加中 | 会話が長くなると数 GB を食う。量子化すると**長いコンテキストと同時実行ユーザ数**が伸びる。vLLM・TensorRT-LLM で普及 |

エージェント実務では 3 つ目が効く。多ターンの trajectory（エージェントが辿った行動列）は KV cache をそのまま膨らませるからである（→ [[llm-inference-optimization]]）。

### 較正データセット——「統計を取るだけ、更新はしない」

GPTQ や AWQ のような訓練後の手法は、量子化の前に小さな**較正データセット（calibration dataset）**を必要とする。代表的なサンプルをモデルに通して活性の統計量を集め、最適なスケーリング係数と「保護すべき重要な重み」を決めるためのものである。

記事はここを強調している——**較正はファインチューニングではない。重みを更新しない。** 数百から数千サンプルで足りる。混同しやすい点なので明示されているのは親切である。

### 4 つの技法

- **bitsandbytes**。8 ビット（LLM.int8()）はブロックごとにスケール係数を持ち、**外れ値の重みだけ fp16 で保持**する混合精度で精度低下を防ぐ。4 ビットは **NF4** データ型を使い、加えて **double quantization（二重量子化）**——スケール係数そのものを量子化する——で重みあたり **0.5 ビット → 0.127 ビット**まで削る。65B モデルで **3GB** の節約になる。主用途は LoRA / QLoRA での省メモリ・ファインチューニング。
- **GPTQ**（general pre-trained transformer quantization）。**層ごと**に量子化し、元の層と量子化後の層の出力の平均二乗誤差（MSE）を最小化するよう重みを調整する。128 列ずつの **lazy batch updating**。較正セットが要る。重みは 4 ビット、活性は FP16 のまま（推論時に逆量子化）。
- **GGML / GGUF**。**CPU 推論**のためのファイル形式。**k-Quant** 方式で重みをブロックへ分け、重要度に応じてビット幅を変える（q2\_k, q5\_0, q8\_0 など）。GGUF は GGML の後継で対応モデルが広く後方互換。動かすには **llama.cpp** が要る。
- **AWQ**（Activation-aware Weight Quantization, W4A16）。**全重みの約 1% の「顕著な（salient）」重み**を較正データの活性統計から特定し、そこだけ量子化を飛ばす代わりに**チャネルごとのスケーリング**を適用してから量子化する。残り 99% を INT3/INT4 へ落とす。ハードウェア効率を保ったまま精度を稼ぐ設計。

### 選択の指針

| 状況 | 推奨 |
|---|---|
| CPU で動かす | **GGUF**（llama.cpp） |
| NVIDIA GPU で動かす | **GPTQ** または **AWQ** |
| 少ない GPU メモリでファインチューニング | **bitsandbytes** ＋ LoRA / QLoRA |
| 精度最優先 | 量子化しない（FP16 / BF16） |
| メモリ削減が主目的 | 4 ビット（最大 4 倍削減、精度低下は小） |

### 最も価値のある節——量子化は必ずしも速くならない

記事の結論部は、実務者が最も誤解しやすい点に踏み込んでいる。**メモリが減ることと速くなることは別である。** レイテンシがむしろ増えうる状況として 4 つ挙げる。

1. **逆量子化のオーバーヘッド** — 多くの手法は INT4/INT8 で**格納**するが計算は FP16/BF16 で行うので、推論のたびに逆量子化の計算が乗る。
2. **ハードウェア支援の欠如** — GPU/CPU に低精度演算の専用回路がなければ、低ビット化の恩恵を受け取れない。
3. **最適化されていない推論エンジン** — 行列積のたびに逆量子化する実装だと遅くなる。
4. **小さなモデル** — 逆量子化のオーバーヘッドがメモリ節約を上回る。

要点として「量子化は**ほぼ常にメモリを減らす**が、**低レイテンシは保証されない**」と明言している。

## 限界・批判的視点

査読を経ていない個人ブログであり、**技術的な誤りが複数ある**。正しい記述は [[concepts/model-quantization]] にまとめた。

1. **INT4 の誤差例で数値がすり替わる。** 「**5.62** を INT4 量子化する」と書き始めながら、次の行では「**0.562** は 0.6 に最も近い」「誤差は 0.6 − 0.562」となる。おそらく 0.562 が意図だが、そのままでは追えない。
2. **INT8 の実例が非対称レンジと対称写像を混ぜている。** scale を `(3.8 − (−2.3)) / 255` と非対称レンジから求めておきながら「簡単のため `zero_point = 0`」と置くため、3.8 が `159` になって **127 へクランプ**され、復元値が **3.03**（元の 3.8 に対して約 20% の誤差）になる。記事はこの破綻に触れず、そのまま「復元された値」として提示している。ゼロ点を正しく計算していればクランプは起きない——[[summaries/2025-llm-quantization-explained]] が載せる affine 量子化の式（$z = q_{min} - x_{min}/s$）がその正しい形にあたる。
3. **「uses nf4 instead of nf8」は誤り。** **NF8 という形式は存在しない**。LLM.int8() は NormalFloat ではなく **INT8 ＋ 外れ値の混合精度分解**である。付図の比較表にも `uses nf4,nf8` と書かれているので、記事全体で一貫した誤解になっている。
4. **8 ビットの説明に 4 ビットの性質が混入している。** 「64 要素ブロックごとにスケール係数」は bitsandbytes の 4 ビット側（NF4 のブロック量子化）の性質で、LLM.int8() の特徴は**ベクトル単位の量子化と外れ値分解**である。

そのほか、押さえておくべき点:

- **数値の出どころが示されていない。** GPTQ と AWQ の精度比較（「AWQ は 4 ビットで GPTQ より精度が良い」）はベンチマークも出典も伴わない。
- **2025 年 3 月時点のカタログ**である。この領域はライブラリの更新が速く、対応ハードウェア・ビット幅・推奨は陳腐化しやすい。
- **エージェント固有の観点はない。** 多段ツール呼び出しや長い CoT で量子化誤差がどう累積するかは扱われていない。ここは [[summaries/2026-llm-optimization-guide]] の「アプリケーションごとの品質検証が必須」という但し書きで補うべきところである。

## 実装・運用上の示唆

- **「量子化＝高速化」と考えない。** メモリと速度は別の目的関数である。低精度演算のハードウェア支援があるか、推論エンジンがネイティブな量子化演算を持つかを先に確認する。これは [[llm-inference-optimization]] の「FLOPs ≠ wall-clock」「律速はどこにあるか」という主題の、量子化版にあたる。
- **較正とファインチューニングを混同しない。** 較正は統計収集だけで重みを更新しない。したがって「較正データにモデルが過適合する」たぐいの心配は的外れだが、逆に**較正データが本番の入力分布とずれていればスケール係数がずれる**という別の注意が要る。
- **デプロイ先から手法を決める。** CPU なら GGUF、NVIDIA GPU なら GPTQ/AWQ、省メモリ・ファインチューニングなら bitsandbytes、という対応づけは実務上そのまま使える。
- **KV cache の量子化はエージェントで効く。** 重みの量子化はモデルを載せるための話だが、KV cache の量子化は**長い trajectory と同時実行数**に直接効く。多ターンのエージェントを捌く文脈では、こちらの優先度が高い場面がある。

## 用語と略称

- **量子化（quantization）** = 高精度の数値を低精度へ写像する圧縮技法
- **FP32 / FP16 / BF16 / INT8 / INT4** = 32・16 ビット浮動小数点／Brain Float 16／8・4 ビット整数
- **仮数部（mantissa / significand）** = 浮動小数点数の有効桁を持つ部分。精度を決める
- **指数部（exponent）** = スケールを決める部分。表現できる値の広さ（動的範囲）を決める
- **PTQ** = Post-Training Quantization（訓練後量子化。訓練済みモデルに後から適用）
- **QAT** = Quantization-Aware Training（量子化を意識した訓練。訓練中に量子化を模擬して誤差へ適応させる）
- **較正データセット（calibration dataset）** = 活性の統計量を集めるための代表サンプル。**重みは更新しない**
- **GPTQ** = general pre-trained transformer quantization（層ごとに MSE を最小化する訓練後量子化）
- **AWQ** = Activation-aware Weight Quantization（活性統計から約 1% の顕著な重みを特定して保護する。W4A16 ＝ 重み 4 ビット・活性 16 ビット）
- **GGML / GGUF** = Georgi Gerganov Machine Learning / GPT-generated Unified Format（CPU 推論向けのモデル形式。llama.cpp で動かす）
- **k-Quant** = GGUF がブロックごとに重要度に応じたビット幅を割り当てる方式
- **bitsandbytes** = LLM.int8() と NF4 を提供するライブラリ。LoRA/QLoRA での省メモリ・ファインチューニングの標準
- **NF4** = NormalFloat 4-bit（重みが正規分布に従う前提で情報理論的に最適な 4 ビット表現）
- **double quantization（二重量子化）** = スケール係数そのものを量子化して追加のメモリを削る手法
- **KV cache** = 生成済みトークンの key/value を保持して再計算を避ける領域
- **VRAM** = GPU 上のビデオメモリ
- **MSE** = Mean Squared Error（平均二乗誤差）
- **vLLM / TensorRT-LLM / llama.cpp / ONNX Runtime** = 量子化モデルを効率的に実行する推論フレームワーク
