# Toolformer — 言語モデルが自己教師ありでツール使用を学ぶ

> 原典: [[translations/2023-toolformer]] ・ `raw/papers/Toolformer_ Language Models Can Teach Themselves to Use Tools.md`
> 著者・年: Timo Schick ほか（Meta AI Research）・2023-02（NeurIPS 2023, arXiv:2302.04761）

## 一言まとめ

言語モデルに **API 呼び出しの使い方を自己教師あり（self-supervised）で学習させる**手法を確立した論文。人手の注釈もタスク固有のプロンプトも使わず、「その API 呼び出しは将来のトークン予測のパープレキシティ（perplexity, 予測の不確かさ）を下げたか」という**モデル自身のフィードバックだけ**を訓練信号にする。6.7B の GPT-J をこの方式でファインチューニングした Toolformer は、25 倍大きい GPT-3 (175B) を複数の zero-shot タスクで上回った。[[tool-use-and-function-calling]] における「ツール利用を重みに埋め込む」系譜の起点となった古典。

## 背景と問題意識

LLM（Large Language Model, 大規模言語モデル）は few-shot で多才だが、逆説的に**算術・事実照合・最新情報・低リソース言語・時間感覚**という基本機能に弱い——これらは小さな専用ツール（計算機・検索・カレンダー等）が易々とこなす領域である。ツールを繋げばよいのだが、2023 年当時のアプローチは 2 択しかなかった: (a) 大量の人手注釈でツール使用を教える（高コスト、しかも「人間が有用と思う使い方」は「モデルが有用と思う使い方」と違いうる）、(b) タスクごとに「この問題ではこのツールをこう使え」と few-shot プロンプトで指示する（汎用性を失う）。Toolformer は第三の道——**モデルが自分で、どのツールをいつどう使うかを学ぶ**——を提示する。要件は 2 つ: 人手注釈に頼らない自己教師あり学習であること、汎用性を失わずモデル自身が呼び出しを判断できること。

## 提案手法 — 自己教師あり注釈の 3 ステップ

<figure>

![](../../raw/assets/2023-toolformer/x2.png)

<figcaption>図2（再掲）: アプローチの 3 ステップ。(1) 位置 i を選んで API 呼び出し候補をサンプリング → (2) 実行して結果を得る → (3) 損失を下げなかった呼び出しを除去。残ったものを元テキストに挿入して拡張データ x* を作る。</figcaption>
</figure>

鍵は「**プレーンテキストのデータセットを、有用な API 呼び出しで自動注釈する**」こと。API 呼び出しは特殊トークンで線形化してテキストに埋め込む（`<API> 名前(入力) → 結果 </API>`）。手順:

1. **サンプリング**: 各 API について、人手で書いた**ほんの数例のデモを含むプロンプト**で LM の in-context learning を使い、テキスト中の各位置に「ここで API を呼ぶ確率」を計算 → 閾値超えの位置で候補呼び出しを生成。
2. **実行**: 生成された呼び出しを実行して結果文字列を得る（別の LM・Python スクリプト・検索システム等、何でもよい）。
3. **フィルタリング（核心）**: 各呼び出しについて、「**呼び出しと結果を与えたときの後続トークンの損失** $L^+$」と「**呼び出さない or 入力だけで結果を与えないときの損失** $L^-$」を比べ、$L^- - L^+ \geq \tau_f$（呼び出しが損失を閾値以上下げた）ものだけを残す。つまり「この呼び出しは実際にモデルの予測を助けたか」を自己採点する。

残った呼び出しを元テキストに挿入して拡張データセット $\mathcal{C}^*$ を作り、**標準の言語モデリング目的で $M$ をファインチューニング**する。$\mathcal{C}^*$ は元データと（挿入された呼び出しを除き）同一テキストなので汎用性が保たれる。推論時は、モデルが `→` トークンを出したらデコードを中断して実際に API を呼び、結果を挿入して続行する。

**5 つのツール**: 質問応答（Atlas——検索拡張 LM）・Wikipedia 検索（BM25 リトリーバ）・計算機（Python・四則演算）・機械翻訳（NLLB・200 言語）・カレンダー（現在日付を返す）。ツールの唯一の制約は「入出力がテキストで表せる」「使用デモが数例得られる」こと。

## 実験結果と知見

すべて**プロンプトつき zero-shot**（タスク固有の例示なし）で評価。ベースは 6.7B GPT-J。

- **LAMA（事実照合）**: Toolformer は SQuAD/Google-RE/T-REx で +11.7/+5.2/+18.6 ポイント、質問応答ツールを 98.1% の例で自発的に使い、25 倍大きい GPT-3 (175B) も上回る。
- **数学（ASDiv/SVAMP/MAWPS）**: 計算機を 97.9% で使い、性能が 2 倍以上に。GPT-3 も明確に上回る。
- **QA（WebQS/NQ/TriviaQA）**: Wikipedia 検索を 99.3% で使い同サイズを上回るが、**GPT-3 には及ばない**（検索が単純で、結果が悪くてもクエリを再定式化・複数結果の閲覧ができないため）。
- **多言語 QA（MLQA）**: 機械翻訳を使い改善するが、CCNet ファインチューニングの分布シフトで GPT-J を一貫しては超えない。
- **時間（Dateset）**: カレンダーを 54.8% で使い大幅改善。ただし TempLAMA ではカレンダーがほぼ役立たず（固有表現が稀すぎる）、Wiki 検索/QA に頼った。
- **言語モデリング能力は劣化しない**: API を無効にすると素の GPT-J とほぼ同じパープレキシティ（WikiText 10.3・CCNet 10.5）。「ツールを覚えても素の能力を失わない」ことの実証。
- **スケーリング則（図4）**: ツールをうまく使う能力は**約 775M パラメータで創発**する。小さいモデルはツールあり/なしで同性能。モデルが大きくなると素の能力もツール活用も同時に伸び、両者の差は最大モデルでも大きいまま。
- **キャリブレーション**: 貪欲デコード（$k=1$）だと、モデルは「ツールなしでは特に苦手な例」で API を呼ぶ（呼ばない例の性能が平均より高い）。ただし $k$ を上げてツール利用を促すとこのキャリブレーションは失われる。

## 限界・批判的視点

原典が明示する限界がそのまま、後続研究の課題設定になっている:
- **ツールの連鎖（chaining）ができない**: 各 API 呼び出しが独立にサンプリングされるため、あるツールの出力を別のツールに渡す例が訓練データにない。TempLAMA の最善手（カレンダー→QA）が学べなかったのはこのため。
- **対話的なツール利用ができない**: 検索で結果が悪くてもクエリを直せない・複数結果を閲覧できない。GPT-3 に QA で負けた主因。
- **入力の言い回しに敏感**: API を呼ぶか否かがプロンプトの細部に左右される。
- **サンプル非効率**: 100 万文書処理しても計算機の有用な呼び出しは数千例しか採れない（反復適用が対策候補）。
- **API 呼び出しのコストを考慮しない**: 「呼ぶ価値があるか」の損得計算をしていない。
- **入力あたり最大 1 回・独立サンプリング**という設計上の制約が、連鎖・対話の不在の根本原因。

これらは 2 年後の視点では**エージェント（agent）が解いた問題そのもの**である（下記）。

## 既存 wiki との接続 — ツール利用の系譜の起点

- **[[tool-use-and-function-calling]] の「ツール利用を重みに埋め込む」系譜の起点**。この wiki のツール概念ページは、プロンプト規約（ReAct の Wikipedia API）→ **Toolformer（自己教師あり学習）**→ 構造化 function calling（API レベル）→ 大規模データ合成（K2）という発展として整理される。Toolformer は「**プロンプトでの教示から、モデルの重みへのツール利用能力の埋め込みへ**」という転換の最初の一手。
- **ReAct との対比**が象徴的。[[summaries/2022-react]]（同 2022-2023 期）が**推論時にプロンプトでツールを呼ぶ**（思考と行動の交互生成）のに対し、Toolformer は**訓練時に重みへ埋め込む**——同じ「LM にツールを使わせる」目的の、逆の層からのアプローチ。Toolformer 自身の Related Work も ReAct を「タスク固有 few-shot に頼る手法」として引き、自己教師あり・タスク非依存を差別化点とする。
- **「連鎖・対話ができない」が agent 化の動機**になった。Toolformer の限界（独立な単発呼び出し）を、[[agent-loop]]（観測→思考→行動の反復ループ）と [[reasoning-and-planning]] の計画が乗り越える。現在のエージェントの「ツールを繰り返し呼び、結果を見て次を決める」ループは、Toolformer が構造的にできなかったことの実現形。
- **フィルタリング＝自己採点は「検証可能報酬」の先駆**。「その行動は損失（=目的）を改善したか」で訓練例を選別する発想は、後の RLVR（Reinforcement Learning with Verifiable Rewards, [[reinforcement-learning-from-human-feedback]]）や Meta-Harness（[[summaries/2026-meta-harness]] の「探索セット性能で候補を選ぶ」）と同型——ただし Toolformer は勾配を使わず**データ選別（棄却サンプリング）**でこれを行う点が K2 のツール利用データ合成（[[summaries/2025-kimi-k2]]）の直接の祖先。
- **ブートストラッピングの一例**。自分の予測をフィルタして自分を訓練する（STaR 等と同系譜）。「モデルが自分の生成物で自分を鍛える」自己改善ループの初期例で、[[self-reflection]] の反省蓄積とも精神を共有する。

## 実装・運用上の示唆

- **ツール利用は「教える」より「有用性で選別する」**: 人間が使い方を指定するより、「実際にモデルの目的を改善した呼び出し」を残す方が、モデル自身に合った使い方を学べる（人間とモデルで有用の基準が違う、という洞察）。この「実行結果で訓練データを選ぶ」発想は現在のツール利用データ合成の基本。
- **創発性を前提にする**: ツール活用は小モデルでは効かず 775M 級で創発する。小さいモデルにツールを持たせても学習にならない——[[reasoning-and-planning]] の CoT 創発や [[self-reflection]] の Reflexion と同型の規模依存性。
- **素の能力を壊さない設計**: 拡張データを「元テキスト＋挿入」に限れば、ツールを覚えても言語モデリング能力は劣化しない。ファインチューニングで新能力を足すときの安全な作り方の一例。
- ただし**単発・独立の呼び出しに閉じるなら agent ループへ**: 連鎖・対話・クエリ再定式化が要るタスクでは、Toolformer 方式でなく [[agent-loop]] を回す設計が要る。

## 用語と略称

- **self-supervised（自己教師あり）** = 人手ラベルなしで、データ自身から作った信号（ここでは「呼び出しが将来トークンの損失を下げたか」）で学習する
- **perplexity（パープレキシティ）** = 言語モデルの予測の不確かさ。低いほど「次のトークンをよく当てられる」。Toolformer のフィルタリングの採点基準
- **API 呼び出しの線形化** = `<API> 名前(入力) → 結果 </API>` の形でテキストに埋め込む表現（実装上は `[ ] ->` トークンで代用し語彙を変えない）
- **in-context learning（ICL, 文脈内学習）** = プロンプト内の少数例から学ぶ能力。API 候補のサンプリングに使う
- **zero-shot / few-shot** = タスク例を 0 個／数個だけ与える設定。Toolformer は zero-shot で評価
- **GPT-J** = 6.7B パラメータのオープン LM（本手法のベースモデル）／ **CCNet** = 訓練に使った Web テキストコーパス
- **Atlas / NLLB / BM25 / fastText** = QA（検索拡張 LM）／機械翻訳（200 言語）／字句検索／言語判定 に使ったツール群
- **LAMA / TempLAMA / ASDiv / SVAMP / MAWPS / MLQA / TriviaQA** = 評価に使ったベンチマーク（事実照合・時間・数学・多言語 QA 等）
- **$\tau_s$ / $\tau_f$** = サンプリング閾値／フィルタリング閾値（どこで呼ぶか・どれを残すか）
