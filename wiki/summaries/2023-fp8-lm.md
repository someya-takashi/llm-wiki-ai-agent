# FP8-LM: FP8 による大規模言語モデルの訓練

> 原典: [[translations/2023-fp8-lm]] ・ `raw/papers/FP8-LM_ Training FP8 Large Language Models.md`
> 著者: Peng, Wu, Wei ら（Microsoft Azure and Microsoft Research）
> 2023 年（arXiv:2310.18313）

## 一言まとめ

**FP8 を「行列積だけ」でなく訓練の全過程——計算・格納・通信——へ浸透させた初のフレームワーク**である。GPT-175B を BF16 比で **75% 高速・メモリ 39% 削減**、当時唯一の実用フレームワークだった NVIDIA Transformer Engine に対しても **37% 高速・42% 省メモリ**を達成した。

## 背景と問題意識

2023 年、H100 の登場で FP8 が「次世代のデータ型」として現実味を帯びていた。理論上は BF16 比で **2 倍の速度・50〜75% のメモリ削減・50〜75% の通信削減**が見込める。

しかし本論文は、当時唯一の実用フレームワークだった **NVIDIA Transformer Engine（TE）を名指しで批判する**——「TE は **FP8 を GEMM の計算にのみ適用し、master weight と勾配は依然として高精度（FP16 や FP32）で保持する**。その結果、端から端までの高速化・メモリと通信コストの節約は非常に限定的であり、FP8 の力を十分に引き出せていない」。

**「どこまで FP8 にするか」が争点である。** TE の答えは「行列積だけ」。本論文の答えは「計算・格納・通信の全部」である。

### なぜ単純に全部 FP8 にできないのか

FP8 には 2 つの部分形式がある。

| 形式 | 構成 | 最大値 | 位置づけ |
|---|---|---|---|
| **E4M3** | 符号 1・指数 4・仮数 3 | ±448 | 範囲が狭く精度が高い |
| **E5M2** | 符号 1・指数 5・仮数 2 | ±57,344 | 範囲が広く精度が低い |

E4M3 の表現範囲は [1.95×10⁻³, 448] しかない。BF16 の [1.18×10⁻³⁸, 3.39×10³⁸] と比べれば桁違いに狭い。**アンダーフローとオーバーフローが日常的に起きる**ので、loss spike や NaN による訓練の崩壊を招く。

対処の基本は**テンソルスケーリング**——FP8 へキャストする前にスケーリング係数を掛けて、値を表現可能な範囲の「快適域」へ移す。ただしこれを分散訓練の全経路に通そうとすると、後述する厄介な問題が次々出てくる。

## 提案手法 — 3 つの障壁を個別に潰す

フレームワークは **3 段階の最適化レベル**として設計されており、8 ビットの集合通信 → オプティマイザ → 分散並列訓練を追加的に有効化していく。既存の 16/32 ビットのコードへの**ドロップイン置換**として使えることが設計目標である。

### (1) FP8 の勾配と all-reduce — 自動スケーリング

勾配を素朴に FP8 にすると精度が落ちる。原因は all-reduce における 2 つの標準的手法のいずれもが破綻することにある。

- **pre-scaling**（先に $N$ で割ってから足す）: $N$ が大きいと**アンダーフロー**する。
- **post-scaling**（先に足してから $N$ で割る）: 値が FP8 の最大値近くに留まるのでアンダーフローは防げるが、集約時に**オーバーフロー**する。

提案する **auto-scaling** は、訓練中に動く係数 $\mu$ を入れて両方を回避する。**FP8 の表現範囲の最大値に達する値の割合が 0.001% を超えたら $\mu$ を半分にし**（オーバーフロー抑制）、**割合が閾値を下回り続けたら 1,000 ステップかけて $\mu$ を 2 倍へ指数的に増やす**（アンダーフロー抑制）。

もう一つの障壁が**スケーリング係数の扱い**である。NCCL の all-reduce はテンソル単位のスケーリング係数を考慮できず、しかも NCCL の総和はサブテンソル水準で動く。解は単純で、**全 GPU のスケーリング係数の最小値 $s'_g$ を 1 つ共有し、それで統一する**。送るのはスカラー 1 個だけなので、標準の NCCL all-reduce がそのまま使える。

### (2) FP8 オプティマイザ — 精度分離

Adam は典型的にパラメータあたり **16 バイト**（master weight 4 ＋ 勾配 4 ＋ Adam 状態 4+4）を食う。全部を 16 ビットに落とすと十億規模で精度が落ちることは先行研究が示していた。そこで**変数ごとに必要な精度を切り分ける**——これが **precision decoupling（精度分離）** である。

導かれた指針が明快である。**「勾配の統計量は低精度でよいが、master weight は高精度を要する」。**

- **一次モーメントは FP8 でよい。** Adam の更新では**勾配の大きさより方向のほうが重要**だから。
- **二次モーメントは 16 ビットが要る。** 勾配の**二乗**を取るのでアンダーフローしやすい。
- **master weight は高精度が要る。** 重みの更新は極端に小さくなったり大きくなったりし、ここで情報を失うと訓練が不安定になる。既定は**テンソルスケーリング付き FP16**。

結果、パラメータあたり **6 バイト**（2 ＋ 1 ＋ 1 ＋ 2）——**2.6 倍の削減**である。論文はこれを「**LLM 訓練のための初の FP8 オプティマイザ**」と位置づける。

アブレーション（Table 6・Figure 8）が指針を裏づけている:

| 設定 | master weight | Adam 状態 | 結果 |
|---|---|---|---|
| FP8 #2a | FP16（スケーリング付き） | FP8+FP16 | FP32 と同等 |
| FP8 #2b | BF16 | FP8+FP16 | #2a よりわずかに悪い（**BF16 は仮数が少ない**） |
| FP8 #3 | **FP8** | FP8+FP16 | **性能低下** |
| FP8 #4 | FP16 | **FP8+FP8** | **発散** |

**#2b と #2a の差が面白い。** [[summaries/2019-bfloat16]] が売り込んだ BF16 の「広い動的範囲」は、ここでは逆に働く——master weight のように**狭い範囲で細かい更新**を扱う場面では、仮数 7 ビットの BF16 より仮数 10 ビットの FP16 ＋ スケーリングのほうが良い。**形式の優劣は用途で反転する。**

### (3) FP8 分散並列訓練

- **データ並列とパイプライン並列は変更不要**（追加の FP8 計算・通信を伴わないため）。
- **テンソル並列・系列並列**では、変換器 $g$ の直前に FP8 変換を挟み、all-gather / reduce-scatter を FP8 で行う。活性に関わる通信量が **34% 削減**。
- **ZeRO には工夫が要る。** ZeRO はテンソルを分割して配るが、**FP8 のパーティションに紐づくスケーリング係数の扱いが難しい**。そこで**テンソルを分割せず丸ごと配る**方式に変え、サイズ降順にソートして残りメモリの多い GPU から割り当てる貪欲アルゴリズム（Algorithm 1）を使う。省メモリと負荷分散を同時に達成する。

## 実験結果と知見

### モデルの品質

125M〜175B の GPT を訓練し、**FP8 と BF16 の損失曲線がほぼ重なる**（Figure 4）。下流のゼロショット評価（Table 2）も、GPT-7B で平均 58.4 対 58.0、GPT-13B で 61.0 対 60.4 と同等。**ハイパーパラメータは一切変更していない。**

### システム性能（Table 5、H100 80GB）

| GPT-175B | メモリ | スループット | MFU |
|---|---|---|---|
| BF16 | 66.1 GB | 22.4 samples/s | 39.0% |
| FP8 (TE) | 69.6 GB | 28.7 | 24.9% |
| **FP8 (Ours)** | **40.3 GB (-39%)** | **39.3 (+75%)** | **34.2%** |

**TE がメモリを BF16 より増やしている**点に注目したい（66.1 → 69.6 GB）。TE は計算に FP8 を使うが高精度のオプティマイザと勾配を保持するので、スケーリング係数などの追加分でむしろ増える。本論文はそこを 40.3 GB まで落としている。

重みに関わる通信量は **63〜65% 削減**。実務的な帰結として、**32 台の H100 で 4,096 トークンのコンテキストの 175B が訓練できる**（TE は 2,048 トークンまで）。

### 事後訓練にも効く

- **SFT**: GPU メモリ 51.1 → 44.0 GB（−14%）、スループット 103 → 131（+27%）、AlpacaEval は 66.15 → 67.20 と**むしろ改善**
- **RLHF**: 重みのメモリ **−32%**、オプティマイザ状態 **−62%**、AlpacaEval 72.05 → 72.42

RLHF は方策・参照・報酬・価値の複数モデルを同時に載せるので、メモリ削減の効きが大きい（→ [[reinforcement-learning-from-human-feedback]]）。

## 限界・批判的視点

- **175B は 40B トークンしか訓練していない。** 論文自身が「炭素排出の緩和とコスト節約のため」と明記しており、**システム性能の評価には十分だがモデル品質の主張の根拠としては弱い**。損失曲線が重なると言っても、地平線が短い。
- **7B・13B も 100B トークンである。** 現代の基準（[[summaries/2025-nvfp4-pretraining]] は 10T トークン）から見ると 2 桁短い。**長い地平線で低精度の誤差が蓄積するかは本論文では分からない**——これは NVFP4 論文が正面から扱う論点である。
- **FP8 の「2 倍の速度」は達成していない。** 実測は 175B で +75%、7B/13B では +38〜53%。理論値との差は通信・非 GEMM 演算・逆量子化のオーバーヘッドである。
- **MFU が BF16 より低い。** 175B で BF16 39.0% に対し FP8 34.2%。スループットは上がるが**計算資源の利用効率は落ちている**——FLOPs あたりの効率でなく、時間あたりのスループットで勝っている。
- **attention 自体は FP8 化していない。** 線形層が対象で、attention の内部は高精度のまま。ここを FP8 にするのは別の論文の仕事になる（→ [[summaries/2024-flashattention-3]]）。
- **多くの数値が単一実行である。** 分散や信頼区間の報告がない。
- **利害関係。** Microsoft Azure の論文であり、比較対象の TE は NVIDIA 製である。批判自体は技術的に正確だが、Azure の H100 プラットフォームでの優位を示す動機がある。

## 実装・運用上の示唆

1. **「どこを低精度にしないか」を先に決める。** 精度分離の指針——**勾配の統計量は低精度でよいが master weight は高精度**——は、FP8 に限らず低精度化の一般的な出発点になる。DeepSeek-V3（[[summaries/2024-deepseek-v3]]）の「埋め込み・出力ヘッド・ゲーティング・正規化・attention は高精度のまま」と同じ発想である。
2. **形式の優劣は用途で反転する。** BF16 は訓練全体の安定性には強いが、**master weight のように狭い範囲で細かい更新を扱う場面では FP16 ＋ スケーリングに負ける**。「BF16 のほうが優れている」と一般化しない。
3. **アンダーフローとオーバーフローは別々に測る。** auto-scaling の設計は、SNR・アンダーフロー率・オーバーフロー率を**別々の指標として計測した**ことから来ている。片方だけを見ると pre-scaling か post-scaling のどちらかに偏る。
4. **既存の集合通信ライブラリに合わせて設計する。** スケーリング係数を全 GPU で 1 つに統一したのは、NCCL の all-reduce をそのまま使うためである。**ライブラリを書き換えるより、ライブラリが受け付ける形に問題を変形するほうが安い。**
5. **ドロップイン置換であることを設計目標にする。** ハイパーパラメータの変更を要求しないことが、この手の低精度フレームワークの採用可否を分ける（→ [[summaries/2019-bfloat16]] と同じ主題）。

## 用語と略称

- **FP8** = 8-bit Floating Point。E4M3（指数 4・仮数 3、±448）と E5M2（指数 5・仮数 2、±57,344）の 2 つの部分形式を持つ
- **TE** = Transformer Engine（NVIDIA の FP8 訓練ライブラリ。本論文の主要な比較対象）
- **precision decoupling**（精度分離）= オプティマイザ内の変数ごとに必要な精度を切り分けること
- **tensor scaling**（テンソルスケーリング）= FP8 へキャストする前にスケーリング係数を掛けて値を表現可能な範囲へ移す技法
- **auto-scaling**（自動スケーリング）= スケーリング係数を訓練中に動的に調整し、アンダーフローとオーバーフローの双方を抑える提案手法
- **just-in-time scaling / delayed scaling** = スケーリング係数を、その場の amax から決めるか、過去数反復の履歴から決めるか
- **amax** = absolute maximum（テンソル内の最大絶対値）
- **all-reduce** = 全 GPU の値を集約して全 GPU へ配る集合通信。勾配の同期に使う
- **NCCL** = NVIDIA Collective Communications Library
- **ZeRO** = Zero Redundancy Optimizer（モデル状態を GPU 間で分割保持してメモリを節約する技法）
- **TP / PP / DP / SP** = Tensor / Pipeline / Data / Sequence Parallelism
- **MFU** = Model FLOPs Utilization（理論ピーク性能に対する実効的な計算利用率）
- **SNR** = Signal-to-Noise Ratio（信号対雑音比。ここでは量子化誤差の評価に使う）
- **SFT / RLHF** = Supervised Fine-Tuning / Reinforcement Learning from Human Feedback
- **loss spike** = 訓練損失が突発的に跳ね上がる現象。低精度訓練で起きやすい
