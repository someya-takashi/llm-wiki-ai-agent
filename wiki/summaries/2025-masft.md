# Why Do Multi-Agent LLM Systems Fail?（MASFT）

> 原典: [[translations/2025-masft]] ・ `raw/papers/Why Do Multi-Agent LLM Systems Fail_.md`（ar5iv クリップ, arXiv:2503.13657）
> 著者・年: Mert Cemri ほか（UC Berkeley）・2025

## 一言まとめ

「マルチエージェントシステム（MAS）はなぜ期待ほど性能が出ないのか」を、5 つの人気 MAS の **150+ 実行トレース（各平均 1.5 万行）の人手分析**で初めて体系化した論文。**14 の失敗モード × 3 カテゴリ**の分類法 **MASFT**（Multi-Agent System Failure Taxonomy）を提示し、「失敗の原因は個々の LLM の能力不足ではなく、**組織設計の欠陥**にある」と主張する。冒頭のトルストイのもじり——「成功するシステムはどれも似た働き方をするが、失敗するシステムはそれぞれに固有の問題を抱えている」——が論文全体を要約している。

## 背景と問題意識

MAS への熱気に反して、実測の性能は冷ややかである。単一エージェントや best-of-N サンプリング（同じモデルに N 回解かせて一番良い答えを採る単純な手法）にすら明確に勝てておらず、著者らの計測では SOTA 級 OSS の ChatDev の正答率は **25%**、AppWorld 上の MAS は 13.3% まで落ちる。しかし「なぜ失敗するのか」を体系的に調べた研究は存在しなかった——既存研究はベンチマークのスコアというトップダウンの視点が中心で、**トレースの中で実際に何が起きているか**というボトムアップの視点が欠けていた。

## 提案手法 / 主張

### 方法論: Grounded Theory ＋ アノテータ間一致

仮説を先に立てずデータから理論を立ち上げる **Grounded Theory**（グラウンデッド・セオリー, 定性研究の方法論）を採用し、6 人の専門家が 5 システム（MetaGPT / ChatDev / HyperAgent / AppWorld / AG2）のトレースを open coding でアノテート。分類の信頼性は **Cohen's κ**（アノテータ間の偶然を補正した一致度）で管理し、初期分類は κ 0.24（ほぼ不一致）→ 定義の分割・統合・修正を経て **κ 0.92 → 0.84（strong）** に到達するまで反復した。「分類法そのものを検証可能な成果物として作る」この手続きは、エージェント評価の方法論として汎用的な価値がある（→ [[agent-evaluation]]）。

| カテゴリ | 失敗モード（出現率） |
| --- | --- |

| **FC2 エージェント間の不整合**（31.4%） | 2.1 会話のリセット（5.5%）／2.2 明確化を求めない（2.1%）／2.3 タスクの脱線（5.5%）／2.4 情報の抱え込み（6.0%）／2.5 他者の入力の無視（4.7%）／2.6 推論と行動の乖離（7.6%） |
| **FC3 検証と終了**（31.4%） | 3.1 早すぎる終了（8.6%）／3.2 検証の欠落・不完全（9.2%）／3.3 誤った検証（13.6%） |

具体例が生々しい: チェス記法を指定したのに座標入力のゲームを作る（FM-1.1）、CPO が CEO の決定権を奪う（FM-1.2）、正しいユーザー名（電話番号）をドキュメントで見つけたのに間違った資格情報のまま進めて黙っている（FM-2.4）、verifier が「コンパイルが通るか」しか見ずチェスのルール準拠を確認しない（FM-3.3）など。

### スケール化: LLM-as-a-judge

人手アノテーションは高価なので、MASFT の定義と例をシステムプロンプトに入れた **LLM-as-a-judge**（LLM を審査員として使う評価手法）パイプラインを構築。o1 + few-shot 例で accuracy 94%・**κ 0.77** を達成し、残りのトレースの自動アノテーションに使用した。

## 実験結果と知見

- **どの失敗カテゴリも支配的でない**（37.2 / 31.4 / 31.4%）。しかもシステムごとに分布が大きく異なる（AG2 は FC2 が少なく、ChatDev は FC3 が少ない）——つまり**万能の特効薬はなく、失敗はシステムのアーキテクチャに応じて現れ方を変える**。失敗はカスケードもする（相関分析）。

<figure>

![](../../raw/assets/2025-masft/x4.png)

<figcaption>図4（再掲）: システム別・カテゴリ別の失敗モード分布。HyperAgent は全カテゴリで失敗数が多く、AG2 は FC1（特に 1.1 タスク仕様不遵守）に、AppWorld は FC3（検証）に偏るなど、アーキテクチャごとに弱点の出方が違う。</figcaption>
</figure>
- **「結局ぜんぶ verifier の責任では？」への反駁**（§4.3）: 検証は最後の防衛線ではあるが、仕様・設計・伝達の失敗は検証より前に発生しており、検証強化だけでは救えない。
- **HRO（High-Reliability Organizations, 高信頼性組織）論との対応**（§4.4）: 事前バイアスなしで得た失敗モードが、原子力空母などの高信頼性組織の設計原則（階層分化・専門性への敬意）の違反とちょうど対応した。「LLM の賢さの問題ではなく組織論の問題」という主張の裏づけ。
- **介入実験**（§6）: プロンプト改善と検証役の分離・トポロジー変更（DAG→巡回グラフ）を試すと、AG2+GPT-4o では有意改善（p=0.03）だが GPT-4 の新トポロジーは有意でない（p=0.4）。ChatDev は 25.0 → 40.6%（+14 ポイント超）に改善するも**実用水準には程遠い**。結論:「自明な修正」は戦術止まりで、包括的検証・標準化された通信プロトコル・MAS 向け強化学習・信頼度の定量化・メモリ管理といった**構造的戦略**が必要。

## 限界・批判的視点

- **対象システムとモデルの世代**: 分析対象は 2024〜25 年の OSS MAS＋GPT-4o / Claude-3 世代。ロールプレイ型（ChatDev/MetaGPT）の比重が大きく、[[summaries/2026-sakana-fugu]] のような**学習されたオーケストレータ世代**に失敗分布がそのまま移るかは未検証。ただし Fugu-Ultra の隔離／共有メモリ設計は、FC2（情報の抱え込み・履歴喪失）への構造的対処と読め、MASFT の処方箋と符合する。
- 著者ら自身が「MASFT は網羅的でない」と明言している。また LLM annotator の κ 0.77 は実用ラインではあるが、人間同士の 0.84〜0.92 には届かない。
- テキスト反復のような**単一 LLM 由来の失敗は意図的に除外**されており、MAS の失敗総量を過小に見せる可能性がある。
- 失敗の定義が「タスク目標の未達」であり、コスト超過や安全性違反（prompt injection 等）は射程外。
- 原典の細部に採番の誤植あり（FM-3.2 が「FM-3.3」と重複表記。翻訳に訳注あり）。

## 実装・運用上の示唆

- **MASFT はそのままデバッグ用チェックリストになる**。自分の MAS のトレースを 14 モードで採点すれば、どこを直すべきかの分布が得られる（公開されている LLM annotator も利用可能）。
- **verifier を「置く」だけでは足りない**。何を検証するか（コンパイル可否ではなく仕様準拠・エッジケース）をドメインごとに設計する必要がある。終了権限を持つ役割の明確化（例: Verifier のみが会話を終了できる）も効く。
- **会話パターンと終了条件の明文化**は安価で効果のある戦術（AG2 の改善プロンプトで +5 ポイント）。ただしモデル依存で、普遍的ではない。
- ReAct 由来の反復ループ（[[summaries/2022-react]]）は MAS でも FM-1.3（11.5%）として主要因のまま——ループ検出は単一・複数エージェントを問わず必須の防御。

## 用語と略称

- **MAS** = Multi-Agent System（マルチエージェントシステム）
- **MASFT** = Multi-Agent System Failure Taxonomy（本論文の失敗分類法。後続版では MAST とも呼ばれる）
- **FC / FM** = Failure Category / Failure Mode（失敗カテゴリ／失敗モード）
- **Grounded Theory (GT)** = データから理論を帰納的に構築する定性研究法。open coding（データの断片へのラベル付け）・theoretical sampling・理論的飽和などの手続きを含む
- **Cohen's κ**（カッパ） = 偶然の一致を補正したアノテータ間一致度。0.8 超で strong、0.9 超でほぼ完全
- **LLM-as-a-judge** = LLM を審査員として出力やトレースを評価させる手法
- **HRO** = High-Reliability Organization（高信頼性組織。原子力空母・管制塔など、失敗が許されないのに失敗率が極めて低い組織の研究領域）
- **best-of-N** = 同一モデルに N 回生成させ最良を選ぶベースライン手法
- **DAG** = Directed Acyclic Graph（有向非巡回グラフ）
- **ChatDev / MetaGPT / HyperAgent / AppWorld / AG2 (旧 AutoGen)** = 分析対象の MAS（役割演技型ソフトウェア企業×2、階層型 SWE、サービス横断ツール呼び出し、エージェント構築フレームワーク）
- **GSM-Plus / HumanEval / SWE-bench Lite** = 数学文章題（敵対的摂動つき）／コード生成／ソフトウェア修正のベンチマーク
