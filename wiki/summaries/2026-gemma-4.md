# Gemma 4 Technical Report（Google DeepMind, 2026）

> 原典: [[translations/2026-gemma-4]] ・ `raw/papers/Gemma 4 Technical Report.pdf`
> 著者・年・出典: Gemma Team, Google DeepMind・2026-06-19・arXiv:2607.02770v2

## 一言まとめ

**オンデバイス（スマホ・エッジ）から 31B までを一つの系列でカバーする**、オープンウェイト・ネイティブマルチモーダル（テキスト・画像・音声）のモデルファミリー。dense 4 種（E2B/E4B/12B/31B）＋MoE 1 種（26B-A4B）で、thinking モードのトグル・KV cache −37.5% の長コンテキスト効率化・投機的デコード用 MTP drafter・QAT（量子化を考慮した訓練）といった**効率化技術の見本市**であり、Arena の人間評価では 31B が 744B〜1.6T 級のオープン MoE 群に伍して **dense オープンモデル首位**（Elo 1451）に立った。wiki 的には、12B の **encoder-free アーキテクチャ**が [[summaries/2026-kimi-k2.5]] の MoonViT-3D と正反対のマルチモーダル設計として好対照をなす。

## 背景と問題意識

フロンティア競争が 1T 級 MoE（[[summaries/2025-kimi-k2]]・K2.5、DeepSeek V4 等）へ向かう一方で、**実デバイスに載るモデル**への需要は別軸で存在する。スマホや組み込み機器では VRAM・ディスク・レイテンシの制約が支配的であり、単にパラメータを減らすだけでなく、KV cache（過去トークンの key/value を保存して再計算を避ける機構。系列長に比例して肥大する）・エンコーダのメモリ断片化・デコード速度という**推論時の物理コスト**そのものを設計対象にする必要がある。Gemma 4 は Gemma 3/3n の後継として、この「効率とフロンティア性能の両立」を主題に据え、同時に thinking モード（推論トレースを応答前に生成する [[test-time-compute]] の機構）を初めて Gemma 系列へ統合した。

## 提案手法 / 主張

### モデルスイート — 2.3B から 31B まで

decoder-only Transformer（RMSNorm の pre/post-norm＋QKNorm）。E2B/E4B は Gemma 3n 由来の per-layer embeddings（層ごとの埋め込みを外部化し、実効パラメータを総パラメータより小さくする技法）で、総 5B/8B のうち実効 2.3B/4.5B。26B-A4B は活性化 3.8B の MoE（→ [[transformer-architecture]]。ただしエキスパート数などの内訳は未開示）。語彙 262k の SentencePiece。事前学習カットオフ 2025 年 1 月。

### 長コンテキスト効率 — KV cache を削る 3 点セット

1. **local:global attention 5:1**（E2B は 4:1）: 大半の層を sliding window（近傍のみを見る）ローカル attention にし、グローバル attention 層を 6 層に 1 層へ間引く。
2. **values = keys**: グローバル層で key を value として再利用し、保存すべきテンソルを半減。
3. **p-RoPE**（p=0.25）: グローバル層の位置エンコーディングを部分回転にし、周波数はグローバル 1M・ローカル 10k。

合わせてグローバル KV cache を**実質 37.5% 削減**。[[summaries/2026-gpt2-to-kimi3]] が示した「KV cache の O(N) 成長が長文の物理コスト」への、linear attention 化（固定状態）とは別解の「**softmax attention のまま間引く・共有する**」路線である。

### 視覚・音声エンコーダ（E2B/E4B/26B/31B）

視覚は 150M / 550M の ViT（patch 16）で、可変アスペクト比をネイティブサポートする——画像をアスペクト比をほぼ保ったままプールされたパッチ格子へ縮小し、視覚トークン上限（N_max = 70〜1120）に収める（Algorithm 1）。音声（E2B/E4B）は 305M の USM ベース Conformer で 40ms チャンクを処理し、Gemma 3n の 680M から −55%。どちらも事前学習中は凍結される。

### encoder-free アーキテクチャ — K2.5 と正反対の賭け

12B はスクラッチから**エンコーダなし**で訓練される: 視覚は 48×48×3 の生 RGB パッチを**単一の行列積（35M パラメータ）**で LLM 埋め込みへ射影（550M ViT を置換。2D 座標埋め込みで空間認識を維持）、音声は 305M の Conformer エンコーダを**完全廃棄**し、16kHz・40ms チャンクの生の 640 次元ベクトルを直接射影する（時系列ゆえ位置エンコーディングも不要）。

これは同時期の [[summaries/2026-kimi-k2.5]]（MoonViT-3D——エンコーダを鍛え、画像・動画で完全共有する路線）と**正反対の設計判断**である。K2.5 が「強いエンコーダへの投資が転移を最大化する」に賭けたのに対し、Gemma 4 12B は「LLM 本体が十分大きければエンコーダは射影で足りる。むしろ別立てエンコーダはメモリ断片化の源」に賭けた。結果は示唆的で、12B は専用音声エンコーダなしで E2B/E4B（305M エンコーダ持ち）と同等以上の ASR/翻訳性能を出す（表8）。マルチモーダル統合の「どこにパラメータを置くか」という設計軸の、現時点で最も明確な対照実験といえる。

### MTP drafter — 投機的デコードを標準装備に

<figure>

![](../../raw/assets/2026-gemma-4/fig1.png)

<figcaption>図1（再掲）: MTP ドラフタ（青）は本体（灰）の最終層活性化と KV cache を受け取り、4 層 Transformer で将来トークンを下書きする。</figcaption>
</figure>

投機的デコード（speculative decoding, 小さなドラフトモデルが数トークン先まで下書きし、本体が 1 回の並列 forward でまとめて検証・受理する高速化）用の **MTP（multi-token prediction）drafter ヘッド**を本体と共に訓練して公開する。ドラフタは本体の KV cache に cross-attention する 4 層 Transformer で、**ドラフタ自身の prefill が不要**・任意ドラフト長に対応。E2B/E4B では語彙全体（262k）への出力射影を top-k クラスタ演算（d×4096）に置き換え、受理率を保ったままドラフト計算を約 64 分の 1 にする。→ [[llm-inference-optimization]]

### QAT — 訓練時から量子化を仕込む

事後量子化でなく **QAT**（quantization-aware training, 訓練中に量子化誤差を織り込む）で 2 形式を提供: **mobile quantization**（int2/int4 混合重み＋int8 活性化）と **Q4_0**（llama.cpp 系のブロック量子化）。E2B は bf16 4.6GB → 0.8GB。エンコーダにも適用し、音声エンコーダはディスク 390MB→**87MB（−78%）**、画像エンコーダは W8A8 でメモリ半減・オンデバイスレイテンシ −44%。

### thinking モードと制御トークン

同一の重みで、システムターンに `<|think|>` を置くだけで thinking モードが有効化される——R1 系の「常時長考」とも K2 の「非思考特化」とも違う、**トークンによるトグル**。思考トレースは `<|channel>thought ...<channel|>` に、関数宣言・呼び出しは `<|tool>declaration:` / `<|tool_call>call:` に、それぞれ**トークナイザレベルの専用制御トークン**で区画化される（表11 に全書式）。PT モデルは `<eos>`・IT モデルは `<turn|>` で終端する。→ [[tool-use-and-function-calling]]

## 実験結果と知見

- **人間評価（Arena, 2026-06-19 時点）**: 31B が Elo 1451 で**リーダーボードの dense オープンモデル首位**（rank 43）。GLM 5（744B MoE, 1457）・DeepSeek V4 Pro（1.6T MoE, 1456）・Kimi K2.5 Thinking（1T MoE, 1450）と統計的に重なる位置で、パラメータ 1 桁〜2 桁差を人間評価で埋めた。26B-A4B（活性 4B）も 1438。首位（closed）は Claude Fable 5 の 1508。
- **静的ベンチ**（表5, thinking）: 31B で MMLU Pro 85.2・AIME 2026 89.2・GPQA Diamond 84.3・LiveCodeBench v6 80.0・Codeforces Elo 2150。**E2B は 10 分の 1 のパラメータで Gemma 3 27B にほぼ並ぶ**（世代進化の速度の実例）。
- **agentic 評価**: Tau2（対話型業務エージェント）は 31B で airline 75.0 / retail 86.4 / telecom 69.3 と健闘する一方、**Terminal Bench Hard は 36.0** に留まり、端末操作系の長い trajectory はこのサイズ帯でもなお難しい（→ [[agent-evaluation]]）。
- **長コンテキスト**（表9, thinking なし）: RULER 128k で 31B 96.4（Gemma 3 27B は 66.0）、LOFT 128k Recall 79.5（同 8.6）——KV 効率化と両立した大幅改善。E4B ですら Gemma 3 27B を上回る。
- **音声**: E2B/E4B はエンコーダを 680M→305M・ディスク 390→87MB に削りながら、Gemma 3n 比で書き起こし 17%/12%・翻訳 12%/10% の相対改善（表7）。
- **視覚**: 31B で MATH-Vision 85.6・InfographicVQA 92.0・OmniDocBench 1.5 誤り率 0.131（表6。1120 視覚トークン時）。

## 限界・批判的視点

- **Arena の解釈**: ブラインド並列比較とはいえ、Arena はチャット的な短対話への選好を測る面が強く、95% CI ±8 の範囲で近傍 20 モデルが団子状態にある。「1.6T に匹敵」は人間選好の土俵での話で、表5 の絶対性能（HLE 19.5 等）はフロンティア closed とは依然差がある。
- **agentic 能力の弱さは残る**: Terminal Bench Hard 36.0・Tau2 telecom 69.3 は、同時期のフロンティア agentic モデル（[[summaries/2026-kimi-k2.5]] 系）に大きく劣る。エッジ向け設計の代償がどこに出るかを示す数字でもある。
- **MoE の詳細が未開示**: 26B-A4B のエキスパート数・ルーティング・共有エキスパートの有無は書かれておらず、[[summaries/2025-kimi-k2]] のスパース性スケーリング則のような設計根拠と突き合わせられない。
- **encoder-free の一般化は未検証**: 12B 一点での実証であり、より小さい（E2B 級）または大きいモデルで同じ賭けが成立するか、動画のような時空間モダリティへ伸びるか（K2.5 の MoonViT-3D が強い領域）は開かれた問い。
- **v2 での数値**: 本訳の底本は v2（2026-07-24 更新）。arXiv 版の更新で数値が改訂される可能性がある。

## 実装・運用上の示唆

- **エッジ配備の設計チェックリストとして読める**: KV cache（5:1・values=keys・p-RoPE）→ 重み（QAT int2/4）→ デコード速度（MTP drafter）→ エンコーダ（薄型化 or 廃止）と、推論メモリ・速度のボトルネックを一つずつ潰す構成は、オンデバイス LLM 設計の参照実装になる。表3 のメモリ実数（E2B 量子化 0.8GB＋32k KV 0.05GB）は機材選定にそのまま使える。
- **thinking のトグル化**: 同一チェックポイントで thinking/non-thinking を切り替えられるため、「単純クエリは非思考・難問だけ思考」というルーティングをアプリ側で制御できる——[[test-time-compute]] の適応的配分をデプロイ時に実現する形。
- **制御トークン書式は fine-tune 時の契約**: PT は `<eos>`・IT は `<turn|>` 終端という差異や `[BOS]` の手動追加など、表11 の書式を破ると挙動が壊れる。ファインチューニング前に必読の仕様。
- **ドラフタ公開の意味**: 投機的デコードは通常ドラフトモデルの用意が障壁になるが、本体と共訓練されたドラフタが同梱されるため、対応推論エンジンならそのまま高速化が効く。

## 用語と略称

- **LLM** = Large Language Model（大規模言語モデル）／ **MoE** = Mixture-of-Experts（→ [[transformer-architecture]]）
- **per-layer embeddings**（層ごとの埋め込みを外部化し実効パラメータを削る Gemma 3n 由来の技法）
- **KV cache**（過去トークンの key/value を保存して再計算を避ける機構。→ [[llm-inference-optimization]]）／ **sliding window / local attention**（近傍トークンのみを見る attention）
- **RoPE / p-RoPE**（回転位置埋め込み／その部分適用版。p は回転を適用する次元の割合）
- **QKNorm / RMSNorm**（query-key 正規化／二乗平均平方根による層正規化）
- **encoder-free**（視覚・音声の専用エンコーダを持たず、生パッチ・生チャンクを射影だけで LLM に入れる構成）
- **ViT** = Vision Transformer ／ **USM** = Universal Speech Model ／ **Conformer**（畳み込み＋Transformer の音声エンコーダ構造）／ **Mel フィルタバンク**（人間の聴覚特性に合わせた周波数特徴量）
- **MTP** = Multi-Token Prediction ／ **投機的デコード（speculative decoding）**（ドラフトモデルの下書きを本体が並列検証する高速化）／ **受理率（acceptance rate）**（下書きトークンが本体に採用される割合）
- **QAT** = Quantization-Aware Training（訓練時から量子化誤差を織り込む）／ **W8A8**（重み・活性化とも 8 ビット）／ **Q4_0**（llama.cpp 系のブロック量子化形式）
- **PT / IT** = Pre-Trained / Instruction-Tuned ／ **SentencePiece**（サブワードトークナイザ）
- **Arena / Elo**（ブラインド並列比較の人間評価とそのレーティング → [[agent-evaluation]]）
- **RULER / LOFT / MTOB / MRCR**（長コンテキスト評価。MTOB は文法書 1 冊からの低資源言語翻訳）／ **ASR** = Automatic Speech Recognition ／ **WER / CER / chrF / CorpusBLEU**（誤り率・文字誤り率・文字 n-gram F・翻訳品質の指標）
- **Tau2 / Terminal Bench**（対話型業務エージェント／端末操作の agentic ベンチマーク）／ **HLE** = Humanity's Last Exam
- **ZeRO-3 / GSPMD / Pathways**（分散訓練のシャーディング・並列化基盤）／ **TPU** = Tensor Processing Unit
