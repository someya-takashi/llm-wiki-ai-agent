# Claude Code の解剖 — ハーネスが 98.4% を占めるという設計点

> 原典: [[translations/2026-dive-into-claude-code]] ・ `raw/papers/Dive into Claude Code_ The Design Space of Today's and Future AI Agent Systems.md`
> Jiacheng Liu, Xiaohan Zhao, Xinyi Shang, Zhiqiang Shen（VILA Lab, MBZUAI・University College London）・2026・arXiv:2604.14228
> 対象: **Claude Code v2.1.88**（npm パッケージから抽出した TypeScript ソース。約 1,884 ファイル・51.2 万行）
> コード: [https://github.com/VILA-Lab/Dive-into-Claude-Code](https://github.com/VILA-Lab/Dive-into-Claude-Code)

## 一言まとめ

**Claude Code の公開ソースコードを第三者が読み通し、そのアーキテクチャを「設計空間の中の 1 つの点」として記述した論文。** Anthropic の刊行物ではなく、著者らは冒頭で原著作権が Anthropic に帰属することを明記している。**中核のエージェントループは「モデルを呼び、ツールを実行し、繰り返す」だけの while ループであり、コードベースのうち意思決定ロジックは推定 1.6%、残る 98.4% は運用ハーネスである**——この比率が論文全体の主張を一言で表している。

## 背景 — なぜ第三者の解剖が要るのか

本 wiki は既に Anthropic 一次資料を 4 本持っている（[[summaries/2025-effective-harnesses]]・[[summaries/2026-harness-design]]・[[summaries/2026-meta-harness]]・[[summaries/2026-managed-agents]]）。**しかしどれも「どう設計すべきか」の指針であって、「実際にどう実装されているか」の解剖ではない。** 著者らが動機として挙げるのもまさにそれで——「**Anthropic は Claude Code についてユーザー向けのドキュメントは公開しているが、詳細なアーキテクチャの記述は公開していない**」。

本論文が信頼できる形をしているのは、**証拠を 3 階層でラベル付けしている**からである。

| 階層 | 意味 | 扱い |
|---|---|---|
| **Tier A** | 公式ドキュメント・工学ブログ由来 | 製品の意図を確立するが、内部実装を反映しない可能性がある |
| **Tier B** | 抽出したコードのファイル名・関数名を引用 | **最も強い証拠** |
| **Tier C** | コミュニティ解析・OpenClaw との比較・コードパターンからの推論 | **留保つきの表現で述べる** |

**有名な「1.6% / 98.4%」は Tier C である**（コミュニティ解析からの推定）。この区別を保ったまま読むのが正しい。

## 提案 — 5 つの価値 → 13 の原則 → 実装

論文の骨格は**価値から実装への追跡**である。**5 つの価値**（Human Decision Authority / Safety, Security, and Privacy / Reliable Execution / Capability Amplification / Contextual Adaptability）を、**13 の設計原則**（deny-first with human escalation、graduated trust spectrum、defense in depth、externalized programmable policy、context as scarce resource、append-only durable state、**minimal scaffolding, maximal operational harness**、values over rules、composable multi-mechanism extensibility、reversibility-weighted risk assessment、transparent file-based configuration and memory、isolated subagent boundaries、graceful recovery and resilience）を通じて具体的なソースファイルへ辿る。

**この追跡が効いているのは、「アーキテクチャが*しない*こと」も同じ枠組みで説明できるから**である。論文の言い方では——**明示的な計画グラフをモデルの推論に課さない。統一された単一の拡張機構を提供しない。resume 時にすべてのセッションスコープの信頼関連状態を復元しない。** これらの不在は原則集合と整合的である。

### 4 つの設計上の問いと、Claude Code の答え

| 問い | Claude Code の答え | 代替 |
|---|---|---|
| **推論はどこに宿るか** | **モデルが推論し、ハーネスが実行する。** モデルはファイルシステムにもシェルにもネットワークにも直接触れない | Devin は明示的な計画構造を持つ。LangGraph は状態グラフで制御フローをルーティングする |
| **実行エンジンは何個か** | **1 個**（`queryLoop()`）。変わるのはレンダリング層だけ | モード固有のエンジン（IDE と CLI で別コードパス） |
| **既定の安全姿勢は** | **deny-first ＋ 人間へのエスカレーション**、複数の独立層が並列に適用 | SWE-agent / OpenHands はコンテナ隔離。Aider は git ロールバック |
| **拘束的な資源制約は** | **コンテキストウィンドウ**（200K / 1M） | 計算予算、明示的なスクラッチパッド |

**「推論はどこに宿るか」への答えにはセキュリティ上の帰結がある**と著者らは指摘する——**推論と強制が別々のコードパスを占めるので、危殆化したモデルでもハーネスのサンドボックス化・権限チェック・deny-first ルールを上書きできない**。モデルの外界への唯一のインターフェースは `tool_use` プロトコルであり、ハーネスが実行前にそれを検証する。これは [[agent-safety-and-guardrails]] の層 (1)（行動空間の設計）の最も明快な実装例である。

## 各サブシステムの要点

### エージェントループ — `queryLoop()` と 5 段の context shaper

1 ターンは 9 段（設定の解決 → 可変状態の初期化 → コンテキストの組み立て → **5 つの context shaper** → モデル呼び出し → tool-use の振り分け → 権限ゲート → ツール実行と結果収集 → 停止条件）。

**実装の細部で真似る価値があるもの**が 2 つある。

- **単一の `State` オブジェクトを 1 回の全体代入で上書きする。** ループには 7 つの `continue` 地点があり、そのすべてでフィールドを個別に変更するのではなく状態オブジェクトごと置き換える。**多数の分岐から可変状態を触る系で、部分更新の取りこぼしを構造的に防ぐ書き方**である。
- **`AsyncGenerator` にする。** ループ内部は単一の同期的な制御フローを保ちながら、UI 層へストリーミングできる。

**5 つの context shaper がすべてのモデル呼び出しの前に順に走る**のが本論文で最も詳しい部分である。→ 下記「コンテキスト管理」。

**停止条件は 5 つ**（tool_use なし／`maxTurns` 到達／`prompt_too_long`／PostToolUse フックの `hook_stopped_continuation`／`abortController`）。**回復機構も 5 つ**あり、うち 3 つに明示的な回数制限がある——最大出力トークンのエスカレーションは**1 ターン 3 回まで**（`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`）、reactive compaction は**1 ターン 1 回まで**（`hasAttemptedReactiveCompact`）。**「静かに回復するが、回復の回数は数える」**という設計である。

### コンテキスト管理 — 5 層の compaction

| 層 | 機構 | ゲート |
|---|---|---|
| **1. Budget reduction** | ツール結果ごとの大きさ上限。大きすぎる出力をコンテンツ参照へ | **常に有効** |
| **2. Snip** | 古い履歴区間の軽量な整理 | `HISTORY_SNIP` |
| **3. Microcompact** | 細粒度・**キャッシュを意識した**圧縮 | `CACHED_MICROCOMPACT` |
| **4. Context collapse** | **読み取り時の射影**（履歴は変更しない） | `CONTEXT_COLLAPSE` |
| **5. Auto-compact** | モデル生成による完全な要約 | 既定で有効・無効化可 |

**設計思想は「遅延劣化（lazy degradation）」** ——最も破壊の小さい圧縮をまず当て、安い戦略が不十分だと判明したときにだけエスカレートする。**auto-compact は先行 4 層がすべて走った後でもなお圧力の閾値を超えている場合にのみ発火する。**

**実装の細部が 3 つ、設計の教訓として読める。**

- **順序に理由がある。** budget reduction が microcompact の前に走るのは、**microcompact が純粋に `tool_use_id` だけで動作し内容を一切見ないから**である。両者はきれいに合成する。
- **節約が計測器から見えない問題。** snip が節約したトークンは、**主要なトークンカウンタが直近アシスタントメッセージの `usage` から算出しており、そのメッセージは snip を生き延びて snip 前の `input_tokens` を付けたまま**なので見えない。だから `snipTokensFreed` を auto-compact へ**明示的に配管している**。**圧縮の効果を測る計測器そのものが圧縮対象の中にある**、という一般的な罠の実例である。
- **context collapse だけは履歴を変更しない。** ソースのコメントを著者らはそのまま引く——「**何も yield されない。折り畳まれたビューは REPL の完全な履歴に対する読み取り時の射影である。要約メッセージは REPL の配列ではなく collapse ストアに存在する。これがターンをまたいで折り畳みを持続させているものである。**」**モデルは折り畳まれた版を見るが、完全な履歴は再構成のために残る。**

**compaction はトランスクリプトを破壊しない。** `buildPostCompactMessages()` は `[boundaryMarker, ...summaryMessages, ...messagesToKeep, ...attachments, ...hookResults]` を返し、境界マーカーに `headUuid`・`anchorUuid`・`tailUuid` を記録して**読み取り時にメッセージの連鎖を修復**する。ディスク上の行は決して書き換えられない。

コスト意識の記録も面白い——コードのコメントが 2026 年 1 月の実験を残しており、**compaction のパスが主要会話のプロンプトキャッシュを再利用しない場合は「98% キャッシュミスで、フリートの `cache_creation` の約 0.76% のコスト」** と定量されている。

### 記憶 — CLAUDE.md の 4 階層と、埋め込みを使わない選択

| 水準 | 場所 | 性格 |
|---|---|---|
| **Managed** | `/etc/claude-code/CLAUDE.md` 等 | OS 水準のポリシー |
| **User** | `~/.claude/CLAUDE.md` | 私的な大域の指示 |
| **Project** | `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` | **コードベースにチェックインされる** |
| **Local** | `CLAUDE.local.md` | gitignore される |

**読み込みは「優先度の逆順」——後から読み込まれたファイルほどモデルの注意を受ける。** CWD より下の入れ子ディレクトリのルールは、エージェントがそのディレクトリのファイルを読んだときに**遅延して読み込まれる**ので、**モデルの指示集合は会話の途中で、探索が進むにつれて増えていく**。

**2 つの設計判断が重要である。**

**(1) 埋め込みもベクトルインデックスも使わない。** 記憶の検索は**記憶ファイルのヘッダを LLM でスキャンして最大 5 ファイルを選ぶ**方式で、**エントリ粒度ではなくファイル粒度**である。トレードオフを著者らは明示している——埋め込みベースの系は個々のエントリをより選択的に取り出せるが、**検査可能性とインデックス維持のインフラのコストを払う**。ファイルベースなら、エージェントが見るすべての指示をユーザーが読み・編集し・バージョン管理し・削除できる。→ [[agent-memory]]

**(2) CLAUDE.md はシステムプロンプトではなく user メッセージとして届く。** 著者らはこの含意を明快に述べる。

> **CLAUDE.md の内容が会話的なコンテキストとして届けられるため、これらの指示へのモデルの遵守は保証されたものではなく確率的である。** 権限ルール（deny-first）が決定論的な強制の層を提供する。**これは指針（CLAUDE.md、確率的）と強制（権限ルール、決定論的）の間の意図的な分離を作る。**

**「エージェントに何を指示すればどこまで守られるか」の答えが、届け方の構造に埋め込まれている**という指摘であり、実務で最も持ち帰る価値がある一節だと思う。

### 権限 — 7 層 × 7 モード

<figure>

![](../../raw/assets/2026-dive-into-claude-code/x4.png)

<figcaption>図4: 権限ゲートの概観。Tools からの Tool Use が Policy Core（Rules / Modes / Hooks の 3 要素）へ入り、Permission Decision が Deny / Allow / Ask に分岐する。Ask は User/Auto Classifier へ回り、その結果が Allow/Deny として決定へ戻る。</figcaption>
</figure>

**7 つの独立した層**（ツール事前フィルタ → deny-first ルール → モード制約 → auto-mode 分類器 → シェルサンドボックス → **resume 時に権限を復元しない** → フック介入）を、要求はすべて通過しなければならず、**どれか 1 つでも遮断できる**。

**7 つのモード**は `plan` → `default` → `acceptEdits` → `auto` → `dontAsk` → `bypassPermissions` という**自律性が上がるほど安全性が下がる単調な勾配**をなし、加えて内部専用の `bubble`（subagent が親ターミナルへ権限をエスカレートする）がある。

**この設計の出発点は行動データである。**

> **ユーザーは権限プロンプトの約 93% を承認する。** …承認疲れが対話的な確認を、唯一の安全機構としては行動的に信頼できないものにしている。

**Anthropic の対応が「警告を増やす」ではなく「問題を再構成する」だった**というのが著者らの読みで、その帰結が**サンドボックス化と auto-mode 分類器**である（サンドボックス化は権限プロンプトの頻度を推定 **84%** 減らした）。**信頼できない人間の承認へのアーキテクチャ上の応答は、人間がしなければならない決定の数を減らすことである。**

**拒否をルーティング信号として扱う**設計も記録に値する——分類器や deny ルールが遮断したとき、**モデルは拒否の理由を受け取り、アプローチを見直し、次の反復でより安全な代替を試みる**。`PermissionDenied` フックが外部コードにこれを観測させる。**権限の強制はエージェントを停止させるのでなく、その挙動を形づくる。**

### 拡張性 — 4 機構をコンテキストコストで階層化

| 機構 | 独自の能力 | **コンテキストコスト** | 挿入点 |
|---|---|---|---|
| **フック** | ライフサイクル介入・イベント駆動の自動化 | **ゼロ**（既定） | `execute()` |
| **スキル** | ドメイン固有の指示・メタツール呼び出し | **低**（記述のみ） | `assemble()` |
| **プラグイン** | 複数コンポーネントの梱包＋配布 | **中** | 3 点すべて |
| **MCP サーバー** | 外部サービス統合（マルチトランスポート） | **高**（ツールスキーマ） | `model()` |

**「なぜ 4 つも要るのか」への著者らの答えが本節の核心**である——**異なる種類の拡張性は、コンテキストウィンドウに異なるコストを課す。単一の機構では、ゼロコンテキストのライフサイクルフックからスキーマの重いツールサーバーまでの全範囲を、拡張の作者に不要なトレードオフを強いることなく張れない。**

そして本論文が抽出した**一般化**が良い——**あらゆるエージェントループには 3 つの注入点がある。`assemble()` はモデルが何を見るかを、`model()` は何に手を伸ばせるかを、`execute()` は行動が実行されるか／どう実行されるかを制御する。** Claude Code の 4 機構はこの 3 点に配置されている。**自分でエージェントを作るときの拡張点の設計チェックリストとしてそのまま使える。**

規模の数字も拾っておく——**27 のフックイベント**（うち 5 が権限フロー、15 がイベント固有の出力スキーマを持つ）、**フックのコマンド型は 4 種**（`command` / `prompt` / `http` / **`agent`＝エージェント的な検証器**）、プラグインのマニフェストは **10 のコンポーネント型**、スキルの frontmatter は **15 以上のフィールド**、MCP クライアントは **stdio / SSE / HTTP / WebSocket / SDK ＋ IDE 変種**を支える。

### subagent — 隔離と要約のみの返却

<figure>

![](../../raw/assets/2026-dive-into-claude-code/x6.png)

<figcaption>図7: subagent の隔離と委譲。Agent ツールは組み込み（Explore、Plan、general-purpose ほか）またはカスタムの subagent へ、routing（teammate）・isolation（remote、worktree）・lifecycle（async、sync）の 3 軸で振り分ける。</figcaption>
</figure>

**SkillTool と AgentTool は同じ基本ツールプールに並ぶメタツールだが、根本的に異なる**——**SkillTool は現在のコンテキストウィンドウへ指示を注入し、AgentTool は新しい隔離されたウィンドウを生成する**。だから前者は低コスト、後者は高コストになる。

**隔離は 3 モード**: **worktree**（一時的な git worktree。**コンテナ不要でファイルシステム水準の分離が得られる**）、**remote**（内部専用）、**in-process**（既定。ファイルシステムは共有、会話コンテキストのみ隔離）。

**sidechain トランスクリプト**——各 subagent が自分の `.jsonl` ＋ `.meta.json` を書く。**デバッグと監査のために履歴は残るが、親のセッションファイルは膨らまない。親のコンテキストへ返るのは最終応答テキストとメタデータだけ。**

**コストの数字が 1 つ記録されている——エージェントチームは plan モードでの標準セッションの約 7 倍のトークンを消費する。** 並列化は無料ではない。→ [[multi-agent-systems]]

**調整はファイルロックで行う**（メッセージブローカーでも分散調整サービスでもない）。タスクは共有リストからロックファイルによる排他制御で主張される。**スループットを 2 つの性質——依存ゼロの配備と、プレーンテキスト JSON を読むだけの完全なデバッグ可能性——と引き換えにしている。**

### 永続化 — 追記のみと、権限を復元しないこと

**3 つの永続化チャネルが独立に動く**: セッションのトランスクリプト（プロジェクトスコープ、セッションごとに 1 ファイル）／グローバルなプロンプト履歴（`history.jsonl`、逆順読み出しで上矢印と `ctrl+r` を支える）／subagent の sidechain。

**追記のみの JSONL はクエリ能力より監査可能性を選んだ意図的な選択**である。すべてのイベントが人間に読め、バージョン管理でき、特殊なツールなしに再構成できる。**コストは、「ファイル X を修正したすべてのツール呼び出しをセッションをまたいで見せて」のような構造化クエリが事後の再構成を要すること。**

そして**最も設計的な選択**——**resume と fork は権限を復元しない**。

> **セッションは隔離された信頼ドメインとして扱われる。** 以前に付与された権限を resume 時に復元することは利便性の便益を作るが、**変化した文脈へ古びた信頼の決定を持ち越すリスク**を生む。アーキテクチャは暗黙の永続化より再付与を選び、**信頼は常に現在のセッションで確立されるという安全性の不変条件を保つためのコストとしてユーザーの摩擦を受け入れている。**

なお **Claude Code の「チェックポイント」は `--rewind-files` のためのファイル履歴のスナップショット**であって、汎用のチェックポイント・ストアではない。用語の混同を著者らが明示的に正している。

## OpenClaw との対比が明らかにするもの

**OpenClaw** は約 2 ダースのメッセージング表面（WhatsApp・Telegram・Slack・Discord・Signal 等）をエージェントランタイムへ繋ぐ **local-first の WebSocket ゲートウェイ**である。Claude Code が「単一リポジトリに束縛された一時的な CLI プロセス」なのに対し、OpenClaw は「**永続的なデーモンとしての制御平面**」。

**同じ問いに、正反対の答えが出ている。**

| | Claude Code | OpenClaw |
|---|---|---|
| **信頼境界** | **モデルと実行環境の間**（行動ごとの deny-first 評価） | **ゲートウェイの境界**（DM ペアリング・許可リスト・ゲートウェイ認証） |
| **エージェントループの位置** | **系の中心**。すべてが収束する | **制御平面の中の 1 コンポーネント**。RPC ディスパッチの内側に埋め込まれる |
| **拡張の対象** | **単一エージェント**のコンテキストウィンドウと行動面 | **ゲートウェイ全体**の能力面（全エージェントに及ぶ） |
| **記憶の力点** | **段階的なコンテキスト圧縮**（キャッシュ意識の 5 層） | **構造化された長期記憶の昇格**（dreaming、日次ノート、ハイブリッド検索） |
| **マルチエージェント** | **タスク委譲**（従属的なワーカー） | **ルーティング**（独立したエージェントのインスタンス）＋ 委譲の 2 本立て |

**著者らが引き出す 3 つの観察が良い。**

1. **問いは安定しており、答えは配備文脈とともに変わる。** 第 3.1 節の 4 つの設計上の問いに OpenClaw も全部答えているが、出発点が違う。
2. **反転は恣意的でない。** 信頼モデルと配備トポロジーから帰結している。
3. **2 つは合成できる。** **OpenClaw は ACP（Agent Client Protocol）を通じて Claude Code を外部のコーディングハーネスとしてホストできる。「エージェントの設計空間は平坦な分類ではなく層状のものであり、ゲートウェイ水準の系とタスク水準のハーネスが合成できる」**——本 wiki の [[agent-frameworks]] にとって重要な整理である。

## 限界・批判的視点

### 著者らが自ら挙げるもの

- **静的なスナップショット。** v2.1.88 の 1 バージョンのみ。**機能フラグがビルド時の可変性を作る**——`TRANSCRIPT_CLASSIFIER` が false のビルドでは**auto-mode 分類器全体が除去される**。「異なるビルドターゲットは機能的に異なるアプリケーションを生成しうる」。
- **リバースエンジニアリングの認識論。** **ソースコードは実装された構造・制御フロー・依存・機能ゲートを明らかにするが、設計の意図・本番で有効なフラグ・ランタイムでの出現頻度・出荷されていない挙動は確認できない。** 本論文で最も誠実な一文だと思う。KAIROS（能動的なバックグラウンドエージェント）についても「本番ビルドで有効であることは確認できない」と明記している。
- **単一システムの分析。** 一般化には限界がある。
- **メモ化の影響。** `getSystemContext()` と `getUserContext()` は lodash の memoize を使うので、**git の状態と CLAUDE.md の内容は毎ターン再計算されずキャッシュされる**。会話中の動的な変更が即座に反映されない可能性がある。

### アーキテクチャそのものの弱点

**(1) 多層防御の独立性の仮定が破れる。** 論文で最も鋭い指摘である。

> **Claude Code の安全性の層は共通の性能上・経済上の制約を共有している。** auto-mode 分類器は直接のトークンコストを伴う別個の LLM 呼び出しである。`bashSecurity.ts` は解析の遅延を伴う逐次的な AST チェックを行う。**性能への圧力がこれらのコストを減らす方向へ押すとき、層は同時に劣化しうる。**

実例として、**50 を超えるサブコマンドを持つコマンドは、サブコマンドごとの解析が UI のフリーズを引き起こしたため、単一の汎用的な承認プロンプトへフォールバックする**（サブコマンドごとの deny チェックを飛ばす）ことが記録されている。**評価すべきは「個々の層が迂回されうるか」ではなく「いくつの独立した層が同時に失敗しなければならないか、そしてそれらが失敗モードを共有しているか」である。**

**(2) 図 4 が捉えていない時間的な順序。** 独立したセキュリティ研究が**信頼前の初期化の順序**という根本原因を持つ 2 つの脆弱性を発見した——**プロジェクト初期化中に走るコード（フック、MCP サーバー接続、設定ファイルの解決）は、対話的な信頼のダイアログがユーザーへ提示される前に実行される**。

> **この信頼前の実行の窓は deny-first の評価パイプラインの外側に落ち、第 5 節で記録した安全性の保証がまだ適用されない、構造的に特権化されたフェーズを作り出す。**

CVE は **CVE-2025-59536（CVSS 8.7）・CVE-2026-21852（CVSS 5.3）**（Check Point Research）と、権限パイプラインの他所のパス検証／コマンド解析の欠陥を突く **CVE-2025-54794・CVE-2025-54795**。**4 つとも開示から数週間以内にパッチ済み。** 教訓は一般化されている——**権限のパイプライン図は安全性チェックの*空間的*な順序を描くが、*時間的*な次元（いつ各機構が有効になるか）を捉えていない。拡張性は組み合わせの複雑さを通じてだけでなく、初期化の順序を通じても攻撃面を作る。**

**(3) 圧縮がユーザーに見えない。** budget reduction が長い出力を参照へ置き換えたとき、context collapse が要約へ置き換えたとき、snip が古い履歴を整理したとき、**ユーザーには何が失われたかを検査する容易な手段がない**。auto-compact は目に見える要約を出し microcompact は境界マーカーを出すが、**context collapse はユーザーに見える出力なしに動作する**。microcompact のキャッシュ意識の挙動はさらに不透明さを加える。

**(4) 4 機構の組み合わせ的な相互作用。** プラグインが PreToolUse フックでツール入力を修正する。auto-mode 分類器がキャッシュされた CLAUDE.md を読む。**パススコープのルールが新しいディレクトリを読んだときに遅延ロードされ、会話の途中で分類器の挙動を変えうる。** 単一の設定ファイルからは予測が難しい創発的な挙動になる。

### アーキテクチャが生む実証的な予測と、それを支持するデータ

**論文の第 11.4 節は、ソースコードからは導けない予測を立ててから外部の実証で裏を取る**という構成をしている。

**予測**: 有界なコンテキストは**コードベース全体の同時把握を妨げる**ので、エージェント生成コードは**パターンの重複と規約違反の率が高くなる**はずである。subagent の隔離がこれを増幅する——**並列のエージェントは、他所に既に存在する解を独立に再実装しうる。**

> **設計哲学はモデルが良い局所的な決定をすることを信頼するが、モデルが大域的な文脈を欠くとき、良い局所的な決定は悪い大域的な帰結を生みうる。**

**裏づけ**: Cursor 導入 807 リポジトリの因果分析で**複雑度 +40.7%（p < 0.001）、初速スパイク +281% は 3 か月目でベースラインへ、複雑度の上昇は将来の開発速度の比例的な低下と関連**（利得は自己相殺的）。AI が書いた **30.4 万コミット・6,275 リポジトリの監査**で、**AI 由来の問題の約 1/4 が最新リビジョンまで持続し、セキュリティ関連はさらに高率で持続**。

**著者らは正直に留保も付ける**——**Claude Code のコンテキスト管理パイプラインはまさにこれらの効果を緩和するよう設計されており、それが十分かは「ソースレベルの解析では解決できない、直接測定可能な実証的な問い」である。**

## 実装・運用上の示唆

1. **拡張点は 3 つしかない、と考える。** `assemble()` / `model()` / `execute()`。自分のエージェントに拡張機構を足すとき、**それがどの注入点に属し、コンテキストをどれだけ食うか**を先に決める。コストが違うものを 1 つの機構に押し込むと、作者にトレードオフを強いる。
2. **指針と強制を分ける。** **プロンプトで届ける指示（CLAUDE.md 相当）は確率的にしか守られない。** 守らせたいものは決定論的な層（権限ルール、スキーマ検証、フック）へ移す。「システムプロンプトに書いたから大丈夫」は成り立たない。
3. **compaction は段階にする。** 単一パスの切り詰めや単一の要約ではなく、**安い層から順に当てて足りなければエスカレートする**。ただし**層が増えるほど挙動が予測不能になる**ので、どの層が何を削ったかは出力するべきである（Claude Code の context collapse は出していない）。
4. **圧縮の効果を測る計測器が圧縮対象の中にないか確認する。** snip の節約がトークンカウンタから見えなかった実例がある。**間接的に導出された指標は、その導出元が圧縮されると壊れる。**
5. **回復は自動化しつつ回数を数える。** `MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`、reactive compaction は 1 ターン 1 回。**無制限のリトライは静かな無限ループになる。**
6. **多層防御を名乗る前に、層が制約を共有していないか調べる。** すべての層が同じトークン予算・同じ解析コスト・同じ UI スレッドに乗っているなら、それは 1 層である。
7. **権限を再開時に復元しない。** 摩擦は増えるが、**信頼は常に現在のセッションで確立される**という不変条件が守れる。
8. **拒否をハードストップでなくルーティング信号にする。** モデルに理由を返してやり直させる。ただし**不可逆な副作用の前では事後の検知は防御にならない**（→ [[agent-safety-and-guardrails]]）。
9. **subagent の並列化はタダではない。** エージェントチームは標準セッションの**約 7 倍**のトークン。**要約のみの返却**は、それでもなお必要な節約である。
10. **調整にインフラを持ち込む前に、ファイルロックで足りないか考える。** 依存ゼロの配備と、プレーンテキストを読むだけのデバッグ可能性は大きい。

## 用語と略称

- **LLM** = Large Language Model（大規模言語モデル）
- **MCP** = Model Context Protocol（ツールやデータソースをモデルに接続する標準プロトコル）→ [[model-context-protocol]]
- **ACP** = Agent Client Protocol。OpenClaw が Claude Code / Codex CLI / Gemini CLI を外部ハーネスとしてホストするのに使う
- **ハーネス（harness）** = モデルを包み、ツールの実行・権限・コンテキスト・回復を担う決定論的な実行基盤。本論文の中心概念
- **compaction** = 会話履歴を圧縮してコンテキストウィンドウに収める操作の総称
- **context shaper** = モデル呼び出しの前にメッセージ配列を加工する処理。Claude Code は 5 つを順に走らせる
- **read-time projection（読み取り時の射影）** = 保存された履歴は変更せず、読み出すときだけ圧縮されたビューを見せる方式
- **sidechain** = subagent の会話を親のトランスクリプトとは別ファイルに保存する仕組み
- **worktree** = Git の機能で、同じリポジトリの別のチェックアウトを作る。Claude Code は subagent の隔離にこれを使う
- **deny-first** = deny ルールが allow ルールに常に優先する評価順序
- **承認疲れ（approval fatigue）** = 確認プロンプトが多すぎて、ユーザーが内容を見ずに承認するようになる現象。実測 93%
- **Tier A / B / C** = 本論文の証拠の階層。A は公式ドキュメント、B はコード検証済み、C は再構成・推論
- **CVSS** = Common Vulnerability Scoring System（脆弱性の深刻度を 0〜10 で表す標準スコア）
- **VLA** = Vision-Language-Action。視覚と言語の入力から物理的な行動を出力する方策
- **KAIROS** = 機能でゲートされた、ティックベースのハートビートを持つ能動的なバックグラウンドエージェント（本番での有効性は未確認）
