# GraphRAG — 「検索で答えられない質問」を、索引の作り方で解く

> 原典: [[translations/2024-graphrag]] ・ `raw/papers/From Local to Global_ A Graph RAG Approach to Query-Focused Summarization.md`
> 著者・年・出典: Darren Edge, Ha Trinh ほか（Microsoft Research / Strategic Missions and Technologies / Office of the CTO）/ 2024-04 / arXiv:2404.16130

## 一言まとめ

「このデータセットの主要なテーマは何か」のような**コーパス全体に向けられた質問**は、そもそも検索タスクではないので RAG（Retrieval-Augmented Generation, 検索拡張生成）では答えられない——という診断から出発し、**LLM にエンティティの知識グラフを作らせ、それをコミュニティに分割して各コミュニティの要約を事前生成しておき、質問が来たら全要約に並列で答えさせて最後に統合する**（map-reduce）という索引の作り方を提案した論文。

## 背景と問題意識 — RAG が構造的に答えられない質問のクラス

RAG の標準形は「クエリを埋め込み、意味的に近いテキストチャンクを top-K 個引いて、プロンプトに入れる」である。この設計が前提にしているのは、**答えがテキストの局所的な領域の内側に含まれていること**——その領域さえ引ければ生成の接地には十分だ、という前提である。

ところが人間が大量の文書に対してやりたいことは、しばしばそれではない。本論文は**センスメイキング（sensemaking）**——「軌跡を予測し効果的に行動するために、（人・場所・出来事の間にありうる）つながりを理解しようとする、動機づけられた継続的な努力」（Klein らの定義）——という語でこれを名指す。「このコーパス全体で何が繰り返し語られているか」「どんな論点の対立があるか」に答えるには、**原文のどこにも書かれていない結論**に到達する必要がある。

これは検索タスクではなく**クエリ焦点型要約**（Query-Focused Summarization, QFS。与えられたクエリの観点からコーパスを要約するタスク）である。しかし従来の QFS 手法は、RAG が扱う規模のテキスト量にスケールしなかった。**RAG は規模に強いが一般性に弱く、QFS は一般性に強いが規模に弱い**——この論文はその隙間を埋めにいく。

素朴な代案として「全部コンテキストに入れる」があるが、著者らはこれを 2 点で退ける。第一に 100 万トークン級のコーパスはコンテキストウィンドウを超える。第二に、超えなくても**長いコンテキストの「途中で情報が失われる」（lost in the middle）**（→ [[context-engineering]] の context rot と同じ現象）。だから**別の形の事前索引化**が要る、というのが問題設定である。

## 提案手法 — グラフの「モジュラリティ」を使う

![](../../raw/assets/2024-graphrag/fig1-pipeline.svg)

<figcaption>図1（再掲, 原典の Figure 1）: Graph RAG のパイプライン。上段が索引化時（原文書 → テキストチャンク → 要素インスタンス → 要素要約 → グラフコミュニティ → コミュニティ要約）、下段がクエリ時（コミュニティ要約 → コミュニティ回答 → グローバルな答え）。ドメインに合わせて調整された LLM プロンプトが各段を駆動する。</figcaption>
</figure>

**中心の着想**は、グラフを「検索・走査するもの」ではなく「**分割するもの**」として使う点にある。関連研究の多くはグラフ索引を「構造化された検索の対象」として扱うが、本論文が着目するのはグラフの**モジュラリティ**——コミュニティ検出アルゴリズムが、グラフを密接に結合したノードのまとまりへ分割できるという性質である。この分割は**相互排他かつ全体網羅（MECE）**なので、各コミュニティの要約を集めれば**元のコーパスの完全なカバレッジ**になる。あとはそれを map-reduce で畳めばよい。

パイプラインは 6 段。実装上の判断が具体的なので、そのまま設計の教科書として読める。

**(1) 原文書 → テキストチャンク。** 粒度の選択がそのまま抽出品質を決める。**チャンクが長いほど LLM 呼び出しは減るが、長いコンテキストでの再現率が落ちる**——HotPotQA での実測では、600 トークンのチャンクは 2400 トークンのチャンクの**ほぼ 2 倍のエンティティ参照**を抽出した（gleaning ゼロの場合）。

**(2) テキストチャンク → 要素インスタンス。** 複数パートの LLM プロンプトで、まず**エンティティ**（名前・型・説明）を、次に明らかに関連するエンティティ間の**関係**（始点・終点・関係の説明）を抽出する。さらに任意で**共変量（covariates）**——既定では**主張（claim）**を、主語・目的語・型・説明・出典テキストのスパン・開始終了日つきで——も抽出する。ドメイン適応の主要な手段は **few-shot 例の差し替え**である（科学・医学・法律のような専門領域では汎用の「固有表現」プロンプトでは足りない）。

ここに面白い工夫があって、**gleanings（拾い集め）**という多段の追い込みを入れる。抽出後に LLM へ「全部のエンティティを抜いたか」と問い、**logit bias を 100 に設定して yes/no を強制**する。見落としたと答えたら「**MANY entities were missed in the last extraction**」という継続で拾わせる。これにより**チャンクを大きくしても品質を落とさずに済む**——(1) の再現率と呼び出し回数のトレードオフを、プロンプト側から緩める手である。

**(3) 要素インスタンス → 要素要約。** 同じエンティティが別々の表記で抽出されて重複ノードになる懸念があるが、著者らは**エンティティ解決（entity resolution）を明示的にはやらない**。「密接に関連するコミュニティが次段で検出・要約されること」と「LLM が表記ゆれの背後にある共通のエンティティを理解できること」を根拠に、**変種から共通の近傍への十分な連結性があれば全体としては頑健**だと主張する。

ここが**通常の知識グラフとの決定的な違い**でもある。従来の知識グラフは下流の推論のために**簡潔で一貫した知識トリプル（主語・述語・目的語）**を要求するが、GraphRAG のノードが持つのは**豊かな記述テキスト**である。読み手が LLM なのだから、正規化された記号よりも自然言語の記述のほうが扱いやすい——という割り切りになっている。

**(4) 要素要約 → グラフコミュニティ。** エンティティをノード、関係をエッジ（重みは検出された関係インスタンスの正規化された個数）とする**同質な無向重み付きグラフ**を作り、**Leiden アルゴリズム**でコミュニティ検出する。Leiden を選ぶ理由は「大規模グラフの**階層的**なコミュニティ構造を効率的に復元できる」から。階層の各水準が MECE な分割を与えるので、**どの水準で切るか**が後段の設計変数になる。

**(5) グラフコミュニティ → コミュニティ要約。** 各コミュニティについて報告書のような要約を作る。トークン上限に収める方法が具体的で、**葉水準**では「始点ノードと終点ノードの次数の合計（＝顕著さ）が大きいエッジから順に、始点・終点・共変量・エッジの記述を詰めていく」。**上位水準**では、収まらなければ「要素要約のトークン数が大きいサブコミュニティから順に、（長い）要素要約を（短い）サブコミュニティ要約で置き換える」。**優先順位づけと再帰的な圧縮**という、コンテキスト予算の配分そのものである（→ [[context-engineering]]）。

なお著者らは、**コミュニティ要約は質問がなくてもそれ自体で有用**だと強調する。上位水準をざっと眺めてテーマを探し、興味のあるものから下位水準へリンクをたどる——という**探索的な読み方**を想定している。索引が副産物として読み物になる、という設計である。

**(6) コミュニティ要約 → コミュニティ回答 → グローバルな答え。** クエリ時は 3 手。

- **準備**: コミュニティ要約を**ランダムにシャッフル**してチャンクに割る。関連情報が 1 つのコンテキストウィンドウに集中して（そして失われて）しまうのを避け、**意図的に分散させる**ため。
- **map**: 各チャンクについて並列に中間回答を生成させ、同時に**「この答えは質問にどれだけ有用か」を 0〜100 で自己採点**させる。**スコア 0 は捨てる**。
- **reduce**: 中間回答を有用度スコアの降順に並べ、トークン上限まで詰めて最終回答を生成する。

自己採点によるフィルタが入っているのが実務的である。全コミュニティに問い合わせるので大半は無関係な答えを返すが、それを**モデル自身に切り捨てさせる**ことで reduce 段の入力を絞っている。

## 実験結果と知見

### 評価設計のほうが結果より示唆的

**正解のないタスクをどう測るか**の実例として、この論文の §3 は独立した価値がある。

**質問をどう作るか。** HotPotQA や MultiHop-RAG のような既存ベンチマークは「明示的な事実の検索」を対象としており、センスメイキングの評価には使えない。原文から要約クエリを機械抽出する手もあるが、**そうして作った質問は原文の事前知識を露呈してしまう**（コーパスを読んだ人にしか思いつかない質問になる）。そこで**活動を起点とした（activity-centered）質問生成**を採る——データセットの短い説明だけを LLM に与え、$N$ 人の想定ユーザー × $N$ 個のタスク × $N$ 個の質問を生成させる。$N=5$ でデータセットあたり **125 問**。「誰が何のために読むのか」から質問を導くので、**特定のテキストの詳細に依存しない**質問が得られる。

**何を測るか。** 正解がないので**頭尾対決（head-to-head）の LLM 判定**を使う。目標指標が 3 つ——**網羅性**（質問のあらゆる側面をどれだけ詳細にカバーするか）・**多様性**（どれだけ変化に富み豊かな視点を提供するか）・**エンパワーメント**（読者が情報に基づいた判断を下すのをどれだけ助けるか）。

そして 4 つ目に**直接性（directness）を「対照指標」として置く**のが巧い。直接性は網羅性・多様性と**事実上対立する**ので、**どの手法も 4 指標すべてで勝つはずがない**。もし何かが全勝したら、それは手法が良いのではなく**判定が壊れている**証拠になる——つまり**評価系そのものの妥当性テスト**が指標セットに埋め込まれている。実際、素朴な RAG が全比較で最も直接的だという期待どおりの結果が出ており、著者らはこれを「妥当性のテストも期待どおりの結果を得た」と明示的に報告している。LLM-as-a-judge を使うなら真似すべき作法である（→ [[agent-evaluation]]）。

加えて、**LLM の確率的な揺れを考慮して各比較を 5 回実行して平均**する。125 問 × 6 条件の総当たり × 4 指標 × 5 回、という規模になる。

### 結果

条件は 6 つ。**C0**（ルート水準のコミュニティ要約、最も少ない）〜**C3**（低水準、最も多い）が Graph RAG、**TS** が同じ map-reduce を**原文に直接**当てるグラフなしのグローバル手法、**SS** が素朴な RAG。**コンテキストウィンドウの大きさとプロンプトは 6 条件で同一**で、違うのは「コンテキストの中身がどう作られるか」だけ——比較としてきれいである。

- **グローバル手法 対 素朴な RAG**: 網羅性の勝率は**ポッドキャストで 72〜83%、ニュースで 72〜80%**。多様性は**75〜82%** と **62〜71%**。素朴な RAG の敗北は一貫している。
- **コミュニティ要約 対 原文（TS）**: 差は**小さいが一貫**。ポッドキャストの中間水準（C2）が網羅性 57%・多様性 57%、ニュースの低水準（C3）が 64%・60%。**ただしルート水準（C0）は TS に勝てない**（50%）。
- **エンパワーメントはまちまち**。著者らが LLM の判定理由を分析したところ、**具体的な例・引用・出典を出せるかどうか**が効いていた。要素抽出のプロンプトを調整すればグラフ索引にそうした詳細をもっと残せるかもしれない、と自ら課題に挙げている。

**トークンの経済性**が本論文の実用上の核心である。クエリあたりの文脈トークン数（Table 3）:

| 条件 | ポッドキャスト（単位数 / トークン / 最大比） | ニュース（単位数 / トークン / 最大比） |
| --- | --- | --- |
| C0（ルート） | 34 / 26,657 / **2.6%** | 55 / 39,770 / **2.3%** |
| C1 | 367 / 225,756 / 22.2% | 555 / 352,641 / 20.7% |
| C2 | 969 / 565,720 / 55.8% | 1,797 / 980,898 / 57.4% |
| C3 | 1,310 / 746,100 / 73.5% | 2,142 / 1,140,266 / 66.8% |
| TS（原文） | 1,669 / 1,014,611 / 100% | 3,197 / 1,707,694 / 100% |

**C0 は原文の map-reduce に対してトークンが 97% 以上少ない**（9〜43 倍安い）。それでいて素朴な RAG に対しては網羅性 72%・多様性 62% の優位を保つ。**同じコーパスに何度も質問する反復的なセンスメイキング**では、これが決定的になる——精度で少し譲る代わりに、桁で安くなる。

### 意外な副次的発見

**コンテキストウィンドウは小さいほうが良かった。** 8k / 16k / 32k / 64k を試したところ、**最小の 8k がすべての比較で網羅性において一様に優れ**（平均勝率 58.1%）、多様性（52.4%）とエンパワーメント（51.3%）でも他と同等だった。gpt-4-turbo は 128k を扱えるにもかかわらず、である。著者らはこれを lost in the middle に帰しており、最終評価では 8k を全条件に固定した。**「使えるだけ詰める」が最適ではない**という、[[context-engineering]] の主題を 2024 年前半の実測で裏づけた一例になっている。

## 限界・批判的視点

- **索引化のコストが Table 3 に入っていない。** あの表は**クエリ時**の文脈トークンだけである。グラフ索引の構築には、チャンクごとの抽出 LLM 呼び出し（1,669 回・3,197 回）＋ gleanings ＋ 要素要約 ＋ 全階層のコミュニティ要約が要る。「C0 は 9〜43 倍安い」は**償却前**の数字であり、比較対象の TS には索引化コストがそもそも無い。著者らはこれを隠してはおらず、議論節で「実世界の決定は計算予算・**データセットあたりの生涯クエリ数の見込み**・グラフ索引から得られる他の価値に依存する」と明示している。逆に言えば、**1 回しか質問しないなら TS のほうが安い**。
- **グラフなしの TS が競争力を持ってしまっている。** 著者ら自身が「多くの場合、グラフを使わない原文のグローバル要約も競争力のある性能を示した」と書く。C1〜C3 の TS に対する優位は 52〜64% で、**大きくはない**。この論文の主張の重心は「グラフが強い」ではなく「**グローバルな map-reduce が素朴な RAG より強い**」のほうにあり、グラフはそれを**安くする**手段だと読むのが正確である。
- **評価の範囲が狭い。** 100 万トークン級のコーパス 2 つ、ある 1 クラスのセンスメイキング質問のみ。著者らは「質問の種類・データの種類・データセット規模の範囲にわたって性能がどう変わるかを理解するにはさらに作業が必要」「センスメイキングの質問と目標指標を**エンドユーザーとともに検証**する必要がある」と自ら書いている。つまり**指標自体がまだ人間で検証されていない**。
- **捏造率が測られていない。** SelfCheckGPT のようなアプローチでの比較が要る、と自ら挙げている。網羅性と多様性で勝つ手法が**より多く捏造していない保証はない**——「詳しく多彩な答え」は幻覚の温床でもある。判定 LLM が網羅性を評価するとき、その内容が正しいかは見ていない。
- **LLM-as-a-judge の既知の偏り**が残る。5 回平均で確率的な揺れは抑えているが、**冗長な答えを好むバイアス**（verbosity bias）は平均では消えない。網羅性・多様性という指標は構造的に長い答えに有利で、それを判定するのも同じ系列のモデルである。直接性の対照指標はこの点を部分的にしか守らない。
- **エンティティ解決を省いた判断は検証されていない。** 「コミュニティ検出が吸収してくれる」という主張は、**十分な連結性がある限り**という条件つきで述べられているが、その条件が破れる場合（表記ゆれが孤立ノードを作る場合）の挙動は測られていない。
- **2024-04 時点の論文である。** モデルは gpt-4-turbo。その後、実装は [https://aka.ms/graphrag](https://aka.ms/graphrag) でオープンソース化され、LazyGraphRAG 等の低コスト派生も出ている。またコンテキストウィンドウは 100 万トークン級が普通になったが、**「詰めれば良い」ではないという本論文の 8k の発見は、むしろ強化される方向で追認されている**（→ [[context-engineering]]）。

## 実装・運用上の示唆

- **まず「その質問はローカルか、グローバルか」を分類する。** 本論文の最大の実務的貢献はここにある。「A 社の 2023 年の売上は」はローカル（RAG で解ける）、「これらの報告書に共通する懸念は」はグローバル（RAG では解けない）。**同じ索引で両方を捌こうとしない**。
- **グラフ索引を作るかは「生涯クエリ数」で決める。** 償却の問題なので、単発の分析なら原文への map-reduce（TS）で十分。同じコーパスに繰り返し問うなら、C0 のトークン単価が効いてくる。
- **階層は「どの水準で切るか」という設計変数を与える。** 精度が要るときは C2/C3、探索的に何度も問うときは C0、と**同じ索引の中で切り替えられる**のが階層構造の利点である。
- **チャンクは小さく、gleanings で補う。** 600 トークン＋ gleaning が既定の出発点。logit bias で yes/no を強制する追い込みは、他の抽出タスクにも転用できる汎用の型である。
- **map の出力にモデル自身の有用度スコアを出させて足切りする。** 全件に問い合わせる設計では必須のフィルタで、reduce 段のコンテキストを守る。
- **正解のないタスクを測るなら、対立する対照指標を 1 つ混ぜる。** 「全指標で勝つ手法は存在しないはず」という制約が、判定系の健全性チェックになる。
- **コンテキストウィンドウは実測で選ぶ。** 大きいほど良いとは限らない。本論文は 4 サイズを比較して最小を選んだ。

## 用語と略称

- **RAG** = Retrieval-Augmented Generation（検索拡張生成。外部知識を検索してプロンプトに与え、それを根拠に生成させる手法）
- **QFS** = Query-Focused Summarization（クエリ焦点型要約。与えられたクエリの観点からコーパスを要約するタスク）。**abstractive**（抽象的。自然言語で書き下ろす）⇄ **extractive**（抽出的。原文の抜粋を並べる）の対がある
- **LLM** = Large Language Model（大規模言語モデル）
- **sensemaking**（センスメイキング）= 人・場所・出来事の間のつながりを理解しようとする継続的な努力。原典は Klein らの定義を引く
- **modularity**（モジュラリティ）= グラフが密に結合した部分集合へ分かれている度合い。コミュニティ検出の目的関数でもある
- **Leiden** = 大規模グラフの階層的コミュニティ構造を効率的に復元するコミュニティ検出アルゴリズム（Traag et al., 2019）。**Louvain**（Blondel et al., 2008）の改良版
- **MECE** = Mutually Exclusive, Collectively Exhaustive（相互排他かつ全体網羅）。コミュニティ分割がこの性質を持つので、要約を集めればコーパス全体をカバーできる
- **map-reduce** = 入力を分割して並列に処理（map）し、その結果を統合する（reduce）計算の型
- **gleanings**（拾い集め）= 抽出後に「見落としはないか」を LLM に問い直し、追加抽出させる多段の追い込み
- **covariate**（共変量）= 本論文ではエンティティに紐づく追加情報。既定では **claim**（主張）
- **logit bias** = 特定トークンの出力確率を強制的に上下させる API パラメータ。本論文では yes/no 回答を強制するのに使う
- **lost in the middle** = 長いコンテキストの中ほどに置かれた情報がモデルに使われにくくなる現象
- **LLM-as-a-judge** = LLM に出力の優劣を判定させる評価手法
- **head-to-head**（頭尾対決）= 2 つの出力を直接比較してどちらが良いかを判定する評価形式
- **verbosity bias**（冗長性バイアス）= 判定者が長い答えを好む傾向
- **entity resolution**（エンティティ解決）= 同一実体を指す異なる表記を 1 つにまとめる処理
- **SS / TS / C0-C3** = 本論文の 6 条件。SS = 素朴な RAG（semantic search）、TS = 原文の map-reduce 要約（text summarization）、C0〜C3 = Graph RAG のコミュニティ水準（ルート → 低水準）
